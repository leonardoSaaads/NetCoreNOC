## 1. The five degeneracy rules, each refusing its own case **and no other**

`PREREGISTRATION-0.11.0.md` §5 registered them before any fit existed. `tests/test_model_version.py`
tests them the way the build prompt requires — *a payload-degeneracy test per rule, each rejecting
its own case and no other* — which is why **every rule's test asserts the message**, not merely that
something was rejected. Five tests that only asserted rejection would all pass against a validator
with one rule and four dead branches.

| Rule | What it refuses | The message it must give |
|---|---|---|
| 1 finiteness | `NaN`, `Infinity`, `-Infinity`, a string, **a `bool`** | `must be a finite number` / `must be a number, got …` |
| 2 feature completeness | a missing weight; **an unexpected key** | `missing […]` / `unexpected […]` |
| 3 non-degenerate discrimination | the all-zero weight vector, intercept or no intercept | `every feature weight is zero` |
| 4 threshold reachability | a threshold above the highest attainable logit, or below the lowest | `at or above the highest attainable logit` / `below the lowest attainable logit` |
| 5 magnitude sanity | any coefficient beyond ±25.0, **intercept included** | `beyond the magnitude bound` |

**The control comes first in the file**, `test_a_valid_logistic_payload_is_accepted`. A validator
that refused *everything* would satisfy all five degeneracy tests while making the scorer kind
unusable — a worse defect than any of them, and invisible to a test that only checks that bad input
fails. This is Gate 2's lesson, one layer up.

### 1.1 Three findings the tests produced, recorded rather than quietly fixed

**(a) `isinstance(True, int)` is `True` in Python.** A `bool` in the document would pass a naive
numeric check and become a weight of exactly `1.0` that nobody fitted. Rule 1 rejects `bool`
explicitly, and `test_rule_1_refuses_a_boolean_…` is why.

**(b) Rule 5 must be checked *before* rule 4, and the order is load-bearing.** A runaway coefficient
makes the reachability arithmetic report an enormous attainable range — which **passes** rule 4. A
build that ordered them the other way would let the least plausible payloads through the rule
written to catch them. `test_rule_5_is_checked_before_rule_4_and_the_order_is_load_bearing` pins it
with a payload that satisfies rule 4 comfortably and must still be refused by rule 5's message.

**(c) A test fixture was wrong, and the validator was right.** The first version of
`test_rule_3_permits_a_single_live_feature` used a weight of 1.5 against an intercept of −1.5, which
makes the highest attainable logit **exactly** the threshold — so rule 4 refused it, correctly,
because such a model links nothing ever. It read as rule 3 being too strict. The fixture moved to
3.0 and the reason is recorded in the test, because *a test's fixture is part of the guard*.

### 1.2 The feature bounds are measured, not assumed

Rule 4 is meaningless without knowing what the features can be:

| feature | range | why |
|---|---|---|
| `decay` | `[exp(-WINDOW_S/TAU0_S), 1]` = `[0.0183, 1]` | `exp(-x)` is positive and `|Δt|` is bounded by the correlation window — **it never reaches 0** |
| `class_affinity` | `[0, 1]` | `learn.npmi`, documented and clamped |
| `entity_affinity` | `[0, 1]` | same, plus the structural 1.0 / 0.8 branches |

Using `[0, 1]` for the decay would compute a lower minimum than any pair can produce and would
therefore **accept** a threshold that in fact links every pair. `WINDOW_S` is **imported from
`correlate`, never restated** — `select_candidates`' own docstring records what happened the last
time two modules each kept a copy of it.

The magnitude bound is argued in **ADR #164** with the arithmetic that chose it, as §5 rule 5
requires. Summary: a coefficient of magnitude `c` moves the logit by at most `c` across a feature's
whole range; at `|z| ≈ 9.2` the probability is within `1e-4` of its limit and the slope has fallen
three orders of magnitude, so one feature has taken the decision beyond the reach of the other two.
25.0 is ~2.7× that — room for a genuinely strong learned effect, and far below the runaway regime an
unpenalised fit on separable data produces.

## 2. Every malformed-input class falls back, warns, and **never raises**

`tests/test_scorer_dispatch.py`, parametrised so a class cannot be dropped without its id
disappearing from the test report. The fixture writes rows by **direct SQL, bypassing every
validator** — the load path's job is to survive a row that should never have been written, and a
fixture that could only produce rows the writer would have accepted could not exercise it.

| class | falls back | warning says |
|---|---|---|
| `unparseable-json` | ✅ | `not valid JSON` |
| `json-not-an-object` | ✅ | `must be a JSON object` |
| `empty-document` | ✅ | `not valid JSON` |
| `unknown-kind` | ✅ | `not one this build implements` |
| `degenerate-all-zero-weights` | ✅ | `every feature weight is zero` |
| `unreachable-threshold` | ✅ | `highest attainable logit` |
| `runaway-coefficient` | ✅ | `beyond the magnitude bound` |
| `non-finite` | ✅ | `finite number` |
| `wrong-keys-for-the-kind` | ✅ | `wrong keys` |
| unsupported contract major | ✅ | `not supported by this build` |
| **a failure the validator cannot produce** | ✅ | names the exception type |

Every one asserts **four** things: it did not raise; the active scorer is the coded default *by
fingerprint*; `scorer_model_version_id` is `None`; and the operator warning names the reason.

**`PREREGISTRATION-0.11.0.md` §6.9, asserted rather than trusted.** A model loads, then a later one
is malformed — the appliance runs the **built-in default**, not the model it was running a minute
ago. `test_the_fallback_goes_to_the_default_and_not_to_the_previous_model`.

**The `except` is wide on purpose.** `ModelPayloadError` covers everything the validator knows how
to refuse; it cannot cover what a *future* kind's constructor does. The test injects a
`RecursionError` at the seam and asserts the load path still degrades cleanly and names the
exception type. It is injected at the seam rather than through a corrupt row **because `0013`'s
`NOT NULL`s make a corrupt row hard to build** — which is a good property of the migration and the
reason this branch cannot be reached from the database side.

## 3. Dispatch exists, and the additive path is byte-identical

**Dispatch** (`test_each_supported_kind_loads_its_own_scorer`): a `logistic` artefact loads a
`LogisticScorer` with its fitted coefficients; an `additive` artefact loads an `AdditiveScorer` with
its parameters; both from the same code path. Fact B measured that no such branch existed.

**Identity is not shared with the shadow challenger, and that is deliberate.**
`challenger.CHALLENGER_SCORER_ID` is `logistic-shadow` — a scorer that decides nothing. A promoted
model is `logistic`, and it decides every grouping in the network. `params_fingerprint` includes the
`scorer_id`, so they hash differently at identical coefficients. An operator reading `/api/scorer`
must be able to tell *the challenger is being evaluated* from *the challenger is what is running*.

### 3.1 Additive parity, proven **twice**, because the eval hash alone cannot prove it

```
c2e8a0ced29d9edf986279d41089ddb68e18da65a46bdc7e9f04811e8b9b6f26
```

The eval hash proves the corpus produces the same output. It does **not** prove the additive branch
is unchanged: the corpus takes one path, and a change to a branch it never takes would leave the
hash alone. *"Before citing a green gate as evidence, ask what input would make it red."*

So the second proof is structural — the additive branch's **lines**, compared by `ast` against the
v0.10.1 tree at `c553dea`:

```
== the additive branch of load_scorer_config, statement by statement ==
  v0.10.1 lines      : 24
  v0.11.0 lines      : 24  (declared additions removed)

  declared additions, and nothing else may differ:
    + self.scorer_model_version_id = None
    + model_row = None if row is not None else await self.store.active_model_version()

  [PASS] every remaining line is IDENTICAL, in the same order
  [PASS] THE CONTROL: an altered threshold in the same branch IS detected

== _use_default_scorer ==
  [PASS] the only change is the declared field clear

== scoring.py, the module that owns the arithmetic ==
  [PASS] byte-identical to c553dea

GATE 3 PARITY: PASS
```

**The control is not optional here.** A comparison that normalises lines away can be made to pass by
normalising too much, so the probe re-runs itself against a branch with the threshold doubled and
must report that difference. It does.

**And the probe itself had two defects the run exposed**, both recorded in it: it first compared at
*statement* granularity, which reported the declared field clear as three whole changed blocks; and
its filter dropped any statement *mentioning* `active_model_version`, which silently removed the
entire `try:` block and then reported the additive branch as having lost its first statement.

## 4. The intentional behaviour changes in this phase, declared and counted

**Four.**

| # | Change | Why it is intended |
|---|---|---|
| 1 | `load_scorer_config` reads `active_model_version()` when `config_id` is `NULL`, and dispatches | the release's purpose; Fact B measured the branch did not exist |
| 2 | three paths clear the new `scorer_model_version_id` field | two live values would be two answers to *"what is running"* |
| 3 | `set_active_scorer_config` writes `model_version_id = NULL` in the same statement | `0013`'s `CHECK` admits exactly one pointer; without this, an additive retune while a model was active would raise `IntegrityError` half-way through an unrelated write |
| 4 | `Engine` gains `scorer_model_version_id`, defaulting to `None` | the other half of change 2 |

**Nothing else moved.** `scoring.py` is byte-identical; `correlate.py`, `engine.py`, `learn.py`,
`capture.py` and `receiver.py` are untouched.
