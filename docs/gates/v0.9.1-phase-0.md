### 1(b) What `learn.penalize()` does with that same bag

`penalize` receives `[(class_id, device_id), …]` and scales **every distinct class-pair cell and
every distinct device-pair cell the bag spans** by `SPLIT_PENALTY = 0.5`:

```
bag size n = 240;  members resolvable to (class, device) = 240
class pairs whose mass penalize() scaled by 0.5:  1
device pairs whose mass penalize() scaled by 0.5: 0
   class pair (31, 31): 7140.0000 -> 3570.0000
```

That bag is **degenerate on purpose of the traffic, not of the code** — 240 members of one class on
one device (an OLT storm), so the 190 member pairs of the capped sample collapse onto a single
matrix cell. §2 shows this is the rule and not the exception in the corpus available.

### 1(c) The arithmetic, on the shape §4.1 of the build prompt actually discusses

A nine-member bag, every member a distinct `(class, device)` — the case an operator reads on a card:

```
bag size n                              9
member pairs n(n-1)/2                   36
class-pair cells scaled by 0.5          36
device-pair cells scaled by 0.5         36
TOTAL matrix cells penalised            72
negatives the operator ASSERTED         0
```

> **A bag of *n* yields `n(n-1)/2` penalised member pairs from an assertion that names none of
> them.** At n = 9 that is thirty-six, driving seventy-two matrix cells, on the strength of one
> click that said only *"these are at least two situations"*.

And what the exclusion set would record instead, marking two of the nine:

```
asserted negative member pairs        14
pairs left UNASSERTED within rest     21
pairs left UNASSERTED within marked    1
check: 14 + 21 + 1 = 36 = n(n-1)/2 = 36
```

The identity closes exactly, which is what makes *"and nothing else"* checkable rather than merely
promised.

### 2.1 The finding this release did not expect, and which changes what it can claim

The thirteen `split` bags, each with the member pairs its capped sample actually spans:

| feedback id | members | sampled | member pairs | class-pair cells | device-pair cells |
|---:|---:|---:|---:|---:|---:|
| 3, 6, 9, 12, 15, 18, 21, 24, 36 | 1 | 1 | 0 | 0 | 0 |
| 30, 33 | 0 | 0 | 0 | 0 | 0 |
| 27 | 240 | 20 | 190 | 1 | 0 |
| 39 | 501 | 20 | 190 | 2 | 0 |

> **Eleven of the thirteen `split` bags have fewer than two members.** Nine are singletons — a
> "split" on a one-member bag asserts nothing whatever and penalises nothing — and two are empty,
> which is a verdict posted to an already-merged situation. The remaining two are storms of 240 and
> 501 members that are very nearly homogeneous.

The consequence is stated plainly because it bounds this release's own claims:

> **The exclusion set cannot be demonstrated on the fullest corpus this repository can construct.
> Not one of its thirteen `split` bags would yield a single asserted negative pair**: eleven have no
> pair to assert anything about, and the other two are storms nobody would mark member-by-member.

That is a property of the **mechanical labelling rule** — every third situation gets `split`
regardless of whether splitting it means anything — and not evidence about operators. It has two
real consequences, both carried into the build report: the release's semantics must be proved on a
**purpose-built fixture** rather than on the corpus, and any projection of how much this raises the
`split ∧ mixed` count is **unsupported by the data available**, which §13 of the build prompt asks
to be said rather than dressed up.

## 3. The labelling rate, measured — and why the prize is not measurable here

```
labels                             41
label span (days)                  0.000463
labels per week (over the span)    619920.00
situations, total                  41
situations closed                  35
  closed WITH a verdict            35
  closed WITHOUT a verdict         0
```

**Both numbers in that block are artefacts, and reporting them as measurements would be
manufacturing.**

* *Labels per week: 619 920.* The mechanical policy applies all 41 verdicts one second apart at the
  end of the replay, so the span is 40 seconds and the rate is the harness's, not a deployment's.
  **The correct statement is that this repository has no data on the labelling rate at all.**
* *Closes without a verdict: 0.* The corpus is built by labelling **every** situation the replay
  formed, so the population the prize is measured over is empty **by construction**. Worse for the
  measurement and better for the honesty: of the 35 closed situations, **none was closed by an
  operator** — every one was closed by `maintenance`'s idle sweep, which is not a moment of
  judgement at all. `audit_log` contains **zero** `situation.close` rows.

> **The prize Workstream 2 aims at is real and is not measurable on any corpus this repository can
> construct.** The change is still worth making — merging two gestures into one cannot lower the
> number of judgements recorded — but this release must not publish a figure for how much it will
> raise it, and the reports must count closes-without-a-verdict from the day the release ships so
> that v0.10.0 has the number this release could not have.

## 5. The seeded-defect calibration run

Three defects, three different subsystems, **chosen and written down before any of them was run**.
Each was injected into a clean tree, the **full** suite run, the outcome recorded, and the tree
reverted with `git checkout` so the next seed started from the same baseline.

| | Subsystem | Injected | Suite | Caught? |
|---|---|---|---|---|
| **A** | authorization perimeter | `rbac/tables.py`: `"feedback.write": "editor"` → `"viewer"` | **923 passed** | ❌ **no** |
| **B** | correlation | `correlate.py`: `MAX_LINKS_PER_ALARM = 5` → `6` | 1 failed, 922 passed | ✅ yes |
| **C** | retention | `store/dataset.py`: the sink's aged `DELETE` loses `lifecycle='sink'` | 4 failed, 919 passed | ✅ yes |

**A — nothing went red.** A capability was moved down a role, granting `feedback.write` to every
`viewer`, and all 923 tests passed. `tests/test_rbac.py` asserts that every `ROUTE_PERMISSIONS`
value exists in `PERMISSIONS`, that the two tables are the same objects, and that the resolver
respects the ceiling — but the only role assignment it **pins** is `PERMISSIONS["config.read"] ==
"admin"` (`test_rbac.py:125`). Every other capability's role is unguarded, including the one on the
endpoint this release changes.

**B — caught, but not where one would look.** The single failure is
`tests/test_dataset.py::test_capture_run_records_the_policy_in_effect`, which asserts the **capture
run records** `max_links_per_alarm == 5`. No correlation test noticed the cap change; a
*provenance* test did. `make eval` was not part of this run and would very likely also have moved.

**C — caught well**, by four tests that name the invariant directly, including
`test_neither_sink_bound_can_reach_a_promoted_row`.

**Calibration verdict: the technique finds things.** Two of three seeds were caught, the one that
was not is in an area Workstream 4 must cover anyway, and it lands on `feedback.write` — the
capability on the endpoint this release modifies. That is enough signal to justify spending Phase 5
on it, which is the question this run existed to answer.

The tree was verified clean afterwards (`git status --short` empty), and `make eval` and the
pre-registration hash re-checked at their expected values.
