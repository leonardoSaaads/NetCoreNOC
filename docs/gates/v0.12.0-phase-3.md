# v0.12.0 — Gate 3: the invariants

**Gate 3 asks four things**: each of the five invariants captured **with a control**; the `TABS`
guard replaced by rendering and cross-checked against `rbac.tables`; the text-level guard retained
with its reason; every docstring stating what it does not cover.

```
$ python -m pytest -q --no-header tests/test_ui_invariants.py
12 passed in 2.84s
```

Twelve tests: five invariants, six controls, one recorded finding.

---

## 0. The fixtures are the real server

Every route table the harness serves is **captured from the running FastAPI app** over the real
fiber-cut corpus, through the same ASGI client the rest of the suite uses, at the exact URLs
`app.js` requests — including query strings.

```
viewer: 13 routes captured
editor: 13 routes captured
admin:  20 routes captured
largest situation #1 with 8 alarms; members=[1, 2, 3, 4, 5, 6, 7, 8]
```

This is not a convenience. Two of the five invariants are statements about the **client's contract
with the server**, and a hand-written fixture that paraphrased the server would let the two drift
apart silently — which is the failure those invariants exist to detect.

The hostile-payload table is captured **last and through the real label route**, because an escaping
test whose payload was injected into a fixture rather than travelling the path an operator's input
actually takes is testing the fixture.

**What is still a stub, said plainly**: responses to writes. `POST …/feedback` is recorded and
answered `200`, never applied. This characterises what the client *sends*.

## 1. Invariant 1 — a role never renders a panel whose capability it lacks

Booted as each real role, with the capability set the real server returned:

| role | panels present in the DOM |
|---|---|
| viewer | `situations`, `timeline`, `entities` |
| editor | `situations`, `timeline`, `entities` |
| admin | `situations`, `timeline`, `users`, `tokens`, `config`, `scorer`, `governance`, `quarantine`, `entities`, `audit` |

The seven admin panels are **absent from the viewer's document**, not hidden — `prunePanels` removed
the nodes, and this is what asserts it actually happened.

**Control**: `assert admin_only` — if no panel distinguished an admin from a viewer, the fixture
would prove nothing and the test says so rather than passing.

## 2. The `TABS` guard, replaced

Phase 0 §1.2 established the old guard is `app_js.split("const TABS", 1)`, and that a rewrite
changing the *shape* of the map leaves the regex matching nothing while
`test_admin_panels_are_gated_to_admin` — which has no vacuity check — stays green.

**The replacement does not read the source at all.** The panel→capability mapping is *discovered by
execution*: click each tab, record the requests it issues, resolve each request to its
`ROUTE_PERMISSIONS` key, and compare the required capability against the set the server itself
reported in `/api/me`.

```
viewer requests, after attempting all seven admin tabs:
  GET /api/me, GET /api/stats, GET /api/graph, GET /api/situations?limit=50&status=open

admin requests, same gestures:
  … + GET /api/users, /api/tokens, /api/config, /api/scorer, /api/rbac, /api/scope,
      /api/quarantine?limit=100, /api/audit?limit=200
```

There is nothing here for a rewrite to make unmatchable, and it cannot pass by matching nothing: a
panel that issued no request would leave `paths` empty, and the admin control asserts the same
gestures **do** produce admin-capability requests.

### 2.1 The text guard is kept, and its docstring now says why

`_tab_caps()` survives in `tests/test_security_ui.py`. It is no longer the primary guard and its
docstring says so — along with the reason it was not deleted (ADR #168):

> *the DOM harness skips when Node is absent, and a skipped guard is a silent one. These two fail
> for different reasons — this one when the source drifts, that one when the behaviour does — and on
> a machine with no Node this is the only one of the pair still watching.*

Deleting it would have made the capability map unguarded on exactly the machines where the
behavioural guard cannot run.

## 3. Invariant 2 — a partial split sends exactly the ids the operator marked

Eight-member situation; the operator ticks positions 1 and 3.

```
checkboxes rendered: 8
POST /api/situations/1/feedback
{"verdict":"split","member_ids":[1,2,3,4,5,6,7,8],"updated_at":1700000007.5,"excluded_ids":[2,4]}
```

`excluded_ids` is exactly `[members[1], members[3]]`. Asserted in **both** directions — set equality
against what was marked, and explicitly that nothing *unmarked* appears.

**Three controls**, because the obvious test passes for several wrong implementations:

| Control | What it rules out |
|---|---|
| nothing marked ⇒ `excluded_ids` **absent**, not `[]` | a client that always sends the key; an empty list reads as "considered every member and excluded none", which is a different claim (DECISIONS #127) |
| ticked boxes + **Confirm** ⇒ no `excluded_ids` | a client that attaches marks to any verdict; a confirm asserts every pair positive and an exclusion would contradict it |
| viewer ⇒ **no checkboxes exist at all** | the gesture being available to a principal who cannot post a verdict |

## 4. Invariant 3 — the v0.7.5 defect, machine-checked for the first time

`FEEDBACK-PATH-0.7.5-DRAFT.md` §5 asked for exactly this: *drive `applyUpdate` twice and assert the
same DOM node is still in the document.* DECISIONS #99 recorded that it could not be done — there
was no DOM to drive — and the claim was carried by `v0.7.5-manual-verification.md`, executed by a
human.

The operator's sequence, executed: expand a card, tick two members, **let a server-sent update
arrive**, then click Split.

```
sameDetailNode:        True
buttonStillConnected:  True
detailStillConnected:  True
heldMarkerPresent:     True
POST body: {"verdict":"split", …, "excluded_ids":[2,4]}
```

Tests A, C and D of the manual protocol, now mechanical. Before v0.7.5, `clear(sits)` was the first
statement of `renderSituations`, so the update destroyed the card mid-gesture and the click landed
on a detached node or on a button from a render the operator never read.

**What this does not cover**, and it is not a small thing: the *browser's* behaviour under a real
2-second SSE stream with real paint timing. One update is delivered, synchronously, into a DOM with
no renderer. It proves node identity and payload; it proves nothing about what the operator saw.
The manual protocol remains the evidence for that, and §5 of `SECURITY-REVIEW-0.7.5.md` remains the
record of the human-factors residual the marker does not close.

## 5. Invariant 4 — no render path writes unescaped data into the document

The payload from `test_security_ui.py`, reused verbatim, pushed through the **real label route**
onto every device and class, then a card expanded and the Entities panel opened.

```
dangerous elements introduced: {}
payload in text nodes:         34
payload in attribute values:   0
```

The assertion is **structural, not textual**: walk the resulting document and count the *elements*
that appeared. Asserting over a serialisation would have measured the harness's escaper rather than
`app.js`'s.

**Why it is not vacuous.** A harness whose only element-creation path is `createElement` could not
construct an injected `<script>` however badly the code behaved. So the harness DOM implements
`innerHTML` as a **real parse** (`html.mjs`), and a bypassed `esc()` really does build elements —
demonstrated red in `v0.12.0-guard-demonstrations.md` §2.

**Control**: `payloadInTextNodes > 0`. A run that rendered nothing would satisfy every other
assertion and prove nothing at all. **This control fired during construction**: the hostile string
was duplicated in `run.mjs` and in `uifixtures.py`, the two drifted (`alert(1)` against
`alert(document.cookie)`), and the scenario silently found zero occurrences of a payload that was
never there. Nothing else in the test would have noticed. The payload now has one source and is
passed as a parameter.

## 6. Invariant 5 — a capability the client lacks produces no request

A viewer attempts all seven admin tabs. **Zero requests to admin routes** — not requests that are
refused; requests that are never made.

**The control is the whole test.** A harness that clicked nothing would report the same zero, so the
identical gestures are run at admin and must produce the requests, at least one of them on an
admin-capability route. Without that, the viewer's zero is unmeasured.

### 6.1 What the harness found, and why the docstring is load-bearing

Bypassing the gesture entirely and calling `renderPanel(id)` directly — what a deep link or a
client-side router would do — as a viewer also issues **no request**. But not for the reason one
would want:

```
outcomes: {users: "threw: TypeError", tokens: "threw: TypeError", … }
requestsAfterBypass: []
```

`prunePanels` removed the container, so `clear(null)` throws before `api(...)` is reached. **There
is no capability check inside the loaders.** The outcome is right; the mechanism is incidental, and
v0.13.0 introduces routing — precisely when an accidental defence stops being available.

Not fixed here (rule 9; this release changes not one byte of `ui/app.js`). Instead the test asserts
**both** that no request is issued *and* that every loader threw — so if a later change made a
loader return normally, the test fails and its docstring cannot quietly become false. Recorded in
`../ROADMAP.md` and constrained in `../architecture/UI-0.13-DRAFT.md` §11.

## 7. What is deliberately not captured

No assertion in `test_ui_invariants.py` names a tab's order, a panel's title, a CSS class, a DOM
shape, a colour or a line of copy. Tab labels appear only as *inputs* that drive clicks, annotated
as such.

> If you are asserting a class name, you are describing what is about to be deleted.
