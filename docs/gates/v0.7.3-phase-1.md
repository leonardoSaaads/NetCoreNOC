# Gate 1 — v0.7.3 mechanism measurement, scope and decisions

**Status: PASSED.** The `Store` mechanism and the `Engine` mechanism were each chosen on a
`mypy --strict` measurement taken on **real sections of the real code**, not on preference and not
on this release's brief. `MODULE-ARCHITECTURE.md` §6's "the choice is v0.7.3's to make" is
superseded by a **dated note pointing at DECISIONS #88**; the original paragraph is left as written.

Two of the four measurements below **disagree with what the build prompt predicted**. Both are
reported as taken, and both changed the design.

---

## 1. What was measured, and how

Two prototypes were built in a scratch tree, outside the repository, each assembled from **method
bodies copied verbatim out of the real files** — not from illustrative stand-ins. Each was checked
with the project's own `mypy --strict` under Python 3.12, and the `Store` prototype was additionally
executed to read back `__mro__` and to hash every moved method against the Phase 0 table.

Choosing sections mattered. The build prompt's own validation used `devices` + `audit_log`; those
two sections happen to have **no cross-mixin calls at all**, which is why it measured zero errors.
The sections chosen here were picked to be adversarial to the mechanism: **`devices` + `alarms`**,
the pair containing a genuine cross-mixin call (`alarms.ingest` calls four `devices` methods).

## 2. `Store` — measurement 1: `StoreBase` exactly as §4.2 specifies

`StoreBase` holding the ten attribute annotations and the `conn` accessor **and nothing else**;
`DeviceMixin(StoreBase)`, `AlarmMixin(StoreBase)`, `Store(DeviceMixin, AlarmMixin, StoreBase)`.

```
$ mypy --strict --python-version 3.12 np
np/alarms.py:27: error: "AlarmMixin" has no attribute "device_id"  [attr-defined]
np/alarms.py:28: error: "AlarmMixin" has no attribute "class_id"  [attr-defined]
np/alarms.py:29: error: "AlarmMixin" has no attribute "ne_id"  [attr-defined]
np/alarms.py:33: error: "AlarmMixin" has no attribute "entity_level0"  [attr-defined]
Found 4 errors in 1 file (checked 5 source files)
```

**Four errors, not zero.** The mechanism is sound; the base as literally specified is not quite
sufficient. The build prompt anticipated this possibility and asked for it to be reported plainly
rather than quietly worked around, so here it is, with the scope of the problem measured exactly.

### 2.1 How big is the problem? Six methods.

An AST sweep of all 109 methods for `self.<method>` calls that cross a §6 module boundary:

| Callee | Lives in | Called from |
|---|---|---|
| `conn` | `store/base.py` | 103 methods in 15 modules — **already on `StoreBase`** |
| `device_id`, `ne_id`, `class_id`, `entity_level0` | `store/devices.py` | `alarms.ingest` |
| `situation_member_nes` | `store/governance.py` | `read_models.list_situations` |

**Six callees, five of them not already handled, and exactly two calling modules.** Every other
cross-module reference in the whole class is `self.conn`.

## 3. `Store` — measurement 2: the two candidate amendments

### Variant A — declare the five signatures on `StoreBase`

```
$ mypy --strict --python-version 3.12 na
na/base.py:29: error: Missing return statement  [empty-body]
...
Found 5 errors in 1 file (checked 5 source files)
```

A signature with a `...` body fails `mypy --strict` outright. Making it pass requires either
`raise NotImplementedError` or `@abstractmethod` — that is, putting **behaviour** on a base that
§4.2 says must hold none. It is also a live hazard rather than a stylistic one: if a mixin were ever
assembled without its sibling, the stub resolves instead of the real method and the failure mode is
a **silent no-op write**. Rejected.

### Variant B — the calling mixin inherits the sibling mixin

`AlarmMixin(DeviceMixin)` instead of `AlarmMixin(StoreBase)`; nothing added to `StoreBase`.

```
$ mypy --strict --python-version 3.12 nb
Success: no issues found in 5 source files
```

```
MRO: ['Store', 'AlarmMixin', 'DeviceMixin', 'StoreBase', 'object']
moved-method hash parity: 9 identical, 0 mismatched
conn accessor resolves from StoreBase: StoreBase.conn
```

**Zero errors, zero declarations, zero duplication, linear MRO, and all nine moved bodies hashing
identically to `store.py`.** Two inheritance edges in the whole package —
`AlarmMixin(DeviceMixin)` and `ReadModelsMixin(GovernanceMixin)` — and the dependency graph stays a
DAG, so there is no import cycle. **Chosen (DECISIONS #88).**

### 3.1 Why option (b) is rejected — restated, because it is the important one

Free functions taking `conn` with `Store` as a façade would rewrite **all 109 method bodies** as
module-level functions with a `conn` parameter, plus 109 delegating one-liners. That changes all 109
hashes. The parity proof of directive 3 — the single thing that makes a 1 512-line split *provable*
rather than *carefully done* — becomes impossible to state. A refactor of the data layer that cannot
prove it moved nothing is not one this project should ship.

## 4. `Engine` — measurement 3

`EngineBase` with the fifteen attribute annotations the may-leave mixins touch, plus
`ScorerLifecycleMixin` and `GapMixin` built from the real method bodies and the real `GapTracker`:

```
$ mypy --strict --python-version 3.12 ne
Success: no issues found in 5 source files
```

**Zero errors and — the notable part — zero method declarations needed on `EngineBase`.** That is a
consequence of DECISIONS #90 rather than luck: once `maintenance` stays in `engine.py`, the
cross-boundary call graph is

```
mixin -> Engine calls : NONE
mixin -> mixin calls  : NONE
Engine -> mixin calls : 6  (fine — Engine inherits every mixin)
```

so `EngineBase` can be what §5.2 wants it to be: a pure declaration site.

## 5. `Engine` — measurement 4: the number that decides §5.3

| | lines |
|---|--:|
| must-stay `Engine` method lines | **425** |
| may-leave `Engine` method lines | 200 |
| total | 625 |

425 method lines before the 31 blank separators, the class header and docstring, `FlapDetector`,
`EngineBase`, the module docstring, the imports and the constants. `engine.py` **cannot** come in at
or under 400.

**`COHESION_EXEMPT` is therefore required** and is designed in Phase 2 (DECISIONS #91). This is
settled here, with the number in hand, rather than discovered at verification and improvised. The
final `engine.py` count remains a *measurement* taken in Phase 4; what is decided now is only that
the mechanism must exist.

### 5.1 Why 425 and not the 397 Phase 0 first computed

`maintenance()` (22 lines) and `maintenance_loop()` (6 lines) stay in `engine.py`, against both
`MODULE-ARCHITECTURE.md` §7 and the build prompt's §5.1 table. Build prompt §5.2 rules that a
may-leave method touching the batch lock or the ingest path does not leave, and that directive 4
outranks the module table. Both triggers fire on `maintenance` and on nothing else — it is the only
candidate that acquires `self.store.lock` (the same object `_commit_batch` acquires; there is one
lock) and the only one that calls a directive-4 must-stay method (`_close_situation`). Full evidence
table in [`v0.7.3-phase-0.md`](v0.7.3-phase-0.md) §4.2; reasoning in DECISIONS #90.

## 6. Decisions recorded

| # | Decision |
|---|---|
| **88** | Mixins over a thin annotated base, with sibling inheritance where a mixin calls a sibling — supersedes `MODULE-ARCHITECTURE.md` §6 in place, by dated note |
| **89** | `main.py` stays a module; `Engine` gets the same mechanism via `EngineBase` |
| **90** | `maintenance()` and `maintenance_loop()` do not leave `Engine`, against both module tables |

| **92** | The layer rule gets a test, with an empty exemption list |

`docs/scope/SCOPE-0.7.3.md` is written, including §2's seven deferrals and §4's honest statement of
what this release does *not* buy.
