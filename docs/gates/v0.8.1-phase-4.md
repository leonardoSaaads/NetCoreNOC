# v0.8.1 — Gate 4: orphans and the denominator

Built alongside Phase 3 rather than after it, because both figures are read by the same
`bias.collect` pass and splitting them would have meant re-freezing the report fixture twice.

## The orphan count

`store.orphaned_promoted_pairs()` — promoted pairs whose `situation_id` no longer matches any
surviving label. Reported, **never collected**: a corpus with orphans is not corrupt, it is a corpus
whose *usable* size is smaller than its row count, and deleting features whose label an operator
destroyed would be a second destruction nobody asked for (DECISIONS #112).

After F44's fix the routine orphan is gone — labels and their promoted pairs now die together at the
audit bound. Two paths still produce them, and the report exists for exactly those: an audit-bound
reduction landing between a label and its features, and any **pre-v0.8.1 database** that already
lost labels to F44.

`test_the_report_counts_orphaned_promoted_pairs` asserts both directions: the clean fixture reports
**0**, and once every label is removed the orphan count equals the full promoted-pair count.

## The denominator

`bias.py` divided by `COUNT(*) FROM situation`, a table the operational prune collects. Phase 0
measured the printed rate at **300.0%**.

The denominator is now `store.labelled_situation_population()` —
`SELECT COUNT(*) FROM (SELECT id FROM situation UNION SELECT situation_id FROM feedback)`, the
population the database has **evidence** of. Every situation in the numerator is by definition
referenced by a label, so it is in the union: **the numerator is a subset of the denominator by
construction**, and no clamp is needed for the rate to be meaningful on any database.

The report names the population rather than leaving it to be inferred — the line reads
`situations known (live + labelled)`, with a paragraph explaining why it is not
`COUNT(*) FROM situation` and citing the 300.0% it replaces.

### The skew, constructed

`test_the_coverage_rate_cannot_exceed_100_percent` builds three labelled situations and then deletes
two while their labels survive. It does that behind `PRAGMA foreign_keys=OFF`, and the comment says
why: v0.8.1's `prune()` **retains** the labelled situation row, so a fresh database can no longer
reach this state — but a database upgraded from v0.8.0 can already be in it, and the report has to
stay honest about it. The test asserts the specific figure (`100.0%`) and the general property
(`situations_labelled <= situations_total`).

Re-running Phase 0's own defect-6 driver against the fixed tree:

```
  (b) two situations collected, their labels surviving:
    situations_total     : 3
    situations_labelled  : 3
    situation_label_rate : 100.0%
```

(The driver's trailing `<-- EXCEEDS 100%` annotation is a hard-coded caption from Phase 0, not a
live assertion; the figure beside it is what changed, 300.0% → 100.0%.)

## The fixture diff, explained

`tests/fixtures/bias-report.txt` is re-frozen. The complete diff is three additions and one rename:

| Change | Why |
|---|---|
| `+ of those, inside the training window   5` | the training window as a selection clause (Phase 3 S2) |
| `+ outside it (held, not selectable)      0` | the corpus's two sizes — what it holds and what a model may read |
| `+ ORPHANED: promoted, label since gone   0` | this gate's orphan figure |
| `+` two prose paragraphs | why the window selects, and what an orphan is. The prose is not decoration in this report; it is what stops a number being misread. |
| `- situations                          3`<br>`+ situations known (live + labelled)   3` | the denominator names its population |
| `+` one prose paragraph | why the denominator is not `COUNT(*) FROM situation`, and the 300.0% it replaces |

**No existing measurement changed value.** `situations` was 3 and `situations known` is 3 — the
denominator change is a no-op on a healthy database, which is exactly the property it should have.
Every other figure in the report is byte-identical to v0.8.0's.

## Determinism

`make bias-report` is deterministic across runs by construction — no wall clock is read, and the new
training-window figure is anchored on `MAX(evaluated_at)` over promoted rows rather than on
`time.time()`, for exactly that reason. The gate is `tests/test_bias.py`'s byte-for-byte comparison
against the frozen expectation, which passes:

```
tests/test_bias.py  ...........   11 passed
```

- the coverage rate cannot exceed 100%, asserted by a test that constructs the skew: **yes**.
- `make bias-report` still deterministic: **yes**, and the byte-for-byte gate is green.
- the fixture updated with the diff explained: **yes**, table above; no existing figure moved.
