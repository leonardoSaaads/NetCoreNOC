# Gate 3 — v0.8.0 migration `0008`

**Status: PASSED.** One migration, forward-only, additive, applying cleanly onto a **populated**
v0.7.5 database. It seeds no dataset rows, adds no trigger to a hot table, preserves the audit chain
with the identical final hash, and leaves first-boot behaviour byte-identical.

`src/netcorenoc/migrations/0008_feedback_dataset.sql` — the eighth and only new migration.

| | |

## 2. Applied to a **populated** v0.7.5 database

The fixture is built by freezing migrations `0001`–`0007` into a temporary directory, opening a
`Store` against it (so the database is written by the *real* v0.7.5 schema path, at
`user_version=7`), populating it through the real `Store` API — devices, classes, three alarms, a
situation with three members, a link, **two feedback rows**, and four chained audit rows — and only
then pointing `MIGRATIONS_DIR` back at the full set.

The identical hash is the stronger claim: not merely "the chain still verifies" (which a rewritten

### No dataset rows seeded

```
  capture_run            = 0  OK (empty)
  dataset_observation    = 0  OK (empty)
  dataset_pair           = 0  OK (empty)
  feedback_member        = 0  OK (empty)
```

**An empty dataset is a correct dataset.** Capture begins when the engine next processes a trap, not
when this script runs. Compare `0005`, which *had* to seed a row because the engine needs scoring
parameters; this needs nothing.

### `legacy_capture` backfilled — a marker, and only a marker

```
  {'id': 1, ..., 'verdict': 'confirm', 'capture_provenance': 'legacy_capture',
   'member_digest': None, 'member_count': None, 'acquisition_channel': None, 'coverage': None}
  {'id': 2, ..., 'verdict': 'split',   'capture_provenance': 'legacy_capture',
   'member_digest': None, 'member_count': None, 'acquisition_channel': None, 'coverage': None}
```

**One column is written; the other fourteen stay `NULL`.** That is the distinction the migration
exists to hold:

> The marker says *"this row was acquired over the pre-v0.7.5 path"* — knowable from the fact that
> the row exists at migration time, and therefore **exact rather than estimated**. It says nothing
> whatever about whether any particular verdict was meant.

Filling `member_digest` or `coverage` would be inventing content. `0007`'s own comment states the
principle — *"inventing a plausible author would be worse than admitting none"* — and it applies
unchanged.

The pre-existing columns are untouched:

```
  before: [{'id': 1, 'situation_id': 1, 'verdict': 'confirm'}, {'id': 2, ..., 'verdict': 'split'}]
  after : [{'id': 1, 'situation_id': 1, 'verdict': 'confirm'}, {'id': 2, ..., 'verdict': 'split'}]
```

### No trigger on a hot table

```
  triggers: [('audit_log_no_delete', 'audit_log'), ('audit_log_no_update', 'audit_log'),
             ('governance_policy_no_delete', 'governance_policy'),
             ('governance_policy_no_update', 'governance_policy'),
             ('scorer_config_no_delete', 'scorer_config'), ('scorer_config_no_update', 'scorer_config')]
```

**The six triggers are exactly the pre-existing ones.** None on `alarm`, `link`, `situation_alarm`,
`situation`, or the new dataset tables — so nothing was added to a table the ingest path writes.

`situation` gains `merged_into` as a **column only**: it is written by the single `UPDATE` that
`merge_situations` already runs, so this adds one assignment to an existing statement and no new
write on the batch path.

### First-boot behaviour byte-identical

```
  tables ADDED by 0008   : ['capture_run', 'dataset_observation', 'dataset_pair', 'feedback_member']
  tables REMOVED by 0008 : []  OK
  tables CHANGED by 0008 : ['feedback', 'situation']
```

Four new tables, **zero removed**, and the two changed only by `ALTER TABLE … ADD COLUMN` — additive
and nullable, so every statement the v0.7.5 application issues against them still resolves. An
appliance that applies `0008` and runs the v0.7.5 code would behave identically.

```
netcorenoc/ui/vendor/CHECKSUMS.txt       netcorenoc/ui/vendor/d3.LICENSE

```

**Sdist** — all eight migrations under `src/netcorenoc/migrations/`, plus
`src/netcorenoc/ui/vendor/CHECKSUMS.txt`.

**Eight migrations in both artifacts.** F12 exists because a wheel once shipped `index.html` alone
and the container UI 404'd; F13 is its sdist twin. `0008` is covered by the existing
`migrations/*.sql` glob in `[tool.setuptools.package-data]`, so no packaging change was needed —
which is itself the check: a migration that needed a `pyproject.toml` edit to ship would mean the
glob had rotted.

> The version string in the artifact names is still `0.7.5`. The bump to `0.8.0` is Phase 7's, where
> `make release-check` verifies `pyproject.toml`, `__init__.py` and `CHANGELOG.md` agree. Building
> here proves the *migration ships*, which is this gate's question.
