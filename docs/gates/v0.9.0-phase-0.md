**The reviewer's measurement is reproduced exactly** on the three numbers that carry the argument:
194 341 evaluated, 339 rejected, **99.83 %** accepted; `dual_incident` at **120** pairs and
`fiber_cut` at **28** are the only scenarios containing both classes. The quoted score ranges also
reconcile: *"rejected 0.02–0.26"* is `background_noise`'s p10/p90 (0.0209 / 0.2565), and
*"accepted 0.55–0.81"* is the range spanned by the accepting scenarios' p10 and p90 columns
(0.5546 … 0.8118).

### One difference, and it is worth stating

The build prompt says *"the four storm scenarios accept 100 %"*. **Six** scenarios accept 100 %:
`camera_nvr`, `chassis_card_fail`, `decoy_varbinds`, `olt_storm`, `pon_dying_gasp`,
`pon_pon_port_down`. The corpus is therefore **seven-ninths uniform** (one at 0 %, six at 100 %) and
two-ninths mixed, not five-ninths uniform. This does not weaken the finding — it strengthens it: the
discriminating population is smaller than the prompt's own framing implies.

### The two populations, and the threshold's position

```
rejected: n=339     min=0.0082  p50=0.1371  max=0.4185
accepted: n=194002  min=0.5339  p01=0.5551  p50=0.6147  max=0.9904
```

The distribution is bimodal with a **gap of 0.115** between the highest rejection (0.4185) and the
lowest acceptance (0.5339), and the 0.50 threshold sits below the accepted population's first
percentile (0.5551). Confirmed.

### The "near the threshold" fraction, and why the obvious reading of it is wrong

| band around 0.50 | pairs | share | below | above |
|---|---:|---:|---:|---:|
| ±0.15 | 170 061 | 87.51 % | 38 | 170 023 |
| ±0.10 | 79 441 | 40.88 % | 11 | 79 430 |
| ±0.05 | 1 481 | 0.76 % | 0 | 1 481 |
| ±0.02 | 0 | 0.00 % | 0 | 0 |

87.51 % within ±0.15 looks like a corpus of close calls and is not one. The accepted mass sits at
0.55–0.65, which is *near* 0.50 in absolute terms while being **entirely on one side of it**: at
±0.15 the split is 170 023 above to 38 below, and at ±0.02 the band is **empty**. Reporting only the
±0.15 figure would have been true and misleading, which is the failure mode this whole release is
organised against, so all four bands are here.

### What this implies for a pairwise classifier — one sentence, as required

**A pairwise classifier trained on the joined data reaches 99.83 % accuracy by emitting "link"
unconditionally, so pairwise accuracy cannot distinguish a model that has learned anything from one
that has learned the base rate, and no metric this release reports may be pairwise accuracy.**

### What these numbers already decide

Read against the §3 floors this release pre-registers, **reading (b) — the more generous of the
two — fails two of the four countable floors**:

| Floor | Required | Reading (b) | |
|---|---|---|---|
| `split` bags | ≥ 40 | **13** | ✗ |
| mixed bags | ≥ 20 | **5** | ✗ |
| distinct operators, top ≤ 60 % | ≥ 3 | 3 at 34.1 % | ✓ |
| merge-aware incidents | ≥ 30 | 37 | ✓ |

The most consequential line in the table is **mixed `split` bags: 1**. A `split` on a uniform bag
tells a model that pairs it already rejects should be rejected; the only rows where the operator
contradicted the champion about a decision the champion actually made number **one bag** in the
richest corpus this repository can construct. Workstream 0 pre-registers against these quantities
knowing them, and the release's expected outcome is **insufficiency plus a projection**, which
directive 2.7 names a success.

**Honest limit on (b).** These are labels generated by a rule, not by people. They establish the
*shape and scale* of a corpus — bag sizes spanning 0 to 1 051, coverage genuinely split four ways,
mixedness rare — and they establish nothing about how operators actually judge. Every conclusion
drawn from them in this release is a conclusion about volume, never about agreement.

## 3. The `LinkScorer` contract, enumerated

```
CONTRACT_VERSION = '1.0'   DEFAULT_SCORER_ID = 'additive'
Protocol members: ['contract_version', 'params_fingerprint', 'score', 'scorer_id']
```

| Member | Kind | `AdditiveScorer` returns |
|---|---|---|
| `scorer_id` | read-only property | `'additive'` |
| `contract_version` | read-only property | `'1.0'` — only the MAJOR component gates activation |
| `score(LinkFeatures) -> LinkScore` | method, **pure** | see below |
| `params_fingerprint() -> str` | method | `c490028245242445e9f58e46e11ac534e5a3f8be03bd9643135557a2e3183418` at the coded defaults |

For `LinkFeatures(delta_t_s=7.0, class_affinity=0.42, entity_affinity=0.0, …)`:

```
LinkScore(linked=False, score=0.3845668699010345, threshold=0.5,
  TermContribution(name='temporal',        weight=0.3,  value=0.7918895663367816, contribution=0.23756686990103448),
  TermContribution(name='class_affinity',  weight=0.35, value=0.42,               contribution=0.147),
  TermContribution(name='entity_affinity', weight=0.35, value=0.0,                contribution=0.0),
)
sum(terms.contribution) = 0.3845668699010345  == score -> True
```

`LinkFeatures` is a `NamedTuple` with **seven live fields** (`delta_t_s`, `class_i`, `class_j`,
`class_affinity`, `ne_i`, `ne_j`, `entity_affinity`) and **seven reserved** ones, all `None`
throughout v0.8.1: `severity_i/j`, `topo_distance`, `probable_cause_i/j`, `event_type_i/j`.
Populating one is a *minor* contract bump (DECISIONS #49).

**`SafeScorer` wrapping**, verified by execution:

* `SafeScorer(delegate).active is delegate` → `True`; after degradation `.active` is the coded
  default, permanently, for the life of the process.
* `scorer_id`, `contract_version` and `params_fingerprint()` all delegate to `.active`.
* `SafeScorer(x).score(f) == x.score(f)` → `True` (no wrapping cost in the answer).
* Contract violations it catches: a result that is not a `LinkScore`; a non-finite score; an
  **empty `terms`** tuple — explainability is enforced, not requested. Plus any exception, and a
  call over `budget_s = 0.5`.

**`scorer_config` stores** (migration 0005): `id`, `scorer_id`, `contract_version`, `w_t`, `w_a`,
`w_e`, `tau_s`, `threshold`, `params_hash`, `created_by`, `created_at`, `note`. The seeded active
row is the coded defaults with `note='coded defaults, seeded by migration 0005'`. **Note for
Workstream 2**: the table has columns for *the additive scorer's five parameters* and no general
parameter blob, so a learned coefficient vector has nowhere to live in it. That is a fact about
v0.11.0's promotion, not about this release, and it is recorded here rather than worked around.

### The second-implementation proof

v0.6.0 shipped it, test-only, exactly for this:

```
tests/test_scoring.py defines: ['ConstantScorer', 'RaisingScorer', 'SlowScorer', 'EmptyTermsScorer']
  isinstance(ConstantScorer(),   LinkScorer) -> True
  isinstance(RaisingScorer(),    LinkScorer) -> True
  isinstance(SlowScorer(),       LinkScorer) -> True
  isinstance(EmptyTermsScorer(), LinkScorer) -> True
```

None inherits a base class; none registers anywhere. The assertion lives in
`tests/test_scoring.py::test_protocol_accepts_more_than_one_implementation`, and its docstring calls
these the *plurality proof*. **The challenger satisfies `LinkScorer` the same way — structurally, no
base class, no registry.**

## 4. Where the slow loop is — the finding that changes a design

Read off the code, by parsing it rather than by eye:

```
Engine.maintenance: 24 lines
  top-level statements in maintenance():             2   (a docstring, and one `async with`)
  of which `async with self.store.lock`:             1
  statements INSIDE the lock block:                 12
  statements AFTER the lock block:                   0

Engine.maintenance_loop:
    tick = 0
    while True:
        await asyncio.sleep(MAINT_INTERVAL_S)
        tick += 1
        await self.maintenance(time.time(), retention_provider(), tick)
```

> **FINDING. There is no point inside `maintenance()` that runs outside `store.lock`.** The lock is
> taken as its first statement and released only when the pass ends; `await self.store.commit()` is
> its last statement inside it. The only code in the periodic path that runs outside the lock is
> `maintenance_loop`'s `await asyncio.sleep(MAINT_INTERVAL_S)`.

That lock is the **same object** `_commit_batch` takes — `Store.lock`, one `asyncio.Lock`, declared
once in `store/base.py` and asserted by `tests/test_store_concurrency.py`. So work added anywhere
inside `maintenance()` delays the next batch by exactly its own duration, and a fit that took two
seconds would stall ingestion for two seconds.

### The consequence for Workstream 2, decided now

The build prompt says to train *"at the point Phase 0 identified as running outside the batch
lock."* **That point does not exist and this release must create it.** The shape it takes:

* training runs in **`maintenance_loop`**, *after* `maintenance()` has returned and released the
  lock — never inside `maintenance()`;
* it takes `store.lock` **only** to read its training rows and, separately, to write its result,
  each a bounded statement; the **fit itself holds no lock**;
* it is bounded in wall time, and a failure degrades training exactly as a capture failure degrades
  capture.

This is recorded as a decision in Phase 1 rather than discovered in Phase 4, which is the whole
purpose of measuring first.

## 5. The champion's per-call cost, on this machine

`AdditiveScorer.score()` timed over features captured from the corpus (every ninth pair, 21 594
calls), after a 1 000-call warm-up:

| | run 1 | run 2 |
|---|---:|---:|
| median | 1.645 µs | **1.496 µs** |
| p99 | 7.676 µs | **2.927 µs** |
| mean | 2.027 µs | 1.670 µs |

**Reported as a range, not a point.** The p99 moved by 2.6× between two runs of the same code on the
same machine, which is scheduler noise on a shared box and not a property of the scorer. The
admission filter of §9.1 is therefore expressed **relative to the champion measured in the same
process at the same time**, never against a number copied out of this table — a budget of
"*k* × champion, both measured now" is robust to exactly this variance and an absolute microsecond
budget is not.

Working figures for the filter's design: **champion median ≈ 1.5 µs, p99 ≈ 3 µs.**
