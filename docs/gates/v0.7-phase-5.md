## The end-to-end run

A single script drove a **real v0.6.0 appliance** through the upgrade and out the other side. Its
output, verbatim:

```
v0.6.0: schema 5, 1 situations, 8 active alarms, scorer_config_id=1
upgraded to schema 6: partition, stats, scorer provenance and audit chain all intact;
                      zero governance rows
no policy: viewer sees 2 NEs, 2 situations, 9 capabilities == its full ceiling
scope applied (same session, no restart): viewer now sees 1 NE, 1 situations,
                      4 member(s) redacted; no leaked addresses
admin is unscoped: still sees every NE
capability policy applied: viewer restricted on the next request of the SAME session;
                      above-ceiling entries rejected at write time and inert regardless
cleared: byte-identical to the no-policy state again; every change audited;
                      audit chain still verifies

GATE 5 OK
```

Step by step, that is:

1. **A genuine v0.6.0 database** — migrations frozen at `0005`, the `fiber_cut` fixture replayed
   through a real `Engine`, a maintenance pass run, users created, an audit row written.
2. **Upgraded in place** — schema 5 → 6. Situation partition, `stats()`, `scorer_config_id` and the
   hash chain all **identical**, and `active_governance_ids() == {}`: the migration seeded nothing.
3. **No policy ⇒ v0.6.0 exactly** — the viewer's resolved capability set equals
   `rbac.ceiling("viewer")`, and `/api/me` reports `scoped: false`.
4. **A scope applied on a different connection** takes effect on the viewer's **next request, same
   session, no restart**: 2 NEs → 1, the cross-boundary situation's other members redacted to a
   count, and no out-of-scope address anywhere in the graph response.
5. **Admin unscoped** under the same policy.
6. **A capability policy naming above-ceiling entries is rejected at write time (400)** — and the
   accepted, in-ceiling policy restricts the viewer on its next request while leaving `stats.read`
   working and `users.manage` still 403.
7. **Cleared** — the appliance returns byte-identically to the no-policy state, every change is in
   the audit log (`rbac.policy.update` and `scope.policy.update`, ≥ 2 each), and the chain still
   verifies.

> One correction worth recording, because it is a real property of the system rather than a
> scripting slip alone: the first run of this script fed the **viewer's own** view of an NE address
> back in as a scope selector, and the scope appeared not to restrict. It was behaving correctly —
> `shaping.py` coarsens `ip` to a `/24` for a viewer, so the "address" the script had was a CIDR
> covering the whole subnet, and it matched both NEs. The script now reads exact addresses as
> admin. The interaction is worth knowing: **a scope written from a coarsened address is a subnet
> selector**, which is why the Governance panel shows the resolved NE count per role.

carried forward from v0.6.0": `situation.scorer_config_id` records the configuration that **created**

line.
