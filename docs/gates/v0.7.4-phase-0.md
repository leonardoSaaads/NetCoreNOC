## 2. The two gate holes, reproduced by execution

Not read — **executed**, against the untouched tree, with
`src/netcorenoc/api/declare.py` exactly as v0.7.3 ships it. Output verbatim:

```
=== Gap 1 — the gate covers three verbs and only the decorator form ===

DeclaredRoutes methods: ['delete', 'get', 'post']
  has .put():   False
  has .patch(): False

app.add_api_route("/api/undeclared-bypass", handler, methods=["GET"])
  registration raised:            False
  route now in the table:         [(['GET'], '/api/undeclared-bypass')]
  routes before / after:          4 / 5
  declared in ROUTE_PERMISSIONS:  False
  declared in ROUTE_SCOPE:        False
  (control) the decorator form:   refused, as designed

=== Gap 2 — the exemption is by path prefix, not by absence of capability ===

  require_declaration("GET", '/metrics'          ) -> returned without raising
  require_declaration("GET", '/admin/debug'      ) -> returned without raising
  require_declaration("GET", '/api/undeclared'   ) -> raised UndeclaredRouteError

  /metrics is already on docs/ROADMAP.md and would be exempt by accident.
```

Both reproductions agree with the output `MODULE-ARCHITECTURE.md` §10.1 recorded when the holes were
found during the v0.7.2 review — line for line, including the control. The document was right and
this release executes its specification rather than re-deriving one.

**What each reproduction establishes, precisely.**

* **Gap 1 (F40).** `app.add_api_route` registers an `/api` route that is in neither declaration
  table, and `require_declaration` is never called. The route count goes 4 → 5, so the route is
  *live*, not merely accepted. The control proves the decorator path still refuses, which is what
  makes this a hole in coverage rather than a broken gate. `DeclaredRoutes` also has no `put` or
  `patch`, so those verbs are a second uncovered path — but wrapping them would close today's list
  and stay silent about tomorrow's, which is why §10.1 specifies the post-hoc assertion instead.
* **Gap 2 (F41).** `require_declaration` returns cleanly for **any** path outside `/api`. `/metrics`
  is the motivating case because it is already on `docs/ROADMAP.md:15`-class idea lists and would be
  authenticated when built. `/admin/debug` is included to show the exemption is not about `/metrics`
  specifically: it is about everything that is not `/api`.

Neither is exploited on the v0.7.3 surface — there is no `PUT`, no `PATCH`, exactly one
`add_api_route` caller (confined to `routes_static.py` and pinned by
`test_add_api_route_is_confined_to_the_static_asset_allowlist`), and no authenticated non-`/api`
route. Both are latent holes in a guard whose entire value is completeness.

### 3.3 The one consumer that reads a module's *source*, and what it costs

> `tests/test_declaration.py:179`
> `source = (Path(rbac.__file__)).read_text(encoding="utf-8")`
> — `test_every_unscoped_declaration_carries_a_written_justification`

This is the **only** place in the tree that reads any of the three modules as text. It slices
`ROUTE_SCOPE`'s table out of `rbac.py` and asserts that each of the five `"unscoped"` entries is
preceded by a comment.

When `rbac.py` becomes `rbac/`, `rbac.__file__` resolves to `rbac/__init__.py`, which will not
contain the table — so `source.split("ROUTE_SCOPE: dict[", 1)[1]` would raise `IndexError`. **This
is precisely the failure mode `tests/apisource.py` was written for in v0.7.2** (DECISIONS #84): when
`api.py` became `api/`, four source-scanning guards silently started scanning almost nothing.

Recorded here so the fix is a decision rather than a discovery in Phase 4. The **assertions** of that
test do not change — only the path it reads changes, from `rbac.__file__` to `rbac.tables.__file__`,
which is a moved import path in the sense build-prompt §11 Phase 5.2 permits and requires be listed.
It is listed there. The alternative — leaving the test pointed at `__init__.py` — is the vacuous
guard v0.7.2 already paid for once.

### 4.1 `shaping.py` (476) — **the prompt is right and `MODULE-ARCHITECTURE.md` §10.2 is wrong**

§10.2 records the seam as *"two axes in one file: **field** shaping by role, and **NE scoping** by
policy"*. **The AST shows three parts.** Confirmed independently here before accepting the build
prompt's §5.1 correction:

| Part | Lines | Symbols | Target |
|---|---|---|---|
| field shaping | **50–108** (59) | `_COARSEN`, `_DROP`, `FIELD_RULES`, `_rank`, `_allowed`, `coarsen_ip`, `shape` ×4 (3 overloads + impl) | `shaping/fields.py` |
| scope resolution | **114–377** (264) | `ScopePolicy`, `Scope`, `UNRESTRICTED`, `DENY_ALL`, `is_scopable`, `_selector_lists`, `parse_scope_policy`, `_matches`, `_layers`, `visible_nes`, `_ADDRESS_CHARS`, `_GLOB_CHARS`, `_can_never_match`, `scope_policy_errors` | `shaping/scope.py` |
| projections | **383–476** (94) | `filter_rows`, `_as_int`, `project_graph`, `project_situation_detail` | `shaping/project.py` |

The build prompt gives the scope block as starting at 115; the AST gives **114**, because
`@dataclass(frozen=True)` decorating `ScopePolicy` is on 114 and the decorator is part of the
statement. A one-line difference with no consequence, recorded because the table is meant to be
measured.

**Why the projections are a third module and not a third axis.** `filter_rows`, `project_graph` and
`project_situation_detail` all take a `Scope` (from the scope axis) and return a response body (the
field axis's subject). They are the **consumer** of the other two, not a peer of them. Forcing them
into `scope.py` would put response-body construction in the module that owns the scope decision;
forcing them into `fields.py` would put `Scope` handling in the module that owns field rules. Both
would be arbitrary, and §10.2's two-way framing is what makes it look as though one of them must be
chosen. Recorded as an ADR in Phase 1, superseding §10.2 **in place**.

**The F35 invariant travels with `scope.py`.** `visible_nes` (274–321) carries the v0.7.1 comment
block stating that every one of its inputs is admin-written or engine-written, and `_matches`
(222–258) carries the paragraph explaining why the operator label is not read. Both move verbatim
with the code that depends on them.
`tests/test_governance.py::test_f35_no_resolver_input_is_writable_by_a_scopable_role` must pass
unedited.

**The four shared symbols are not a judgement call.** Decision protocol §10 says ambiguity about
which module a symbol belongs to resolves toward leaving it where it is — but leaving
`ENTITY_MIN_DISTINCT`, `ENTITY_MAX_CARD_RATIO`, `FD_MIN_PAIRS` or `value_hash` in
`varbind_profile.py` would make `varbind_accum.py` import from `varbind_profile.py` while
`varbind_profile.py` imports `Accumulator` from `varbind_accum.py` — a circular import. The import
graph decides, not taste. They move with the classes whose semantics they define, and
`varbind_profile.py` imports them back, which also preserves `varbind_profile.MAX_DISPLAY_CHARS`
for `severity.py` and `varbind_profile.ENTITY_PROMOTE_SCORE` for `tests/test_promotion.py`.

**`varbind_accum.py` is `engine` layer, not cross-cutting.** Build prompt §5.4 says the new modules
are "all of them cross-cutting". That is true of `rbac/*` and `shaping/*` — and for those two,
`tests/test_layers.py::_module_files` keys a packaged module by its **package name**
(`rel.parts[0]`), so `rbac` and `shaping` are already in `LAYER_OF` and **no entry is needed**. But
`varbind_accum.py` is a new *top-level* module, so it gets its own key — and `varbind_profile` is
classified `engine` (`tests/test_layers.py:60`), as `MODULE-ARCHITECTURE.md` §1 places it. An
extraction from an `engine` module is `engine`. Classifying it cross-cutting would put a domain
concept in the layer reserved for "no layer's private concern", and
`test_cross_cutting_imports_only_cross_cutting` would then fail on its `known_oids` dependency.
Recorded as an ADR in Phase 1.
