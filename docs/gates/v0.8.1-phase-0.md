## Defect 1 — F44: the operational prune deletes human labels

The defaults that set the clock:

```
  settings.retention_days default = 7.0
  IDLE_CLOSE_S                    = 3600.0
```

So a label dies roughly **seven days and one hour** after its situation's last activity.

Driving `fiber_cut.json`, labelling situation 1, closing it, then one
`engine.maintenance(now, 7.0, tick=0)` at `close + 7d + 1h`:

```
  situations after replay: [1, 2]; labelling situation 1
  BEFORE   feedback=1  feedback_member=8  dataset_pair=[('dataset', 19), ('sink', 9)]  situation=[(2,)]
  the label row: [(1, 'confirm', 1, 1000010.0)]
  AFTER    feedback=0  feedback_member=0  dataset_pair=[('dataset', 19), ('sink', 9)]  situation=[(0,)]
```

`feedback 1 -> 0`, `feedback_member 8 -> 0` (by `ON DELETE CASCADE`, with `PRAGMA foreign_keys=ON`
set in `store/lifecycle.py:30`), `situation 2 -> 0`, and **the 19 promoted `dataset_pair` rows
survive**. The corpus keeps the features and loses the verdict that justified them. This matches the
independent audit's observation exactly.

The line is `store/retention.py:31`:

```sql
DELETE FROM feedback WHERE situation_id IN (<closed/merged situations older than cutoff>)
```

### Finding (a) — the naive fix does not work, and reproduction is how we know

`feedback.situation_id` is a **restricting** foreign key with no `ON DELETE` action
(`0001_init.sql:89`: `situation_id INTEGER NOT NULL REFERENCES situation (id)`), and
`foreign_keys=ON`. Removing only the `DELETE FROM feedback` line therefore does not create a
"dangling reference by design" — SQLite refuses the delete outright:

```
  (a) deleting a labelled situation, FKs ON -> IntegrityError: FOREIGN KEY constraint failed
```

Every `maintenance` pass would raise once any labelled situation aged out. The fix must therefore
**retain the `situation` row that carries a label** while still collecting that situation's
operational satellites. Recorded here because it changes the shape of Phase 2, and because it is the
clearest possible argument for reproducing before fixing.

Exactly two restricting FKs point at `situation`: `situation_alarm.situation_id`
(`0001_init.sql:66`) and `feedback.situation_id` (`0001_init.sql:89`). `link.situation_id` carries
no `REFERENCES` clause. `prune()` already deletes `situation_alarm` before `situation`, so
`feedback` is the sole remaining blocker.

### What the documentation says about this

Nothing. Grepping the whole tree for any statement connecting `RETENTION_DAYS` to the dataset,
feedback, or labels:

```
=== any doc statement connecting RETENTION_DAYS to the dataset/feedback/labels ===
(no match — the documentation is silent)
```

`README.md:85` describes it only as *"Pruning horizon for cleared/closed history"*. Meanwhile
`MIGRATION.md:52-57` promises a **12-month** training tier, and `MIGRATION.md:90` states outright:

> The background maintenance loop **never** deletes labelled data. It bounds the sink and nothing
> else.

That sentence is false in the shipped product, and it is the promise F44 falsifies.

## Defect 2 — the retention policy does not survive a restart

Applying a policy exactly as `POST /api/dataset/retention` with `preview=False` does, then
constructing a **new `Engine` over the same `Store`**, as `runner.py` does at boot:

```
  shipped default            : RetentionPolicy(sink_days=21.0, sink_rows=2000000, training_days=365.0, audit_days=730.0)
  after the route applies    : RetentionPolicy(sink_days=3.0, sink_rows=111111, training_days=90.0, audit_days=180.0)
  read back live             : (3.0, 111111, 90.0, 180.0)
  after a fresh Engine       : RetentionPolicy(sink_days=21.0, sink_rows=2000000, training_days=365.0, audit_days=730.0)
  meta keys holding retention: []
```

The route answers `"saved"`, audits `retention.change`, and the next restart silently returns the
shipped defaults. `engine.py:148` is `self.retention = RetentionPolicy()` and nothing reads a stored
value at startup.

The persistence pattern exists and was not used — `runner.py:146-148`:

```python
    saved_allow = await store.get_meta("config.allowlist")
    saved_ret = await store.get_meta("config.retention_days")
    effective_allowlist = saved_allow if saved_allow is not None else settings.allowlist
    effective_retention = float(saved_ret) if saved_ret is not None else settings.retention_days
```

The asymmetry is what makes this serious rather than annoying: **the destruction an admin asked for
is permanent, and the configuration they asked for is not.**

## Defect 3 — neither the training nor the audit tier is swept

Four `maintenance` passes past `training_days` (365), then four past `audit_days` (730):

```
  policy: training_days=365.0  audit_days=730.0
  BEFORE   feedback=1  feedback_member=8  dataset_pair=[('dataset', 19), ('sink', 9)]  situation=[(2,)]
  T+train  feedback=0  feedback_member=0  dataset_pair=[('dataset', 19)]  situation=[(0,)]
  T+audit  feedback=0  feedback_member=0  dataset_pair=[('dataset', 19)]  situation=[(0,)]
```

The 19 promoted pairs survive both bounds. (The label had already died at defect 1's seven-day
bound, which is the point: the only tier that reached it was the one that was never meant to.)

Every use of `audit_days` in `src/`:

```

src/netcorenoc/api/routes_admin.py:22,216,237   named, returned, accepted
src/netcorenoc/api/models.py:73             validated (gt=0, le=3650)

Filtering those for a deletion path: **`(none)`**. `audit_days` is validated, recorded, reported,
and read by no deletion path at all. `training_days` is used only as the cutoff of the explicit
admin reduction. Two of the three tiers are numbers that describe nothing.

## Defect 4 — one label promotes the whole sink

Replaying `olt_storm.json` and labelling the single resulting situation **once**:

```
  situations from olt_storm.json: 1 -> [1]
  sink BEFORE the single label : [('sink', 45050)]
  sink AFTER  the single label : [('dataset', 45050)]
  the labelled bag holds 501 alarms
  promoted pairs: 45050; with BOTH ends inside the bag: 45050
  promoted pairs with an end OUTSIDE the bag: 0
```

**45 050 rows promoted by one verdict — the entire sink**, matching the audit.

`DESIGN.md` and `SCOPE-0.8.0.md` claim the dataset grows with *labels* and not with *traffic*. The
condition under which that does not hold, stated precisely: **promotion is per-situation, so one
verdict promotes every evaluated pair of that situation — and a situation's evaluated-pair count
grows with its member count, which grows with traffic during a storm.** The corpus is bounded by
`labels × (pairs evaluated within the labelled situation)`, not by labels. Here one label bought
45 050 rows because the storm made one situation 501 alarms wide. The claim is true per *situation*
and false per *row*, and v0.8.0 stated the row version.

Note the promotion is not indiscriminate: all 45 050 promoted pairs have both ends inside the
labelled bag. The volume is a property of the situation's size, not of a leaky promotion rule.

## Defect 5 — the orphan state

After F44's prune on the `fiber_cut.json` run:

```
  promoted pairs total          : 19
  promoted pairs with NO label  : 19
  surviving feedback rows       : 0

**All 19** promoted pairs survive with zero labels — features nothing can interpret. Not corruption:

## Defect 6 — the coverage denominator

`bias.py:163-166`:

```
  bias.py: situations = await _scalar(store, "SELECT COUNT(*) FROM situation")
  bias.py: out["situation_label_rate"] = pct(int(labelled_situations or 0), int(situations or 0))
```

The numerator is `COUNT(DISTINCT situation_id) FROM feedback`; the denominator is a table `prune()`
collects on the operational schedule. Once labels outlive situations, the denominator shrinks under
its own numerator:

```
  three situations, each labelled — the healthy case:
    situations_total     : 3
    situations_labelled  : 3
    situation_label_rate : 100.0%

  (b) two situations collected, their labels surviving:
    situations_total     : 1
    situations_labelled  : 3
    situation_label_rate : 300.0%   <-- EXCEEDS 100%
```

The report prints **`300.0%`** — a number that destroys a reader's trust in every other figure on
the page.
