# v0.9.0 — Gate 5: sampled online shadow and offline reconstruction

Both mechanisms ship, and **they are not alternatives** (DECISIONS #119). Offline reconstruction
measures model quality at no ingest cost and **cannot** measure training/serving skew by
construction — recomputing from the stored features is tautologically consistent with them. Online
shadow measures real per-call latency and real behaviour under real traffic and says nothing further
about quality.

**Their divergence is the skew test**, and it is the one number in this release that was
pre-registered at an exact value: **0.0000 %**.

---

## 1. The skew test — the two paths agree bit for bit

### On a fixture

```
tests/test_shadow.py::test_online_and_offline_opinions_agree_bit_for_bit    PASSED
tests/test_shadow.py::test_the_skew_test_can_actually_fail                  PASSED
```

The first drives fifty pairs through `Shadow.observe` — the same call `Engine._process` makes —
flushes them, and reconstructs each from what capture stored. Compared with **`==` on the float**,
not with a tolerance, and `linked` compared as a bool. Zero divergences.

The second is the guard on the guard: it corrupts one stored score by `1e-12` and asserts the
comparison notices (`diverged == 1`, `rate_pct == 100.0`). **A skew test that could not go red would
be measuring nothing**, and `1e-12` is far below any tolerance a lazier implementation would have
used.

### On real data

Four corpus scenarios (`fiber_cut`, `dual_incident`, `olt_storm`, `background_noise`) driven through
a real `Engine` at `sample_rate = 1.0`, then reported:

```json
{ "opinions": 2000, "compared": 2000, "diverged": 0, "unmatched": 0, "rate_pct": 0.0 }
```

**2 000 sampled opinions, 0 divergences, 0.0000 %.** Matching the pre-registered expectation
exactly, and it is worth saying why it holds rather than treating it as luck: `feature_vector` is
**one function**, called by training, by the online path and by the reconstruction alike, and the
online path reads `class_affinity` and `entity_affinity` back from the terms the champion emitted
rather than re-deriving them from a learner whose masses have already moved.

`unmatched` is reported separately and is **0** here. An unmatched opinion — one whose captured pair
the sink's row cap has since collected — is *missing evidence*, not agreement, and is never folded
into the rate.

## 2. What the online half costs, measured in rows, bytes and microseconds

Two identical replays into two **file-backed** databases, one with sampling off and one on, so the
byte figure is a real file-size delta including indexes rather than an estimate of payload.

```
 sample rate   pair rows  opinions  rows/trap    db bytes   delta B   wall s
----------------------------------------------------------------------------
         0.0       45474         0     0.0000     5304320         0     2.25
        0.01       45474       454     0.8270     5349376     45056     2.32
         1.0       45474      2000     3.6430     5496832    192512     2.21
```

| | at the shipped default (1 %) |
|---|---|
| **rows** | **454** shadow opinions against **45 474** captured pair rows — **1.0 %** |
| | 0.83 opinions per activation, against the **82.8 pair rows per activation** capture already writes |
| **bytes** | **+45 056 B** on a 5 304 320 B baseline — **+0.85 %**; ≈ **96 B** per opinion |
| **microseconds** | 454 `score()` calls on the ingest path, **6.09 ms total over the entire replay** |

The per-call figure needs one honest note. At `sample_rate = 0.01` the measured mean is **13.4 µs**;
at `1.0` it is **3.6 µs**. The difference is not the sampling rate — it is that 454 calls are
mostly cold, with no warm-up on the ingest path, while 2 000 calls amortise it. The warm figure is
the one to plan against, and the isolated benchmark below agrees with it:

```
additive           median 1.500 us  p99 2.527 us
logistic-shadow    median 2.397 us  p99 7.367 us
```

**The challenger is ~1.6× the champion at the median**, comfortably inside the admission filter's
10× budget — and the budget is a *ratio measured in the same process*, because Phase 0 §5 measured
the champion's own p99 moving 2.6× between two runs on one machine.

`make eval` is unchanged: `c2e8a0ced29d9edf986279d41089ddb68e18da65a46bdc7e9f04811e8b9b6f26`. The
correlation path did not change; a reader and a shadow writer were added.

### The measurement that changed the product — the buffer drops, loudly

At `sample_rate = 1.0` the replay recorded **43 474 dropped opinions of 45 474**. The in-memory
buffer (`MAX_BUFFERED = 2000`) fills long before the maintenance flush, so 95 % of the sample is
discarded — **counted**, never silently.

The bound is working exactly as designed: dropping a sample costs a data point, growing without
bound costs the process. But an operator who set the rate to 1.0 believing they would get every pair
would read a 2 000-row truncated prefix as a census. So this release added an **operator warning**:

> *"43 474 shadow opinion(s) were dropped because the in-memory buffer (2000) filled between
> maintenance flushes. The sample is smaller than the configured rate implies; lower
> `config.shadow_sample_rate` to make the sample representative rather than truncated. Nothing else
> was affected."*

It reaches `/api/stats` through the wiring `runner.py` already has, beside the capture and scorer
warnings. Found by measuring; it would not have been found by reading the code.

## 3. What the deployment chooses

**The rate and the duration — not whether online shadow ever runs.** A model that was never measured
inside the engine must not be promotable two releases later.

| | |
|---|---|
| key | `meta` → `config.shadow_sample_rate`, absent by default (**no route, no capability, no new HTTP surface**) |
| default | `0.01` |
| clamped | into `[0, 1]`; unreadable falls back to the default, never to a rate nobody chose |
| recorded | on `challenger_run.sample_rate`, so a report always carries the rate its numbers came from |

```
test_the_sampling_rate_is_deployment_settable_and_recorded   PASSED
test_zero_sampling_stops_the_online_half_and_nothing_else    PASSED
test_the_buffer_drops_rather_than_growing                    PASSED
```

**Zero means *buffer nothing online*; it does not mean *switch shadow mode off*.** The offline
reconstruction still runs, so quality is still measured — only the skew test loses its subject, and
that is a deployment's choice to make.

## 4. The online path is the real one

`test_the_engine_scores_a_sample_on_the_real_ingest_path` drives `fiber_cut.json` through
`Engine._process` — not through a unit-test double — and asserts the challenger scored, that a
per-call cost was measured, that the rows reached the table on flush, and that

```python
assert engine.correlator.scorer.active.scorer_id == "additive"
assert isinstance(engine.correlator.scorer.active, AdditiveScorer)
```

The champion is still the champion. That is the whole point of the release, asserted at the one
place it could have gone wrong.
