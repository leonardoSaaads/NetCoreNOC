**Status: PASSED.** `make qa && make eval` green on the untouched v0.7.2 tree; all **109** `Store`
methods are hashed and assigned a target module; all **32** `Engine` methods are classified with
their line ranges and the must-stay total is recorded; the attribute inventory, the external import
surface and the per-module line counts are taken.

Everything below is measured, not asserted. It is the baseline the rest of this release must return
to unchanged: the whole value of v0.7.3 is that a 1 512-line file and a 1 079-line file become two
readable module sets **and nothing else moves** — and that claim is only worth something against
numbers taken first.

Three of the measurements below **contradict what the build prompt expected**. They are reported as
found, in §3, §5.1 and §6.2, because a baseline that quietly agrees with its own brief is not a
baseline.

## 2. The `Store` method-hash table — the parity proof

`sha256` of each method's source, taken from the `def`/`async def` line through the method's last
line, dedented to column zero. **Decorator lines are excluded from the hash and recorded
separately**, because the decorator is the one line a move may legitimately re-indent without the
method changing. **Two** methods carry a decorator: `conn` (`@property`) and
`latest_schema_version` (`@staticmethod`). No other `Store` method is decorated.

The hash is deliberately taken *below* the class header, so the only edit a move requires — the
enclosing class name — is outside the hashed region **by construction**. That is the whole trick,
and it is what makes a 1 512-line split provable.

A cross-check is taken at the same time and recomputed in Phase 5: the same hash via
`inspect.getsource` on the **live attribute resolved through `Store.__mro__`**. The AST table proves
the text did not change; the runtime table proves the text Python actually resolves is that same
text — so a mixin split cannot pass the file-level test while resolving to something else. Both
tables agreed on all 109 methods at baseline.

### 3.1 Cross-domain sharing — measured, and **not** what the brief expected

The build prompt (§4.3) anticipated that "several are **mutable caches shared across domains**".
**They are not.** Measured against the §6 module map, every private cache is touched by
`__init__` plus methods that all land in a **single** target module:

| Cache | Target modules that touch it (besides `__init__`) |
|---|---|
| `_device_ids`, `_ne_ids`, `_entity0_ids`, `_class_ids`, `_touched` | `devices.py` only |
| `_entity_ids` | `entities.py` only |
| `_path`, `_conn`, `integrity_warnings` | `lifecycle.py` only |
| `lock` | **no `Store` method touches it at all** |

The real cross-domain coupling is one thing, and it is much stronger than a cache:

> **103 of the 109 methods — spread across 15 of the 16 target modules — read `self.conn`.**

That is the concrete reason one object with one connection is preserved, and it is a better reason
than the one the brief supplied. Exactly six methods do not read `self.conn`, and each is a case
where that is expected: `__init__` and `conn` (which *define* it), `open` and `close` (which use the
raw `self._conn` because they are the ones assigning and clearing it), `latest_schema_version` (a
`@staticmethod`, no `self` at all) and `_should_touch` (pure cache arithmetic).

`lock` deserves its own line. **No `Store` method acquires `store.lock`.** It is acquired entirely
by *callers* — `Engine._commit_batch`, `Engine.maintenance`, and `Perimeter.write_txn`. The lock is
therefore a **public contract of the `Store` object**, not an implementation detail of any module in
the package, which is precisely why splitting `Store` into several objects would be invisible to the
data layer's own tests and catastrophic in production. §4.4's concurrency test exists for this.

### 4.2 `maintenance` and `maintenance_loop` do **not** leave — §5.2 fires

`MODULE-ARCHITECTURE.md` §7 and the build prompt's §5.1 module table both list `maintenance()` and
`maintenance_loop()` as may-leave. **Measurement overrides both**, via the escape hatch §5.2 wrote
for exactly this case:

> "If a `may-leave` method turns out to touch the batch lock or anything on the ingest path, **it
> does not leave** — record that in the gate evidence and leave it in `engine.py`. Directive 4
> outranks the module table."

Both triggers fire on `maintenance`, and it is the **only** may-leave candidate on which either
fires:

| Candidate | acquires `self.store.lock` | calls a directive-4 must-stay method |
|---|---|---|
| **`maintenance`** | **yes** (`async with self.store.lock:`) | **yes** — `self._close_situation` |
| `maintenance_loop` | no | calls `self.maintenance`, which stays |
| `_promotion_sweep`, `_maybe_promote`, `_maybe_confirm_severity`, `_flush_profiler` | no | no |
| `_record_ingest_gaps` | no | no |
| `load_scorer_config`, `_use_default_scorer`, `scorer_warning_list`, `_audit_scorer_fallback` | no | no |

`maintenance` acquires the same `asyncio.Lock` object that `_commit_batch` acquires — there is one
lock, so "the batch lock" and "the store lock" are the same object — and it closes situations
through `_close_situation`, which directive 4 names as must-stay. A reviewer asking "what closes a
situation, and under which lock?" must not have to follow an import to answer it.

`maintenance_loop` stays with it: it is six lines whose whole body is a call to `maintenance`, and
separating a loop from the one thing it loops over would be fragmentation for its own sake.

This costs 28 method lines on `engine.py` (397 → 425) and it is the honest reading of the rules as
written. It also has a structural payoff recorded in §6.2: it removes the **only** call that would
have pointed from a mixin back into `Engine`.

### 5.3 Three module-attribute patch sites — the one place `tests/` must change

A module-level constant is read through the `__globals__` of the module where the *reading function
was defined*. When that function moves to a submodule, patching the name on the old module object no
longer reaches it. Three sites do exactly this today, and no amount of re-exporting can preserve
them — the re-exported name is a **second binding**, not an alias:

expects to see in the `tests/` diff. **No assertion changes.** They are listed here, before the move,
so that when they appear in the diff they are a predicted edit rather than a discovered one.

### 5.4 The entry-point constraint

`README.md`, `Makefile` (`make run`), `docker-compose.yml`, the `Dockerfile` and `MIGRATION.md` all
run the correlator as **`python -m netcorenoc.main`**, and `main.py` ends with an
`if __name__ == "__main__": main()` guard. This is why §5.1 keeps `main.py` a **module**: turning it
into a package would require `main/__main__.py` and would change the semantics of the one command
every operator types.

Separately, `python -m netcorenoc audit verify` reaches `main.py` through
`src/netcorenoc/__main__.py`'s `from netcorenoc.main import legacy_env_error, legacy_env_names`.
That import is runtime, not test-only, and it is the reason §5.5's re-export list is a hard
requirement rather than a courtesy to tests.
