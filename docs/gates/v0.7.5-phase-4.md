# Gate 4 — v0.7.5 the operator-feedback acquisition path

**Status: passed — with an explicit statement of what "passed" does not mean here.**

> ## Read this before reading the rest
>
> **The automated suite does not prove the behavioural claims of this release.** Three of the four
> intentional behaviour changes v0.7.5 ships are browser behaviour, and there is no JavaScript
> runtime in this repository to observe them with. The tests below assert the **shape of the
> source**. The behaviour is proved by `docs/gates/v0.7.5-manual-verification.md`, executed by a
> human — **and this build did not execute it.**
>
> §5 of this document lists exactly which claims rest on the manual protocol. That list is the most
> important thing in this gate.

---

## 1. The three changes, one commit each

| § | Commit | Change | `app.js` |
|---|---|---|---|
| 5.1 | `16e2aba` | reconcile instead of clear-and-rebuild | +18 / −3 |
| 5.2 | `1006e0f` | build into a fragment, swap atomically | +12 / −2 |
| 5.3 | `6b33f7e` | the held card says it is stale | +25 / −1 |

**One file changed.** `index.html` and `style.css` are untouched; the marker reuses the existing
`.badge.redacted` rule, which already carries warn colours and `cursor: help`. The UI is still four
files, there is no build step, and no dependency was added.

### 5.1 — the held card

`clear(sits)` was the first statement of `renderSituations` and destroyed every card every two
seconds, expanded ones included, along with the feedback buttons whose `onclick` closures
`renderDetail` had created. Detail nodes of currently-expanded cards are now harvested **before**
the clear and re-appended — `clear` detaches nodes rather than destroying them, so the node keeps
its identity and its listeners. `data-sid` on the card is how the next render finds it again.

Collapsed cards are still cleared and rebuilt: they are cheap and carry no click target the operator
is aiming at. This is the narrow version the draft prefers; a general reconciler is out of scope
(SCOPE §3.3). Collapsing resumes normal rebuilding with **no extra code**, because `expanded`
already governs the harvest.

The un-awaited `renderDetail(detail, s.id)` in the rebuild path is now guarded by
`!held.has(s.id)`: a held card already has its content, and refetching it is precisely the rebuild
§5.1 exists to stop.

### 5.2 — the atomic swap

`clear(container)` ran after the `await` resolved but before any content was appended, while the
container had already been set to `display: block`. The content is now assembled in a
`DocumentFragment` and swapped with `clear(container); container.append(frag)` **back to back with
no await between them**. Five `container.append(` calls became `frag.append(`.

`renderEntityDetail` has the same `clear`-then-fill shape on the entities panel. It is **deliberately
untouched** — a fix smuggled into this diff is invisible to review, which is the whole reason the
diff is small (directive 6). Recorded in §6 below as a ROADMAP candidate, not fixed.

### 5.3 — the staleness marker

A `held while open` badge in the header of any expanded card, explanation in the `title`. Emitted
only under `expanded.has(s.id)`, and **removed on collapse** rather than at the next render — a
collapsed card carrying "held while open" would assert something false for up to two seconds.

It appears on the first update actually being withheld rather than at the instant of expansion. That
is correct rather than a lag: a card just opened is not yet stale.

## 2. §5.4(a) — the structural assertions, and their honesty

Six added to `tests/test_security_ui.py`. **Each carries, in the test itself, a sentence saying it
asserts the shape of the source and not the behaviour of the browser, and naming the manual test
that does prove the claim.** The block they sit in opens with a comment saying the same thing about
all of them.

| `test_render_situations_does_not_clear_the_list_unconditionally_first` | `clear(sits)` is not among the first statements; the harvest precedes it | that the node survives, that its listeners are intact, or that a click lands on it → **Test A** |
| `test_render_situations_does_not_refetch_a_held_card` | the rebuild-path call either awaits or is guarded by `!held.has(s.id)` | that no refetch occurs at runtime → **Test A** |

### 2.1 One thing the first draft of these tests got wrong, recorded

`test_render_detail_never_clears_before_its_fetch` failed on the *fixed* tree at first — because the
comment explaining the fix contains the string `clear(container)`, and a positional test scanning
raw source found the **prose about the code** before the code.

The tempting repair was to water down the comment. Instead `_code_only()` strips whole-line `//`
comments before any positional assertion, and its docstring records that this is the same failure
the documentation guard had in v0.7.4 — text *about* a thing matched as though it were the thing
(DECISIONS #100). Assert over code; comment freely.

## 3. §5.4(c) — the contract tests, unedited

This is the strongest thing that **can** be proved automatically here, which is why it is listed as
evidence rather than as a formality: it is what shows the release touched the acquisition path and
nothing else.

**A correction to the build prompt, recorded because it affects what this row means.** §5.4(c) says
"every SSE test in `tests/test_events.py`". `tests/test_events.py` does not contain SSE tests — it
tests trap-event parsing (fingerprints, varbind carriage, field validation). The real SSE tests are
`test_f30_sse_*` in `tests/test_governance.py`, plus the `_first_sse_update` helper in
`tests/test_declaration.py`. Both files pass unedited, so the requirement is met either way, but
citing `test_events.py` as the SSE evidence would have been citing a file that proves something else.

## 4. `POST /api/situations/{sid}/feedback` is unchanged

No new route, capability, audit action, migration, dependency or served path. The contract is still
`{verdict}`. No version field, no precondition, no 409 — the membership fingerprint is v0.8.0's and
`FEEDBACK-PATH-0.7.5-DRAFT.md` §3.4 records why rejection-on-mismatch is the wrong primitive for an
*observation*.

## 5. **What this gate does NOT establish**

Stated plainly, because the build prompt requires it and because a reader who skims a green gate
will otherwise assume the opposite.

| Claim | Established by the suite? | Actually established by |
|---|---|---|
| An expanded card's DOM node survives an SSE update | **No** | manual **Test A** |
| The feedback buttons keep working across updates | **No** | manual **Test A** / **Test D** |
| No reachable state has the detail container displayed and empty | **No** | manual **Test B** (needs network throttling) |
| The marker is visible while held and gone once collapsed | **No** | manual **Test C** |
| A click lands on the card the operator was reading | **No** | manual **Test D** |
| The operator *notices* the marker | **No, and no test can** | human-factors residual, `SECURITY-REVIEW-0.7.5.md` |
| The source has the shape those behaviours require | **Yes** | §2 |
| The API contract and SSE behaviour did not change | **Yes** | §3 |
| The UI is still four files, CSP unchanged, no `innerHTML` | **Yes** | §3 |

**`docs/gates/v0.7.5-manual-verification.md` was written by this build and NOT executed by it.**
There was no browser and no operator. Its §9 says so in the document itself, so a maintainer opening
it later cannot mistake it for a completed record. It is written to be run by someone who did not
build this: 20 minutes, exact commands, explicit PASS/FAIL criteria, a sign-off block, and a
checkpoint that stops the protocol if the SSE stream is not actually live — because every test after
that point would otherwise pass for the wrong reason.
