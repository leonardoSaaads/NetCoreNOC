Both `make eval` modes were hashed on the untouched v0.5.0 tree at Gate 0 and re-hashed after the
extraction and again after every subsequent step:

| `eval/harness.py --json` (learning) | `c873d525…d1cd` | `c873d525…d1cd` | **identical** |
| `eval/harness.py --json --cold` (parity) | `811b4c54…2754` | `811b4c54…2754` | **identical** |

Full hashes: learning `c873d525abd1e8c20a839d37e1c1bc1813f26bbe9ba4bed3e4a3783d5fd6d1bd`,
cold `811b4c54231c2b9621f1d58a4020a0b6f02023b1b3a1e95e475ab8d1bbc82754`.

`make eval` exits 0 with "no gated regressions", and
`tests/test_eval.py::test_cold_mode_reproduces_the_v020_baseline` still compares per-scenario
dicts with `==` against the frozen v0.2.0 baseline.

**Why parity held, mechanically.** `AdditiveScorer.score` computes the same three products and
sums them left-to-right in the same order the inlined expression did; float addition is not
associative, so the *order* was the thing that had to be preserved. The inputs are the same
`learner.class_affinity` / `learner.entity_affinity` calls with the same arguments, the reserved
`LinkFeatures` slots are `None` and unread, and acceptance is still the strict `score > threshold`
on the same float. A property test
(`test_default_scorer_reproduces_the_v050_expression`) asserts equality with `==`, not a
tolerance — a tolerance would hide exactly the class of error this gate exists to catch.

## Two implementation decisions taken during the phase

Both were forced by evidence, and both made the design better rather than merely passing:

1. **A configuration reload must be a no-op when nothing changed.** The first cut re-instantiated
   the scorer on every maintenance pass. That silently *un-degraded* a scorer that had already
   proven it fails — every 5 s, forever. `Engine.load_scorer_config` now compares
   `(config_id, params_hash)` and returns early when unchanged, so a fail-safe degradation is
   genuinely sticky, and the `scorer.fallback` audit row is written *before* the reload so a
   fallback can never be lost to the swap an admin's fix would cause.
2. **`create_situation` omits the provenance column when there is nothing to write.** With
   `scorer_config_id is None` — the fail-safe state — the INSERT does not name the column at all.
   That is not tidiness: it is what lets the *same* engine code run against a schema that predates
   migration `0005`, which is how `test_upgrade.py` proves the migration changes no grouping by
   replaying one fixture on both sides of it.

## `scoring.py` stays small (hard constraint 7)

| File | Total lines | Docstring | Comment | Blank | **Code** |
|---|---|---|---|---|---|
| `scoring.py` | 387 | 92 | 23 | 68 | **204** |
| `preview.py` | 155 | 33 | 4 | 29 | **89** |
| `correlate.py` | 234 | 50 | 9 | 39 | **136** |

The read-only preview machinery was moved to its own module specifically to honour the
"`scoring.py` stays under ~300 lines" constraint: `scoring.py` is now the contract, the default
scorer, the validator, and the fail-safe wrapper — nothing else. There is no plugin framework, no
dynamic loading, no registry, and no external call anywhere in either file.
