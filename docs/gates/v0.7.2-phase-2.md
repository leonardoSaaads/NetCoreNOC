## 1. What was added

### 1.1 The module-size guard

`MAX_MODULE_LINES = 400`, with `DEBT_ALLOWLIST` measured against the current tree:

| Module | Lines | Owner |
|---|---:|---|
| `api.py` | 1 752 | v0.7.2 — the subject of this release; becomes the `api/` package |
| `store.py` | 1 512 | v0.7.3 — split by domain along its own section comments |
| `main.py` | 1 079 | v0.7.3 — the maintenance loop, gap tracker and process runner leave `Engine` |
| `shaping.py` | 476 | v0.7.4 — two axes in one file: field shaping and NE scoping |
| `varbind_profile.py` | 417 | v0.7.4 — one extraction (the accumulator), not a package |

Five assertions, and each one closes a way the guard could rot:

| Test | Closes |
|---|---|
| `test_modules_discovered` | a glob that matched nothing would make every other assertion vacuous |
| `test_no_module_exceeds_the_size_guard` | a new module over 400 lines |
| `test_allowlisted_modules_have_not_grown` | debt compounding — the recorded count is a **ceiling**, so an allowlisted module cannot absorb new code because it is already exempt |
| `test_allowlist_only_shrinks` | **stale exemptions**: a module that drops to or below the limit must be deleted from the list, so it can never silently exempt a future regrowth |
| `test_allowlist_names_only_real_modules` | a dead entry left behind by a rename or deletion |

`test_the_package_is_at_most_one_level_deep` enforces `MODULE-ARCHITECTURE.md` §9 — one level of
nesting, where earned, never two. It passes trivially today (the package is flat) and is the reason
the v0.7.2 `api/` package cannot grow a `routes/` subdirectory later.

### 1.2 The route-order parity baseline

`ROUTE_ORDER_BASELINE` — the 48-entry ordered `(method, path)` list recorded in
`docs/gates/v0.7.2-phase-0.md` §5.1 — plus three tests:

* `test_route_table_order_is_unchanged` — the built app's route table equals the baseline,
  **in order**. FastAPI resolves the first matching route, so `/api/situations` before
  `/api/situations/{sid}`, and `/api/scorer/preview` and `/api/scorer/rollback` before the bare
  `POST /api/scorer`, are *behaviour*. This is the test that makes "we only moved code between
  files" mean something, and it is why the split calls its nine `register()` functions in
  registration order rather than alphabetically.
* `test_route_order_baseline_has_no_duplicates` — a duplicated `(method, path)` would let the
  comparison above pass while shadowing a handler the router never reaches.
* `test_every_baseline_route_is_uniquely_named` (48 parametrised cases) — the baseline itself is
  well-formed.

The baseline is inlined in the test rather than loaded from a data file: it is 48 lines, a reviewer
should be able to read the expectation next to the assertion, and a fixture would be one more thing
that can drift.

## 3. Why both guards had to come first

The module-size guard installed *after* the split would be a rule written to describe what the
author happened to produce. Installed before, it is a rule the author then had to satisfy — and
`api.py` sits on its allowlist at 1 752 lines with `v0.7.2` named as its owner, so the release
carries an explicit, machine-checked obligation to remove that entry before it ends.

The route-order test installed *after* the split would compare the new tree against itself. Taken
now, against the tree the v0.7.1 security review was written about, it is the only thing that can
detect a reordering introduced during the move — and a reordering is the one class of behaviour
change that no handler-level hash could ever reveal.
