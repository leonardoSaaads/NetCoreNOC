# v0.12.0 — Gate 0

**The fence. No v0.12.0 code exists until this gate closes.**

This release's whole premise is a measurement: *`src/netcorenoc/ui/app.js` is 52 738 bytes and no
test executes it.* A premise of that size is not something to assert from a `grep`. §2 reproduces it
**by execution, with controls**, and §3 reproduces the second premise — that nothing in the suite
notices a build step appearing — the same way.

Two probes below are of the shape Appendix B warns about ("measuring nothing and concluding
CLOSED"), so each carries a control that had to behave differently. A probe whose negative result
could equally mean *the probe does not work* is not evidence.

## 1. The instruments that exist today, quoted

### 1.1 The four text-level UI assertions

From `tests/test_security_ui.py::test_ui_source_has_no_f1_antipatterns`, verbatim:

```python
assert ".innerHTML" not in app_js
assert "localStorage" not in app_js and "localStorage" not in index
assert "function esc(" in app_js and "createTextNode" in app_js
```

and, from `test_static_assets_served_with_correct_types`:

```python
assert "createTextNode" in js.text and "textContent" in js.text  # safe DOM building
```

These are good supply-chain tests. **Every one of them is `read_text()` plus substring matching**,
and none observes behaviour. The file's own v0.7.5 comment block already says so, in terms this gate
does not need to improve on:

> *"Every assertion below inspects the **shape of the source**. None of them observes the
> **behaviour of the browser**, because there is no JavaScript runtime anywhere in this repository
> — no node, no npm, no jsdom, no browser automation … So these tests CANNOT establish the three
> claims this release actually makes."*

### 1.2 The capability map is validated by splitting source text

```python
def _tab_caps() -> dict[str, str]:
    app_js = (UI_DIR / "app.js").read_text()
    block = app_js.split("const TABS", 1)[1].split("];", 1)[0]
    return dict(re.findall(r'id:\s*"(\w+)".*?cap:\s*"([\w.]+)"', block))
```

`TABS` is the panel/capability map — **the only client-side defence against an admin panel rendering
for a viewer**. Two tests consume this function, and both are downstream of a literal `"const TABS"`
and a regex over the text between it and the next `];`.

The failure mode is not hypothetical and not subtle: a rewrite that changes the *shape* of the map
— an array of objects becoming a `Map`, or each panel declaring its own requirement — makes
`re.findall` match nothing. `test_every_tab_is_gated_on_a_real_capability` carries `assert caps`,
which would catch an empty parse; `test_admin_panels_are_gated_to_admin` does **not**, and would
report every admin panel correctly gated against a map it had failed to read.

## 2. Fact A — no test executes `app.js`

### 2.1 Probe A: instrument the file so that execution would be observable

`app.js` was prefixed with one line that records its own evaluation to a file, then the **full**
suite was run.

```diff
--- a/src/netcorenoc/ui/app.js
+++ b/src/netcorenoc/ui/app.js
@@ -1 +1,2 @@
+try { require("node:fs").appendFileSync(process.env.NETCORENOC_APPJS_PROBE, "app.js executed\n"); } catch (e) { /* no fs: a browser */ }
 "use strict";
```

```
$ .venv/bin/python -m pytest -q --no-header -p no:cacheprovider
1302 passed in 214.24s (0:03:34)

$ test -f "$NETCORENOC_APPJS_PROBE" && echo PRESENT || echo ABSENT
ABSENT
```

**Zero executions.** Note the second observation in that transcript, which is evidence of its own:
the instrumented file passed **all 1302 tests**. Not one of them noticed a line of foreign
JavaScript at the top of the shipped UI.

### 2.2 The control — the instrument works

A negative result from a probe with no control is worthless. The **same instrumented file** was
handed to a JavaScript runtime:

```
$ node -e 'try { require("/home/user/NetCoreNOC/src/netcorenoc/ui/app.js"); } catch (e) { … }'
app.js threw after the probe fired: ReferenceError: document is not defined
$ cat "$NETCORENOC_APPJS_PROBE"
app.js executed
```

The marker appears. The probe fires when something executes the file, and did not fire during the
suite. §2.1's ABSENT is therefore a fact about the suite, not about the probe.

(The `ReferenceError` is itself informative: `app.js` binds DOM elements at module scope, so any
harness must supply a document *before* evaluation, not after.)

### 2.3 Probe C: a defect no executing test could survive

Stronger than a marker, because it needs no instrument to be trusted. `app.js` was given a leading
line that no JavaScript engine can parse:

```diff
--- a/src/netcorenoc/ui/app.js
+++ b/src/netcorenoc/ui/app.js
@@ -1 +1,2 @@
+function ( { { syntax error not valid javascript ===;
 "use strict";
```

```
$ node --check src/netcorenoc/ui/app.js
/home/user/NetCoreNOC/src/netcorenoc/ui/app.js:1
function ( { { syntax error not valid javascript ===;
^^^^^^^^

$ .venv/bin/python -m pytest -q --no-header -p no:cacheprovider
1302 passed in 211.34s (0:03:31)
```

**1302 passed against an `app.js` that no JavaScript engine can parse.** This is the release's
premise, reproduced. Any test that executed the file would have failed on it; none did.

## 3. Fact B — nothing guards against a build step

The full apparatus was added to the **tracked** tree: a `package.json` with a `vite build` script,
three lockfiles (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`), a `vite.config.js` writing its
output into `src/netcorenoc/ui/dist`, and a tracked `node_modules/`.

```
$ git ls-files | grep -E "package|lock|vite|node_modules"
node_modules/vite/index.js
package-lock.json
package.json
pnpm-lock.yaml
vite.config.js
yarn.lock

$ .venv/bin/python -m pytest -q --no-header -p no:cacheprovider
1302 passed in 217.79s (0:03:37)
```

**1302 passed** with a bundler, three lockfiles and a vendored `node_modules` committed.

**The control, and the precise shape of the gap.** One existing test is adjacent —
`test_security_ui.py::test_the_ui_is_still_one_file_changed_and_no_build_step_appeared`:

```python
assert not list(UI_DIR.rglob("package*.json"))
assert not list(UI_DIR.rglob("node_modules"))
```

It is scoped to `UI_DIR`. A `package.json` **inside `src/netcorenoc/ui/`** would be caught; one at
the repository root is not, and the root is where every package manager actually puts it. Likewise
`test_ui_stays_four_files` would have caught the `dist/` directory had it been created — which is
why the probe above put the bundler output there and the suite *still* passed: `vite.config.js`
merely *names* that directory, and no build was run.

So the gap is not "no guard exists near the UI". It is that **the guard is scoped to the one
directory a build step would not live in**, and the tracked tree as a whole is unguarded. That is
`SECURITY-REVIEW-0.11.0.md` §3.4's class, and Workstream 2 closes it — deriving the file list from
`git ls-files` rather than from a directory walk, because a walk with literal skips is F51 in the
mirror.

The probe was reverted; `git status --porcelain` is empty.

## 4. The prerequisite this release satisfies, quoted

ADR #163 (v0.11.0) refused a promotion UI and named the condition for reopening it:

> **What would make the UI safe to build, stated so it is a prerequisite and not a vague
> intention**: a test that executes `ui/app.js` **in a real DOM**.

ADR #99 (v0.7.5) chose source inspection plus a manual protocol, and recorded where that decision
should be revisited:

> **Consequence**: `docs/ROADMAP.md` records that the planned UI rebuild is the point at which
> testability should be a **design input** — the honest place to reopen this, and not before.

`SECURITY-REVIEW-0.11.0.md` §4 carries it as open question 6. **This is that point.** ADR #167
supersedes #99 on the narrow question of whether a JavaScript runtime may exist in the test tree,
and records what changed: not the constitution, but the release in front of it.

## 5. Coverage, reported rather than reconciled

```
$ make coverage
Required test coverage of 85.0% reached. Total coverage: 96.02%
1302 passed
```

ADR #159 records the band as **96.10–96.21 %**, from two `@given(st.binary(...))` properties in
`tests/test_receiver.py` that run without `derandomize` and drift ±0.11 points. The measured figure
here is **96.02 %**, which is 0.08 below the bottom of that band.

Three things this gate does **not** do about it: derandomise the properties (ADR #159 records why
not), widen the band to make the number fit, or quote the band instead of the measurement. The
figure is recorded as measured, on the shipped v0.11.0 tree, before this release changed anything —
so that the same measurement after the release is comparable to something real. Phase 6 reports the
post-release figure against this baseline and against ADR #159's band, and says which it missed.
