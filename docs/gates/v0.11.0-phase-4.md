# v0.11.0 — Gate 4: fold materialisation

`evaluation_folds.py` writes `(run_id, incident_id, repeat, fold)` when an evaluation runs, so a
promotion's citation points at **immutable rows** rather than at a recomputation.

Ratified plan `e011ee6ad2367d44f2ede14cad7b072df598298f91ecc1a405744358b589d449`.

---

## 1. Why, in one measurement rather than one worry

`DATA-LINEAGE.md` §4, unchanged:

* fold assignment is a **pure function of the incident ids**;
* incident identity is `incidents.resolve_all` over the merge edges;
* **the merge edges change when situations merge**;
* and **no snapshot of the merge graph is retained anywhere** — `situation.merged_into` holds the
  *current* state, there is no history table, no `merged_at`, and no audit event for the edge.

So a bag labelled today belongs to incident *I*; tomorrow its situation is merged and it belongs to
*J*; `assign_folds` over a different id set produces a different rotation; **the bag moves to a
different fold**, and every fold-level number moves with it.

Until this release nothing decided, so nothing broke. **From this release an admin approves a swap
citing an evaluation**, and a citation to a number nobody can reproduce is not evidence.

---

## 2. The four properties, and the one that matters

| Gate 4 requirement | Test | State |
|---|---|---|
| an evaluation writes its fold assignment | `test_an_evaluation_writes_its_fold_assignment` | **met** — and it equals what `assign_folds` gives, so the stored copy is not a second implementation |
| the rows are immutable | `test_a_stored_fold_assignment_cannot_be_edited_or_deleted` | **met** — `UPDATE` and `DELETE` both abort, **with the insert asserted first** |
| a promotion can cite them | `test_the_promotion_row_can_cite_the_stored_assignment` | **met** — `evaluation_run_id` resolves to rows |
| **re-running against a changed merge graph produces different folds while the stored ones are unchanged** | `test_a_changed_merge_graph_moves_the_recomputed_folds_and_not_the_stored` | **met** |

**The fourth is the only one that would have gone red before this phase, and it is the one that says
whether the release bought anything.**

### 2.1 The fixture builds a merge edge on purpose, and that is the point

**Appendix B's last trap applies directly here.** v0.10.1's byte-frozen reports *could not have*
verified the incident-identity consolidation, **because neither corpus contains a single merge
edge** — a green gate that no input could have turned red.

A drift test run on either corpus would be a drift test **on data that cannot drift**. So this
fixture does not use either. Six situations, none merged, are six incidents; merging 6 into 1 makes
them five; `assign_folds` is a rotation over the **sorted** ids, so removing one shifts every id
after it and the recomputation moves for real rather than by a single entry.

The test asserts **both halves explicitly**, and the first assertion is the one that keeps the
second honest:

```
assert recomputed != stored_at_write   # else this fixture cannot demonstrate the hazard at all
assert stored_now  == stored_at_write  # the defect this table exists to prevent
```

### 2.2 Idempotence, and why the run id has no clock in it

`run_id_for` is `sha256(params_hash + sorted incident ids)`. Two runs over the same corpus with the
same model produce the same id, so re-evaluating is a no-op rather than a second row — and **a
promotion that cites a run id still finds the run it cited.** A run id containing a timestamp would
make an evaluation impossible to recognise as the one already stored.

A second write for the same `(run_id, incident_id, repeat)` fails on the `PRIMARY KEY` rather than
replacing an assignment a promotion may already cite.

## 3. What this buys, and what it does not — stated here, not discovered later

**It buys**: the *stored* assignment stops moving, so a citation resolves to the same numbers a year
later.

**It does not buy**:

* **it does not reproduce the merge graph**, so it cannot explain *why* an incident moved;
* **it does not make the seal's own membership reproducible** — `holdout_seal_member.incident_id`
  was written once from the incident map as it stood, and if identity drifts, the sealed set and the
  estimator's exclusions are computed from **two different maps taken at two different times**.
  That is `DATA-LINEAGE.md` §4's second-order hazard and it is **still open**.

**The deferral, recorded.** Snapshotting the merge edges would fix all three. `DATA-LINEAGE.md` §5
names its cost — *a second copy of a live table, with the drift risk that implies* — and **this
release deliberately does not choose it**. It is a ROADMAP line for v0.12.0, and the security
review's critical analysis returns to whether this phase made an evaluation *reproducible* or merely
*citable*.

**Measured on the real corpus**: the refusal in Gate 5 cites `115a9f5ca974f00278ee69fd9ce5112e`,
which resolves to **111 rows** — 37 merge-aware incidents × 3 repetitions.
