## 8. Coverage, against the band and against the baseline

**Three runs of `make coverage` on the *same* v0.12.0 tree gave three different answers.**

| Measurement | Figure |
|---|---|
| v0.11.0 baseline (Phase 0 §5) | **96.02 %** |
| v0.12.0, first run | **96.13 %** |
| v0.12.0, second run | **96.02 %** |
| v0.12.0, third run | **96.05 %** |
| ADR #159's documented band | 96.10 – 96.21 % |

**An earlier draft of this section quoted only the first run and said the figure was "inside the
band". That was a claim resting on one sample, and the second run falsified it; the third confirmed
the falsification rather than rescuing the claim.** The correction is
recorded here rather than made quietly, because the whole point of ADR #159 is that this number is a
band and not a value — and quoting the run that happened to land inside it is exactly the failure
the band exists to prevent.

What the three observations actually show:

* **The spread is 0.11 points**, which is precisely the drift magnitude ADR #159 attributes to the
  two `@given(st.binary(...))` properties in `tests/test_receiver.py` that run without
  `derandomize`. The mechanism is confirmed rather than assumed.
* **The observed range straddles the band's lower edge.** One run of three is inside
  96.10 – 96.21 %; two are below it, by 0.08 and 0.05. So the honest statement is *not* "coverage is
  inside the band" — it is **"coverage on this tree is 96.02 – 96.13 %, and the documented band's
  lower bound sits inside that range."** Reporting the single run that landed inside would have been
  the same error as recomputing a percentage the tool already printed (ADR #159's own subject).
* **Nothing here is attributable to this release.** The v0.11.0 baseline was also 96.02 %. A
  0.11-point move that reproduces the known drift is not evidence of anything the new tests did,
  even though there is a plausible real contribution (`uifixtures` drives the real engine, API and
  label route to build its captures).

Three things deliberately not done: derandomising the properties (ADR #159 records why not),
widening the band so the measurements fit, or quoting the band in place of the measurement.

**A ROADMAP line follows from this**, and it is new: **three of four observations across two trees
now fall below ADR #159's lower bound of 96.10 %** (96.02 % on v0.11.0; 96.13 %, 96.02 % and 96.05 %
on v0.12.0). Either the band is slightly misplaced or the drift is not symmetric about it.
Re-deriving it needs a designed sample rather than the four runs this release happened to make, and
guessing from four would repeat the mistake this section is correcting.
