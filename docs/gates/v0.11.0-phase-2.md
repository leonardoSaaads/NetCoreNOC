**The final-hash assertion is the one worth naming.** `audit chain: ok` would pass on a chain that
was recomputed during the migration. The *final hash being the same value* is what says no chained
row was touched at all.

**`holdout_access` has no pre-existing rows on any real upgrade**, measured rather than assumed: no
code path in v0.10.x writes it. `seal.ratify` and `seal.spend` have no call site in `src/` (Gate 0
§3, by `ast`), and `seal.construct` does not log. So the unchained prefix the migration's design
allows for is, in practice, always empty.

## 2. The `scorer_active` `CHECK`, proven by attempted violation

The pointer table is **rebuilt** — `config_id` has to become nullable and SQLite cannot drop a
`NOT NULL` or add a `CHECK` in place. This is the migration's riskiest step: a rebuild that lost the
pointer would leave every upgraded appliance loading the coded defaults, **silently**. §1 compares
the row field by field rather than counting it.

```
== the scorer_active CHECK, proven by attempted violation ==
  [REFUSED] BOTH pointers set at once
              IntegrityError: CHECK constraint failed: (config_id IS NOT NULL) + (model_version_id IS NOT NULL) = 1
  [REFUSED] NEITHER pointer set
              IntegrityError: CHECK constraint failed: (config_id IS NOT NULL) + (model_version_id IS NOT NULL) = 1

  THE CONTROL: a legitimate move to the model pointer must be ACCEPTED
  [ACCEPTED] exactly one pointer set (model_version_id)
```

**The control is not decoration, and it caught a defect — in the probe.** The first run reported

```
  [REFUSED] IntegrityError: FOREIGN KEY constraint failed  <-- the CHECK refuses everything
```

which read as *"the `CHECK` rejects every value, so the pointer is unmovable"* — a far worse defect
than the one being guarded against. It was not the `CHECK`: the probe rolled back after each refused
`UPDATE`, and the rollback discarded the `model_version` row the control then referenced. A probe
that only checked *bad input fails* would have passed and reported a wall as a constraint.

Both refusals and the control are now in the suite as
`tests/test_upgrade.py::test_the_active_pointer_admits_exactly_one_of_the_two`, **with the control
first**, so the "refuses everything" failure mode cannot pass.

## 4. The intentional behaviour change in this phase, declared and counted

**One**, and it is a test edit rather than a runtime change:

| # | Change | Why it is not a defect |
|---|---|---|
| 1 | four assertions in `tests/test_upgrade.py` move from `latest_schema_version() == 12` to `== 13` | They pin **the current schema head**, which is the thing this phase moves. Leaving them at 12 would mean the migration had not been added. |

Two tests are **added** (not changed): the `0013` upgrade test and the pointer-exclusivity test.
No runtime module is touched in this phase at all.
