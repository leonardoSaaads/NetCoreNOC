## 2. The parity proof

```
baseline methods : 109
post-split       : 109
missing          : NONE
added            : NONE
HASH MISMATCHES  : NONE

PARITY: ALL 109 METHOD BODIES IDENTICAL
```

The comparison is taken through `inspect.getsource` on the **live attribute resolved via
`Store.__mro__`**, not by re-reading the files. That matters: a file-level check would prove the
text exists somewhere, while this proves the text Python actually resolves for `Store.<method>` is
byte-for-byte what v0.7.2 resolved. A mixin split that placed a method correctly but shadowed it
would pass the former and fail this.

The mechanism is what made it possible: methods were **sliced by line range and pasted**, never
retyped. The enclosing class header is the only edit.

## 4. Two changes that are not method bodies

Directive 5 permits only the class-header edit inside moved code. Two things moved that are not
methods, and both are recorded here rather than left to be found.

### 4.1 `MIGRATIONS_DIR` gains one `.parent`

`store.py` computed `Path(__file__).parent / "migrations"`. The file moved one level down, so
`types.py` computes `Path(__file__).parent.parent / "migrations"`. Verified equal, not assumed:

```
MIGRATIONS_DIR resolved : /home/user/NetCoreNOC/src/netcorenoc/migrations
pre-split value         : /home/user/NetCoreNOC/src/netcorenoc/migrations
IDENTICAL               : True
migrations visible      : 7
```

It is a module-level constant, not a method, so the 109-method hash table is unaffected.

### 4.2 Three module-attribute patch targets in `tests/`

Predicted in Gate 0 §5.3 and applied as predicted. A module-level constant is read through the
`__globals__` of the module where the reading *function* was defined, so when that function moves,
patching the name on the old module object stops reaching it. **No re-export can fix this** — a
re-exported name is a second binding, not an alias.

| Site | Was | Now |
|---|---|---|
| `test_upgrade.py` ×3 | `import netcorenoc.store as store_mod` | `import netcorenoc.store.lifecycle as store_mod` |
| `test_governance.py:1450` | `"netcorenoc.store.MAX_SCOPE_PARAMS"` | `"netcorenoc.store.read_models.MAX_SCOPE_PARAMS"` |

Both are import paths naming a moved symbol, which §9.2 permits explicitly. **No assertion changed.**

`lifecycle.py` names `MIGRATIONS_DIR` in `__all__`, so the seam is supported rather than accidental
— and `mypy --strict`'s no-implicit-reexport rule requires it.

### 4.3 The coverage gate caught a test going vacuous

Worth recording on its own, because it is the clearest evidence in this release that the gates are
load-bearing rather than ceremonial.

After the first step, coverage fell **95.69 % → 95.52 %** and `make qa` was still green — 676
passed. The lost lines were the over-`MAX_SCOPE_PARAMS` branches of `list_situations` and
`timeline_marks`. Cause: `test_governance.py`'s F38 test patched
`netcorenoc.store.MAX_SCOPE_PARAMS`, which after the move no longer reached the code that reads it,
so the fallback branch was never entered.

**The test still passed.** It compares the bound path against the fallback path and asserts they
agree; with the patch inert, both runs took the same branch and the equality held trivially. A test
whose whole purpose is comparing two code paths was silently comparing one path with itself, and
nothing but the coverage number said so. Fixed by repointing the patch; both branches confirmed
exercised again.

This is exactly why "coverage may not drop" is a gate and not a nicety.
