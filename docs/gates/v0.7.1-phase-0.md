**The conclusion that defines the release.** Of the 19 non-`GET` routes in `ROUTE_PERMISSIONS`,

```

POST /api/situations/{sid}/close       -> situation.close (editor)   ← NE-bearing, unscoped
```

scope rather than to being forgotten.

→ 0) and **1 time** in `main.py` (line 405, the engine batch path). That asymmetry is F39.

## 3. Every input `shaping.visible_nes()` reads, and who can write it

The F35 analysis, done from the code. `visible_nes(role, principal_ref, policy, nes)` is called
from exactly one place — `api.py::create_app.scope_for()` — and reads four inputs.

| Input | Where it comes from | Lowest role that can write it | Verdict |
|---|---|---|---|
| `role` | `auth.Principal.role`, from the `user` / `api_token` row | **admin** (`users.manage`, `tokens.manage`) | safe |
| `principal_ref` | `auth.Principal.ref` (`user:<id>` / `token:<id>`) | **admin** (identity creation) | safe |
| `policy` | `governance.scope`, the active `scope` governance policy | **admin** (`scope.write`, no delegation) | safe |
| `nes[].id` | `ne.id`, assigned by the engine on first trap from an address | not writable through any API route | safe |
| `nes[].ip` | `ne.ip`, the trap source address | not writable through any API route; settable only by a party with **network position** to send a trap | out of scope — pre-existing, threat-model network attacker, not an authenticated-role escalation |
| `nes[].label` | `label.label` where `kind='device'`, joined `ne.ip = device.ip` | **editor** (`label.write`, `POST /api/labels`) | **DEFECT — F35** |

`store.list_ne_for_scope()` (store.py:1090) is the query that supplies `nes`; its projection is
`SELECT n.id, n.ip, l.label`. The label reaches the authorization decision through two paths, and
**both** must be closed:

1. `shaping._matches()` (shaping.py:225–250) falls through to
   `fnmatch.fnmatchcase(label or ip or "", selector)` — a glob selector resolves against the
   **operator label** whenever the NE has one. An editor who writes a label matching an in-scope
   glob adds that NE to their own scope.
2. `shaping._mark_visible()` (shaping.py:388–392) tests `device in scope.ips or device in
   scope.labels`, where `device` is the rendered `COALESCE(label, ip)` display string from
   `store.timeline_marks()`. Labels are **not unique**, so an editor who copies an in-scope NE's
   label onto an out-of-scope NE leaks the latter's alarm timing and classes. This variant needs no
   glob in the policy at all.

`Scope.labels` (shaping.py:151) exists only to serve (2). Once the timeline filters on `ne_id`,
that field and the `label` column of `list_ne_for_scope()` are both dead, and the `vulture`
dead-code gate will say so.

## 5. The transaction model, as it is today

- `Store` holds **one** `aiosqlite` connection (`store.conn`) shared by the engine task and every
  API request, serialised by `store.lock` (an `asyncio.Lock`). There is no per-request connection
  and no nested transaction.
- `Store.commit()` (store.py:132) and `Store.rollback()` (store.py:135) both delegate straight to
  that one connection. A `commit()` from **any** caller commits **every** statement pending on it,
  whoever issued them.
- `main.py` calls `rollback()` on the engine batch path (main.py:405), with a docstring explaining
  that the audit chain only advances on commit so a rolled-back batch never breaks it.
- **`api.py` calls `rollback()` nowhere.** Every mutating handler is
  `async with store.lock: … mutate … audit_row(…) … await store.commit()`, with no `except` and no
  `finally`. A handler that raises between the mutation and the commit — `audit.write_event`
  failing, a `RETURNING` assertion, a serialization error — leaves the statement **pending on the
  shared connection**, and the next `commit()` from the engine's maintenance loop or from another
  request adopts it. The mutation lands, unaudited, committed by an unrelated caller. **F39.**
- `Engine.apply_feedback` (main.py:753–768) calls `await self.store.commit()` at line 767 — *inside*
  a handler (`api.py:866–885`) that then writes its audit row and commits again at line 882. That
  one route is two transactions, in the order mutation → commit → audit → commit, which is the
  reverse of every other write path in the file and means the mutation is durable before it is
  attributable.

The Phase-3 fix is one async context manager placed next to `audit_row` inside `create_app` —
acquire `store.lock`, run the body, commit on success, `rollback()` on any exception, re-raise —
and the internal commit removed from `Engine.apply_feedback` so the API owns the boundary.

### The learning path, for F36

`Engine.apply_feedback` → `learn.Matrix.learn_epoch` (learn.py:342) calls `self.A.tick()` **and**
`self.E.tick()` before reinforcing. `Matrix.tick()` (learn.py:68) advances `self.epoch`, and every
stored mass decays lazily by `(1-λ)^Δepoch` with `LAMBDA = 0.05` (learn.py:24). `store.add_feedback`
(store.py:489) checks only that the situation exists — no uniqueness, no dedupe, no bound — so N
identical posts drive N epochs. `split` additionally multiplies each pair mass by
`SPLIT_PENALTY = 0.5` (learn.py:29) through `penalize` → `scale_pair`, compounding.

`learn_epoch` has exactly **two** callers: `_close_situation` (main.py:709, one epoch per **closed
situation** — which is what the `learn.py` module docstring already declares an epoch to be) and
`apply_feedback` (main.py:764). Separating the tick from the reinforcement therefore touches the
feedback path only and leaves the close path byte-identical.

**The eval does not drive feedback.** `grep -rn 'apply_feedback\|add_feedback' eval/ tools/` returns
nothing; the only callers are `tests/test_scenarios.py` and `tests/test_store.py`. The F36 epoch
change therefore cannot move the eval baseline, and Gate 3 will prove it rather than assume it.
