# v0.7.5 — manual verification protocol for the operator-feedback acquisition path

**Read this first.** This protocol is **the actual proof** that v0.7.5's three UI changes work.
The automated test suite does **not** prove them, and the tests that look as though they might say
so in their own comments. This is not a formality to be signed off — it is the only place the
behavioural claims of this release are established.

**Why it is a document and not a test.** There is no JavaScript runtime anywhere in this
repository — no node, no npm, no jsdom, no browser automation, in `pyproject.toml`, the `Makefile`,
`flake.nix` or `.github/workflows/`. Every existing UI assertion is a source-inspection test that
reads `app.js` as text. Adding a JS harness to test three lines would be the largest dependency
decision this project has made since v0.2.0, taken inside a patch release; the reasoning is
DECISIONS #99 and it was deliberately not taken. So the behavioural claims are verified by a human,
here, and the release says so out loud rather than letting a green suite imply otherwise.

**Who can run this.** Anyone with Docker and a browser. It assumes no knowledge of the codebase.
Budget **20 minutes**.

**What is being checked** — the three changes, and the four things that must be true:

| # | Claim | Test |
|---|---|---|
| A | An expanded situation card is no longer destroyed by an SSE update | Test 3 |
| B | The detail container is never displayed empty | Test 4 |
| C | A held card carries a staleness marker, and loses it when collapsed | Test 5 |
| D | A feedback click lands on the card the operator was looking at | Test 6 |

---

## 0. Start the appliance

From a clean checkout of v0.7.5:

```
docker compose up --build
```

Wait for the log line containing the one-time bootstrap admin password and copy it. If port 162/udp
is unavailable on your host (common on Linux with systemd-resolved, and on macOS), edit
`docker-compose.yml` to map `"1162:1162/udp"` and add `NETCORENOC_TRAP_PORT=1162` to a `.env` file
first — the protocol works identically either way, and the replay commands below take `--port`.

Open `http://localhost:8080/` and sign in as `admin` with that password. Set a new password when
prompted. You should land on the **Situations** tab with the message
*"No situations match — the network is quiet."*

**Keep the browser devtools console open (F12) for the whole protocol.** A CSP violation or a
JavaScript error would invalidate every result below, and both are silent otherwise.

## 1. Generate a multi-alarm situation

In a second terminal, from the repository root:

```
python tools/trap_replay.py tests/fixtures/fiber_cut.json --port 162
```

(use `--port 1162` if you remapped). This fixture raises a correlated group across several devices —
the situation it produces has **at least four member alarms**, which is what makes the test
meaningful. Within about two seconds the Situations list shows a card such as `#1  open  6 alarms`.

**Checkpoint 1.** You have a situation card with **four or more alarms**. If you only see
singletons, replay the fixture again — correlation needs the alarms inside one temporal window. Do
not continue with a one-alarm situation; every test below depends on the card having content worth
reading.

## 2. Establish the baseline: the stream is live

Watch the card for ten seconds without touching it. The **age** field on the right of the header
(`3s`, `11s`, …) must tick upward. The connection dot in the header must be green/live.

**Checkpoint 2.** The age is advancing. This proves SSE updates are arriving every two seconds —
without which Tests 3 to 6 would pass vacuously, because nothing would be rebuilding the card.

> This checkpoint is the one people skip. If the stream is not live, **every remaining test passes
> for the wrong reason.** Do not proceed until the age is moving.

## 3. Test A — an expanded card survives an SSE update

1. Click the card's header to expand it. The detail panel opens: probable root, the alarm table,
   the link rows, and at the bottom the **✓ Confirm grouping** / **✗ Split (wrong grouping)**
   buttons.
2. Now **watch it for at least 20 seconds** — ten SSE cycles. Do not touch the mouse.

**PASS if:** the detail panel stays open and stable for the whole 20 seconds. The alarm table does
not blink, vanish, or reflow. The buttons stay where they are.

**FAIL if:** the panel collapses and reopens, flickers, goes blank and refills, or the buttons jump.
That is the v0.7.4 behaviour — the card being destroyed and rebuilt every two seconds — and it means
§5.1 did not take effect.

**What you are really checking:** in v0.7.4 the card was torn down and rebuilt on every update, so
the buttons you are aiming at were replaced roughly ten times during those 20 seconds.

## 4. Test B — the detail container is never displayed empty

This is the change that is hardest to see, because the window it closes was short. Force it open
with network throttling.

1. Collapse the card (click the header).
2. In devtools, open the **Network** tab and set throttling to **Slow 3G** (or a custom profile with
   ≥2 s latency).
3. Click the header to expand the card, and **watch the area immediately below the header** as it
   opens.

**PASS if:** the detail area shows **nothing at all** until the content appears complete, all at
once. There is no visible empty box.

**FAIL if:** an empty bordered/indented panel appears first and fills in afterwards — a visible gap
between the panel opening and its content arriving.

4. Set throttling back to **No throttling**.

**What you are really checking:** §5.2 builds the content into a `DocumentFragment` and swaps it in
one synchronous step after the network response resolves. In v0.7.4 the container was cleared
*before* the round trip, so under any latency it was displayed and empty — and a click in that
window hit nothing.

## 5. Test C — the held card says it is stale, and stops saying it when collapsed

1. Expand the card again (no throttling).
2. Look at the card's **header**, among the badges next to the status and alarm count.

**PASS if:** a badge reading **`held while open`** is present, styled like the existing "outside your
scope" badge (warn-coloured, `cursor: help` on hover). Hovering it shows a tooltip explaining that
the card is frozen while open, may not reflect the last few seconds, and that collapsing resumes
live updates.

3. It may take up to two seconds to appear after expanding — that is correct and deliberate. The
   card is not yet stale at the instant you open it; the marker appears with the first update that
   is being withheld.
4. Now **collapse** the card.

**PASS if:** the `held while open` badge disappears **immediately** on collapse — not after a delay.

**FAIL if:** the badge persists on a collapsed card (the header would be asserting something false),
or never appears at all on an expanded one.

**What you are really checking:** holding the card (Test A) fixes the race by freezing what the
operator sees, which trades a *wrong* label for a *stale* one. A stale label is only better if the
operator knows. Without this marker the release would replace a visible defect with an invisible
one.

## 6. Test D — the click lands on the card the operator was looking at

The label-integrity test. This is the one the release exists for.

1. Expand the card and read the alarm table. **Note the exact number of member alarms** — count the
   rows.
2. In the second terminal, add more alarms to the same situation while the card is open:

   ```
   python tools/trap_replay.py tests/fixtures/olt_storm.json --port 162
   ```

3. **Without collapsing the card**, watch for 10 seconds.

**PASS if:** the alarm table you are reading **does not change** — the same rows, the same count.
The header's alarm count and the `held while open` badge tell you the situation is moving underneath;
the detail you are judging does not.

4. Now click **✓ Confirm grouping**.

**PASS if:** the click registers — the panel refreshes and no error alert appears. Check the
**Audit** tab: a `feedback` action is recorded, with your username and the situation id.

**FAIL if:** the click does nothing at all, or an alert appears saying the feedback failed.

**What you are really checking:** in v0.7.4 the list was rebuilt underneath you, so the button you
pressed belonged to a render you never read — the verdict could be recorded against a membership you
never evaluated. That is a *silently wrong label*, and nothing downstream can detect one.

> **What this test does NOT establish, and it matters.** The verdict is recorded against the
> situation, which now has more members than the four (or six) you judged. v0.7.5 makes the click
> **deliberate**; it does **not** make the label **traceable to what was on screen**. Recovering
> *which* membership a verdict was about is the membership fingerprint, and that is v0.8.0
> (`FEEDBACK-DATASET-0.8-DRAFT.md` §2.2). Do not record this protocol as having verified label
> provenance. It has not.

## 7. Test E — nothing else moved

1. Click through every tab available to an admin: Timeline, Entities, Users, Tokens, Config,
   Scorer, Governance, Quarantine, Audit. Each must render as it did in v0.7.4.
2. Confirm the devtools **Console** is still clean — **no errors, and no CSP violations**, across
   the entire session.
3. Collapse and re-expand the situation card three or four times in quick succession. It must open
   and close cleanly each time, with fresh content on each expansion.

**PASS if:** all three hold. This release changed three places in one function pair; anything else
behaving differently is a defect in the work.

## 9. Status of this protocol in the v0.7.5 build

**Written but NOT executed by the build that produced it.** The build ran with no browser, no
Docker daemon check for this purpose, and no operator. It is recorded as unexecuted in
`docs/gates/v0.7.5-phase-4.md` and `docs/gates/v0.7.5-phase-6.md`, and in
`docs/releases/BUILD-REPORT-0.7.5.md`, rather than being implied to have passed.

That is the honest position and it is the point of DECISIONS #99: where a property cannot be
asserted automatically, say so in the test, say so in the gate, and specify the manual protocol —
never write a source-scanning test and let its green tick stand in for the assertion nobody made.
