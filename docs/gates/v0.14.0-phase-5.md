# v0.14.0 — Gate 5: the console

**Three scorer kinds, and a screen that was telling an operator something false about all of them.**

`UI-0.13-DRAFT.md` §8 planned this phase as a **placeholder** — a statement naming the release that
would enable tree ensembles and the reason they could not run yet. That statement was to be:

> *"Tree ensembles run out of process behind the worker harness, which is v0.14.0. Not a limitation
> of the model: a limitation of what may run inside this process."*

**It is false, and this release is why.** Tree ensembles run *inside* this process, in pure Python,
with no worker harness and no new dependency. ADR #183 supersedes the ROADMAP sentence that said
otherwise. So the placeholder is not rendered with corrected wording — there is nothing left to
place-hold, and the screen shows the model instead.

Then, building it, the phase found that the screen had a **different** false statement on it
already, and had had one since v0.11.0.

---

## 1. F60 — the console reported the coded defaults as "Active configuration"

`scorer_config` and `model_version` are mutually exclusive by a database CHECK: when a model version
is active there is no scorer configuration row at all. `routes_scorer._active_scorer()` handled that
by falling back:

```python
active = engine.correlator.scorer.active
return active if isinstance(active, scoring.AdditiveScorer) else scoring.default_scorer()
```

and `GET /api/scorer` published that fallback as `scorer_id`, `params` and `params_hash`. The console
rendered it under the heading **"Active configuration"**, with the caption *"What the running engine
is grouping with right now."*

**An operator whose champion was a promoted model would have read five weights that decided nothing,
under a heading asserting that they did, with nothing on the screen to say otherwise.**

### 1.1 It is not a v0.14.0 defect and that is the interesting part

The fallback predates the tree kinds. A promoted **`logistic`** champion — reachable since v0.11.0 —
produced exactly the same misreport. Two releases shipped with it, including one whose entire subject
was the console.

It survived because nothing had ever promoted anything: every corpus this project had returned
`INSUFFICIENT_EVIDENCE`, so `active_model_version()` was always `None` and the fallback branch was
never taken outside a unit test. It took a release that **built a model worth promoting** for the
screen's claim to become checkable.

That is the same shape as F59 one layer down, and the two together are this release's argument for
walking a chain rather than reading it.

### 1.2 The repair

| | before | after |
|---|---|---|
| `_active_scorer()` | one function, two meanings | split: **`_tunable_scorer()`** (what the form edits) and **`_running_scorer()`** (what is deciding) |
| `scorer_id`, `contract_version`, `params_hash` | the fallback's | **the running scorer's own** |
| the artefact | invisible | `running.model_version` — id, kind, fingerprint, challenger run, and the `params_document` |
| the heading | "Active configuration" | **"What is deciding"**, then "Configured parameters" |
| the five weights under a model version | shown as active | shown, **labelled inactive**, with what to do about it |

The rename is the repair. `_active_scorer` claimed to answer *"what is the engine scoring with"* and
answered *"what may an admin retune"*, and those are the same question only while the additive kind is
the only kind there is.

**The five weights are still rendered**, and that is right: an admin may retune the stored
configuration and roll the model version back, and a screen that hid the table would make that
impossible to reason about. What must not happen is presenting them as what is running.

### 1.3 Demonstrated red, with a control

Reverting the four lines that publish the running scorer's identity:

```
===== RED: the v0.13.0 behaviour restored =====
>       assert "tree" in dump, "the screen never names the kind that is running"
E       AssertionError: the screen never names the kind that is running
FAILED tests/test_ui_invariants.py::test_the_console_says_a_tree_is_deciding_and_not_five_additive_weights
1 failed, 20 passed

===== GREEN: restored =====
21 passed
```

The control is `test_the_control_an_additive_champion_is_not_warned_about`: with the additive scorer
running, the warning must be **absent** and the section must still be there. Without it, the
assertion above could be satisfied by a console that warns unconditionally — a different defect
wearing the same words.

The fixture is not hand-written. It fits a real tree with `tree.fit_document`, registers it with
`store.insert_model_version`, activates it with `store.set_active_model_version` and loads it with
`engine.load_scorer_config` — **the four steps a promotion takes** — then captures what the console
reads. An operator with a promoted tree reads exactly that.

## 2. The three classes, and why the screen has three

`app/views/model.js`. A scorer's parameters are read differently depending on where they came from,
and presenting all three identically would be the screen's own version of §1's defect.

| class | kinds | what the screen offers |
|---|---|---|
| **typed by an admin** | `additive` | the tunable form: five numbers, hardening-only, previewable |
| **fitted from labels** | `logistic` | the coefficients, read-only. **No form** |
| **fitted, with hyperparameters** | `tree`, `forest`, `gradient_boosting` | the hyperparameters, the structure, the artefact's provenance. **No form** |

**Why the fitted kinds get no form.** The numbers are a *result*. A screen offering to edit them would
be inviting an operator to overwrite evidence with an opinion, and the resulting artefact would carry
a `params_hash` naming a fit that never happened. There is no HTTP route that creates a model version
at all — registration is CLI-only — and that is a design decision rather than a gap: *the thing that
could put a new model in front of traffic is not reachable from the network.* The screen says so.

**The hyperparameters come from `params_document`**, which is `UI-0.13-DRAFT.md` §8's own
instruction — *"exposing what is already recorded is a far stronger design than inventing fields"* —
and its constraint:

> A hyperparameter that changes the trained model must appear in `model_version.params_document`, and
> therefore in `params_hash`. Otherwise two models with the same hash and different hyperparameters
> are indistinguishable, and the provenance v0.11.0 built becomes fiction.

`tests/test_tree_kinds.py::test_a_hyperparameter_change_moves_the_params_hash` holds that from the
model's side. This screen is the other side: every hyperparameter it displays it reads *out of the
hashed document*, so there is no field it can show that the fingerprint does not cover.

The `base_value` is displayed with its meaning, because it is the one number on the screen that does
not mean what a reader would assume: contributions sum to the score **minus** the base value, which
is what makes the decomposition exact rather than approximate.

## 3. The promotion screen: the branches that had never been reachable

v0.13.0 rendered a decision as a table row — verdict, outcome, reason, triggers. That is complete for
`INSUFFICIENT_EVIDENCE`, **which is the only verdict this project has ever produced**, and thin for
the other two: a `BETTER` or a `NOT_BETTER` is a *comparison*, and a comparison shown without the
numbers it compared is an assertion.

`app/views/verdict.js` adds the decision detail:

* **The four named quantities, both arms, with their intervals.**
  `PREREGISTRATION-0.11.0.md` §2 item 4 — *both arms come from one code path, because a challenger
  number with no champion number beside it is not a comparison* — applied to the screen.
* **Never composed.** Four quantities are shown as four. There is no expression in the file that adds,
  averages or ranks them against each other, which is the rule `promotion_metrics.py` states on the
  server. A single "score" would be a fifth quantity no plan registered and no code derives.
* **A quantity that could not be computed says so.** A degenerate interval renders as *"not
  computable"* and never as `0.0000`. That distinction cost this project a release once and
  `docs/ROADMAP.md`'s "Found while building v0.11.0" records what.
* **The names are transcribed, not derived from the document's keys.** A document carrying three
  quantities renders three rows and one visibly missing. A table that shows what it was given cannot
  tell you it was given less than it should have been.
* **The applied branch says what the consequence was**: *"The champion changed. Every grouping
  decision from the engine reload after this one onwards was taken by model version N. Situations
  that already existed were not regrouped."*

### 3.1 The candidate selector

v0.13.0 proposed `versions[0]` with **no selector**. Defensible with one logistic artefact in the
inventory; not defensible now, when the CLI registers five kinds — a screen where the consequential
action depends on a sort order the operator cannot see.

An artefact with **no challenger run** stays selectable on purpose, with a warning saying it can be
proposed and never applied. Hiding it would leave an operator to infer a rule nobody stated; letting
them propose one and read the server's refusal is how the rule becomes visible.

## 4. What did not change, and how that is known rather than claimed

```
served surface     88 -> 90 method/path pairs
of which /api      unchanged: not one route added, removed or renamed
UI files           46, of which 4 changed and 2 are new
```

Three scorer kinds, a repaired promotion gate and two new screens moved the **served API surface by
exactly nothing**. `test_f42_/f43_every_path_served_today_still_registers` assert the count, and the
`/api` half of the claim is asserted directly rather than inferred from it.

The two new modules are enumerated **individually** in three places — `routes_static._UI_MODULES`,
`declare.UNAUTHENTICATED_PATHS` and `test_build_step.UI_HASHES` — and every one of the three failed
until it was. That verbosity is the design: each line is the reviewable claim *"fetching this needs
no capability"*, and a glob would make the claim unreadable and re-open F41.

### What this gate does not establish

* **Nothing about how it looks.** `docs/gates/v0.12.0-phase-6.md` §8 established that the visual
  layer is outside the instrument, and that is inherited unchanged. Phase 9 is the pass with eyes on
  it and it has its own gate.
* **Nothing about the graph screen.** d3 is a recording double in the harness, and
  `SECURITY-REVIEW-0.13.0.md` records it as the largest uncovered surface. This release did not
  narrow it.
* **Nothing about a champion actually changing.** The applied branch is rendered from a `promotion`
  row written by a fixture. The gate never returned `BETTER` on any corpus this project holds — §8.3,
  and `docs/gates/v0.14.0-phase-7.md` leads with it.
