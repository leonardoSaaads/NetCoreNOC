## 2. The checkability guarantee is algebraically vacuous

Migration `0010` offers the closing identity as what makes *"and nothing else"* checkable rather
than merely promised. It is a **polynomial identity in `m` and `n`** with `r = n − m`:

```
m(n−m) + (n−m)(n−m−1)/2 + m(m−1)/2
  = mn − m² + (n² − 2mn + m² − n + m)/2 + (m² − m)/2
  = mn − m² + (n² − 2mn + 2m² − n)/2
  = mn − m² + n(n−1)/2 − mn + m²
  = n(n−1)/2                                        ← m cancels entirely
```

`m` does not survive the expansion, so the identity cannot constrain it. Executed:

```
============================================================================================
§2  the identity holds while `m*r < 0` — a control and the hostile case
============================================================================================
     n     m |        m*r   r(r-1)/2   m(m-1)/2 |        sum     C(n,2)  closes?  all components >= 0?
  ------------------------------------------------------------------------------------------------
     9     2 |         14         21          1 |         36         36   YES      yes
     4     2 |          4          1          1 |          6          6   YES      yes
     4    10 |        -60         21         45 |          6          6   YES      NO  <-- the discriminating half
     4   512 |    -260096     129286     130816 |          6          6   YES      NO  <-- the discriminating half
    60    30 |        900        435        435 |       1770       1770   YES      yes
     0     5 |        -25         15         10 |          0          0   YES      NO  <-- the discriminating half
     1     3 |         -6          3          3 |          0          0   YES      NO  <-- the discriminating half

  WHY THE EXISTING TEST COULD NEVER HAVE CAUGHT IT, in one sentence:
  `tests/test_partial_split.py::test_a_partial_split_asserts_marked_by_rest_and_nothing_else`
  fixes n = 9 and derives `marked` as a set of POSITIONS IN THE BAG (`frozenset({0, 1})`),
  so `m` is |marked| computed over real bag positions and `m <= n` holds by construction —
  the hostile case is not merely untested there, it is UNREACHABLE from that fixture.

  (And migration 0010's comment names `tests/test_learn.py` as the file that asserts the
   identity. It does not. The assertion is in `tests/test_partial_split.py:98`.)
```

**One sentence on why the existing test could never have caught it**, as the gate requires: the test
fixes `n = 9` and derives `marked` as a set of **positions in the bag**, so `m ≤ n` holds by
construction and the hostile case is not merely untested — it is unreachable from that fixture.

### 2a. A second reading the prompt's framing does not supply, and it changes the design

Look at row `n = 60, m = 30`. **Every component is non-negative and the identity closes**, and yet
§1.E measured that label as asserting nothing at all. So:

> **Component non-negativity is necessary and is not sufficient.** It discriminates `m > n`. It does
> not discriminate *"`m ≤ n`, and every one of those `m` marks names an alarm that is not in the
> bag."*

What discriminates the second case is **reconciliation itself** — the intersection — and nothing
else can. This matters for how §5.3's property test must be written: the property is asserted over
the **reconciled** count, where `0 ≤ m ≤ n` holds by construction and the test is therefore a guard
against the construction being undone, not a filter applied to a client number. Stated in Phase 1
and carried into the test's own docstring, because a reader who takes non-negativity as the whole
repair will have missed the half that matters.

## 4. F47 has a clock, and it is the most important fact in the release

**One clock throughout** (Appendix B, §1): `TS = 1 000 000.0`; the verdict, the alarm clear and the
situation close all at `TS + 10 s`; the prune pass at `TS + 20 days` with `RETENTION_DAYS = 7`, so
the cutoff is `TS + 13 days`. Nothing reads wall clock.

```
============================================================================================
§4  ONE CLOCK: TS = 1000000.0; verdict/clear/close at TS+10s; prune at TS + 20 d = 2728000.0, retention 7 d (cutoff = TS + 13 d)
============================================================================================
  prune() reported: {'situations': 0, 'alarms': 4, 'quarantine': 0}

                                             before  ->  after
  alarm rows                                      4  ->      0   <-- COLLECTED
  alarms with ne_id                               4  ->      0   <-- COLLECTED
  feedback rows                                   1  ->      1
  feedback_exclusion rows                         2  ->      2
  server bag rows                                 4  ->      4
  marked ids still resolvable to an NE            2  ->      0   <-- COLLECTED

  CONTROL: `feedback rows` is unchanged. That is F44's fix still holding — the
  label outlives the situation. `feedback_exclusion` and the server bag survive with it.

  THE QUERY THAT BECOMES UNANSWERABLE:
    SELECT x.alarm_id, a.ne_id FROM feedback_exclusion x
      LEFT JOIN alarm a ON a.id = x.alarm_id
    before the pass: [{'alarm_id': 1, 'ne_id': 1}, {'alarm_id': 3, 'ne_id': 3}]
    after  the pass: [{'alarm_id': 1, 'ne_id': None}, {'alarm_id': 3, 'ne_id': None}]

  So the two repairs have DIFFERENT AVAILABILITY PROFILES:
    - the correct `m`  = |feedback_exclusion n feedback_member(source='server')|
      is recomputable FOREVER: both sides survive the pass, measured above.
      recomputed AFTER the pass: m = 2
    - 'was this mark about a member the labeller could SEE?' needs `alarm.ne_id`,
      which is gone. PERMANENTLY UNANSWERABLE one retention pass after close.
```

**The exact query that becomes unanswerable** is printed above:
`SELECT x.alarm_id, a.ne_id FROM feedback_exclusion x LEFT JOIN alarm a ON a.id = x.alarm_id`. It
returns `ne_id` before the pass and `NULL` after it, for rows that still exist.

**The design consequence, and it decides Phase 3.** Tier 2 (the reconciled count) is recomputable
forever, because both of its inputs survive. Tier 3 (was the mark about a member the labeller could
see?) is recomputable only until the next retention pass after the situation closes. If tier 2 were
computed lazily and tier 3 eagerly, two quantities belonging to the same assertion would have
different availability profiles forever, and every consumer for the rest of the project's life would
have to know which is which. **Both are computed eagerly and stored** — which also keeps `0010`'s
own denormalization rationale intact.

This is F44's shape one level deeper: F44 deleted the label; this deletes the label's
interpretability. The `feedback` control above is F44's fix, still holding.

## 7. SQLite's actual behaviour for the constraint, determined by experiment

```
============================================================================================
§7  SQLite 3.45.1
============================================================================================
  -- (a) can ADD COLUMN carry a column-level CHECK at all? --------------------------
     ALTER TABLE t ADD COLUMN m INTEGER CHECK (m IS NULL OR (m >= 0 AND m <= n))
     -> ACCEPTED

  -- (b) is it in the stored schema? -----------------------------------------------
     CREATE TABLE t (id INTEGER PRIMARY KEY, n INTEGER, m INTEGER CHECK (m IS NULL OR (m >= 0 AND m <= n)))

  -- (c) is it ENFORCED on a subsequent INSERT? ------------------------------------
     legal   m=2 n=9   -> accepted
     legal   m=NULL    -> accepted
     illegal m=10 n=4  -> REFUSED: IntegrityError: CHECK constraint failed: m IS NULL OR (m >= 0 AND m <= n)
     illegal m=-1 n=4  -> REFUSED: IntegrityError: CHECK constraint failed: m IS NULL OR (m >= 0 AND m <= n)

  -- (d) is it ENFORCED on a subsequent UPDATE? ------------------------------------
     legal   m=3 on n=9 -> accepted
     illegal m=99 on n=9 -> REFUSED: IntegrityError: CHECK constraint failed: m IS NULL OR (m >= 0 AND m <= n)

  -- (e) does the CHECK see a row written BEFORE the column existed? ---------------
     (1, 9, None)
     (2, 9, 3)
     (3, 9, None)
     (row 1 predates the column and holds NULL; a CHECK is not retroactive in SQLite,
      which is why the migration must state the invariant AND the drift check must exist.)

  -- (f) the control: a CHECK the same statement should NOT be able to smuggle in ---
     ADD COLUMN ... REFERENCES with non-NULL default -> REFUSED: OperationalError: Cannot add a REFERENCES column with non-NULL default value
     CONTROL: `ALTER TABLE ADD COLUMN` is NOT unconditionally permissive — it refuses
     constructs it cannot apply, so (a)'s acceptance is a real capability, not a silence.
```

**Answer: yes.** `ALTER TABLE ... ADD COLUMN` carries an enforced `CHECK` that may reference an
existing column of the same row, and it is enforced on both subsequent `INSERT` and subsequent
`UPDATE`. The **control** in (f) matters: `ADD COLUMN` refuses a construct it cannot apply, so (a)'s
acceptance is a real capability rather than a statement being silently discarded.

Three design inputs follow.

1. **The schema may hold the invariant**, so §3.4's *"enforce at every layer where it is tractable"*
   includes the schema layer and the invariant does not have to retreat to the store.
2. **It is not retroactive** ((e)). A row written before the column existed is never re-checked, so
   the constraint bounds the future and the **drift check** bounds the past. Both are required; the
   constraint alone would leave a pre-`0011` corruption invisible forever.
3. **The predicate must be written to fail closed on a missing bag size.** SQLite treats a `CHECK`
   evaluating to `NULL` as satisfied, so `m <= member_count` with `member_count IS NULL` **passes**.
   The constraint therefore has to say `member_count IS NOT NULL AND …` explicitly, or a reconciled
   count could be written against a bag whose size was never recorded. Phase 2 writes it that way.
