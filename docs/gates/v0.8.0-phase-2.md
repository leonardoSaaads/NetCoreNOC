## 1. F43 — the fix

`declare.py:216-235`. An empty method set is **unverifiable** — there is no verb to look up in
`rbac.ROUTE_PERMISSIONS` or `rbac.ROUTE_SCOPE`, so there is nothing to check — and it is therefore
**refused**, by exactly the reasoning F42 applied to unknown shapes.

```python
if not methods:
    raise UndeclaredRouteError(
        f"{checked.path} is registered with an empty method set, which this gate cannot "
        "check: there is no verb to look up in rbac.ROUTE_PERMISSIONS or rbac.ROUTE_SCOPE. "
        "Starlette does not filter by verb when `methods` is falsy, so such a route serves "
        "every verb — it is refused rather than skipped (F43). Register through "
        "netcorenoc.api.declare.DeclaredRoutes, which always names the verb."
    )
```

**The option not taken, because it is worse.** Treating an empty set as *the full verb set* — the
"what Starlette actually serves" reading — is superficially more precise. It invents a declaration
requirement for seven verbs nobody wrote, so the natural fix a contributor reaches for is to declare
all seven, turning a mistake into seven authorizations. It also encodes an assumption about
Starlette's dispatch behaviour, and DECISIONS #101 already recorded a dependency's internal
representation as the mechanism by which this gate silently regressed once. Recorded as
**DECISIONS #106**.

**The claim, narrowed so it is checkable rather than reassuring.** v0.7.5 said *"every object on
`app.routes` is either checked or refused; none is skipped"* — true of shapes, false of methods. It
now reads:

> every object on `app.routes` is either checked against both authorization tables for every verb it
> carries, **or refused — as an unknown shape, or as a known shape carrying no verb to check.**

`SECURITY-REVIEW-0.7.5.md` is **not edited**; records are not rewritten, and the correction is
issued in `SECURITY-REVIEW-0.8.0.md`.

## 3. The physical layout — measured before choosing, and chosen **against** the measurement

Both layouts built with identical columns at Phase 0's measured **194 341-row** sink volume:

| Operation | **A**: one table + `lifecycle` | **B**: two tables | winner |
|---|---|---|---|
| file size after load | 23.92 MB | 21.52 MB | **B** by 10 % |
| promotion of one label's pairs | 18.42 ms | 12.57 ms | **B** by 32 % |
| dataset-only query (the report) | 0.44 ms | 0.06 ms | **B** |
| bounded sink deletion by age | 326.03 ms | 297.04 ms | **B** by 9 % |
| bounded sink deletion by row cap | 12.51 ms | 11.07 ms | **B** by 12 % |

**Layout B won every measurement. Layout A was chosen anyway**, and the reason is a correctness
property no timing can show:

> A pair row references two **observation** rows. Under B a promoted pair lives in `pair_dataset`
> while its observations are still in `observation_sink`, so promotion must either preserve ids
> across four independently-autoincrementing tables or **rewrite every reference as it moves**. The
> failure mode is a dataset row silently pointing at the wrong observation — on the per-label path,
> which produces the release's entire output.
>
> Under A **nothing moves**: promotion is one `UPDATE` of one column, ids are stable, references
> cannot break.

The margins being overridden are 6 ms on an operation that runs **per label** and 29 ms on one that
runs **once a minute**. Recorded as **DECISIONS #107**, with the cost stated rather than argued
away: A separates the sink's deletion from the labelled corpus by a `WHERE lifecycle='sink'` clause
rather than a table boundary — a **checked** guarantee where B's would have been **structural**, and
this project normally prefers structural. Mitigated by a dedicated test in Phase 4, not by the
layout.

## 4. Every column justified — the audit §Gate 2 requires

The rule: **a column exists because it cannot be recomputed, or because it is a key. There is no
third reason.** The full table is in `DESIGN.md`; this is the audit that no column escapes it.

| Table | Columns | cannot-recompute | key | other |
|---|---|---|---|---|
| `capture_run` | 13 | 13 | 0 | **0** |
| `dataset_observation` | 15 | 9 | 6 | **0** |
| `dataset_pair` | 18 | 13 | 5 | **0** |
| `feedback_member` | 4 | 1 (`position` — the order) | 3 | **0** |
| `feedback` (added) | 15 | 15 | 0 | **0** |
| `situation` (added) | 1 (`merged_into`) | 1 | 0 | **0** |

**Zero columns exist for a reason outside the two.**

Four decisions worth naming, because each is where the rule did real work:

1. **`class_affinity` / `entity_affinity` store the *value*, never `term_a`/`term_e`.** The
   contribution is `weight × value`, and dividing the weight back out **fails when the weight is
   zero** — a legal, supported, and especially interesting configuration. `scorer_config_id` on
   `capture_run` keeps the contribution derivable in the direction that always works.
2. **`truncated` was added because Phase 0 measured that it matters.** 183 029 of 194 341 discarded
   pairs — 94 % — are accepted links the cap dropped, not pairs the scorer rejected. Without this
   column the two are indistinguishable, and v0.9.0 would read a cap artefact as a scoring decision.
3. **Severity, entity and `alarm_count` are captured although `AdditiveScorer` ignores them.**
   `LinkFeatures`' reserved slots are `None` because the *incumbent* does not use them, not because
   v0.9.0 will not. The cost is bytes; the cost of omitting them is that the release which wants
   them cannot have them for any period before it ships.
4. **"Same /24?", "same OID root?", "same vendor?" are NOT columns.** They are derivable from the
   stored raw material and they are *modelling decisions*; freezing one now is the same mistake as
   freezing the label-derivation policy.

### The structural expression of directive 3

> **`dataset_pair` has no target column.**

`incumbent_linked` is present and is commented, at the column, as **the machine's decision —
provenance, not a target**. The only label lives in `feedback`, and reaching it requires the join.
That friction is the mechanism: a v0.9.0 author writing a training loop must go and *get* the human
label and cannot reach for the machine's by autocomplete (DECISIONS #103).
