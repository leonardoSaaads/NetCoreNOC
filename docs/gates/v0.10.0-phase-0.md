## 1. `EVIDENCE-BOUNDARY-0.9.2.md` §10 — the arithmetic, enumerated

### 1.1 What was published, and what is true

§10 declines to store a count of *unobservable asserted pairs* on the grounds that the surviving
columns already bound it. It published the bound as

```
observable asserted pairs ∈ [(m − b)·(n − m − (h − b)),  (m − b)·(n − m)]
```

and stated the measured case (`n = 6, m = 2, h = 3, b = 1`) as `[2, 2]`.

**Two things are wrong with that sentence, and they are different mistakes.**

1. **The upper expression is spurious.** `(m − b)·(n − m)` is the count that would obtain if the
   remainder held *no* hidden members — the special case `h = b` — not an attainable maximum given
   `h`. Once `h` and `b` are both known, the hidden count in the remainder is not a free parameter.
2. **The measured case is misstated.** Under the interval as published it evaluates to `[2, 4]`,
   not `[2, 2]`. The exact value is **2**.

The lower expression is **exact**, and the argument is one line: the hidden set `H` is partitioned
by the marked set `M` into the `b` members that are marked and the `h − b` that are not; every
member that is not marked is in the remainder; therefore `h − b` *is* the number of hidden members
in the remainder rather than a ceiling on it. The remainder holds exactly `(n − m) − (h − b)`
visible members, and a marked-by-remainder pair is observable exactly when both ends are visible:

```
observable asserted pairs = (m − b) · ((n − m) − (h − b))
```

### 1.2 The enumeration

Every non-empty marked set against every hidden set, for `n` from 2 to 8 — **86 868**
configurations. Truth counted the long way, over the actual pairs, sharing no arithmetic with
either expression under test.

Run first as a throwaway script, then committed as the test below so it re-runs on every commit
rather than living in this document as a quoted number:

```
configurations enumerated : 86868
lower expression == truth : 86868  (disagreements: 0)
upper expression == truth : 18658  (21.5%)
first disagreement of the lower expression: None

the case cited by section 10 (n=6, m=2, h=3, b=1):
  interval as published : [2, 4]
  published as          : [2, 2]
```

`86 868 = Σ(n=2..8) (2ⁿ − 1)·2ⁿ` — the `2ⁿ − 1` non-empty marked sets against all `2ⁿ` hidden sets.
The count is pinned by a test, so the figure quoted here and the figure the suite enumerates cannot
drift apart.

### 1.3 What changed, and the control that makes the test worth having

* `../architecture/EVIDENCE-BOUNDARY-0.9.2.md` §10 — the interval replaced by the exact expression,
  stated as exact rather than as a bound, with the superseded text quoted and named so a reader of
  the old sentence can find the correction.
* `../ROADMAP.md` — the same correction mirrored, with the same pointer.
* `tests/test_evidence_boundary_observable.py` — **new**, 4 tests, and the claim is now
  machine-checked on every run rather than asserted in prose.

**The correction makes §10's justification stronger.** "The surviving columns *bound* the quantity"
is a weak reason to omit a column; "the surviving columns *determine* it" means the omitted column
would have been strictly redundant.

**The control is the point of the file.** Appendix B's rule — *before trusting an invariant, ask
what value of its inputs would make it false* — exists in this repository because v0.9.2 found an
identity test that could never fail. So the suite also runs the **superseded** expression through
the same enumeration and requires it to *disagree*:

```
$ python -m pytest tests/test_evidence_boundary_observable.py -q
....                                                                     [100%]
4 passed in 0.93s
```

`test_the_superseded_upper_expression_disagrees` asserts the old formula is right in 21.0–22.0 % of
the space (measured: 21.5 %). Had it passed everywhere, the enumeration could not have distinguished
a correct expression from an incorrect one and the other three tests would have been worthless.

**Why 4, 5 and 6 are not edited.** A gate document and a build report are *dated records of what was
believed at the time*; editing one retroactively is the failure the project's append-only
conventions exist to prevent, and it would also destroy the evidence that the mistake was made. An
applied migration is never touched (Part VII rule 2 and prime directive 7). Each is named here so
the correction is findable from any of them, and #3 gets an erratum rather than an edit because
v0.10.0 is appending F48 to that file anyway and leaving a wrong sentence in a document this
release is actively writing would be a different kind of failure.

**This is itself the Appendix B trap firing a third time.** The brief's own count of how far the
wrong sentence had spread was low by four.
