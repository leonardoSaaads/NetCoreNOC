## 1. The scoring computation — every site that reads a parameter or computes `s`

**All scoring arithmetic lives in exactly one method today**, `Correlator.score`
(`src/netcorenoc/correlate.py:122-130`):

| Location | What it does |
|---|---|
| `correlate.py:24-28` | module constants `TAU_S=30.0`, `W_T=0.3`, `W_A=0.35`, `W_E=0.35`, `LINK_THRESHOLD=0.5` |
| `correlate.py:83-87` | `Correlator` dataclass fields: `window_s`, **`tau=TAU_S`**, **`threshold=LINK_THRESHOLD`**, `max_candidates`, `max_window` |
| `correlate.py:125` | `term_t = W_T * math.exp(-abs(new.ts - old.ts) / self.tau)` — reads the **module constant** `W_T` and the **instance field** `self.tau` |
| `correlate.py:126` | `term_a = W_A * learner.class_affinity(new.class_id, old.class_id)` — module constant `W_A` |
| `correlate.py:127-129` | `term_e = W_E * learner.entity_affinity(...)` — module constant `W_E` |
| `correlate.py:130` | returns `(term_t + term_a + term_e, term_t, term_a, term_e)` — the score and its three terms |
| `correlate.py:140-142` | `Correlator.process`: calls `self.score(...)`, accepts when `score > self.threshold`, builds `ScoredLink(old, score, term_t, term_a, term_e)` |
| `correlate.py:143` | keeps the `MAX_LINKS_PER_ALARM = 5` strongest links |

**Where the three per-term values surface to the API/UI today** (the "three score terms"):

- Persisted: `store.add_link(...)` (`store.py:418-433`) writes `link(score, term_t, term_a, term_e)`
  into the `link` table (`migrations/0001_init.sql:74-85`).
- Read: `store.situation_detail` (`store.py:535-540`) selects
  `alarm_a, alarm_b, score, term_t, term_a, term_e`.
- Served: `GET /api/situations/{sid}` (`api.py:488-494`), shaped by `shaping.shape`.
- Rendered: `ui/app.js:314-322` (`termBar`) draws one `<i>` per term with a
  `t=… A=… E=…` title, and `app.js:364` prints `score.toFixed(2)`.
- Asserted: `tests/test_api.py:105`, `tests/test_scenarios.py:101`, `tests/test_store.py:89`,
  `tests/test_correlate.py:38-40,147-150`.

**Where links and situations are formed and written** — engine side, under the batch lock,
never `datagram_received`:

- `Engine._process` (`main.py:347-399`) calls `self.correlator.process(entry, self.learner)`
  at `main.py:387` and then `await self._assign_situation(entry, outcome.links)` at
  `main.py:399`.
- `Engine._assign_situation` (`main.py:620-658`) creates/merges situations
  (`store.create_situation`, `store.merge_situations`, `store.add_alarm_to_situation`) and
  writes each link (`store.add_link`, `main.py:645-654`).
- Both run inside `Engine._commit_batch` (`main.py:302-322`), which holds `async with
  self.store.lock` for the whole batch and commits once.
- `receiver.datagram_received` (`receiver.py:299-315`) does: allowlist check → `parse_trap`
  (which includes the F4 community HMAC) → `queue.put_nowait`. **No lock, no I/O, no config
  read, no scoring.** This is the line v0.6.0 may not cross.

## 5. Was the v0.5.0 P2 constant tidy applied?

**No.** `W_T`, `W_A`, `W_E` are still module-level constants read directly inside
`Correlator.score` (`correlate.py:125-129`); only `tau` and `threshold` are dataclass instance
fields (`correlate.py:84-85`). `EXTENSIBILITY-0.6-DRAFT.md:35-39` predicted exactly this and
named the tidy "the first, byte-identical step of v0.6.0".

**Consequence for this release:** moving the three weights into the scorer dataclass is step
S1's first mechanical action, and it must be proven byte-identical (§2). Note that
`tests/test_correlate.py` imports `LINK_THRESHOLD, W_A, W_E, W_T` from `netcorenoc.correlate`
(lines 6-13), so those names must remain importable from `correlate` for the existing suite to
pass unchanged — they will be re-exported from the new `scoring` module rather than deleted.
