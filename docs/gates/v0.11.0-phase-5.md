## 1. The real corpus, through the built gate

Phase 1 predicted this outcome from the census, against machinery that did not exist yet
(`v0.11.0-phase-1.md` §1.2). **If the two disagreed, the gate would be wrong, not the census.** They
agree.

```
== the real corpus, through POST /api/promotion ==
  HTTP status        : 200
  status             : refused
  verdict            : INSUFFICIENT_EVIDENCE
  triggers           : ['FLOOR_UNMET', 'HOLDOUT_UNSPENT', 'THIN_SPLIT', 'POWER']
  seal query count   : 0
  evaluation_run_id  : 115a9f5ca974f00278ee69fd9ce5112e
```

The refusal, verbatim:

```
PROMOTION REFUSED — INSUFFICIENT_EVIDENCE.
This corpus cannot decide whether the challenger is better. It is not a finding that the
challenger is worse.

Triggers that fired (4):
  - FLOOR_UNMET: a §2 floor is unmet
  - HOLDOUT_UNSPENT: the sealed holdout has not been spent
  - THIN_SPLIT: fewer than 10 incidents on one side of a reported split
  - POWER: the minimum detectable difference at this n exceeds the observed difference

Detection threshold at n = 37 incidents: 0.2384 (23.8 percentage points).
Observed difference: 0.0000.
Sealed-holdout query count at decision time: 0.

What would have to change: every trigger above must clear. The floors are counts of labelled
evidence and are met by labelling, not by tuning. Projected time to sufficiency: undefined —
this deployment has no labelling-rate data, and printing a rate derived from the test harness
would be manufacturing one.
```

**Three things in that message are worth naming.**

* **0.2384 at n = 37** reproduces ADR #154's corrected closed form exactly (0.238), which is the
  figure the plan's §0 recorded as *known when it was written*.
* **The projection is `undefined`**, as §4 registered it would be. The harness applies 41 verdicts
  one second apart; printing that as a labelling rate would be manufacturing one.
* **`HOLDOUT_UNSPENT` fired**, and it is not decorative — it fired *because* the floors failed, which
  is §3's order working rather than a formality being observed.

What was unavailable, and why:

```
- the four named quantities: this corpus supplies zero asserted negative pairs, so no over-merge,
  under-merge, intact or respected rate can be computed for either arm. They are recorded as
  absent rather than as zero.
- sealed holdout: not read — the floors and the power condition are evaluated first, and the seal
  is spent when and only when both pass (plan §3)
```

**Recording them as absent rather than as zero is the F46 discipline applied to a promotion row.**
A zero would have been a number, and a number in that column would have been evidence.

## 3. The two refusals cannot be produced by one condition

**A single `if not decisive or verdict is not BETTER: refuse()` would satisfy a naive test and
destroy the distinction.** The guard here is structural: there are two functions, and **each raises
`PromotionPathError` if handed the other's verdict**.

```python
promotion.insufficient_evidence_refusal(not_better_judgement)  # -> PromotionPathError
promotion.not_better_refusal(insufficient_judgement, metrics)  # -> PromotionPathError
promotion.refusal_for(better_decision)  # -> PromotionPathError
```

Asserted by *handing each the other's verdict*, not by comparing message strings — a reworded
message would silently break a string comparison and would not break this.

`refusal_for` dispatches with a `match` over the three-valued type, so **no branch is shared by two
verdicts** and a future fourth value falls through to the final case rather than borrowing a refusal
written for something else.

## 4. The seal policy: floors, then power, then the seal

Registered in the plan's §3 and obeyed literally.

| Claim | Test | Result |
|---|---|---|
| floors fail → the seal is **not** read | `test_the_seal_is_not_read_when_the_floors_fail` | query count stays 0 |
| power fails → the seal is **not** read | `test_the_seal_is_not_read_when_the_power_condition_fails` | query count stays 0 |
| both pass → the seal **is** spent, once | `test_the_seal_is_spent_exactly_once_when_both_pass` | count 0 → 1 |
| exactly one module may spend it | `test_exactly_one_code_path_can_spend_the_seal_and_it_is_the_promotion_gate` | `['promotion.py']` |
| the spend is guarded by **both** conditions | `test_the_one_spend_is_guarded_by_the_floors_and_the_power_condition` | AST: the call sits inside a branch testing `floors_met` **and** `sufficient` |

**v0.10.0's guard was rewritten narrower, not softened.** It asserted *no* code path calls
`seal.spend`; v0.11.0 deliberately adds one. Relaxing it to *"some code path may"* would have retired
the only mechanical statement anyone had about who can spend the holdout. The new form names the
single authorised module, so a report that peeked or a CLI that read the membership to print it
fails.

The **structural** test is the addition worth arguing for: a behavioural test alone would pass
against code that short-circuited for an unrelated reason, and would go quiet the day that reason
changed.

## 5. Every trigger fired individually — and the finding that came out of trying

Eight of the nine `INSUFFICIENT_EVIDENCE` conditions are fired by their own fixture, with the
**exact** expected set asserted rather than "at least this trigger".

**The finding: two triggers cannot be isolated, and that is a consequence of the plan rather than a
defect.** §3 registers that the seal is spent *when and only when* the floors and the power
condition both pass. So a corpus that fails a floor, or fails the power condition, **necessarily**
leaves the holdout unspent and fires `HOLDOUT_UNSPENT` with it:

| trigger | fires alone? | expected set |
|---|---|---|
| `FLOOR_UNMET` | no | `{FLOOR_UNMET, HOLDOUT_UNSPENT}` |
| `POWER` | no | `{POWER, HOLDOUT_UNSPENT}` |
| `THIN_SPLIT`, `COVERAGE_EXCLUSIONS`, `UNKNOWN_POPULATION`, `TRUNCATED_LOAD_BEARING`, `UNSOUND_CHAINS`, `PRE_V080_MERGES` | yes | `{itself}` |
| `HOLDOUT_UNSPENT` | yes | `{itself}` — floors and power pass, no seal exists to read |

The expected set is written out **exactly per case**. A relaxed assertion (`trigger in fired`) would
have passed and would have hidden the day an unrelated trigger started co-firing — which is the
whole thing the test exists to detect. `test_every_registered_trigger_has_a_test` guards the table
against losing an entry.

## 6. The applied path, proved where the corpus cannot exercise it

**Both directions are required, and the second is the one a build is tempted to skip.**

The real corpus refuses (§1). A purpose-built sufficient fixture produces a genuine `BETTER`:
`test_a_sufficient_fixture_produces_a_real_better_verdict` asserts the verdict, that no trigger
fired, that `may_apply` is true, and that asking for a refusal message **raises**.

`test_promotion_api.py` deliberately does **not** force `BETTER` by monkeypatching the route's
derivation helpers. A fixture that reached the applied path by patching three module attributes
would be testing the patches, and the one property that file exists to prove is that **nothing a
client sends can reach that verdict**.

**A promotion is also refused when the verdict is `BETTER` but the artefact carries no
`challenger_run_id`** — the coefficients could not be traced to the run that produced them, and *a
promotion whose evidence cannot be named afterwards is a retune with a better story*. The schema
cannot tell a registration from a proposal, so that rule lives in the handler, and it is a refusal
**with a reason**, never a silent skip.

## 7. Human approval, and no UI

Route plus CLI (`netcorenoc promotion list`, `netcorenoc promotion register`). **No UI change: not a
button, not a field, not a string** (ADR #163).

* `POST /api/promotion` is **admin-only with no editor delegation**, exactly as `scorer.write` is;
  viewer and editor get 403 and **write no row** while being refused.
* `GET /api/promotion` is `viewer+` and `unscoped`, for `GET /api/scorer`'s reason: a refusal
  *explains* why the correlator is still what it is and names no network element.
* **There is no `auto_promote` flag, not even defaulted off.** A flag defaulted off is a flag.
* `netcorenoc promotion register` prints, in the operator's own words, that it has created an
  **artefact and not a promotion**, and that nothing will run it until an admin proposes it and the
  server's verdict permits.
