# v0.14.0 — the demonstrated guards

**Every guard this release depends on, shown catching the defect it exists for.**

A guard that has never been red is a guard nobody has tested. Fifteen defects were written into the
real tree, one at a time, and each one's guards were run against it; the file was then restored from
a byte-exact backup and the guards re-run. Every RED, GREEN and CONTROL block below is captured
output, not a transcription.

**The control is the half that makes the red mean something.** Under each injection a *different*
test — one that must be unaffected by that defect — is run and must stay green. Without it a red
could mean "the guard fired" or "the injection broke the suite", and those are not the same result.

## Why these fifteen

Each one is a defect a reviewer could plausibly write, not a strawman:

* **1-3** are the model contract. A tree whose explanation does not add up, an attribution that
  approximates rather than refuses, a seed that leaves the hashed document — each is one line and
  each would make a shipped claim false.
* **4** is `resolved = max(project floor, deployment policy)`. Dropping the `max` is the natural
  simplification and it inverts the rule.
* **5-6** are the simulator's separation from the promotion path — the prohibition
  `PREREGISTRATION-0.14.0.md` §1 extends from `incumbent_linked` to the generator.
* **7-10** are the pre-registration's own discipline: the shape, the seed, the stopping rule and the
  floors, each edited the way a build under pressure would edit it.
* **11-12** are this release's two found defects, reverted. A repair with no test is a repair that
  will be undone.
* **13-15** are the structural guards: prime directive 1, the size limit, and the enumerated static
  allowlist.

## What the exercise found about itself

**Injection 10's first control was not a control.** The control chosen was
`test_the_shortfall_is_per_floor_and_never_a_single_number`, which asserts a shortfall of 40 and 20
— numbers **derived from the floors the injection changed**. It went red alongside the guard, which
looks like a broken suite and is actually a second guard on the same property.

That is exactly the failure the control exists to detect, caught pointing at itself. The injection
was re-run with two genuinely independent controls (the principal count and the labelling rule) and
the second test was moved into the guard column where it belongs. **A control that shares a constant
with the injection is not a control**, and the only way to find one is to run it.

## What this exercise does not establish

* **That the guards are complete.** Fifteen defects caught is fifteen defects caught. F58, F59 and
  F60 were each found by *driving* the system, not by a guard — the guards for them exist now
  because the defects did first.
* **That the suite is a substitute for the demonstrations.** `docs/gates/v0.14.0-phase-8.md` §3
  names **eight surviving mutations**, each confirmed against all 1542 tests. Six of the eight are
  properties a docstring states emphatically and no test asserts.
* **Anything about the visual layer.** It stays outside the instrument
  (`docs/gates/v0.12.0-phase-6.md` §8) and Phase 9 is the pass with eyes on it.
