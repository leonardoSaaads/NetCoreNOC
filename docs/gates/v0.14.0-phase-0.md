# v0.14.0 — Gate 0

**The fence. No v0.14.0 code exists until this gate closes.**

A plan ratified after implementation began is not a pre-registration, and this release's honesty
rests entirely on the plan having been fixed before any model existed **and before any simulated
corpus existed**. That second half has no precedent in this repository: the three plans before this
one constrain how an existing corpus may be *read*; this one also constrains how a corpus may be
*made*.

Every probe below carries a **control that had to behave the other way**, and a **witness** that the
treatment was exercised at all. Two of the five premises came back differently from the way the
build prompt states them, and both are recorded here as measured rather than reconciled away — §3
and §4.

The probes are `phase0/premise1_2.py`, `phase0/premise4.py`, `phase0/premise5.sh` and
`phase0/malformed_probe.sh`, run from a scratch directory outside the repository, against the
shipped `Engine`, the shipped `Store` and the real `parse_trap` — never against a hand-built
`TrapEvent`, for `tools/corpus_census.py`'s reason: a probe built from hand-made events measures a
different corpus from the one `make eval` replays, and the two can drift with nothing going red.

## 2. Premises 1 and 2 — the scorer, and the challenger, on the ingest path

Both in Appendix D's shape: one clock (`time.monotonic`), one scenario (`tests/fixtures/fiber_cut.json`,
8 events through the wire encoder and the real parser), one engine per run, identical except for the
one thing under test.

### 2.1 Premise 1 — the champion scorer runs on the per-trap ingestion path

```
  events replayed          : 8
  CONTROL   (built-in)     : 0.069 s   slow-scorer calls 0
  TREATMENT (sleeps 0.3s)  : 8.429 s   slow-scorer calls 28
    [PASS] CONTROL   control_s < 5.0                       0.069 < 5.0
    [PASS] WITNESS   calls > 0                             28 > 0
    [PASS] TREATMENT treat_s > control_s + calls*SLEEP*0.5 8.429 > 4.269
  => PREMISE 1 CONFIRMED
```

Ingestion absorbs the scorer's latency in full: 28 calls at 0.30 s is 8.4 s of the 8.43 s elapsed.
**This is why v0.15.0 is a separate release and why this one does not touch `correlate.py`.** A
model that can block is a model that can stop the appliance receiving traps, and no in-process
mechanism can preempt a synchronous call — `SafeScorer`'s own docstring says so.

### 2.2 Premise 2 — the challenger's scoring is on that path too

`shadow.observe` is called from `engine._process` after `capture.record`, and `shadow.py:190` calls

```

    -> with run_id None, `observe` returns before scoring; a probe without the
```

## 4. Premise 4 — **the build prompt's premise is wrong in two places, and the correction is stronger**

The prompt states that the all-zero logistic *"raises nothing, … **no situation forms**, and its
median and p99 microseconds are **lower** than the champion's."* Measured over the whole eval corpus
(194 341 evaluated pairs, ten scenarios, one engine per arm):

```
  CONTROL   champion  : situations 41,   links 10976, score() calls 194341
  TREATMENT all-zero  : situations 2256, links 0,     score() calls 194341

  pairs scored by the all-zero model      : 194341
  exceptions raised                       : 0
  pairs with linked=False                 : 194341
  pairs whose contributions sum to score  : 194341
```

**Correction 1 — "no situation forms" is false. 2 256 situations form, one per alarm, with zero
links.** The appliance does not go quiet; it produces a *singleton per alarm*, so an operator
watching a situation count sees it go from 41 to 2 256 — **more** apparent activity, not less. The
true symptom is `links == 0`, and a monitor watching situation counts would read the failure as a
busy night.

**Correction 2 — the degenerate model is not faster. Measured like with like, the clock cannot tell
the two apart at all.** Comparing the all-zero *logistic* against the *additive* champion measures
the **implementation** (a loop building four `TermContribution`s against straight-line arithmetic),
not the model. The comparison that isolates the model holds the code path fixed and moves only the
numbers:

```
  THREE RUNS PER ARM, same process, same samples (median us / p99 us):
    champion  additive :  1.9590/ 3.4970   1.8880/ 3.3960   1.8640/ 3.8710   median spread 0.0950
    all-zero  additive :  1.8690/ 3.4440   1.9010/ 3.6080   1.8530/ 3.8720   median spread 0.0480
    fitted    logistic :  3.0730/ 6.4250   3.0680/ 6.5730   3.0790/ 6.8190   median spread 0.0110
    all-zero  logistic :  3.0740/ 6.6780   3.0850/ 8.0050   3.0690/ 6.9640   median spread 0.0160

  degenerate-vs-working gap, additive shape : 0.0190 us
  degenerate-vs-working gap, logistic shape : 0.0010 us
  worst run-to-run spread on ONE unchanged arm: 0.0950 us
```

**The gap between a working model and a model that has stopped the product is 0.019 µs and
0.001 µs. The noise on a single unchanged arm is 0.095 µs — five to ninety-five times larger.**

> **This is a stronger result than the premise as written, and Part V.4 is better justified by it.**
> *"The degenerate model is fastest"* invites the reply *"then floor the clock from below"*. What is
> actually true is that **the clock carries no signal about this failure in either direction**,
> while the output separates the two absolutely: 10 976 links against 0. A wall-clock lower bound
> would be a floor on a quantity measured to contain no information about the thing it is guarding.
> The discrimination floor of §4.2 of the plan is not a better version of a timing floor; it is the
> only kind of floor that can work here.

```
    [PASS] CONTROL   the champion forms situations        41 > 0
    [PASS] CONTROL   the champion forms links             10976 > 0
    [PASS] WITNESS   the all-zero model was called        194341 > 0
    [PASS] TREATMENT no exception                         0 == 0
    [PASS] TREATMENT linked=False everywhere              194341 == 194341
    [PASS] TREATMENT contributions sum to score           194341 == 194341
    [PASS] TREATMENT no LINK forms                        0 == 0
    [PASS] TREATMENT every alarm is a singleton situation 2256 situations, 0 links
    [PASS] TREATMENT additive gap is inside the noise     0.0190 <= 0.0950
    [PASS] TREATMENT logistic gap is inside the noise     0.0010 <= 0.0950
    [PASS] TREATMENT the OUTPUT separates them absolutely 10976 links vs 0 links
  => PREMISE 4 CONFIRMED
```

**Neither correction changes the plan**, which was ratified before this was re-measured and which
records the prompt's wording in its own §0. `PREREGISTRATION-0.14.0.md` §10 is explicit about where
a disagreement goes: the security review, as an opinion for v0.15.0, never as an edit. Both are
carried there.

### 4.2 A defect found by accident, reproduced deliberately

The first version of the premise-5 probe wrote a hand-made scenario that omitted the `truth` key.
`eval/harness.py` did not fail. It **hung**, at 0 % CPU, until killed. Reproduced with a control:

```
  CONTROL   well-formed extra file  : exit 0     (terminated)
  TREATMENT 'truth' key removed     : exit 124   (KILLED AT DEADLINE)
  stderr/stdout the treatment produced before the deadline:
      Traceback (most recent call last):
        ...
        File "/home/user/NetCoreNOC/eval/harness.py", line 322, in run_all
          results = [await run_scenario(p, promote=promote) for p in ...]
        File "/home/user/NetCoreNOC/eval/harness.py", line 233, in run_scenario
```

The `KeyError` at `harness.py:233` (`truth = event["truth"]`) **does** propagate and **does** print
a traceback — the process then never exits, because `run_scenario` leaves the `Engine.run()` task
alive when it raises and `asyncio.run`'s shutdown waits on it. In CI that is an indefinite hang
rather than a red build.

**Not fixed here.** Part VII.8: no fix inside a move. It is a ROADMAP line under *"Found while
building v0.14.0"* and it carries **finding F56**, issued in `SECURITY-REVIEW-0.14.0.md`.

## 7. Coverage: the sampling that precedes the band

ADR #181's band is **95.60 – 96.60 %**, registered before v0.13.0's measuring run and reported
against in `v0.13.0-phase-7.md`. Part VII.10 forbids re-cutting it.

What Gate 0 contributes is **variance on the unchanged tree**, so that Phase 1's band is registered
against a measured spread rather than a guess. Three consecutive `make coverage` runs on the
Gate-0 commit — `git rev-parse --short HEAD` = `4aed642`, `git status --porcelain | wc -l` = **0**,
the working tree stashed for the purpose exactly as ADR #181 did:

```
tree: 4aed642, 0 files modified
--- baseline sample 1 ---
Required test coverage of 85.0% reached. Total coverage: 96.03%
1428 passed in 477.72s (0:07:57)
--- baseline sample 2 ---
Required test coverage of 85.0% reached. Total coverage: 96.03%
1428 passed in 474.12s (0:07:54)
--- baseline sample 3 ---
Required test coverage of 85.0% reached. Total coverage: 96.05%
1428 passed in 473.16s (0:07:53)
```

**96.03 %, 96.03 %, 96.05 % — a spread of 0.02 points**, against Part II's expected band of
96.03–96.09 % and comfortably inside ADR #181's registered 95.60–96.60 %. The Gate-0 commit adds no
`src/` code, so this is the v0.13.0 tree's number.

**Two honest notes about this measurement, because three samples is not many.**

* v0.12.0's equivalent measurement gave 96.02 / 96.02 / 96.13 — a spread of **0.11**. Two of its
  three agreed exactly and the third did not. Getting 0.02 here does **not** establish that the
  suite is more deterministic than it was; it establishes that this particular triple happened to
  land close. The honest reading of the two measurements together is *"the spread is at most 0.11
  and is often much less"*, and a band cut to 0.02 would fail for reasons that have nothing to do
  with the code.
* **The first triple run here was discarded, and saying so matters.** It was started while the
  working tree still carried this release's first modules, so it measured a tree that was changing
  under it — one sample completed, at 95.98 %, before the run was killed. A baseline measured
  against a moving tree is not a baseline, and quoting that 95.98 % beside the three above would
  have been quoting a different tree's number as this one's.

**The band for v0.14.0 is not set here.** It is set in Phase 1 (ADR #193), before one line of model
code is written, with its width justified from this measurement plus what this release does to the
denominator. Both bands are reported in Phase 8.

## 8. What this gate does not establish

* **Nothing about whether any tree kind is any good.** No model has been fitted. Every threshold in
  the plan comes from the corpus census, the arithmetic of a three-dimensional feature space, and
  the statistics of the sample size.
* **Nothing about the simulated corpus.** It does not exist. §5 of the plan fixes its shape; Phase 6
  builds it; the near-threshold measurement that says whether the adversarial shapes have any
  content is Gate 6's, not this one's.
* **Nothing about the visual layer.** Unchanged from v0.13.0 and inherited: the harness has no
  layout, no cascade and no paint. Phase 9's browser pass is the only instrument for it.
* **Nothing about whether the plan is *honest*, only that it is *immutable*.** The hash guard's own
  docstring has said so since v0.9.0 and this release does not upgrade the claim.
