## 1. A1 / F50 — the cycle rule resolves over the cycle, not over the walk

### 1.1 The repair

```diff
         if nxt in seen:
-            return Resolution(min(seen), cycle=True)
+            return Resolution(min(_cycle_members(nxt, merged_into)), cycle=True)
         seen.add(nxt)
         current = nxt
     return Resolution(current, unterminated=True)
+
+
+def _cycle_members(entry: int, merged_into: Mapping[int, int]) -> set[int]:
+    """The ids on the cycle reached at ``entry``, and nothing that merely led into it."""
+    members = {entry}
+    node = merged_into[entry]
+    while node != entry:
+        members.add(node)
+        node = merged_into[node]
+    return members
```

`entry` is `nxt` — the already-visited node the walk arrived at a second time — so it is **on** the
cycle by construction, and every node from it back to itself has an edge in the mapping. The walk
therefore terminates without a bound, and `KeyError` is unreachable: each node between `nxt` and
`current` was followed *through* on the outward walk, and `merged_into[current] == nxt` is what
triggered the branch.

`incidents.py` is **205 lines** of a 400-line ceiling. No module was split and no ceiling was raised.

### 1.2 The four tests

|---|---|
| `test_a_tail_below_the_cycle_minimum_does_not_become_its_own_incident` | the defect: `{1: 7, 7: 8, 8: 7}` is **one** incident, and it is `7` |
| `test_a_tail_above_the_cycle_minimum_resolves_to_the_cycle_minimum_too` | **CONTROL** — passes on the defective code too, and rejects `max(cycle)` |
| `test_two_separate_tails_into_one_cycle_agree_with_each_other` | the general property: which door you came in by must not matter |

`test_every_entry_point_into_one_cycle_gets_the_same_incident` is **unchanged** and serves as the
second control.

## 2. A2 — the variance-correct closed form, pinned against an independent simulation

### 2.1 The repair

`shadow_cv.minimum_detectable_difference` now solves

```
delta = (z_α/2 + z_power) · sqrt((p(1−p) + q(1−q)) / n),    q = min(1, p + delta)
```

by fixed-point iteration from the equal-variance value, converging monotonically downward. The `q`
clamp matters at small `n`, where the naive starting value can push the second arm past 1.0 and
`q(1−q)` would go negative under the root; at `q = 1` the arm's variance is zero, which is the
correct limit.

`_MDD_MAX_ITERATIONS = 64` is a **second guard**, not the stopping rule — the same shape as
`incidents.MAX_CHAIN_DEPTH`, and for the same reason: reaching it would be evidence that the
arithmetic changed rather than that the problem was hard. It returns the last iterate rather than
raising, because this is an offline report and a slightly wrong threshold is a number to report where
an exception takes the whole evaluation down.

**No dependency was added.** `shadow_cv.py` is **290 lines** of a 400-line ceiling.

### 2.2 The pin, and why it is a test rather than a paragraph

`tests/test_shadow_cv_power.py` searches for the threshold by **simulation**: it draws two binomials
from an exact log-space inverse CDF, runs a two-sided pooled z-test, counts rejections over 4 000
trials, and scans a **fixed absolute grid** (0.010 → 0.500, step 0.005) for the smallest difference
reaching 80 % power. It uses a xorshift64\* generator, deliberately not the LCG in `shadow_cv`.

The grid is absolute rather than bracketed around the closed form's answer on purpose: a bracket
centred on the answer would confirm that a crossing exists *near* the answer rather than find the
crossing.

**The tolerance is 0.010, and it is derived rather than chosen:**

| term | value | what it is |
|---|---|---|
| grid step | 0.005 | the simulation cannot report a threshold between two grid points |
| MC standard error | 0.002 | `sqrt(0.8·0.2/4000) = 0.0063` in power units, ÷ ~3 power-units per unit delta |
| discreteness | 0.003 | at `n = 37` a binomial proportion moves in steps of 1/37 = 0.027, so the rejection rate crosses 0.80 in jumps |

Added rather than combined in quadrature, because the first is a hard quantisation and not a random
error. **Observed agreement is 0.0016 at worst** — six times inside the bound — so the tolerance is
not carrying the result.

### 2.3 Measured

```
     n    naive  corrected      sim  |corr-sim|  |naive-sim|  plan
    37   0.2985     0.2384    0.240      0.0016       0.0585  0.25
   120   0.1657     0.1488    0.150      0.0012       0.0157  0.16
   300   0.1048     0.0985    0.100      0.0015       0.0048  0.10
```

**The plan reproduces.** The corrected form lands within 0.012 of every registered figure; the naive
form was 0.048 high at 37.

Note the last column of `|naive-sim|`: **0.0048 at n = 300, inside the tolerance.** The naive form is
nearly right at large `n`, which is exactly why v0.10.0 saw agreement there and disagreement at
small `n` and concluded the *plan* was wrong. `test_the_simulation_rejects_the_form_this_release_replaced`
asserts the discrimination at 37 and 120 and asserts the *convergence* at 300, rather than claiming a
rejection it does not have.

### 2.4 A second finding: `n = 12` is not a threshold that was optimistic

§3.1 registers **0.42** at `n = 12`. At `p = 0.70` that puts the second arm at **1.12**, which is not
a proportion. Measured:

```
n=12 — the largest attainable difference at p=0.70 is 0.30 (q would exceed 1.0):
   delta=0.20  q=0.90  simulated power = 0.203
   delta=0.25  q=0.95  simulated power = 0.322
   delta=0.30  q=1.00  simulated power = 0.519
   the plan registers 0.42 at n=12, which would put q at 1.12
   the corrected closed form returns 0.3706 (the q<=1 clamp binds)
```

**At 12 incidents there is no detectable difference at all**, and both methods say so — the
simulation by never reaching 80 % power, the closed form by returning a value above every attainable
difference. That is a *stronger* version of the plan's own conclusion, and it means the registered
figure is not a threshold that was too optimistic but one that does not exist.

Recorded, not repaired. The plan is ratified and hash-guarded; §8 forbids editing it; the figure is a
reported quantity and a verdict trigger, never a floor.

## 3. A3 — the coverage figure, and the arithmetic that produced it

### 3.1 The command is pinned

```make
coverage:
	$(PYTHON) -m pytest -q --cov=netcorenoc --cov-report=term
```

`make coverage` is the one true command, with a comment above it stating the rule that matters:
**quote the `Total coverage:` line and nothing else.** That line is coverage.py's own
`percent_covered`. `make test` reports the same percentage — `term` and `term-missing` differ only in
a trailing column — so the ambiguity being closed is not which report flag to use. It is that
**recomputing a number the tool already printed is how the two come to disagree with nobody
noticing.**

### 3.2 The honest figure, and the honest baseline

```
$ make coverage
TOTAL                                      6666    186   1462    123    96%
Required test coverage of 85.0% reached. Total coverage: 95.95%
1174 passed in 451.68s (0:07:31)
```

**95.95 %.** `96.20 %` was never a coverage.py output — it is the four printed columns computed by
hand, and `BrPart` (123 partially-covered **statements**) is not `missing_branches` (143 missing
branch **arcs**). The counts reproduced exactly; only the arithmetic on them did not.

**So the 0.27-point drop the build brief asks about is not the drop.** `96.22 %` appears in this
repository only as *"the brief asks for coverage at or above 96.22 %"* — no run in `docs/gates/`
produced it. The last figure that came off the same line of the same tool is **v0.9.2's 96.19 %**, and
rather than argue that, this build re-measured it:

```
$ git worktree add … v0.9.2 && … && python -m pytest -q --cov=netcorenoc --cov-report=term
TOTAL                                      6210    159   1382    118    96%
Required test coverage of 85.0% reached. Total coverage: 96.19%
1086 passed in 455.32s (0:07:35)
```

**96.19 % reproduces to the digit.** The like-for-like movement across v0.10.0 is therefore
**96.19 % → 95.95 %, a drop of 0.24 points**.

> **QUALIFIED IN GATE 5 §8, and the qualification matters.** Two runs of `make coverage` on the
> *same* tree differ by **0.11 points** — the suite contains `@given(st.binary(…))` properties whose
> generated inputs vary per run, and `receiver.py` carries the entire drift. A 0.24-point movement
> measured once per release is therefore about **two bands**: larger than the noise, and not cleanly
> separable from it on one sample each. Read as *probably real and not established*. DECISIONS #159.

### 3.3 Which modules account for it, exactly

Attributed by differencing the two JSON reports in *uncovered units* — a unit being a statement or a
branch arc, which is what the percentage is over:

```
v0.9.2   total units 7592  uncovered 289  -> 96.19%
v0.10.0  total units 8128  uncovered 329  -> 95.95%

uncovered units ADDED: 40; total units added: 536

 d(unc) module                                           units  unc    cov%
    +16 maintenance.py                                     117   23   80.3%
    +15 census.py                                   NEW     70   15   78.6%
     +8 shadow_render.py                                   269   13   95.2%
     +2 shadow_cv.py                                NEW     75    2   97.3%
     -1 shadow.py                                          152    4   97.4%

sum of the top rows: 40 of 40 added uncovered units
```

**Four modules, and the accounting is exact rather than approximate** — the five rows sum to the
whole 40-unit increase with nothing left over. `census.py` at **78.6 %** is the largest new
contributor, as the brief predicted; `maintenance.py` is the larger one and it is not new, so it grew
uncovered branches rather than arriving with them.

### 3.4 No test was written to buy the number back

`census.first_label_per_incident`'s `_ = identity` is removed — a discarded computation whose only
job was to keep a name used, which is a leftover rather than a design and the kind of line a
dead-code gate cannot see because the discard is what makes it look used. That removal *lowers* the
statement count by one; it was not made to move the figure and does not meaningfully move it.

**A number reported honestly is the deliverable.** The definitive figure for this release is measured
on the final tree in Gate 5 §8.
