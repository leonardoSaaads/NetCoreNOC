## 1. The corpus census, re-run

Built exactly as v0.10.0 Phase 1 §4 built it, which built it as v0.9.0 Phase 0 §2(b) did: every
`eval/corpus` scenario replayed through **one** `Engine`, one store, scenarios an hour of synthetic
time apart, then every situation the replay formed given a verdict under the declared mechanical
policy — **every third situation `split`, the rest `confirm`; three operators round-robin; every
fifth label under a restricting scope.** One clock throughout.

**It is a command, not a quoted number**: `make census` (`tools/corpus_census.py`). v0.10.0 ran its
census as a throwaway script and recorded the output, which made the figures checkable once. This
release predicts its own headline outcome from them and Phase 7 §4 requires the census byte-identical
across two runs and two processes — neither of which a number inside a Markdown file can satisfy.

Two properties of the method are load-bearing and are stated rather than assumed:

* **Events go through the wire encoder and the real parser**, exactly as `tests/util.fixture_events`
  does. A census built from hand-made `TrapEvent`s would be counting a different corpus from the one
  `make eval` replays.
* **The counting is done by the judge's own code** — `Store.asserting_bag_rows`, the expression the
  promotion gate reads — not by a query written for this document. A census with its own query would
  be measuring the query.

```
===== THE REAL CORPUS (the declared mechanical policy) =====
  situations formed          : 41
  labelled bags              : 41
  confirm / split            : 28 / 13
  merge-aware incidents      : 37
  one-hop incidents          : 37
  unsound chains             : 0
  coverage distribution      : {'empty': 4, 'full': 25, 'none': 6, 'partial': 6}
  members / reconciled marks : 2256 / 0
  unknown-population rows    : 0
  asserted_negative_pairs    : 0
  max contributed by one bag : 0
  ASSERTING_BAGS (floor 50)  : 0
  ASSERTING_INCIDENTS (fl 30): 0
```

**Every figure reproduces the plan's §0 and v0.10.0's measurement**: 41 bags, 28/13, 37 merge-aware
incidents, coverage full 25 / partial 6 / none 6 / empty 4, and `asserting_bags` **0** against a
floor of 50. The transitive and one-hop incident counts are both 37, so the reduction between them is
**zero** — reproducing v0.10.0 §5.1's finding that every chain in this corpus is exactly one hop.

### 1.1 The control, because a zero is the most dangerous measurement here

*"Measuring nothing and concluding CLOSED"* is on this repository's record (Appendix B): a probe
once compared `None → None`, observed nothing, and would have reported the finding closed. So the
zero above is paired with a probe that had to come back **non-zero through the same code**.

The control corpus is the identical mechanical policy with one addition: **a `split` on a bag of four
or more members also marks its first two.**

```
===== THE CONTROL (same policy; a split of >= 4 also marks its first two) =====
  members / reconciled marks : 2256 / 4
  asserted_negative_pairs    : 1474
  max contributed by one bag : 998
  ASSERTING_BAGS (floor 50)  : 2
  ASSERTING_INCIDENTS (fl 30): 2
```

`1474 = 2·(240−2) + 2·(501−2)`, reproducing v0.10.0's arithmetic exactly. **The census code can see
an assertion**, so the real corpus's zero is a property of the corpus and not of the query.

The control carries its own finding, and it is the sharper one: even when **every** eligible `split`
is marked, only **two** bags assert anything, because only two of the thirteen `split` bags have four
or more members. Two asserting bags against a floor of fifty, from a corpus where the labelling rule
marked everything it could.

### 1.2 What the gate will decide, stated before it is built

```
  asserting_bags           0  against a floor of 50  -> UNMET
  asserting_incidents      0  against a floor of 30  -> UNMET
  => Trigger.FLOOR_UNMET fires. Verdict INSUFFICIENT_EVIDENCE.
  => Under the plan's §3 order (floors, then power, then seal) THE SEAL IS NOT READ.
  => v0.11.0's predicted query count: 0.
```

This is a **prediction**, recorded in Phase 1, against machinery that does not exist until Phase 5.
Phase 7 §6 re-measures it against the built gate, and the two must agree. If they disagree, the gate
is wrong — not the census.

### 1.3 Determinism, measured now rather than assumed at Phase 7

```
$ python tools/corpus_census.py > c1.txt ; python tools/corpus_census.py > c2.txt
$ diff c1.txt c2.txt && echo IDENTICAL
IDENTICAL

```

Two runs in **two separate processes**, byte-identical. Recorded here because the census is an input
to a prediction, and a prediction from a number that moves between runs is not one.

## 2. The four scope decisions

Recorded as ADRs #160–#163, continuing from #159. Each carries its context, its options, its choice
and its reason; they are summarised here in one line apiece and argued there.

| ADR | Decision | The reason in one sentence |
|---|---|---|
| **#160** | **Three tables** — `model_version` (artefact), `promotion` (event), `scorer_config` unchanged | The draft's single table is refuted three independent times, and the second refutation is a **safety regression** rather than a schema inconvenience. |
| **#161** | The parameters are a **canonical JSON document with a per-kind validator** | Typed columns mean one migration per scorer kind forever, with v0.12.0 and v0.13.0 both coming; and `SafeScorer` catches an exception at score time, never a parameter set that scores fine and destroys grouping. |
| **#162** | The audit catalog reopens for **exactly** the actions this release makes possible | Ambiguity about scope resolves to the smaller theme; the v0.9.2 reconciliation-drift gap is not newly reachable and stays a ROADMAP line and a finding. |
| **#163** | **No UI**, not a button, not a field, not a string | The catalog is reopening in the same release, and the v0.7.5 defect — the most expensive here — was a click gesture in a UI no test executes to this day. |

## 3. The Part IV check: draft versus build prompt, and what it found

Part IV names **three** claims of `CHAMPION-CHALLENGER-0.11-DRAFT.md` that it overrules, and
instructs that *any other* apparent disagreement be reported here rather than resolved silently.
Every section of the draft was checked against the schema, the code and the ratified plan.

### 3.1 The three named claims — all three confirmed overruled, by measurement

| Draft | Claim | Verdict | Evidence |
|---|---|---|---|
| §1 | *"Promotion is that table gaining a row"* (`scorer_config`) | **overruled** | Gate 0 §2.1 and §2.3 — three independent refutations, each executed |
| §4 | *"`scorer_config` becomes a model inventory"* | **overruled** | the same three; the inventory is `model_version` |
| §2 | the seal question posed as *spend / do not require* | **overruled** | the plan's §3 registers a **third** answer, conditional, with an evaluation order |

A fourth consequence follows from §1 and is worth naming separately because a build could
accidentally preserve it: §1 also asserts *"the engine loads it exactly as it loads a retune today —
`scorer_lifecycle` is unchanged."* That is false once the artefact is a document of a declared kind.
`scorer_lifecycle` **gains dispatch**, which Fact B measured it has never had.

### 3.2 What the draft got right, and is kept

Reported because a check that only lists errors is not a check.

* **§0.1 human approval, §0.2 ONNX last** — kept exactly, and §0.2 is why #161 refuses an adapter
  column.
* **§1's "rollback is the mechanism that already exists"** — **survives intact.** Rollback is a
  pointer move and `scorer_active` already is one; V.2 needs no new mechanism for it.
* **§1's "what must be added is the provenance"** — survives; only its *location* moves.
* **§2's two refusals, required to differ by code path and message** — survives and is the release's
  centre of gravity.
* **§4's "a refused promotion should leave a row too"** — survives verbatim, and the plan's §2
  raises it from a suggestion to a validity condition.
* **§3's inherited mechanisms and facts** — survive, including the seal's twelve incidents and the
  refusal of `incumbent_linked`.
* **§5's five exclusions** — survive entirely and are §2 of `SCOPE-0.11.0.md`.

### 3.3 The one further disagreement found, and it is already resolved

**Draft §3, fourth bullet:** *"The plan's detection-threshold table does not reproduce below
`n = 120` (`../gates/v0.10.0-phase-1.md` §2). v0.11.0 should re-derive it and record the simulation's
assumptions this time."*

**This is no longer true, and the correction runs in the opposite direction to the one the draft
expected.** v0.10.1 (ADR #154) found that v0.10.0's closed form gave **both** arms the base-rate
variance, when the second arm sits at `p + delta` and has far smaller variance in exactly the small-`n`
regime. Corrected, the table gives 0.238 / 0.149 / 0.099 at `n` = 37 / 120 / 300 against the plan's
registered 0.25 / 0.16 / 0.10 — **it reproduces**. The v0.10.0 conclusion ran backwards: the plan's
table was not optimistic, the closed form was pessimistic, and the two "independent" methods that
agreed with each other shared the assumption that was wrong.

**Resolution: nothing to do.** `PREREGISTRATION-0.11.0.md` §0 already records the corrected figures
as *known when it was written*, so the draft's instruction has been discharged by the plan rather
than by this build. It is reported here because Part IV requires apparent disagreements reported
rather than silently dropped, and because *"the draft asked for something and the build did not do
it"* would otherwise look like an omission.

### 3.4 No disagreement between the build prompt and the plan

Checked explicitly, since `SCOPE-0.11.0.md` names the plan as winning if they diverge. Every
analytical question the build prompt raises — the seal policy, the two refusals, the degeneracy
rules, what a promotion's evidence must contain — is answered by the plan in the same terms the
build prompt uses, because the build prompt's Appendix C **is** the plan. **No divergence found.**
