## 2. Migration `0007_write_perimeter.sql`

Forward-only, additive, four statements plus two clean-ups:

| Statement | Finding | Purpose |
|---|---|---|
| `ALTER TABLE feedback ADD COLUMN principal_ref TEXT` | F36 | attribution — nullable, **not** backfilled |
| `ALTER TABLE feedback ADD COLUMN role TEXT` | F36 | attribution — nullable, **not** backfilled |
| `DELETE FROM feedback WHERE EXISTS (…earlier sibling…)` | F36 | de-duplicate before the index can exist |
| `CREATE UNIQUE INDEX idx_feedback_situation_verdict` | F36 | the idempotence constraint |
| `DELETE FROM label WHERE …NOT IN (SELECT id FROM device/alarm_class)` | F37 | orphan cleanup |

Three choices are recorded in the file itself and in `DECISIONS.md`:

- **No backfill of the attribution columns.** The information does not exist for pre-`0007` rows,
  and inventing a plausible author would be worse than admitting none — an audit column that is
  sometimes a guess is not an audit column. `NULL` means "written by v0.7.0 or earlier, author
  unrecorded".
- **`CREATE UNIQUE INDEX`, not a `UNIQUE` table constraint.** SQLite cannot add the latter in place,
  and the former is exactly as binding for `INSERT … ON CONFLICT`. No table rebuild.
- **De-duplication keeps the EARLIEST row by `created_at`** (`id` breaks a tie, and is monotonic, so
  the survivor is deterministic). The earliest row preserves *when the operator first said this*,
  which is the fact the learned state was actually derived from; keeping the latest would rewrite
  that history. The `DELETE` reads as "delete every row that has a strictly earlier sibling in its
  own `(situation_id, verdict)` group", which leaves exactly one survivor per group.
- **No foreign key on `label`** (DECISIONS #71). A table rebuild is the one class of migration that
  can lose rows, and running one against every operator's populated database inside a security patch
  is disproportionate to the defect. The ROADMAP carries the structural fix.

**It seeds nothing.** No governance rows, no scorer rows, no rows of any kind. An appliance that
applied `0007` and kept running the v0.7.0 code would behave identically.

## 3. Evidence — a populated v0.7.0 database, migrated

The fixture: `fiber_cut.json` driven through the real engine on a database built with `0007` removed
from the migrations directory (so it is genuinely a v0.7.0 database at `user_version = 6`), then
seeded with exactly the states the two findings produce — 5 identical `confirm` rows and 3 identical
`split` rows on one situation (what v0.7.0's unbounded `add_feedback` writes), 5 orphan `device`
labels and 1 orphan `class` label on ids that do not exist (what v0.7.0's missing existence check
allows), and 1 **real** label that must survive.

```
[v0.7.0 fixture] schema=6 feedback=8 label=7 alarm=8 situation=2 edge=0 audit=0
[after 0007    ] schema=7 feedback=2 label=1 alarm=8 situation=2 edge=0 audit=0

  de-duplicated feedback rows removed: 6
  orphan label rows removed:           6
  surviving feedback:
    {'id': 1, 'situation_id': 2, 'verdict': 'confirm', 'created_at': 3000100.0,
     'principal_ref': None, 'role': None}
    {'id': 6, 'situation_id': 2, 'verdict': 'split',   'created_at': 3000200.0,
     'principal_ref': None, 'role': None}
  surviving labels:
    {'kind': 'device', 'target_id': 1, 'label': 'core-1', 'updated_at': 3000300.0}

  foreign_key_check:  clean
  integrity_check:    ok
  data intact: alarm 8==8 True, situation 2==2 True, edge 0==0 True, audit 0==0 True
  UNIQUE index enforced: UNIQUE constraint failed: feedback.situation_id, feedback.verdict
  re-open (idempotent): feedback=2 schema=7
```

**Recorded counts, as required:** **6** de-duplicated `feedback` rows removed, **6** orphan `label`
rows removed.

The survivors are the correct ones: `id=1` at `created_at=3000100.0` is the **earliest** confirm
(not the last), and `id=6` at `3000200.0` is the earliest split. The one real label survived; all
six orphans are gone.

### The audit chain, on a database that has one

The run above had an empty `audit_log` (the engine was driven directly, not through the API), so the
chain check was re-run against a database carrying 12 hash-chained rows:

```
[v0.7.0] audit rows=12 chain ok=True checked=12 head=a52f01e32ec80c7b…
[0007  ] audit rows=12 chain ok=True checked=12 head=a52f01e32ec80c7b…
  chain head unchanged: True
  foreign_key_check: clean   schema=7
```

The chain head is **byte-identical** across the migration — `0007` touches no audited table, so
tamper-evidence is preserved rather than merely re-derived.
