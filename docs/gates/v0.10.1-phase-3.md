# v0.10.1 — Gate 3: the three documents

Three architecture documents that **specify and implement nothing**. They exist so that v0.11.0, the
UI work and the storage work can be *scoped* rather than *discovered* — which is the least urgent
part of this release and the reason the next three can start from a plan.

## 3. The measurements each document rests on

**These are not illustrative.** Each was taken on this tree, with the command recorded in the
document, and each is the reason its document exists rather than a decoration on an opinion already
formed.

### C1 — the lineage

The finding is **§4: incident identity is not stable in time.** Fold assignment is deterministic in
the incident ids; incident identity depends on `merged_into`; `merged_into` changes when situations
merge; **and no snapshot of the merge graph is retained anywhere** — the column is forward-only, no
history table exists, and no audit event records the edge.

So an evaluation is reproducible **today** and not necessarily **later**, and nothing in the system
says so. The second-order version is the one that matters: `holdout_seal_member.incident_id` was
materialised once, so a drifting identity means the sealed set and the estimator's exclusions come
from **two maps taken at two different times** — the disagreement §3.3 of the ratified plan exists
to prevent, arriving through *time* instead of through a second implementation. **v0.10.1's B1 and
B2 close the spatial version of that hazard. The temporal version is open.**

Three candidate answers are named — materialise the fold assignment per run, snapshot the merge
edges, version the incident map — with a one-line cost each, and **none is chosen**.

### C2 — the observability gap

```
      2 .error(      1 .exception(      3 .info(      3 .warning(      0 .debug(
```

**Nine call sites in 17 418 lines, and zero `debug`.** Two of the nine are startup banners and one
is argparse's.

The document's central distinction is why nobody noticed: **audit answers "who did what" and
NetCoreNOC has that, excellently.** Observability answers "what is the system doing" and it has
almost none. Every review has looked at the hash-chained audit, found it strong, and moved on —
and an operator at 3 a.m. is asking the other question, about which `audit_event` is silent by
design, because nobody did anything.

Principle 4 is treated as eliminating designs rather than constraining them: **the correlation
identifier is not per-trap**, ingest gets none at all, and the honest consequence — *a trap cannot be
followed through the system and never will be* — is stated rather than engineered around.

The retention-pass event is singled out because **F44 would have been a question somebody asked on
day one** if a retention pass had ever emitted `{feedback: 3}`.

### C3 — the storage coupling

```
RETURNING 43 (portable) · PRAGMA 28 · AUTOINCREMENT 21 · INSERT OR IGNORE/REPLACE 6 · rowid 2
user_version as the schema-version mechanism (a PRAGMA, so it has no PostgreSQL equivalent)

methods on Store mixins total: 148
methods carrying SQL: 142
files carrying SQL: 19
```

**The syntax is the easy part.** 142 hand-written statements with no dialect layer, and the risk is
not that a statement fails to parse — it is that it parses and means something slightly different.

The document records **`ON CONFLICT DO SELECT` as a simplification available once PostgreSQL 19 is
GA and never as a dependency**, states that **no PostgreSQL release makes PostgreSQL plug-and-play**
because zero-config is a property of packaging (Zabbix as the worked example), and names four
invariants that direct write access destroys — the seal's structural query count, the hash-chained
audit accepting *a valid chain with an invented actor*, `excluded_reconciled` becoming plantable
(F46 through the back door), and `eval`'s byte-identity presuming a single writer.

**The first of those four is a READ rather than a write**, which is why it is listed first: the
read-only role §3 recommends is itself the threat to §4's first invariant, and the mitigation — the
seal in its own schema, with a database-permission proof beside the AST proof — is the one place
this document lets the shape of the schema change.

Principle 6 is **raised and explicitly not reopened**; two-backends-or-one is **recorded and not
answered**.

### A number the brief and the tree disagree about, reported rather than adopted

The build brief states *"144 `Store` methods carrying SQL across 12 files"*. Measured by AST over
the mixin classes with docstrings excluded, this tree has **142 across 19**. The document carries the
measured figure with the method that produced it, and says so in a parenthesis rather than silently
substituting one number for another — the A3 lesson applied the first time it came up again.
