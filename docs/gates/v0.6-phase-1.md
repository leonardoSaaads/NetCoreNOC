## Gate checks

### 1. The scope document is complete and matches the mandate

Five in-scope items (the `LinkScorer` seam; Tier A parameters with preview/apply/rollback; the
`OPTICORR_*` removal; the security review; the v0.7/v0.8 specifications), the deferred list in the
mandated order, and the nine hard constraints reproduced as build-failure conditions. Nothing
outside those five appears as work; everything else that surfaced during Phase 1 became a ROADMAP
line (nine of them).

### 2. The resequencing is recorded as a decision, not an omission

DECISIONS **#43** states the reason explicitly: the three surfaces have three different risk
profiles — engine (gated by exact parity), HTTP security perimeter (gated by the authorization
matrix and 404-not-403 evidence), and a new runtime dependency plus trust surface (gated by
sandboxing and determinism evidence). A parity gate only means something when nothing else in the
release can move a number, which is the concrete reason scoring ships alone.

DECISIONS **#44** records that Tier B was **rejected**, not deferred: `LinkScorer.score` is
specified pure, deterministic, side-effect-free and inference-only, which forecloses an outbound
call at the type level. The threat model records the three Tier-B threats under "Rejected by
design" rather than as controls — a deliberately stronger statement.

### 3. `EXTENSIBILITY-0.6-DRAFT.md` is superseded in place, not rewritten

The original body is byte-for-byte intact. Two additions bracket it: a disposition box at the top
(table of all five dispositions plus three corrections the reader must carry into the old text)
and a "what actually happened" section at the bottom. The three corrections are the ones that
matter for a reader who trusts the old text:

1. The draft's "optionally editor, if the admin delegates" was **deliberately not implemented** —
   preview and write are admin-only with no delegation.
2. The predicted P2 tidy was indeed not applied in v0.5.0 (confirmed in Gate 0 §5) and is the
   first step of S1.
3. v0.6.0 delivered an *interface*, not just configurable constants.

### 4. The governance spec names the tenant-isolation limit — mandatory

`GOVERNANCE-0.7-DRAFT.md` carries a dedicated, flagged subsection:

> **⚠ Visibility scoping is a presentation control and is NOT tenant isolation**

It then states the three concrete reasons rather than asserting the slogan: the `A`/`E` matrices
are global so a storm on one customer's NEs shapes another's grouping; situations are connected
components computed *before* scoping, so a scoped viewer can see a situation whose membership is
influenced by alarms they cannot see; and aggregate counters, edge weights, timing, and situation
ids remain global side channels. It also states that true multi-tenant isolation would change the
engine, the schema, and the eval methodology, and requires the limit to appear in
**operator-facing** text, not only in the spec. A documentation test is specified for v0.7.0 so
the statement cannot be quietly dropped.

### 5. The plugins spec confirms the contract accommodates ONNX and entry points

`SCORER-PLUGINS-0.8-DRAFT.md` §3 maps each v0.6.0 contract element to its v0.8.0 use:
`Protocol` (structural, no registry change), `scorer_id`, `contract_version` (major-version
refusal), `params_fingerprint` (artifact SHA-256 for ONNX), `LinkFeatures`' reserved optional
slots (populating them is a *minor* bump per DECISIONS #49), variable-length `LinkScore.terms`,
the pure/deterministic/inference-only `score()` signature, the fail-safe fallback and
`scorer.fallback` audit action, and the append-only config + pointer + rollback storage.

**The one schema change v0.8.0 will need is named up front**: `link.term_t/term_a/term_e` are the
*default* scorer's projection (DECISIONS #50), so a scorer with a different term set needs a
`link_term` child table or a JSON column — additive and forward-only. Naming it here is what makes
"no breaking contract change" an honest claim rather than an optimistic one.

The spec is also honest where honesty costs something: floating-point non-associativity across
runtimes/BLAS/thread-counts is called out by name, the mitigations are listed
(single-thread/FP32/CPU/pinned-opset plus a recorded reference vector re-checked at load), and the
guarantee is stated as *reproducibility on a given host and runtime version*, not bit-identical
scores everywhere — which is why the eval gate continues to run against the built-in
`AdditiveScorer`, never against a customer model. The entry-point hatch is labelled **not a
security sandbox** in those words, with the reason (the plugin runs in-process with the process's
privileges; `setrlimit` and a timeout bound resource misbehaviour, not intent).
