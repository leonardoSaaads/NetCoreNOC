## 2. Fallback — a broken scorer degrades, it does not stall or crash

| Failure mode | Behaviour | Test |
|---|---|---|
| Scorer raises | falls back to coded defaults, `degraded=True`, reason recorded | `test_f25_raising_scorer_falls_back_to_the_defaults` |
| Returns no terms (contract violation) | same; reason "explainability is contractual" | `test_f25_scorer_that_returns_no_terms_is_a_contract_violation` |
| Over budget | degrades; the delegate is never called again | `test_f25_over_budget_scorer_degrades_on_the_next_call` |
| Repeated failures | degradation is sticky, counted **once** | `test_f25_degradation_is_sticky_and_counted_once` |
| Healthy scorer | never degraded, no warning | `test_f25_healthy_scorer_is_never_degraded` |
| End to end | `scorer.fallback` written **once** (system actor, `outcome=error`), correlation continues, situations still form, operator warning raised | `test_f25_engine_never_runs_scorerless_and_audits_the_fallback` |

The audit row records the exception **type**, never the message. The engine never runs
scorer-less: `SafeScorer` always has the coded default available.

**Not fully closed (F25 is `partial`).** A synchronous in-process call that never returns cannot
be interrupted from the wrapper; the budget is checked after the call completes and degrades every
*subsequent* call. Theoretical for v0.6.0 (one scorer ships and it is five floating-point
operations with no loop, no I/O and no allocation that can block); a stated **prerequisite** of
v0.8.0, where `SCORER-PLUGINS-0.8-DRAFT.md` specifies a worker process with `resource.setrlimit`.
ROADMAP line filed.

## 3. Bounds and validation

Every boundary and every degenerate combination is rejected with a precise reason and never
stored: 14 parametrised rejection cases plus the inclusive-boundary check
(`test_f20_*` in `test_scoring.py`), and 6 more over HTTP
(`test_f20_invalid_parameters_are_rejected_and_never_stored`), which additionally asserts
`COUNT(*) FROM scorer_config == 1` afterwards — the seed only.

The bounds are justified, not asserted:
`test_f20_degenerate_extremes_would_indeed_have_been_catastrophic` shows that at `threshold = 0`
an unrelated cross-NE pair 90 s apart links anyway, and at `threshold = 1.0` a perfect pair does
not link at all.

Pydantic bounds the shape (422) and `scoring.validate_params` is the semantic authority (400);
both run, and the precise reason always comes from the one validator. Live confirmation:

```
POST /api/scorer {"threshold": 0.0, …}
→ 400 "threshold must be at least 0.01, got 0.0: a threshold at or below zero links every
   candidate pair into one situation"
```

## 6. RBAC matrix

- `scorer.preview` / `scorer.write` are `admin`; editor and viewer get **403** on all three
  mutating routes (6 parametrised cases); `scorer.read` is allowed to viewer, editor and admin;
  anonymous gets 401.
- Every new route is in `ROUTE_PERMISSIONS`, so the generated `test_authorization_matrix` and the
  fail-closed `test_every_api_route_is_in_the_permission_map` both cover them without being told.
- Denied attempts are audited as `scorer.config.update` / `scorer.preview` with `outcome=denied`

  prior authority (`test_f21_config_change_grants_no_capability`).

## 12. Performance — the honest number

The seam costs something, and hiding it would have been the wrong call.

| Measurement | v0.5.0 | v0.6.0 |
|---|---|---|
| Per scored candidate pair (micro-benchmark, 300 k pairs) | 0.89 µs | **4.20 µs** (4.7×) |
| Full `make eval` corpus replay, 3 147 traps (mean of 3) | 10.45 s | **10.81 s** (+3.5 %) |

The micro-benchmark ratio and the system number tell different stories, and the system number is
the true one: scoring was never the bottleneck — BER decode, parsing and SQLite dominate. The cost
is one `LinkFeatures`, one `LinkScore` and three `TermContribution`s per pair, which is the price
of a typed, explainable, swappable contract.

It was reduced from an initial **8.4×** by making the three contract types `NamedTuple`s rather
than frozen dataclasses (DECISIONS #52) — the faster option that is also the *stricter* one, since
a `NamedTuple` is genuinely immutable. A further "trust the built-in scorer and skip the guard"
fast path was **rejected**: complicating the fail-safe wrapper, the most security-relevant code in
this release, to recover a fraction of 3.5 % is a bad trade.

**All of this is engine-side.** `receiver.datagram_received` is unchanged and is asserted to
contain no scoring, config, lock, await or DB call, and `receiver.py` is asserted not to import
`correlate`, `scoring` or `preview` at all.

### One test envelope changed — and why that is not a regression

`test_perf.py`'s p95 API-latency assertion is now skipped when a tracer is active. The
**unmodified v0.5.0 tree** breaches the same 2.0 s bound under `pytest --cov` on this machine
(2.17 s, 2.00 s) while passing comfortably without it: under a line tracer the number measures the
tracer. The bound was **not widened**, and the assertions the test exists for — zero trap loss and
audit rows written during the storm — run unconditionally in every mode. Recorded as
DECISIONS #51.
