## S1 — the ADR (DECISIONS #93)

Written **before** any document was touched. §6.2 requires the reasoning, not merely the outcome,
and all four parts are recorded:

| Recorded | Substance |
|---|---|
| **v0.8.0 is the operator-feedback dataset** | the feedback click is the only human label in the system; every later ML step consumes it, so nothing downstream can be built or honestly evaluated first |
| **Customer models → v0.13.0** | they plug into the champion/challenger framework, which does not exist yet; building the riskiest surface — a new runtime dependency and a new trust surface — before the framework that receives it inverts how this project has sequenced every release since v0.2.0 |
| **ONNX only; the entry-point hatch is REJECTED, not deferred** | ONNX is *data executed by a pinned runtime*; an entry-point scorer is *arbitrary code running as the process*. Recorded as a rejection so nobody reintroduces it as an obvious convenience — the treatment DECISIONS #44 gave the external-criterion API |
| **The worker-process preemption harness stays a blocking prerequisite** | `SafeScorer` is post-hoc: it degrades the *next* call, and a C extension that never returns has no next call. §R2 also requires the worker→parent channel not use `pickle` — a malicious pickle from a compromised worker is RCE in the parent by the back door |

**Why the order cannot be permuted** is recorded as the chain of evidence dependencies, not as a
preference: you cannot train a challenger without a label; you cannot trust the label without
knowing it is scarce and biased; you cannot declare a winner without an evaluator that never saw the
training data; you cannot automate the promotion without proof of real agreement with humans. Each
release also carries the specific failure that permuting it would cause.

Both admission criteria §6.4 warns are easy to lose are recorded in the v0.11.0 section:

* a model competes on quality **only after** passing a speed-and-explainability admission filter —
  a marginally more accurate model that threatens ingestion **loses on purpose**;
* **logistic regression is the natural front-door candidate** because it *is* the three-term formula
  with learned weights, while **tree ensembles can only enter through the ONNX door** and therefore
  cannot be champion before v0.13.0 — stated explicitly as *plumbing, not merit*, so a future reader
  does not mistake it for a judgement about model families.

## S3 — the guard, installed against the still-contradictory tree

`tests/test_documentation.py`, written before any document was fixed, and run against the tree with
the contradiction still in it.

### The mechanism (DECISIONS #94)

1. **One machine-readable source of truth** — S2's release table. Everything is checked *against*
   it; nothing is inferred from the documents.
2. **Two marked claim forms**, because they do different jobs and conflating them makes the guard
   noisy or vacuous:
   * `<!-- release-claim: vX.Y.Z = key -->` — what a release **is**. Invisible when rendered.
   * `vX.Y.Z: planned` — what a spec **element** is planned for. The pre-existing convention, kept.
   * A document that makes a claim may only tag elements for **its own** release — the half that
     actually catches a half-finished supersession.
3. **A narrow, enumerated check** for the specific contradiction, labelled in the test as *not* the
   general guarantee.

Both forms are documented in `docs/README.md` so a contributor knows the convention.

### The live/historical split, and why it exists

`SCOPE-0.6.md` says v0.8.0 is customer models. That is not a defect — it is what v0.6.0 believed,
and `DECISIONS.md` is append-only by its own charter. Rewriting either would falsify a record, which
is the opposite of the supersede-in-place rule this release follows. So `scope/`, `adr/`, `gates/`,
`releases/` and the per-release security reviews are excluded, and — because that exclusion is the
guard's biggest risk — the excluded set is itself asserted, including that `architecture/` can never
join it.

### Two design bugs the guard found in itself

Both surfaced when the fixed documents were re-run, and both are recorded because they are the
difference between a guard and a nuisance:

1. **Fenced examples were parsed as real claims.** `docs/README.md` *documents* the claim form, so
   it contains a fenced `<!-- release-claim: v0.8.0 = ... -->` example — which made the index appear
   to specify v0.8.0. Fixed by stripping fenced blocks and inline code before claim parsing, which
   is precisely what `test_structure.py::_strip_code` already does for links ("a `[text](target)`
   written as documentation-about-links must not be treated as a link"). Same precedent, same fix.
2. **Historical quotation fired the element-tag check.** The supersession box's then/now table
   quoted `` `v0.8.0: planned` `` in its "then" column, and the guard read it as a live tag.
   Resolved by a convention rather than a special case: **the marked forms are reserved for live
   assertions; a historical mention is written as prose.** Stated in `docs/README.md`.

The forbidden-phrasing check deliberately keeps **inline code** (only fenced blocks are stripped),
because the phrases it hunts are filenames and filenames are written in backticks — stripping them
would blind it to exactly what it looks for.
