# v0.8.1 — Gate 3: the tiers and the persistence

## S1 — the audit sweep

`store/dataset.py::prune_dataset` becomes **`prune_dataset_audit`**, and it now deletes `feedback`
as well as the pairs and observations it always did. It is called from two places, both bounded by
a number the operator set:

* `capture.Capture.prune`, on the maintenance tick — the background sweep;
* the explicit admin reduction of the audit bound, which previews first and is audited.

**A name collision `mypy --strict` caught, and it mattered.** The first name was `prune_audit` —
which already exists on `AuditLogMixin` as the audit-**log** deleter (the one sanctioned deleter,
DECISIONS v0.2 #3). Both are mixed into one `Store`, so the new method would have **silently
shadowed audit-log retention**:

```
src/netcorenoc/store/__init__.py:67: error: Definition of "prune_audit" in base class
  "DatasetMixin" is incompatible with definition in base class "AuditLogMixin"  [misc]
```

Renamed to `prune_dataset_audit`, which names both subject and tier and cannot collide.

Deletion order inside the sweep is **pairs → observations → labels**, so a crash mid-sweep leaves
features without a label — a state the report already measures and names — rather than a label whose
evidence has silently gone.

`engine.py` gains **zero lines**: `capture.prune_sink(...)` becomes `capture.prune(...)`, one call
doing both background bounds. The file is still exactly **580**, its `COHESION_EXEMPT_CEILING`,
which this release does not raise.

## S2 — the training window selects, and the preview says which tier destroys

* `bias.py` applies the window as a `WHERE` clause and reports **`pairs_in_training_window`** and
  **`pairs_outside_training_window`**. Anchored on the newest promoted row, never the wall clock,
  so the report stays reproducible and can remain a byte-for-byte gate.
* `POST /api/dataset/retention` now cuts on **`audit_days`**, not `training_days`. v0.8.0 cut on the
  training bound, which made the middle tier the destructive one and left the preview reporting a
  `labels` figure the apply never deleted. Both responses now carry `"bound": "audit"` and
  `"training_deletes": 0` — additive fields; nothing existing changed shape.

## S3 — the policy is persisted

One `meta` value, `config.dataset_retention`, written in the **same transaction** as the audit row
and the deletion, so the record and the policy cannot disagree. **No migration.**

Loaded in `maintenance.py::_capture_run` — the documented configuration reload point, already called
from `Engine.start` and from the top of every maintenance pass. That placement costs `engine.py`
nothing and means a policy written by one process is picked up by another, with the resulting pair
rows correctly attributed.

The fail-safe warning goes to **`store.integrity_warnings`**, the existing channel for damaged
durable state, which `runner.py` already surfaces — so the engine needed no new field.

## The gate's four assertions

```
tests/test_dataset.py -k "survives_a_fresh_engine or corrupt_stored or four_passes or
  audit_sweep_deletes or training_window_destroys or shipped_default or cleared_when_repaired"
====================== 11 passed, 34 deselected in 1.58s =======================
```

| Gate 3 requires | Test | Result |
|---|---|---|
| four passes past the **training** bound delete nothing | `test_four_passes_past_the_training_bound_delete_nothing` | pass — pairs and label both intact after 4 passes at +500 days |
| four past the **audit** bound delete exactly the rows outside it **and nothing newer** | `test_the_audit_sweep_deletes_outside_its_bound_and_nothing_newer` | pass — two cohorts 1000 days apart, bound falls between; only the old cohort and its label go, and the sweep's count is asserted |
| a policy set through the route is in effect after a **fresh `Engine` over the same `Store`** | `test_a_policy_set_through_the_route_survives_a_fresh_engine` | pass |
| a corrupt stored value falls back to the shipped default **with a warning** | `test_a_corrupt_stored_policy_falls_back_to_the_shipped_default_and_warns` | pass — 5 parametrised cases |

The corruption cases are deliberately not all "bad JSON": malformed text, `{}`, a **partial** object,
a **wrong-typed** field, and a stored **ordering violation** (`sink >= training` — valid JSON, valid
types, illegal policy). The last is the one that matters most: it proves `validate()` runs on the
*stored* value rather than being trusted from the write path.

Two further tests hold properties the gate implies but does not name:
`test_nothing_stored_means_the_shipped_default` (zero-config stays silent) and
`test_the_fallback_warning_is_added_once_and_cleared_when_repaired` — `_capture_run` runs every five
seconds, so a warning that appended each pass would flood `/api/stats`, and a repaired policy must
not leave a stale complaint behind.

## Assertions changed in existing tests, with justification

`tests/test_dataset.py::test_the_maintenance_loop_prunes_the_sink_and_never_the_dataset` — its clock
was `TS + 10**9` (~31 years), so under DECISIONS #110 the audit sweep now correctly collects its
rows. Rewritten rather than deleted: it now runs at **+60 days** — past the sink's 21 days, far
inside the 730-day audit bound — and asserts the half of directive 9 that survives, *"the loop may
not destroy labelled rows inside the audit bound."* The boundary itself is held by the two new tests
above. No assertion was weakened; one was made specific about *which* bound it was testing, which
the original could not distinguish because only one bound existed.

### One structural change, recorded rather than smuggled

`RetentionPolicy` moved to `src/netcorenoc/retention_policy.py` (**DECISIONS #113**). `capture.py`
was at 374 of 400 and this release legitimately needed ~44 more lines there. The alternatives were
trimming the reasoning out of docstrings on a data-destroying policy (which DECISIONS #108 explicitly
rejected as *"makes the code worse to satisfy a number"*), putting `capture.py` on `DEBT_ALLOWLIST`
(which must stay empty), or raising a second ceiling in two releases. `capture.py` re-exports every
name, so **no import site anywhere else in the tree changed** — the arrangement `MAX_CLIENT_MEMBERS`
already has. One `LAYER_OF` entry added; the new module imports nothing from the package, so it
cannot violate the dependency direction.
