## 1. A1 — the cycle rule resolves to the wrong minimum

### 1.1 The claim, and the code

`incidents.resolve`'s docstring:

> **A cycle resolves to the minimum id in the cycle**, not to wherever the walk happened to stop.
> […] two bags entering the same cycle at different points would otherwise be assigned different
> incidents, so a corrupt chain would silently *inflate* the incident count — the exact error the
> transitive resolution exists to remove, re-entering through the failure path.

The code (`src/netcorenoc/incidents.py:98`):

```python
        if nxt in seen:
            return Resolution(min(seen), cycle=True)
```

`seen` is the **whole walk**, not the cycle. It contains the *tail* that led into the cycle. When a
tail id is smaller than every member of the cycle, `min(seen)` is a tail id, and the tail resolves to
itself while the cycle members resolve to the cycle minimum — which is the docstring's own failure
mode, produced by the line that claims to prevent it.

### 1.2 Reproduced by execution

```python

    print("  distinct:       ", m.incidents)
    print("  cycles flagged: ", set(sorted(m.cycles)), "\n")

    "CONTROL — every entry point IS a cycle member (the existing test's fixture)",

    "DEFECT — two tails into one cycle disagree with each other",

)
```

**Two distinct incidents where there is one, and three where there is one.** The situations are all
flagged `cycle`, so §7.9 would exclude them — but the *count* they are excluded from is already
wrong, and `IncidentMap.incidents` is the `n` every clustered estimate in this project is expressed
in.

### 1.3 Why the existing test did not see it

`tests/test_incidents.py::test_every_entry_point_into_one_cycle_gets_the_same_incident` fixes
`{301: 302, 302: 303, 303: 301}`. **Every entry point in that fixture is a cycle member**, so
`seen == the cycle` at every call and `min(seen) == min(cycle)` by coincidence of the fixture rather
than by the code. The tail case is outside the instrument.

The test is not a bad test. It kills the obvious mutation — `min(seen)` → `current` — and v0.10.0's
mutation ledger records exactly that (`A7  cycle resolved to the stop point   KILLED (2 failed)`).
Re-verified here on the shipped tree:

**A test's fixture is part of the guard, and a guard is only as wide as the inputs it was watched to
fail on.** This is Appendix B's entry in a fourth place.

### 1.4 Severity, stated in both directions

**Exploitability: low, and it is currently unreachable.** `engine.py:466` does `sid = min(sids)` and
merges into the *smaller* id, so `merged_into` always points downward, every chain is strictly
descending, and **no cycle can be written through the live path today**. Nothing an operator or an
API client can do produces one.

**Correctness of a measurement: high.** This is a guard for the case where that property fails —
a hand-edited database, a future merge policy that does not pick the minimum, a restore from a
partial backup — and the guard is not merely untested but **wrong**. It is the same argument that
made the perimeter's fail-open branch worth a test in v0.9.2: the value of a fail-safe path is
entirely in the case nobody expects to reach.

Issued as **F50** in `../security/SECURITY-REVIEW-0.10.1.md`.

## 2. A2 — the detection-threshold conclusion runs backwards

### 2.1 What v0.10.0 concluded

`DECISIONS #142` and `SECURITY-REVIEW-0.10.0.md` §3.2: the plan's minimum-detectable-difference
table *"does not reproduce below n = 120"*, on a closed form giving **0.298** at `n = 37` and a
Monte-Carlo giving **0.33**, against **0.25** registered — and therefore *"the plan's small-`n`
figures are optimistic"*.

### 2.2 The variance assumption

The shipped closed form (`shadow_cv.py:214`) is

```
delta = (z_α/2 + z_power) · sqrt(2 · p(1−p) / n)
```

The `2 ·` gives **both** groups the variance of the base rate `p = 0.70`. But the second group sits
at `p + delta`, and when `delta` is large — which is exactly the small-`n` regime — its variance is
much smaller than `p(1−p)`. The form therefore **demands a larger delta than reality**, and the
error grows as `n` shrinks.

### 2.3 Reproduced by execution

The variance-correct form is the fixed point of

```
delta = (z_α/2 + z_power) · sqrt((p(1−p) + (p+delta)(1−p−delta)) / n)
```

reached by iteration from the naive value. The Monte-Carlo shares **no arithmetic** with either: it
draws two binomials at `p` and `p + delta`, runs a two-sided pooled z-test at α = 0.05, and searches
upward on a 0.001 grid for the smallest `delta` whose rejection rate over 4 000 trials reaches 0.80.
It uses a xorshift64\* generator, deliberately a different generator from the LCG in `shadow_cv.py`.

Both halves of the reproduction ship as code in Gate 1 — the variance-correct form as
`shadow_cv.minimum_detectable_difference`, the search as the Monte-Carlo pin in
`tests/test_shadow_cv_power.py` — so the measurement below is re-run by `make test` on every future
release rather than living only in this document. **The next disagreement should be detected, not
argued.**

```
    n   p+delta   var(g1)   var(g2)        naive   var-correct   indep MC   plan
   37     0.938     0.210     0.058        0.298         0.238      0.237   0.25
  120     0.849     0.210     0.128        0.166         0.149      0.150   0.16
  300     0.799     0.210     0.161        0.105         0.099      0.099   0.10
```

**The variance-correct form and the independent Monte-Carlo agree to within one grid step at all
three sizes, and they bracket the plan's registered figures rather than exceeding them.** At
`n = 300` the second group sits at 0.80 and the two variances are close (0.210 against 0.161), so the
naive form is nearly right — which is precisely why it *appeared* to agree at large `n` and disagree
at small `n`. The disagreement was never about the plan. It was about the formula.

### 2.4 Controls

```
CONTROL — the naive form and the variance-correct form must DIFFER, and by more at small n:
  n=   12  naive-minus-correct = +0.1535
  n=   37  naive-minus-correct = +0.0601
  n=  120  naive-minus-correct = +0.0170
  n=  300  naive-minus-correct = +0.0063
  n= 1000  naive-minus-correct = +0.0018

CONTROL — both forms must fall as n rises:
  naive              strictly decreasing: True
  variance_correct   strictly decreasing: True

CONTROL — the gap must be smallest at p = 0.50, where the base rate sits at the maximum-variance
          point and the second group's variance falls furthest only after moving far from it:
  p=0.50  n=37  naive=0.326  correct=0.296  gap=+0.0299
  p=0.70  n=37  naive=0.298  correct=0.238  gap=+0.0601
  p=0.90  n=37  naive=0.195  correct=0.138  gap=+0.0572
```

The first control is the one that matters: **if the two forms returned the same numbers the
correction would be measuring nothing**, and the monotone growth of the gap as `n` falls is the
signature of the variance term rather than of an arithmetic slip.

### 2.5 Why v0.10.0's own Monte-Carlo did not catch it

v0.10.0 reported a Monte-Carlo of **0.33** at `n = 37` — *higher* than the naive form, where the
correct answer is *lower*. **Two methods that share an assumption are not two methods.** Whatever
that search did — applying the base-rate variance to both arms, or using a more conservative
rejection criterion — it did not provide independent confirmation, and its agreement with the closed
form is what made the wrong conclusion look corroborated.

The v0.10.0 harness is not in the tree, so this cannot be diagnosed further than that; what is
recorded here is the measurement, and §2.4's first control is the instrument that would have caught
it.

### 2.6 The direction, and what it does and does not change

**Nothing about v0.10.0's verdict changes.** A *lower* true threshold makes the power condition
`observed > detectable` **easier** to satisfy, so `INSUFFICIENT_EVIDENCE` was reached on a floor
failure and would have been reached anyway. What changes is that the trigger was **more conservative
than intended** — a future release with a real corpus would have been told it could not resolve a
difference it actually could.

The plan is **not touched.** §8 forbids editing it, it is hash-guarded, and the table is a *reported
quantity and a verdict trigger, never a floor* — nothing registered depends on the number.

## 3. A3 — the coverage figure does not reproduce, and the cause is arithmetic

### 3.1 What was recorded, and what runs

`docs/gates/v0.10.0-phase-7.md` §coverage:

```
$ python -m pytest -q --cov=netcorenoc --cov-report=term
TOTAL   6666 stmts   186 miss   1462 branch   123 partial   96%
exact: 96.20%
```

The same command on the same tree, this build:

```
$ .venv/bin/python -m pytest -q --cov=netcorenoc --cov-report=term
TOTAL                                      6666    186   1462    123    96%
Required test coverage of 85.0% reached. Total coverage: 95.95%
1174 passed in 451.68s (0:07:31)
```

**Every count reproduces exactly** — 6666, 186, 1462, 123 — and the percentage does not.

### 3.2 The cause

It is neither `term` versus `term-missing`, nor a `.coveragerc` interaction (there is no
`.coveragerc`; the configuration is `[tool.coverage.*]` in `pyproject.toml`), nor plugin ordering.
**`96.20 %` was never a coverage.py output.** It is what you get by computing the percentage *by
hand from the four printed columns*, and the `BrPart` column is not the number the percentage
divides by.

From the same run's JSON report:

```
$ .venv/bin/python -c "import json; print(json.load(open('cov.json'))['totals'])"
  covered_lines               6480
  missing_lines               186
  num_statements              6666
  num_branches                1462
  num_partial_branches        123      <- the BrPart column
  missing_branches            143      <- what the percentage divides by
  percent_covered             95.95226377952756

coverage.py's own arithmetic : (6480 + (1462 - 143)) / (6666 + 1462) = 7799/8128 = 95.9523%
the v0.10.0 hand-arithmetic  : (6480 + (1462 - 123)) / 8128 = 7819/8128 = 96.1983%
```

`96.1983` → `96.20`, to the digit.

**`BrPart` counts partially-covered *statements*; the percentage divides by missing branch *arcs*.**
A statement with two unexercised exits contributes **1** to `BrPart` and **2** to `missing_branches`.
On this tree those two numbers are 123 and 143, and the twenty-arc difference is the whole
0.25-point discrepancy.

### 3.3 The baseline is the second half of the finding

Every release before v0.10.0 recorded the figure **from coverage.py's own line**:

| release | recorded | source line |
|---|---|---|
| v0.7.5 | 95.99 % | `Required test coverage of 85.0% reached. Total coverage: 95.99%` |
| v0.8.0 | 95.95 % | `                                 Total coverage: 95.95%` |
| v0.9.1 | 96.11 % | `pytest 960 passed in 409.47s — coverage 96.11%` |
| v0.9.2 | **96.19 %** | `Required test coverage of 85.0% reached. Total coverage: 96.19%` |
| v0.10.0 | 96.20 % | **`exact: 96.20%` — computed, not printed** |

**v0.10.0 is the only release that reports a hand-computed figure**, and it is the release whose
figure does not reproduce. The `96.22 %` it measures itself against appears in this repository only
as *"the brief asks for coverage at or above 96.22 %"* — there is no run in `docs/gates/` that
produced it.

So the comparison the release actually owes its reader is against **v0.9.2's 96.19 %**, which came
off the same line of the same tool. That like-for-like measurement is taken in Gate 1 §3 rather than
argued here.

### 3.4 One thing found while looking

`census.first_label_per_incident` contains

```python
    identity = await resolve_identity(store, bags, [])
    ...
    _ = identity
```

`resolve_identity` stamps `bags` in place and the returned map is never read. `_ = identity` is a
discarded computation that exists to keep the name used — a leftover rather than a design, and the
kind of line a dead-code gate is deliberately unable to see. Removed in Gate 1; no behaviour change,
and `census.py` is 78.57 % covered, the largest single contributor among v0.10.0's new modules.
