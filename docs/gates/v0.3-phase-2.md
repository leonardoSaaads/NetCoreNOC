## What the migration does (additive, forward-only, `user_version` 2 → 3)

- Adds `ne` (one row per device, ids preserved so `alarm.ne_id` backfills from `device_id`),
  `entity` (one level-0 entity per NE: `parent_id NULL`, `level 0`, `key = ip`,
  `key_source = 'self'`, `confidence = 1.0`), `ingest_gap`, and `varbind_profile`.
- Augments `alarm` with nullable `ne_id`, `entity_id` (backfilled to the level-0 entity),
  `severity`, `severity_rank`, and adds `UNIQUE (entity_id, class_id, instance)` as an index
  alongside the retained v0.2.0 `UNIQUE (device_id, class_id, instance)`.
- `device_id` is retained and kept in sync for one version (its removal is a v0.4.0 line).

The store now records `ne_id`/`entity_id` on every ingested alarm via `Store.ne_id` and
`Store.entity_level0` (S3, level 0 only): the dedup key and correlation are still device-based,
so this is a pure refactor. The evaluation harness confirms **exact parity** with the frozen
baseline — every aggregate delta is `+0.0000`.

Rationale for the additive approach (Decision 22): SQLite cannot ALTER a constraint in place,
and rebuilding `alarm` (which `situation_alarm` and `link` reference) needs FK-toggling inside
the migration and would break every unmodified v0.2.0 store the moment it lands. Additive keeps
the whole v0.2.0 suite green and applies cleanly onto populated data; the two unique keys never
conflict because an alarm's `instance` always carries its entity's discriminator value.

## Gate 2 checklist — migration applies to a populated v0.2.0 database

Proven by `tests/test_migration.py::test_migrate_populated_v020_database_with_audit_chain`,
which builds a real v0.2.0 DB (migrations 0001+0002, `user_version=2`) with two devices, three
alarms, a situation, a link, and a **live two-entry audit hash chain**, then upgrades it:

1. **Schema advances** — `PRAGMA user_version` is 3. **PASS.**
2. **Data intact** — 2 devices, 2 active alarms, 1 open situation survive. **PASS.**
3. **Entity model backfilled** — 2 NEs, 2 level-0 entities; every alarm has `entity_id` and
   `ne_id = device_id`; every level-0 entity is `self` / confidence 1.0 / key = its NE's IP.
   **PASS.**
4. **New UNIQUE index enforced** — a duplicate `(entity_id, class_id, instance)` insert is
   rejected. **PASS.**
5. **Audit triggers still active** — a `DELETE FROM audit_log` still aborts with
   `audit_log is append-only`. **PASS.**
6. **Audit chain still verifies** — `audit.verify_chain` returns ok over the 2 pre-existing
   entries after the schema change. **PASS.**

The v0.1.0 → v0.2.0 → v0.3.0 path is also covered
(`test_migrate_populated_v010_database` now reaches `user_version 3` with the entity model
backfilled) and the migration is idempotent across repeated opens.
