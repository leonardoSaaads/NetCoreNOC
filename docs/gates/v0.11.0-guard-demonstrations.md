# v0.11.0 — the demonstrated guards

**A guard nobody has watched fail is not a guard.** Every guard this release adds is shown red under
an injected defect, then green on restore, with a **control that had to pass in both** — so a red
that came from breaking the suite generally is distinguishable from a red the guard actually caught.

The shape is `v0.10.1-guard-demonstrations.md`'s, inherited exactly: the guard named with its test
id, the defect as a diff against the corrected tree, the command, the verbatim RED, the verbatim
GREEN, and the control.

Command, for every entry:

```sh
python -m pytest -q --no-header -p no:cacheprovider <test id>
```

## 1. The two refusals collapsed into one condition

**The collapse the whole release exists to prevent.**

```diff
--- a/src/netcorenoc/promotion.py
+++ b/src/netcorenoc/promotion.py
-    if judgement.verdict is not Verdict.INSUFFICIENT_EVIDENCE:
-        raise PromotionPathError(
-            f"the INSUFFICIENT_EVIDENCE refusal was asked to describe a {judgement.verdict.name} "
-            "verdict. These are opposite claims and one message may never stand for the other."
-        )
+    if judgement.verdict is Verdict.BETTER:
+        raise PromotionPathError('better is not a refusal')
```

**RED**

```
FAILED tests/test_promotion_gate.py::test_neither_refusal_message_is_producible_by_the_others_condition
1 failed in 0.22s
```

**CONTROL** (`test_the_insufficient_evidence_refusal_is_reachable_and_says_what_it_must`) — `1 passed in 0.33s` under the injection. The refusal still *works*; only the distinction is gone, which is exactly the failure a reachability test alone would miss.

**GREEN** — `1 passed in 0.19s`.

## 3'. §14 — a promotion applied with no `challenger_run_id`, and the gap the injection found

**The first run of this injection produced no red at all**, and the reason was not that the guard
was weak: **there was no guard.** The rule lived inline in the route handler, and on the real corpus
the verdict is `INSUFFICIENT_EVIDENCE`, so `applied` is `False` either way and no test could reach
the branch.

That is precisely the failure mode Part XI names — *"where you write 'a test that guarantees X', ask
whether you would know how to write that test"*. The answer here was no, until the rule moved.

**The repair**: `promotion.missing_run_refusal` is now a function with the same verdict guard its two
siblings carry, and it is unit-tested directly. Re-injected as `if False and not decision.may_apply:`:

```
RED   : FAILED tests/test_promotion_gate.py::test_the_missing_run_refusal_cannot_describe_a_verdict_that_never_permitted_a_promotion
        1 failed, 23 passed in 1.24s
GREEN : 24 passed in 1.17s
```

**This is a third refusal and it is deliberately not one of the plan's §4 pair.** The evidence is
sufficient and the challenger won; what is missing is the *provenance*. Keeping it separate is the
same discipline that keeps the other two apart.

**The injection**: `asserting_bag_rows`'s predicate widened from `excluded_reconciled >= 1` to
`>= 0`.

```

GREEN : 5 passed in 1.73s
```

**Not caught.** So the measurement was widened to the whole suite:

```
$ python -m pytest -q          # with the predicate widened to >= 0
1296 passed in 270.86s
```

**Every test in the repository stays green.** `asserting_bags` is `PREREGISTRATION-0.10.0.md` §2.2's
**PRIMARY floor**, and the predicate that decides what counts toward it was unguarded. A widened
predicate counts bags asserting **nothing** — it is F46 in a new place: *a threshold counting a
quantity other than the one it names.*

**Why nobody noticed**: on this corpus the verdict does not change (13 split bags is still below 50
either way). The release's headline outcome is insensitive to it. **A larger corpus would not be**,
and this release is the one that makes the floor decide something.

## 5. The injection this release could not perform, stated rather than omitted

**`incumbent_linked` used as truth where a human verdict is missing.**

The mandated injection assumes there is a place to inject it. There is not: **no expression in
`src/netcorenoc/` reads `incumbent_linked` on any path that reaches a promotion decision.** The
column exists in the shadow tables and is read by the shadow report; the promotion gate's inputs are
`asserting_bag_rows`, the incident map and the four named quantities, none of which touches it.

Injecting *"use `incumbent_linked` as truth"* would therefore mean **writing the defect first** —
adding a call that does not exist and then showing a test catches it. That is a demonstration of the
test, not of the code, and it would report a guard the tree does not actually have.

**What is asserted instead**, and it is the honest form of the same claim: `tests/test_shadow.py`'s
pre-existing guard that no training or decision path consumes `incumbent_linked`, plus the fact that
the promotion gate takes its inputs as explicit parameters that a reader can enumerate. **This is
named as a limitation in `SECURITY-REVIEW-0.11.0.md`, not as a passed check.**

## 6. The mutation ledger — survivors by name, not a ratio

Run over this release's own surface: `promotion.py`, `evaluation_folds.py`, `model_version.py`,
`store/promotion.py`, `api/routes_promotion.py`, and the dispatch branch of `scorer_lifecycle.py`.

**The ratio is deliberately not reported.** A ratio invites tuning; a survivor list invites a
decision about each survivor.

| survivor | disposition |
|---|---|
| `LOGIT_MARGIN = 0.01` → `0.0` | **Accepted.** The margin is the boundary case, and rule 4 still refuses `threshold >= high`. Killing it needs a payload whose threshold sits within 0.01 of the attainable maximum — a fixture chosen to kill a mutant rather than to describe a model. |
| `deciding_quantity`'s `> 0.95` → `>= 0.95` | **Accepted.** §6.7's "near 1.0" is a judgement the plan states in words; no registered threshold makes 0.95 exact, and pinning it would encode a number the plan did not register. |
| `MAX_PROMOTION_HISTORY = 50` → any other bound | **Accepted.** A display limit. |
| `run_id_for`'s `[:32]` truncation → `[:31]` | **Accepted.** Any injective truncation works; the length is a readability choice, and its collision behaviour is not what any test claims. |
| `Quantity.difference`'s sign | **Killed** by the `NOT_BETTER` message assertion (`+0.2000`). |
| every degeneracy rule's comparison | **Killed** — §5–8. |
| the `evaluation_fold` `PRIMARY KEY` ordering | **Accepted.** `(run_id, incident_id, repeat)` versus another order changes no behaviour any caller depends on; the read orders explicitly. |

**Limitations of this ledger**, stated because a ledger without them reads as a coverage claim:

* It is a **manual** ledger over a named surface, not an automated run over the whole package. It
  finds what its author thought to try, which is exactly the bias §4 above caught in a different
  guard — and §4 is the honest measure of how much this section is worth.
* **The four accepted survivors are all constants**, and a constant nobody pinned is a constant a
  later release can move without noticing. They are listed so that is a recorded decision.
* Nothing here mutates SQL. `0013`'s `CHECK`s are exercised by attempted violation (§4, Gate 2 §2)
  rather than by mutation, and the two are not equivalent — a mutation ledger over SQL text is not a
  technique this project has.
