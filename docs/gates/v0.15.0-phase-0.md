## 1. The fence: the tags, and why the release stops here

### 1.1 What the remote actually has

```
$ git ls-remote --tags https://github.com/leonardoSaaads/NetCoreNOC

e367a99319e2bbd510d8b4c7a62af9963a80e4fc	refs/tags/v0.12.0^{}
```

**Only `v0.12.0`, exactly as the brief states.** `v0.13.0`, `v0.14.0` and `v0.14.0-gate0` are absent.
This is the **eighth** occurrence of a release ending without an immutable reference on the remote,
and the seventh was recorded one release ago in `TAG-RECOVERY.md` §v0.14.0.

### 1.2 What this clone arrived with, and how the tags were recovered

```
$ git tag -l
(empty — this clone, like v0.10.1's and v0.14.0's, arrived with no local tags at all)
```

The three tag objects exist in the `.git` directory shipped inside the v0.14.0 archive, and were
recovered into this clone by the mechanism `TAG-RECOVERY.md` §7 already documents:

```sh
$ unzip -q NetCoreNOCv0.14.0.zip 'NetCoreNOC/.git/*' -d /tmp/zipgit
$ git fetch /tmp/zipgit/NetCoreNOC/.git 'refs/tags/*:refs/tags/*'
 * [new tag]         v0.13.0       -> v0.13.0
 * [new tag]         v0.14.0       -> v0.14.0
 * [new tag]         v0.14.0-gate0 -> v0.14.0-gate0
```

**The tags exist nowhere else.** Deleting the working tree's copy of any document before they are
published would turn this release's cleanup into permanent loss, which is the whole reason Phase 0
ends in a halt.

### 1.3 The candidates, and how each was identified

All three are **annotated** tag objects, so each carries its own message and each dereferences to a
commit:

    printf '%-15s obj=%s type=%s commit=%s\n' "$t" \
      "$(git rev-parse $t)" "$(git cat-file -t $(git rev-parse $t))" "$(git rev-parse $t^{commit})"

v0.14.0         obj=4361459d97b1918e5e5194d14d5c1b85d1a09375 type=tag commit=6dd7fcd602679f69e09a2bb749f8ecc613bb8686

They were not *chosen*; they were **recovered as objects**, which is a stronger position than the
six recoveries of `TAG-RECOVERY.md` §2, where a commit had to be inferred from a branch name. Each

checked.

### 1.5 The one thing that makes this push safe, and it is new

```
$ for t in v0.13.0 v0.14.0 v0.14.0-gate0; do
    git merge-base --is-ancestor $(git rev-parse $t^{commit}) 3ecf237 && echo "$t YES" || echo "$t NO"
  done
v0.13.0 YES
v0.14.0 YES
v0.14.0-gate0 YES
```

**All three commits are already reachable from the remote's `main`.** The push therefore transfers
three small tag objects and **no commits, no branches and no history**. Every previous entry in
`TAG-RECOVERY.md` had to reason about rebases orphaning tags; here there is nothing to orphan,
because the history is already published and only the labels are missing.

> **A correction, stated plainly because it changes what the maintainer is being asked to do.** This
> clone's `origin/main` remote-tracking ref and its local `main` branch both sit at `c31817c` (PR
> #16) and are **stale**. Read from them alone, `v0.14.0`'s commit looks unreachable from `main` and
> the push would look like it carried a release's worth of history. The live `git ls-remote --heads`
> above is the authority: remote `main` is `3ecf237`, and the v0.14.0 work is already on it.

### 1.6 One choice left to the maintainer

`v0.14.0` points at `6dd7fcd`, the **release-branch tip**, not at the merge commit `3ecf237`.
`TAG-RECOVERY.md` §4 prefers the merge commit; the maintainer's own existing tags (`v0.12.0` →
`e367a99`) point at branch tips. **Both capture the byte-identical tree `e2542cc`**, so nothing
about the released content depends on the choice. §0 tags the recovered objects as they are —
substituting `3ecf237` for `6dd7fcd` is equally correct and the §0 verification passes unchanged.

### 3.1 The citation rule, verified rather than assumed

A first pass counted only the explicit `DECISIONS #N` / `ADR #N` forms and undercounted `src/` by
five, because the repository also writes `DECISIONS **#191` (bolded) and wraps citations across
lines. So the rule was checked instead of chosen: every `#N` token in `src/` and `tests/` was
scanned for a nearby `DECISIONS`/`ADR` anchor, and the five occurrences without one were read by
hand —

```
src/netcorenoc/engine_base.py:25      "#88's objection was to …"
src/netcorenoc/store/audit_log.py:71  "(DECISIONS v0.2\n        #3)"
tests/test_findings.py:178            "(DECISIONS v0.3 #29)"
tests/test_security_ui.py:612         "#38 fixed the UI …"
tests/test_shadow_cv_power.py:218     "… runs opposite to #142"
```

— and all five are ADR citations too. Every such number falls in 1…196. **In this repository a `#N`
token is an ADR citation**, and the census counts it as one.

### 3.2 Why this is the constraint that shapes V.3

**183 citation sites across 70 files in `src/`.** These are docstrings and comments in shipped code.
`docs/adr/DECISIONS.md` is not a document those files link to — it is a document they **address**.
Renumbering breaks 183 references in code that ships to users, which is why Prime Directive 5 exists
and why the condensation may rewrite prose and may not touch a number.

### 3.3 The supersession count is 2, not ~12 — and the difference is a rule, not an error

The brief's V.3 gives ~12 entries "superseded by a later entry", each to collapse to one line:
*"Superseded by #M."* and nothing else. **Measured, there are two:**

```
#99   superseded by #167   [24 lines, cited live]
#142  superseded by #154   [28 lines, cited live]
```

The reason the number is so much smaller is that **this project supersedes in place and never
rewrites** — DECISIONS #102's rule, which #154 and #167 and #183 each restate when they use it:

> `## 154. The detection threshold was pessimistic, not the plan optimistic — superseding #142`
> — **Supersedes #142**, which stays exactly as written. A correction to an append-only ledger is an
> **addition**.

So a superseded entry carries no "Superseded by" marker of its own; the *superseding* entry names
its target. Both of the two are cited live, and both are the target of an explicit "stays exactly as
written" promise made by the entry that supersedes them.

**This is recorded, not resolved.** V.3's one-line collapse and DECISIONS #102 are in direct
tension, and Part VIII's decision protocol resolves the tension by itself: *"Ambiguity about whether
an ADR entry may be shortened resolves to 'keep the reason.'"* Phase 1 registers the target and the
ADR that reasons about it; Phase 0 only measures. What Phase 4 may **not** do without saying so in
the record is reduce #99 or #142 to one line while the entries that superseded them promise the
opposite.

## 5. The record taxonomy, read from the guard

`tests/test_documentation.py`, lines 61–80:

```python
HISTORICAL_DIRS = frozenset({"scope", "adr", "gates", "releases"})
HISTORICAL_FILE_PREFIXES = ("SECURITY-REVIEW-",)
```

`live_docs()` returns every `docs/**/*.md` that is **not** historical, plus `README.md` and
`CONTRIBUTING.md` from the root. `_is_historical` matches a directory *anywhere* in the relative
path, plus the filename prefix.

`test_the_historical_exclusion_is_exactly_the_record_taxonomy` pins the set **exactly** and asserts
`"architecture" not in HISTORICAL_DIRS`, with the docstring: *"Widening this set is how this guard
would quietly stop guarding anything."*

**Three consequences this release must carry:**

1. **`docs/record/` will not be in the taxonomy**, so the ledger is a **live document** and is
   scanned for release claims. A ledger row quoting a historical release theme could trip
   `test_every_release_claim_agrees_with_the_roadmap_table` — but only if written as a
   `<!-- release-claim: -->` marker, which a ledger has no reason to do.
2. **Widening `HISTORICAL_DIRS` to include `record` would be exactly the move the guard forbids**,
   and Phase 8's injection list already requires demonstrating that it goes red.
3. **The claim-scanning guards cannot see a document that was never in `live_docs()`**
   (Appendix B). `docs/gates/` is historical, so removing 154 of its 155 files changes **nothing**
   that `test_every_release_claim_agrees_with_the_roadmap_table`,
   `test_no_element_is_tagged_for_a_release_the_roadmap_does_not_name` or
   `test_a_documents_element_tags_match_its_own_release_claim` check.

   **Two tests in the same module are the exception, and they are path pins rather than claim
   scans**: `test_each_forbidden_phrasing_was_real` reads `docs/gates/v0.7.4-phase-0.md` (11

   `test_documentation.py` after the prune proves those *paths* still resolve — it does **not**

### 6.4 The controls

Part IV requires a control: *"a file for which the relation does **not** hold, or the demonstration
that no such file exists and why that is itself the finding."* Four controls ran, and each one
isolates a different way the proof could be vacuous.

| control | must be | **measured** |
|---|---|---|
| **C1a** — drop `description` only, keep `truth` | False | **False, all four** |
| **C1b** — drop `truth` only, keep `description` | False | **False, all four** |
| **C1** — fixture == corpus with no strip at all | False | **False, all four** — so the fixtures are derived files, not copies |
| **C2** — stripped corpus vs a *different* fixture | False | **False, all four** — the relation is specific, not a relation that holds against everything |

C1a and C1b together are the ones that matter: **each half of the strip is load-bearing**, so the
relation in §6.3 is the minimal true one rather than an over-specified guess that happened to pass.

### 6.5 A second finding the proof turned up, which Phase 7 needs

The four fixtures are not formatted consistently:

```
background_noise.json    matches json.dumps(indent=2) + "\n"
fiber_cut.json           matches json.dumps(indent=2) + "\n"
flapping_noise.json      matches json.dumps(indent=2) + "\n"
olt_storm.json           matches json.dumps(indent=None) + "\n"     <- compact
```

V.6 requires the loader be *"asserted to produce byte-identical **structures**"*, which §6.3 already
establishes. **Gate 7's wording — *"asserted byte-identical to the four files"* — is not achievable
for all four at the byte level under any single formatting choice**, and the reason is a formatting
inconsistency in the files being deleted, not a defect in the loader. Phase 7 asserts structural
identity, states this, and does not quietly redefine "byte-identical" to mean something else.

### 6.6 What actually consumes these files

data = json.loads((FIXTURES / name).read_text())
for entry in sorted(data["events"], key=lambda e: float(e.get("delay", 0.0))):
