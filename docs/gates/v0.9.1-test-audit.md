# v0.9.1 — a critical audit of the test suite

The project is flying blind on data. It must not also be flying blind on whether its guards work.
**923 tests is a number, not a guarantee**, and this release's own history says the difference
matters: the documentation guard shipped at 31 % visibility, and the declaration gate shipped
complete twice before it was.

> ## This is a sample, not a proof.
>
> Thirty-one seeded defects is a **sample of one kind of defect** — a single-token slip of the kind
> a tired engineer makes. It says nothing about defects of other shapes: a wrong algorithm, a
> missing case, a race, a design that is coherently wrong. A subsystem whose seeds were all caught
> is a subsystem where **these** seeds were caught, and nothing more. **The value of this document
> is the map, not the score.**

## Method

Each defect was injected into a clean tree, the suite was run, the outcome recorded, and the tree
reverted with `git checkout` so the next seed started from the same baseline. Every seed is a
**single-token change**: an off-by-one, a dropped clause, a flipped comparison, a widened bound.
None is sabotage a reviewer would obviously catch.

The suite ran with `-x`, so a **caught** row records the *first* test to fail rather than all of
them. Where nothing failed, `-x` had no effect and the full suite ran to completion — which is the
case this audit actually cares about. Baseline at the time of the run: **958 passing tests**.

A three-defect calibration run preceded this one, in [Gate 0](v0.9.1-phase-0.md) §5, to decide
whether the technique found anything before a whole phase was spent on it. It found two of three.

### Two observations about *how* things were caught

**Three of the nineteen were not caught by a test.** A3 and H2 stopped the run with a **collection
error** — an import-time `assert` in `rbac/tables.py` and an `ImportError` respectively. That is a
real defence and a cheap one, but it is not the suite: a defect that merely *imports* would have
sailed past. Counting them as "caught" is generous, and it is recorded here so the 19 is read
correctly.

**Six were caught by a frozen report fixture rather than by a test of the thing that broke.** P1
(promotion reaching non-sink rows), P3, B1, L3 and L6 all first failed at `test_bias.py` or
`test_agreement.py`'s byte-for-byte expectation. The three report gates are, empirically, **the
broadest net in this repository** — they notice changes far outside the reports. That is a strength
and a warning: a reviewer seeing "the bias report changed" must not assume the bias report is what
broke.

## 2. The twelve misses, and what each one is

Split into **gaps worth closing** and **accepted limits**, because the difference is the whole point
of the exercise.

### 2.1 Gaps — closed in this release (its own themes touch them)

| # | Why it is this release's business | What closed it |
|---|---|---|
| **A1, A2** | `feedback.write` and `situation.close` are the capabilities on **the two endpoints this release changes**. Both could be moved to `viewer` — granting every read-only account the ability to write labels and close situations — with all 958 tests green. | `tests/test_rbac.py::test_every_capability_names_the_role_it_was_designed_for` pins the **whole table** |
| **L4** | `excluded_count` is a column *this release added*, and migration `0010` states "0 cannot occur". Nothing checked it. | `tests/test_partial_split.py::test_marking_nothing_records_no_assertion_rather_than_an_empty_one` |
| **S1** | Carried explicitly from `SECURITY-REVIEW-0.9.0.md` into this release's brief. | one assertion in `tests/test_shadow.py::test_online_and_offline_opinions_agree_bit_for_bit` |

**A1/A2 — why nothing noticed.** Everything downstream of `PERMISSIONS` is *derived*: `role_allows`,
`resolve_capabilities`, `ROUTE_PERMISSIONS`'s completeness test and the generated authorization
matrix all read that dict and agree with whatever it says. The generated matrix in particular
regenerates its own expectation from the resolver, so it is **self-consistent under any table**.
Before this release the only role assignment asserted anywhere was
`PERMISSIONS["config.read"] == "admin"` (`test_rbac.py:125`). A table that is the source of truth
for every derived check needs its own assertion, or the derivation is measuring itself.

**S1 — the one v0.9.0 predicted, now confirmed by execution.** `SECURITY-REVIEW-0.9.0.md` said the
skew comparison "is blind to a feature divergence that does not move the score, and its correctness
depends on a column-aliasing convention that a future `SELECT` rewrite would silently invert." The
audit inverted it. **Nothing failed.** The mechanism: `shadow_skew_rows` selects
`served_delta_t_s`, `served_class_affinity` and `served_entity_affinity`, and `_skew` never reads
them — `shadow_eval.reconstruct` recomputes from the *offline* `dataset_pair` columns, so the served
columns are dead weight in the comparison they exist for. One assertion now pins the convention.
**The deeper half is not closed**: the comparison is still blind to a feature divergence that leaves
the score unchanged, which is a v0.10.0 question because it needs the comparison redesigned rather
than an assertion added.

### 2.2 Gaps — recorded, not closed (outside this release's themes)

Each is a `docs/ROADMAP.md` line. A release that fixes everything it finds is not a patch release
and its diff cannot be read in one sitting.

**A4 — the authorization perimeter fails *open* on an undeclared route, untested.** Inverting
`if permission is None or permission not in capabilities` so that a route with **no declared
capability is allowed** left everything green. The mitigation is real and is why this is not a
finding: the declaration gate refuses to register such a route at all, so `permission is None`
should be unreachable in a built application. But that makes this the **second layer of a two-layer
defence, and the second layer is not tested** — the first layer's own seeds (D1, D2) were caught, so
the suite is testing the belt and not the braces.

**R2, R3, R4 — three retention behaviours nothing pins.** The row cap deleting **newest**-first
instead of oldest-first is a real behaviour change with a real consequence (the sink would retain
the wrong end of its window); the audit tier losing its `lifecycle` clause lets it reach sink rows;
`<` → `<=` shifts a boundary by one row. R1 — the sink prune losing its lifecycle clause — *was*
caught, so the tier that can destroy a promoted corpus is guarded and the ordering and boundary
within each tier are not.

**C2 — the observation buffer's bound can be widened tenfold unnoticed.** A bound whose only
consequence is memory under storm, and no test exercises a storm large enough to feel it.

**H1 — `SHADOW_MAX_ROWS` can grow a thousandfold unnoticed.** Same shape as C2: a bound with no test
that reaches it.

**P2 — the coverage classification is off by one and no fixture notices.** `promoted >= expected`
becoming `>= expected - 1` reclassifies a `partial` bag as `full`. The bias fixture's bags are small
enough that the boundary never lands where the change matters. This one is the most likely of the
twelve to bite silently, because `coverage` is a **label-quality field v0.10.0 will filter on**.

### 2.3 An accepted limit, and a deliberate control

**B2 was designed to be missed.** `self.verdict == "confirm"` → `self.verdict != "split"` is
**behaviourally identical** while `verdict` has exactly two values, which a `CHECK` constraint
enforces. A suite that failed here would be asserting the shape of an expression rather than its
meaning. It is in the table as a **control on the audit itself**: it shows the technique is
measuring behaviour and not text, and that a "miss" is not automatically a gap.

## 3. The four questions

### 3.1 Which tests cannot fail?

Three kinds, and the first is the largest.

**(a) Guards installed green, over collections that are empty.** `DEBT_ALLOWLIST` is `{}`, and four
tests in `tests/test_architecture.py` iterate it — `test_allowlisted_modules_have_not_grown`,
`test_allowlist_only_shrinks`, `test_allowlist_names_only_real_modules`, and (in part)
`test_no_module_may_join_the_allowlist`. Every one builds an empty list and asserts it is empty.
**They cannot fail today.**

They are not worthless: the day someone adds an entry, three start meaning something and the fourth
fires immediately, which is the ratchet they exist to be. But they are **dormant**, and the suite's
green count includes four assertions no change to the product can move. **Not a gap and deliberately
not closed** — a dormant ratchet is the correct shape for a ratchet. Recorded so the count is read
honestly.

**(b) Assertions over presence rather than content.** The three report tests contain seventeen
assertions of the form `assert "SOME PROSE" in text`. They check a paragraph is *present*, never
that it is *true* or that it matches the numbers above it. `test_bias.py:270` asserts the report
contains *"n IS THE NUMBER OF INDEPENDENT BAGS, NOT THE NUMBER OF PAIRS"*; it would pass if the
figure printed above that sentence were the pair count.

**Mitigated**: the byte-for-byte frozen expectation *does* pin the numbers, so these are a second,
weaker layer over content already covered. Their real job is to stop an editor deleting the prose —
which the frozen fixture also catches. **Redundant rather than false.**

**(c) Tests whose subject is a constant.** `test_rbac.py:125` was, until this release, the only place
pinning a capability's role. Seeds A1 and A2 measured the consequence.

### 3.2 Where is the suite testing the shape of the source rather than behaviour?

Nineteen test files read source text. Most are guards whose subject genuinely *is* the source — the
module-size guard, the layer test, the documentation link check, the d3 checksum, the
pre-registration hash. Those are correctly shaped and correctly named.

**The declared case.** `tests/test_security_ui.py` asserts over `app.js` — `".innerHTML" not in
app_js`, `"function prunePanels(" in app_js`, `"session.capabilities.has(cap)" in app_js` — and its
module docstring **says so**: *"the shipped UI source must be free of the unsafe patterns that caused
F1."* There is no browser in this suite, so source inspection is the only instrument available, and
v0.7.5 accepted that trade explicitly. Declared, and fine.

**The undeclared case, which is what the question asks for.**
`tests/test_governance.py::test_f39_every_mutating_handler_uses_the_transaction_helper` is named and
documented as a **behavioural** guarantee — *"No mutating handler may take `store.lock` directly and
commit by hand"* — and is, end to end, a string search over `apisource.api_source()`. It never
executes a handler, never raises inside one, and never checks that anything was rolled back.

Its assertions are not equally load-bearing, and a reader cannot tell them apart:

* *"every mutating handler reaches `write_txn()`"* is a **reachability** property over twenty-odd
  handlers. Source inspection is the right instrument — exercising every handler's failure path is
  not realistic. Correct, merely unsaid.
* `assert "async def write_txn(" in source` and `assert "await self._store.rollback()" in source`
  restate a property the suite **already tests behaviourally**, in
  `tests/test_store_concurrency.py::test_write_txn_rolls_back_and_leaves_nothing_for_another_caller`,
  which mutates, raises, lets an unrelated caller commit, and asserts the abandoned write did not
  ride along. **Seed T1 proves the behavioural test gets there first** — it failed at
  `test_api.py::test_f39_a_failed_write_leaves_nothing_to_commit`, not at the string search.

So the finding is not "this test is wrong". It is that **its docstring sells a source scan as a
behavioural guarantee**, and a maintainer who deleted the behavioural tests would still see it pass.
The same pattern, undeclared, is in `tests/test_scoring.py` (forbidden imports on the datagram path)
and `tests/test_governance.py:208-212`.

### 3.3 Which tests are coupled to fixture size or corpus shape?

**This release found out the hard way**, which is the most honest evidence available: extending the
bias fixture by two labels and one situation — a change that added no behaviour — broke assertions
pinned to the old counts (`provenance["current"] == 3`, and a guard that fired because bags now
outnumbered pairs).

| Kind | Examples | When the corpus grows |
|---|---|---|
| counts pinned to the fixture | `test_bias.py:282-303`, `test_agreement.py:231-248` | **break loudly** — annoying, correct, self-announcing |
| the three frozen report fixtures | `bias-report.txt`, `agreement-report.txt`, `shadow-report.txt` | **break loudly**, by design |
| ratios and shares | `top_operator_share` 66.7 % → 60.0 % | break loudly |

Breaking loudly is the *good* outcome. **The dangerous class is the assertion that keeps passing
while ceasing to mean anything**, and the clearest instance in the suite is self-aware and says so:

```python
assert measurements["bags"] < measurements["pairs_sink"] + measurements["pairs_dataset"], (
    "the fixture must have more pairs than bags for this assertion to mean anything"
)
```

That comment is the pattern to imitate. **The instances without it are the interval refusals.**
`agreement.py`'s cluster bootstrap prints `[interval n/a]` below `MIN_INCIDENTS_FOR_INTERVAL`, and
every fixture sits **below** that threshold — so every interval in every frozen expectation reads
`n/a`, and **the interval arithmetic is exercised by no gate at all**. When a real corpus crosses
that threshold the intervals will appear for the first time in production, having never been
compared against a frozen value. Nothing will break; the coverage simply was never there.

Same shape, different subsystem: `EPOCH_PAIR_CAP = 20` is never reached through the report path,
because the bias fixture's largest bag is three members. It is exercised only in `test_learn.py` and
in this release's `test_partial_split.py`.

### 3.4 What is the suite not testing at all?

The three I would cover next — **an opinion, with the reasoning, not a commitment.**

**(a) The UI, as a program.** `app.js` is a thousand lines of behaviour — the held card, the atomic
detail swap, the reconciler, and now the exclusion checkboxes — and **not one line of it is ever
executed by this suite.** Every UI test is a string search. The two defects v0.7.5 existed to fix
were *composition* defects between four individually correct lines, and no string search can see one.
The cost is real — a headless browser is a dependency and a CI surface — which is why it has not been
done. The exposure is that the most operator-facing, most label-integrity-critical code in the
product has no executable test, and **this release increased it** by adding a stateful `Set` to that
file whose contents become an assertion in the corpus. **This is the one I would do first.**

**(b) A migration that fails part-way through.** `test_migration.py` covers every forward path and
`test_upgrade.py` covers upgrade-in-place, but nothing exercises a migration that **fails
half-applied** — a disk-full or a constraint violation between two `ALTER TABLE`s in one script.
`lifecycle.py` runs the script and *then* sets `user_version`, so a crash mid-script leaves a
database whose version says "not applied" while some statements have landed. Whether
`executescript`'s implicit-transaction semantics save this is **a fact nobody in this repository has
checked**, and it is one semantics question away from being either fine or silent corruption. Cheap
to test, and the answer is worth knowing before a customer finds it.

**(c) The engine and the API contending for the one connection under sustained load.**
`test_store_concurrency.py` proves the invariants — one connection, one lock, no `Store` method takes
it — and exercises three concurrent domain writes. `test_perf.py` loads the ingest path alone.
Nothing runs the batch loop and a stream of API writes **against each other** long enough for the
interleaving to matter. The property at risk is not the correctness of one write but **the latency of
the batch under API pressure** — which an operator experiences as a NOC that stops keeping up during
an incident, exactly when they are also clicking Confirm and Split.
