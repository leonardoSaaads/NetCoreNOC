## 2. The capability-without-surface enumeration — **derived by execution**

Not read off the UI by eye. Resolved by walking `rbac.ROUTE_PERMISSIONS` and matching each templated
route against every `/api` literal `app.js` can build:

```
totals: 30 capabilities, 43 routes;
        8 routes and 4 capabilities unreachable from the UI
```

| Route | Capability | Min role |
|---|---|---|
| `GET /api/promotion` | `promotion.read` | viewer |
| `POST /api/promotion` | `promotion.write` | admin |
| `GET /api/dataset/retention` | `config.read` | admin |
| `POST /api/dataset/retention` | `config.write` | admin |
| `POST /api/audit/prune` | `audit.prune` | admin |
| `POST /api/users/{uid}/role` | `users.manage` | admin |
| `POST /api/password` | `self.read` | viewer |
| `GET /api/classes` | `classes.read` | viewer |

**The one worth naming separately is `POST /api/password`.** The login overlay handles a *forced*
change on first sign-in, so a signed-in operator has no way to change their own password at all —
a missing security affordance in a product that ships password policy. Nobody had noticed, because
nothing enumerated the surface.

Plus **six CLI-only reports** (§4 of the draft) that an admin without shell access to the appliance
cannot see at all: `dataset stats`, `bias-report`, `agreement-report`, `shadow-report`, `census`,
`audit verify`.

The draft's requirement on those is a constraint rather than a feature: the UI **displays** them and
never recomputes them. Several are byte-compared by tests, and a second implementation of the shadow
verdict would be a second source of truth for the number four releases of evidence discipline rest
on.

## 3. The three parameter classes, with examples from this tree

| Class | Examples named in the draft | UI permits |
|---|---|---|
| **Mechanism** | shadow sampling rate; the three retention tiers; session TTLs; display limits (`limit=50`, `limit=200`, the 30-link cap); training hyperparameters | freely settable, **with the cost shown** |
| **Hardening-only** | `asserting_bags ≥ 50`; the detection-threshold condition; the visibility-scope policy; the scorer's degeneracy bounds | **raise only**, refuse looser **with the reason** |
| **Structural, read-only** | the `eval` output hash; the seal and its query count; `incumbent_linked`; the audit hash chain; `params_hash`; the capability ceiling | displayed, **no edit control** |

Two requirements in §6 are the ones that carry the section's weight:

* **A structural value renders visibly differently from a settable one — not as a disabled input.**
  A greyed-out field says *"you may not"*; a fact says *"this is what is true"*. Different
  sentences, and conflating them is how principle 1 gets broken by a widget.
* **The hardening-only refusal shows four things**, including *why the floor exists* and that the
  stricter direction is still available. A bare "rejected" teaches nothing and invites a workaround
  — the standard `SECURITY-REVIEW-0.6` §4 already set for the scorer preview's wording.

## 4. The env-then-database precedent, quoted

§7 quotes `runtime.py` verbatim rather than paraphrasing it, because the point is that **the
mechanism already exists and is already audited**:

> *"Config precedence (DESIGN v0.2): environment variables are the defaults; an admin saving a value
> from the UI writes a `meta` row that then takes precedence … refreshed from `meta` at startup and
> on every audited change so the running receiver (allowlist) and maintenance loop (retention) pick
> it up without a restart."*

It works today for exactly two values. **v0.13.0 generalises a proven pattern; it does not invent
one.**

Three things follow, all specified:

* **Three columns** — environment default, database override, effective — because *"why is this
  value what it is?"* is the question a two-source configuration must be able to answer.
* **The impact statement per setting**, with `routes_admin.py`'s retention reasoning as the model
  (*"lowering retention deletes rows and there is no rollback"*, hence preview-by-default). The
  draft **names which settings need preview-before-destroy**: operational retention, the three
  dataset tiers, `audit.prune`, and entity/profiler resets. Scorer configuration is explicitly *not*
  among them — it is append-only and rollback is a pointer move.
* **What needs a restart, honestly.** `Settings` is read once at startup and never mutated, so **two**
  values are live and **nine** require a restart. The draft tabulates both lists and requires that a
  restart-required setting says so *before* it is saved. A settings page that accepts a new
  `trap_port` and appears to succeed while the receiver keeps listening on the old one is worse than
  no settings page.

## 5. The framework, recommended with its reasoning

**Preact + htm, vendored as one ESM asset with pinned bytes** (ADR #171, draft §10).

The argument is from precedent rather than from taste: `d3.v7.min.js` is **279 706 bytes — five
times `app.js`** — and already ships under `CHECKSUMS.txt` with its licence beside it, guarded by
`tests/test_supply_chain.py` and permitted by `script-src 'self'`. A second vendored asset walks a
path that already has an instrument on it, and asks the project for nothing new.

**Preact + htm over Lit** on one project-specific ground: **htm needs no compile step**, whereas
Lit's ergonomic form is decorators plus TypeScript — a build step wearing a different hat.

**The decisive reason is a security one**: it makes the capability guard **structural rather than
textual**. Phase 0 measured exactly how weak `split("const TABS")` is.

§10.1 carries the vendoring procedure as six numbered steps, including the one most likely to be
skipped: *`tests/test_supply_chain.py` lists no assets by name, so its coverage of the new file must
be verified rather than assumed.* The **version is deliberately not named** — a version chosen a
release early is a version nobody re-checked.

## 6. Room for Phase 2 and Phase 3, with no placeholders

§2 shows where a *Diagnose* group (LLM troubleshooting), test templates and an *Escalate* group
(tickets) attach, and then says:

> **No Phase 2 or Phase 3 item appears in v0.13.0's sidebar. Not disabled, not greyed, not "coming
> soon". Absent.**

This project was right to criticise "mechanism with no volume" when v0.9.1's `close` channel shipped
unused. A greyed-out *Troubleshooting* item is that error with worse ergonomics — it teaches an
operator that parts of the product do not work.

The cost is four concrete obligations rather than a promise: sidebar groups are **data, not markup**;
a section owns its own sub-navigation; the context panel is addressable by any section; a situation
is linkable.

## 7. The `#sidebar` collision, and the guard it could break quietly

`index.html` already has `<div id="sidebar">` — the **detail panel beside the graph**, not
navigation. §1.1 names it, names the eight ids and the `.panel[data-panel=…]` selector the new tests
reach for, and sets the rule:

> when a selector changes, the assertion count in `tests/test_ui_invariants.py` **may not go down**.

A guard rewritten during the change it guards is at its least trustworthy, and the count is the
cheapest thing to check. The harness helps here by construction: its selector engine **throws** on a
selector outside its grammar, so a new form fails loudly rather than matching nothing.

## 8. Routing, and the accidental defence it removes

The single most important operational note in the draft (§3), and it exists only because the harness
found it:

> Calling `renderPanel("audit")` directly as a viewer issues no request — but only because
> `prunePanels` removed the container, so `clear(null)` throws before `api(...)` is reached.
> **There is no capability check inside the loaders.**

Today nothing can call a loader except a tab that was not rendered. **With routing, a URL can.** The
draft's requirement: every view resolves its capability **before it fetches**, and constraint 10 of
§11 restates it as a prohibition.

## 9. The questions left open, listed

Six, in §12 — recorded because a decision noted as open is honest and one quietly assumed is not:

1. the held card versus a real reconciler (the **invariant** is the constraint; both designs can
   satisfy it);
2. **whether the graph moves off d3** — 279 706 bytes for one view, and the one part of the UI the
   harness does not execute at all. *No opinion registered*, but it may not be decided silently;
3. one context panel or per-section;
4. how much of the admin dashboard is live versus on demand;
5. whether `RuntimeConfig` grows — each addition is a live-reload path in a running receiver, which
   is engine work;
6. **accessibility beyond what exists** — keyboard navigation of a sidebar, focus management across
   route changes, screen-reader semantics for the graph. Unaddressed here *and today*, and the draft
   says naming them is not the same as specifying them.
