# v0.13.0 — Gate 0

**The fence. No v0.13.0 code exists until this gate closes.**

This release replaces the entire UI. Three things had to be measured on the **unmodified v0.12.0
tree** before a byte moved, because each of them is something the rewrite makes unmeasurable
afterwards:

1. **what the current UI actually renders, for each of the three roles** — you cannot improve what
   you have not looked at, and after the rewrite there is nothing left to look at;
2. **F53, reproduced by execution** — the latent finding routing arms, observed rather than quoted;
3. **which declared routes have no UI surface**, re-derived from the code rather than copied from
   `../architecture/UI-0.13-DRAFT.md` §4.

Every probe below carries a control. Two of them changed their answer when the control was added,
and both changes are recorded in §4 rather than quietly corrected — a probe whose negative result
could equally mean *the probe does not work* is not evidence (Appendix B).

The probe itself is `.phase0/probe.mjs` and `.phase0/run_probe.py`, which import the **shipped**
harness (`tests/domharness/env.mjs`) rather than a copy of it, and assert `app.js`'s own `esc()`
output on every run exactly as `domdriver` does. A run that could not produce
`&lt;a href=&quot;x&quot;&gt;` raises rather than returning a result.

## 2. The baseline DOM, rendered and dumped

`domDump` boots the shipped `ui/app.js` against the **real** captured responses for each role
(`tests/uifixtures.py`, real engine, real fiber-cut corpus) and walks the resulting `#app` subtree.
Full dumps: `.phase0/out/dom-{viewer,editor,admin}.txt`.

| Role | dump lines | tabs offered | panels present in the DOM |
|---|---|---|---|
| viewer | 109 | Situations, Timeline, Entities | `situations`, `timeline`, `entities` |
| editor | 109 | Situations, Timeline, Entities | `situations`, `timeline`, `entities` |
| admin | 170 | Situations, Timeline, Entities, Users, Tokens, Config, Scorer, Governance, Quarantine, Audit | the ten above |

Boot requests are identical for all three roles:
`GET /api/me`, `GET /api/stats`, `GET /api/graph`, `GET /api/situations?limit=50&status=open`.

### 2.1 Four observations about the baseline that are not defects, and one that is a fixture artefact

* **A viewer's DOM and an editor's DOM are byte-identical at boot.** Every editor affordance —
  the marking checkboxes, Confirm, Split, Close, the renameable names — lives *inside* a card the
  operator has expanded, so it does not exist until a click. Invariant 1 is therefore asserted at a
  level where viewer and editor are indistinguishable, and the difference between them is only
  observable through the `partialSplit` scenario. **This is why
  `test_a_viewer_is_offered_no_member_checkboxes_at_all` exists and why it is phrased as an expected
  exception rather than as a DOM comparison.**
* **Ten tabs, one row, and no grouping.** The admin dump shows all ten `<section class="panel">`
  siblings inside one `<div id="sidebar">` — which is the collision §V.1 has to resolve: the element
  called `sidebar` today is the *work area*, not navigation.
* **The whole authenticated UI is one scroll.** There is no route, no fragment, no history entry.
  A situation cannot be linked to, which is the deep-link requirement of draft §3.
* **`p95 latency` renders as `86807950.0767 s`.** This is Appendix B's *two clocks* visible in the
  fixture: the corpus is replayed at epoch `1_700_000_000`, and the server computes p95 against
  wall-clock at capture time. It is a property of the **captured JSON**, present before the UI sees
  it, and not a rendering defect. Recorded because a reader of the dumps will otherwise think the
  new UI introduced it.

## 3. F53, reproduced by execution

**Finding F53** (`../security/SECURITY-REVIEW-0.12.0.md` §2): the panel loaders have **no capability
check**. A viewer's zero-request property holds only because `prunePanels` removed the container and
`clear(null)` dereferences null.

The probe calls `renderPanel(id)` directly — what a router does — as a **viewer**, for all seven
admin panels, and reports how each call terminated:

```
users       TypeError: Cannot read properties of null (reading 'firstChild')
tokens      TypeError: Cannot read properties of null (reading 'firstChild')
config      TypeError: Cannot read properties of null (reading 'firstChild')
scorer      TypeError: Cannot read properties of null (reading 'firstChild')
governance  TypeError: Cannot read properties of null (reading 'firstChild')
quarantine  TypeError: Cannot read properties of null (reading 'firstChild')
audit       TypeError: Cannot read properties of null (reading 'firstChild')

requestsAfterBypass: []
```

`'firstChild'` is `clear()`'s first statement (`while (node.firstChild)`), reached with `node ===
null`. **The observed outcome is right and the mechanism is an exception.** Seven panels, seven
`TypeError`s, zero requests.

**The control** is that the same probe reports zero requests *and* a `TypeError` — if it reported
zero requests and "returned normally", the zero would be evidence of a capability check that does
not exist. It reports the exception, so the zero is attributable to the null dereference and to
nothing else. This is the reading `test_a_panel_reached_without_its_capability_still_issues_no_request`
already records in its docstring, now re-observed against the tree this release starts from.

## 4. Every capability with no UI surface, re-derived by execution

Draft §4 states *"30 capabilities and 43 routes; 4 capabilities and 8 routes are unreachable from
any screen"*. **That table was not copied.** It was re-derived by booting the admin UI, clicking
every tab, expanding every card, clicking every rendered `.name`, clicking every rendered `<button>`
and submitting every rendered `<form>`, then resolving each observed request onto its
`rbac.ROUTE_PERMISSIONS` template.

### 4.1 The two controls, and what each of them changed

A reachability drive reports a *lower bound*. Two things can make a route look unreachable when it
is not, and both were caught:

**Control 1 — an empty corpus.** The first drive reported **14** unreached routes. Four of them
(`DELETE /api/tokens/{tid}`, `POST /api/scorer/rollback`, `POST /api/labels`, `GET /api/events`)
were unreachable because the *data* was absent, not the control: there was no token to revoke, no
second scorer configuration to roll back to, `.name` spans were never clicked, and `EventSource` is
not `fetch` so the probe could not see it. Seeding a token, a second user and a second scorer
configuration, clicking `.name`, and counting `EventSource` opens brought it to **10**.

**Control 2 — an incomplete fixture.** `uifixtures.CLIENT_GETS` stops at `/api/entities` and never
captures `/api/entities/{ne_id}`, so the harness answered 404, `renderEntityDetail` took its
`catch { return; }` and the two reset buttons were never rendered. That would have reported
`entity.reset` and `profile.reset` as having **no UI surface** when what they have is **no
fixture** — measuring the capture table instead of the product. Capturing the detail brought it to
**8**.

Without either control this gate would have overstated the missing-surface list by 75 %.

### 4.2 The measurement

| | |
|---|---|
| capabilities in `rbac.PERMISSIONS` | **30** |
| routes in `rbac.ROUTE_PERMISSIONS` | **43** |
| routes reached by driving every control | **35** |
| routes with **no UI surface** | **8** |
| capabilities with **no UI surface** | **4** |
| controls rendered and driven | 36 buttons, 18 `.name` spans, 5 forms, 1 `EventSource` |
| harness errors during the drive | **0** |

Unreached routes, exactly:

| Route | Capability | Min role |
|---|---|---|
| `GET /api/classes` | `classes.read` | viewer |
| `GET /api/promotion` | `promotion.read` | viewer |
| `POST /api/promotion` | `promotion.write` | admin |
| `GET /api/dataset/retention` | `config.read` | admin |
| `POST /api/dataset/retention` | `config.write` | admin |
| `POST /api/audit/prune` | `audit.prune` | admin |
| `POST /api/users/{uid}/role` | `users.manage` | admin |
| `POST /api/password` | `self.read` | viewer |

Capabilities with **no** reachable route at all: `classes.read`, `promotion.read`,
`promotion.write`, `audit.prune`. The other four routes belong to capabilities that *are* surfaced
elsewhere (`config.read`/`config.write` through `/api/config`, `users.manage` through `/api/users`,
`self.read` through `/api/me`) — which is why the route count and the capability count differ, and
why quoting only one of them would be misleading.

**This independently reproduces draft §4's figures.** It is the specification for §V.2, and Phase 5
reports back against this exact table, by name.

### 4.3 What this derivation does not cover

It is a **lower bound on reachability**, so it can only ever *over*-report the missing set. A route
reachable through a gesture the drive did not make — a keyboard-only path, a control rendered by a
response shape this corpus does not produce — would appear here wrongly. Both controls above were
instances of exactly that, found by looking. There may be a third nobody has thought of; the drive
is evidence, not proof, and the honest form of the claim is *"eight routes were not reached by any
gesture this drive could make"*.

## 5. Coverage: the sampling that precedes the band

ADR #159's band is **96.10–96.21 %**, set from **two** samples, and four of the five observations
this project has recorded fall below it. Part VII.10 forbids re-cutting it to fit this release.

What Gate 0 contributes is **variance on the unchanged tree**, measured now so that the band
registered in Phase 1 is registered against a known spread rather than against a guess. Three
consecutive runs of `make coverage` on the untouched v0.12.0 tree:

```
tree: e8de092 (v0.12.0 merge), 0 files modified — the working tree was stashed for the duration
--- baseline sample 1 ---
Required test coverage of 85.0% reached. Total coverage: 96.02%
1339 passed in 424.77s (0:07:04)
--- baseline sample 2 ---
Required test coverage of 85.0% reached. Total coverage: 96.02%
1339 passed in 400.36s (0:06:40)
--- baseline sample 3 ---
Required test coverage of 85.0% reached. Total coverage: 96.13%
1339 passed in 405.04s (0:06:45)
```

**96.02 %, 96.02 %, 96.13 % — a spread of 0.11 points on a tree that did not change between
runs.** Two runs agreeing exactly and the third differing is the interesting shape: the suite is
*nearly* deterministic in coverage and not quite, so a band narrower than 0.11 fails for reasons
that have nothing to do with the code under test.

**ADR #159's band is 96.10 %–96.21 %, which is exactly 0.11 wide.** The whole band is one noise
interval. That is the mechanical reason four of five recorded observations fall below it, and it is
why Part VII.10 is right that re-cutting it to fit this release would be choosing a band after
seeing the data — the honest move is to leave it alone, report against it, and register a second
band whose width is justified by a measurement taken *before* the release existed.

The band for v0.13.0 is **not** set here. It is set in Phase 1, before one line of the new UI is
written, and `docs/adr/DECISIONS.md` records it with its reasoning. Both bands are reported in
Phase 7.

## 6. What this gate does not establish

* **Nothing about how the current UI looks.** The harness has no layout, no cascade, no
  `getComputedStyle` and no renderer; `dom.mjs` says so at the top. The dumps in §2 are structure
  and text, and every judgement in this release about spacing, contrast or hierarchy is unmeasured.
  `../gates/v0.12.0-phase-6.md` §8 already records this and it is inherited unchanged.
* **Nothing about the graph or the timeline.** d3 is a recording double. The two SVG render paths
  are not executed by any probe here and will not be executed by any test this release adds.
* **Nothing about whether an operator can use any of it.** That is not a property this instrument
  can measure, and no gate in this release will claim it.
