# v0.13.0 — Gates 2 to 7

One document for the build phases, because the evidence is one drive: every screen was rendered as
every role in a single harness run, and splitting that into five documents would split one
measurement into five quotations of it.

**Every figure here comes from one drive of the real console through the real harness against real
captured server responses.** Nothing in this document is a count of collected tests.

Reproduce it:

```sh
python tools/evidence/render_drive.py          # every screen, every role; writes .drive/
python tools/evidence/guard_demonstrations.py  # the fifteen injections
python tools/evidence/mutation_ledger.py       # the mutation ledger
```

The recorded results are committed under
[`evidence/v0.13.0/`](evidence/v0.13.0/) — the summaries in full, and nine representative DOM
dumps out of the 87 the drive produces (every screen × every role, plus the empty and error
sweeps). The rest are reproducible from the command above rather than carried in the tree; keeping
2.3 MB of generated text under version control would be storing an output where a command belongs.

### 2.1 F53, before and after

A viewer navigating **by address** to all seven admin views, plus two addresses that name no view:

| | v0.12.0 (Gate 0 §3) | v0.13.0 |
|---|---|---|

The one non-admin view a viewer *does* hold in the Evidence group — `#/promotion`, because
`promotion.read` is `viewer+` — renders and issues `GET /api/promotion`. That is the control: a

### 2.3 The keyboard

```
tabStops: 1        (across 16 items — roving tabindex, not sixteen stops)
navLabel: "Sections"
headingFocusable: "-1"     (programmatically focusable; never a tab stop)
ArrowDown -> at 1;  ArrowDown -> at 2;  End -> at 15;  Home -> at 0;  Enter -> activates
```

**The first version of this failed**, and the failure is recorded in `SCOPE-0.13.0.md` §5: `render`
recomputed the roving `tabindex` from the active route on every pass and discarded what the keyboard
had set, so `at` stayed 0 after every keypress. The markup was correct throughout.

### 2.4 The `#sidebar` collision

`#sidebar` was the **work area** in v0.12.0, not navigation. Three ids now, none of them ambiguous:
`#nav`, `#work`, `#context`. `selftest.mjs` asserts the old ids are **gone** from `index.html`, not
merely unused — a document that still carried `#sidebar` would let a guard match it and report that
it had found navigation.

| Requirement | Evidence |
|---|---|

### 3.1 The screen that justifies the release

Every expanded card renders a *Why these were grouped* section: one row per link, carrying the
score, the three named terms **with each term's number beside its bar**, and the pair. The
threshold the sum had to clear is stated in prose above it.

The bar is a second encoding of the same numbers, never the only one — a bar cannot be read off a
bad monitor and cannot be copied into a ticket.

### 3.2 The held card

`sameDetailNode: true`, `buttonStillConnected: true`, `detailStillConnected: true`,
`heldMarkerPresent: true`, and `excluded_ids` equal to exactly the two ids the operator marked,
after a server-sent update landed mid-gesture.

**Two mechanisms, both needed** (ADR #173). The reconciler keeps the node; the store keeps the
*payload*. Demonstration §4 injects `state.held.clear()` into `applyUpdate` — the node still
survives, and the guard still goes red, because the meaning did not.

### 3.3 The graph

`app/views/graph.js` is 172 lines and **no assertion in this repository executes any of them.** d3
is a recording double. Node placement, edge rendering, zoom, drag and the simulation are entirely
uncovered. The double throws on an unknown d3 API, which is a **drift alarm, not coverage**.

The mitigation is not a test: everything the graph shows is on the Entities screen as text, and the
graph says so on screen with a link.

## Gate 4 — Evidence

| Requirement | Evidence |
|---|---|
| the partial-split gesture sends exactly the marked ids | `test_a_partial_split_…`, red under demonstration §3 |
| the judge's verdict and the seal's query count displayed and **not editable** | §4.1 |
| a promotion refusal shows which refusal it was and why | §4.2 |

### 4.1 The seal

Rendered inside a `param-structural` block on *Judge & promotion*: query count, active model
version, active configuration, and the ratified plan hash. **There is no control.** A structural
value is a fact, and §6.1 requires it to be visibly different from a settable one rather than a
disabled input — a greyed field says *"you may not"*; a fact says *"this is what is true"*.

### 4.2 Refusals

The decisions table renders `verdict`, `outcome`, **`refusal_reason`**, `triggers` and
`query_count` for every row, applied and refused alike. A gate that refuses and cannot say why is
indistinguishable from a gate that is broken.

Proposing goes through the same destructive-preview component as every other consequential action,
and its preview is explicit that **no dry run exists**: the gate's verdict *is* the evaluation, and
computing it without recording it would create a decision nobody can audit.

## Gate 5 — Administer

| Requirement | Evidence |
|---|---|
| the three parameter classes visibly distinct | §5.1 |
| the three-column precedence shown | §5.2 |
| **a hardening-only value cannot be lowered**, demonstrated red | §5.3 |
| every destructive action previews first | §5.4 |

### 5.1 Three classes

`param-mechanism`, `param-hardening`, `param-structural` — three different left borders, three
different backgrounds, and a legend on the screen naming what each permits. The structural sections
render `<dl>` facts and contain **no `<input>` at all**.

### 5.2 Precedence

One `PrecedenceTable` component, four columns: setting, environment default, database override,
effective. `GET /api/config` gained `precedence` to make it possible (ADR #179) — `RuntimeConfig`
holds only the merged value, and growing it is what draft §12.5 closes.

**A mutant survived here** and is recorded in §7.2: nothing asserted that the environment column
reported the *environment*. The table could have shown the override twice — reading as *"the
environment was already set to this"*, the opposite of what happened — with the whole suite green.

### 5.3 The hardening-only refusal

Submitting `tau_s = 0.1` against a floor of `1.0` **the server published**:

```
sent:          []          <- no request was issued
refusalShown:  true
```

and the refusal carries all four things draft §6.2 requires — the floor, the submitted value and
that it was not applied, **why the floor exists**, and that the stricter direction is available.

**The control**: `tau_s = 120`, inside the bounds, sends `POST /api/scorer/preview` and shows no
refusal. Without it the zero above could be a console that never sends anything.

Demonstration §6 makes `hardeningRefusal` always return `null`; the guard goes red.

### 5.4 Destructive previews

One `Destructive` component, imported by every screen with a destructive control. The consequence
is stated **before** anything is clicked; the apply control **does not exist** until a preview has
been requested — absent, not disabled, because a disabled button is a thing to click twice.

Where a route has no preview mode (`audit.prune`, `retention_days`, a user deletion) the component
says so explicitly rather than inventing a count. **A fabricated preview is worse than none.**

### 5.5 The capability-without-surface list, reported back by name

Gate 0 §4 derived eight routes and four capabilities. All eight now have a screen:

| Route | Screen |
|---|---|
| `GET /api/classes` | Alarm classes |
| `GET /api/promotion` | Judge & promotion |
| `POST /api/promotion` | Judge & promotion (propose) |
| `GET /api/dataset/retention` | Corpus, and Settings |
| `POST /api/dataset/retention` | Settings (with a real preview) |
| `POST /api/audit/prune` | Audit |
| `POST /api/users/{uid}/role` | Users |
| `POST /api/password` | Your account |

**Eight of eight.** The four CLI-only reports (`bias`, `agreement`, `shadow`, `census`) are
**named on screen with their commands and are deliberately not recomputed** — draft §11.11.

## Gate 6 — themes, density, states, accessibility

### 6.1 Both themes rendered and dumped

| | `data-theme` | dump lines |
|---|---|---|
| default (no cookie) | *(absent — `prefers-color-scheme` decides)* | 200 |
| cookie `light` | `light` | 200 |
| after the toggle | `dark`, cookie `ncn_theme=dark` | — |
| cookie `<script>evil</script>` | *(absent — discarded)* | — |

The hostile cookie is the interesting row: a value outside the closed set of three is **discarded**,
so the worst a hostile cookie can do is select a supported theme. Demonstration §9 removes the
validation; the guard goes red.

`cookiePairs` after the toggle is exactly `{ncn_theme}` — one pair, a theme name, nothing else.

### 6.2 States

Seventeen views, driven three ways: populated, empty, and with every route failing.

| | present | absent |
|---|---|---|
| empty state | 13 / 17 | `settings`, `scorer`, `governance`, `account` |
| error state | 16 / 17 | `account` |

**The four absences are by design and are stated rather than counted as passes.** A settings screen
always has settings; a scorer always has parameters; a governance screen always has a ceiling to
show; an account screen always has the signed-in user. None of them has an "empty" to render.
`account` performs no read on mount, so it has no load to fail — its error surface is the password
form's own, which is exercised.

**One absence was a real defect and is fixed**: the Overview sat on `Reading the appliance…`
indefinitely when `/api/stats` failed. On screen, a console that cannot reach its own API and a
network that is merely quiet looked identical.

**And one was a fault in the probe, not the product**: the first run reported the Corpus screen as
having no empty state, because the "empty" fixture reused admin's populated retention payload. The
probe was measuring itself. Corrected, and recorded here because an uncorrected version would have
sent someone to fix a screen that was already right.

### 6.3 Accessibility — met, and what was not attempted

Met: every interactive control reachable and operable by keyboard; visible `:focus-visible` in both
themes; `nav`/`main`/`aside` landmarks with accessible names; an `aria-label` on every icon-only
control **stating its current value as well as its action**; focus moved to the work-area heading on
every route change; a label on every form control; severity and connection state encoded in glyph
and text as well as colour; `prefers-reduced-motion` honoured.

**Not attempted, named** (ADR #180):

1. **The force-directed graph has no ARIA semantics and is not keyboard-operable.** It carries a
   label and a pointer to the Entities screen, which holds the same facts as text. That pairing is
   the mitigation, not a fix.
2. The timeline SVG is the same, paired with its own table.
3. **No screen-reader testing was performed at all.** There is no assistive technology in this
   environment and the harness has no accessibility tree, so every claim above is a claim about
   **markup**, not about what is announced.
4. **Colour contrast was chosen by eye and is not measured.** The harness has no cascade.

### 7.2 The mutation ledger — **the survivor list, not the ratio**

Nineteen mutants over this release's own surface, run against the whole UI-facing suite.

**Seventeen killed. One probe failure. One genuine survivor:**

> `routes_admin.py` — `precedence` reporting the database override as the environment default.
> Every test in the repository stayed green (`319 passed`). The three-column precedence table would
> have rendered the same value in the "environment default" and "database override" columns, which
> reads as *"the environment was already set to this"* — the opposite of what happened — and §7.1
> of the design draft would have been decoration.

**Closed**, with `test_config_precedence_distinguishes_the_environment_from_the_override`, which
asserts the two fields differ *after a save* (before one, they agree by definition and the mutant is
invisible). Re-running the mutant kills it.

A third mutant was found while closing it — the same defect in the `retention_days` field, which the
first version of the new test did not cover. Also closed. **Final ledger: 21 mutants, 21 killed, 0
survivors.** The value was never the number; it was the two named gaps.

### 7.4 Coverage — reported against both bands

Three consecutive `make coverage` runs on the finished v0.13.0 tree, after the band was registered
and against a tree with no failing tests. The measuring run was taken **once, cleanly** — an earlier
attempt raced two suites against each other and produced two contended failures, which are recorded
here as a discarded measurement rather than quoted as a result.

```
--- v0.13.0 sample 1 ---
Required test coverage of 85.0% reached. Total coverage: 96.09%
1428 passed in 400.29s (0:06:40)
--- v0.13.0 sample 2 ---
Required test coverage of 85.0% reached. Total coverage: 96.03%
1428 passed in 395.60s (0:06:35)
--- v0.13.0 sample 3 ---
Required test coverage of 85.0% reached. Total coverage: 96.03%
1428 passed in 397.98s (0:06:37)
```

| Band | Range | Width | Result |
|---|---|---|---|
| **ADR #159** (set from two samples, v0.10.1) | 96.10 % – 96.21 % | 0.11 | **all three fall below it** — 96.09 misses the floor by 0.01 |
| **ADR #181** (registered in Phase 1, before any v0.13.0 number was seen) | 95.60 % – 96.60 % | 1.00 | **all three inside** |

**Reported against both, and neither is moved.**

Three things are worth saying about that table rather than leaving it to be read off.

1. **#159's band is exactly as wide as this suite's measured noise.** Gate 0 §5 measured the
   *unchanged* v0.12.0 tree at 96.02 %, 96.02 %, 96.13 % — a spread of 0.11 points on a tree that
   did not move. #159's band is 0.11 wide. A band one noise-interval wide fails for reasons that
   have nothing to do with the code, which is the mechanical explanation for four of five recorded
   observations falling below it.
2. **v0.13.0 came within 0.01 of it anyway**, which is worth knowing: the release did not move
   coverage materially. It adds Python only in `routes_static.py` and `routes_admin.py`, both fully
   exercised, and adds a large body of test code that is not measured by this figure.
3. **Neither band was re-cut after the data was seen.** Part VII.10 is explicit that doing so is
   choosing a band after seeing the answer, and #159 in particular is left exactly where v0.10.1
   put it. What #181 adds is a band whose width is justified by a measurement taken *before* this
   release existed — and it is not a band this release could not have failed: a single untested
   module would have taken it out.
