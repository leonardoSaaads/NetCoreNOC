## 2. The three facts, reproduced by execution

Each fact is reproduced **and** paired with a control that had to behave the other way. Appendix B's
second trap is a probe with no control: a first probe of the declaration gate used a bare
`FastAPI()`, whose default `/docs` is itself undeclared, so every "CAUGHT" might have been `/docs`.

### 2.1 Fact A — a fitted challenger cannot be stored in `scorer_config`

A plausible fitted `Coefficients` — an intercept and three logit weights, one negative and one above
1.0 — passed through `scoring.validate_params`, which is **the sole barrier between a database row
and the correlation engine**.

```
== the fitted challenger ==
  coefficients      : {'intercept': -2.4, 'decay': 1.7, 'class_affinity': 3.1, 'entity_affinity': -0.8}
  weights           : (1.7, 3.1, -0.8)
  pre-link threshold: 0.0   (exactly p = 0.5 through the logistic link)
  tau               : 30.0 (held fixed, not learned)
  fingerprint       : 00d2d3cf18de522c…

== THE PROBE: the fitted challenger through the additive validator ==
challenger, as fitted
  validate_params(1.7, 3.1, -0.8, 30.0, 0.0)
    -> ScorerParamsError: w_t must be between 0 and 1, got 1.7
```

**Reproduces the build prompt's reference measurement exactly**, to the character.

The first message names `w_t` only, and a build that read no further would conclude that relaxing
**one** bound was enough. It is **four independent rejections**:

```
== every reason it fails, one parameter at a time ==
w_t alone (decay = 1.7 > 1)
  validate_params(1.7, 0.35, 0.35, 30.0, 0.5)
    -> ScorerParamsError: w_t must be between 0 and 1, got 1.7
w_a alone (class_affinity = 3.1 > 1)
  validate_params(0.3, 3.1, 0.35, 30.0, 0.5)
    -> ScorerParamsError: w_a must be between 0 and 1, got 3.1
w_e alone (entity_affinity = -0.8 < 0)
  validate_params(0.3, 0.35, -0.8, 30.0, 0.5)
    -> ScorerParamsError: w_e must be between 0 and 1, got -0.8
threshold alone (0.0 pre-link)
  validate_params(0.3, 0.35, 0.35, 30.0, 0.0)
    -> ScorerParamsError: threshold must be at least 0.01, got 0.0: a threshold at or below zero links every candidate pair into one situation
```

**THE CONTROL**, which had to behave the other way:

```
== THE CONTROL: the seeded additive defaults through the same call ==
migration 0005's seeded row
  validate_params(0.3, 0.35, 0.35, 30.0, 0.5)
    -> ACCEPTED
```

**The threshold is the part that cannot be negotiated.** `MIN_THRESHOLD` is `0.01`; the challenger's
threshold is `0.0`. For the **additive** scorer a threshold at zero links every candidate pair into
one situation. For the **logistic** scorer `0.0` is the neutral point — exactly `p = 0.5`. *The same
number means opposite things to the two kinds*, so one validator cannot hold both without ceasing to
protect the additive one. That is Part IV.1's second refutation, measured.

### 2.2 Fact B — `scorer_lifecycle` has no dispatch

By `ast`, not `grep`. Appendix B: a grep once reported `engine.py` importing `netcorenoc.api` when
it was the docstring saying it never must, and six modules currently name a forbidden SQL expression
in prose.

The probe asks two structural questions of `load_scorer_config` — which scorer classes it constructs
and whether any construction is guarded by a branch; and where the `scorer_id` column's value goes,
into a comparison (dispatch) or a keyword argument (a label).

```
== THE PROBE: the shipped module ==
-- shipped (src/netcorenoc/scorer_lifecycle.py) --
  Q1  scorer constructions in load_scorer_config: 1
        line  69  scoring.AdditiveScorer(...)  -> UNCONDITIONAL
  Q2  reads of the `scorer_id` column, and where each value goes:
        line  75  row["scorer_id"] -> keyword argument scorer_id= (A LABEL)
  ==> comparisons on scorer_id: 0; match statements: 0
  ==> VERDICT: NO DISPATCH
```

**THE CONTROL** — a synthetic module that *does* dispatch, through the same probe. Without it,
"NO DISPATCH" could be the probe's only answer:

```
== THE CONTROL: a module that does dispatch, through the same probe ==
-- synthetic control (<control>) --
  Q1  scorer constructions in load_scorer_config: 2
        line   6  challenger.LogisticScorer(...)  -> guarded by if
        line   8  scoring.AdditiveScorer(...)  -> guarded by if
  Q2  reads of the `scorer_id` column, and where each value goes:
        line   5  row["scorer_id"] -> comparison (DISPATCH)
  ==> comparisons on scorer_id: 1; match statements: 0
  ==> VERDICT: DISPATCH FOUND
```

`scorer_id` is **written to the scorer it constructs**, never read to choose one. Dispatch by kind
is a thing this module has never had, and Phase 3 is where it acquires one.

### 2.3 Fact C — `scorer_config` receives manual retunes

Three parts, because the claim has three halves and a static probe alone would not carry it.

**C1, by `ast`** — what `POST /api/scorer`'s handler passes to `insert_scorer_config`:

```
  handler   : async def set_scorer(...)   ["route.post('/api/scorer')"]
  arguments to store.insert_scorer_config(...): 11
        [ 0] scoring.DEFAULT_SCORER_ID
        [ 1] scoring.CONTRACT_VERSION
        [ 2] body.w_t
        [ 3] body.w_a
        [ 4] body.w_e
        [ 5] body.tau_s
        [ 6] body.threshold
        [ 7] params_hash
        [ 8] principal.actor
        [ 9] now
        [10] body.note
  ==> arguments naming a judgement / challenger run / approver: 0 []
```

**C2, by schema** — the columns, with **a control that had to behave the other way**:

```
  scorer_config: ['id', 'scorer_id', 'contract_version', 'w_t', 'w_a', 'w_e', 'tau_s', 'threshold', 'params_hash', 'created_by', 'created_at', 'note']
  ==> columns naming a judgement / challenger run / approver: 0 []

  THE CONTROL: a table that DOES record which evidence authorised its rows.
  holdout_seal   : ['id', 'singleton', 'release', 'plan_sha256', 'created_at', 'digest', 'incident_count', 'corpus_incidents']
                   ==> evidence-naming columns: 1 ['plan_sha256']
  holdout_access : ['id', 'at', 'release', 'plan_sha256', 'purpose', 'granted', 'outcome']
                   ==> evidence-naming columns: 2 ['plan_sha256', 'purpose']
```

**C3, by execution** — a retune POSTed at a live app, and the row read back:

```
  POST /api/scorer -> 200 {'status': 'applied', 'config_id': 2, 'params_hash': '8580813d…f70e845'}
  scorer_config row id=2:
        id                 = 2
        scorer_id          = 'additive'
        contract_version   = '1.0'
        w_t                = 0.4
        w_a                = 0.3
        w_e                = 0.3
        tau_s              = 45.0
        threshold          = 0.55
        params_hash        = '8580813d41a45c8d9a7a4489315a6cea901909acfee571c25b9e84741f70e845'
        created_by         = 'adm'
        created_at         = 1786700956.7013416
        note               = 'widened the window after the Tuesday storm'
```

*(The probe applies the suite's own `_fast_scrypt` setting by hand, because it runs outside pytest.
That changes the cost of hashing a password and nothing about the row it reads.)*

**The conclusion the three parts carry together.** Add `challenger_run_id` / `verdict` /
`approved_by` to `scorer_config` and **every manual retune writes NULL into them**. `NULL` then
means both *"a human retuned this by hand; there was no judgement to record"* and *"this was a
promotion and its provenance is missing"*. Those are different facts and one column cannot hold
both — which is the ambiguity v0.9.2 spent a release eliminating, and the **third independent
reason** for a separate table, independent of the typed columns (Fact A) and of the validator.
