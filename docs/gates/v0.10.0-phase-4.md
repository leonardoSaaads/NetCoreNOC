# v0.10.0 — Gate 4: the sealed holdout

**Built before the estimator, deliberately.** DECISIONS #145: retrofitting isolation onto an
estimator that already holds a `Store` handle is exactly how a structural guarantee decays into a
convention — the code compiles either way and the only thing between them is somebody remembering.
Building the seal first means the estimator (Phase 5) is written against an interface that never
offered the sealed ids.

---

## 1. What was built

| | |
|---|---|
| `src/netcorenoc/seal.py` | the access path: construct, ratify, **spend**, summarise |
| `src/netcorenoc/store/seal.py` | the SQL, and the one expression that returns the membership |
| `maintenance._seal_once` | cuts the seal on a training tick, **off the batch lock**, degrading like every other slow-loop step |

**Construction, exactly as plan §3.3 fixes it and no other way:**

1. every labelled bag maps to its merge-aware incident, through Phase 2's single implementation;
2. incidents ordered by the timestamp of their **earliest** label, **ties broken by incident id**;
3. the **last third** by that order is sealed;
4. an explicit, ordered, immutable list with a SHA-256, written once.

The tie-break is not a detail. This project's own corpus applies 41 verdicts **one second apart**,
so collisions are ordinary, and an order depending on a stable sort of equal keys would depend on
the row order the store happened to return.

`sealed_third` is `ordered[len - len // 3 :]`, so the **kept** portion rounds up and the seal never
exceeds a third. On 37 incidents: **12 sealed, 25 kept.**

## 2. The four protections, and why each is structural

### 2.1 Constructed once — the refusal is the schema's

`holdout_seal.singleton` is `UNIQUE` and `CHECK (singleton = 1)`, so a second construction fails at
SQLite. `construct_seal` does **not** check-then-insert: it inserts, and the database says no. A
check-then-act would be a race and, worse, a rule a later caller could forget.

**The test tries to re-cut against a *different, larger* corpus**, so a silent re-derivation would
show as a changed membership rather than as a no-op:

```python
first = await _sealed(store)  # 9 incidents  -> 3 sealed
bigger = {200 + i: TS + 100 + i for i in range(30)}
with pytest.raises(sqlite3.IntegrityError):
    await _sealed(store, bigger)
assert after.digest == first.digest
assert after.corpus_incidents == 9
```

### 2.2 Unreadable — and the guard says the *right* thing

The first draft of this guard forbade the estimator **and every report** from importing `seal`. It
failed, and the failure was correct: **a report must print the query count** (§4.3(4) requires it
beside every holdout number ever published), so forbidding the import would only have moved the
counter out of the report — a weaker outcome dressed as a stronger rule.

The guard now states the property that actually matters, in two halves:

* **the estimator and the training path may not import the module at all** —
  `shadow_cv.py`, `training.py`, `census.py`, `shadow.py`;
* **exactly one function in the package may call the one expression that returns the membership.**

```python
assert callers == ["seal.py"], (
    f"the sealed membership is reachable from {callers}; only seal.spend may call it"
)
```

`seal.summary` returns a `SealSummary`, which **cannot carry the membership** — no field for it, no
method that yields it. So `shadow_report.py` holds the module, prints the state and the query count,
and still has no way to obtain the ids. That is a stronger guarantee than an import ban.

A third guard requires exactly one `SELECT … FROM holdout_seal_member` in the whole package. Its
first draft counted `store/seal.py`'s **docstring** as a second read; the shipped version subtracts
docstrings by AST and requires `FROM`, because a scan that cannot tell prose from SQL would have
reported the module that is correct.

### 2.3 Every access is a row — including refusals

`granted = 0` is what makes the log answer *"how many times has somebody tried"* rather than only
*"how many times did it work"*, and it is the only trace a missing-plan refusal leaves anywhere.

**`seal.summary` logs nothing**, on purpose: the report prints the seal's state on every run, and a
counter that moved when a report ran would be counting reports rather than counting the times the
holdout was spent.

### 2.4 A read requires a ratified plan already on record

Three refusals, each logged with its own reason: **no seal**, **no ratified plan**, and the caller's
own. `ratify` records a plan hash in an append-only, timestamped row **before** any read; the seal's
own `plan_sha256` counts, because the plan that authorised cutting it had to exist first.

**What this cannot do, stated in the module rather than implied:** it cannot stop a determined author
registering and reading in the same minute. What it does is make that sequence **permanently
visible** in an append-only log — which is the whole of what a *process* hazard can be defended
against by mechanism.

**The function is called `spend`, not `read`.** Reading a holdout is not a retrieval, it is an
expenditure: it costs the one-shot property permanently, and a function called `read` invites a
caller to do it twice.

## 4. Query count 0, asserted two ways

```python
async def test_v0100_spends_nothing(store):
    ...
    assert summary.query_count == 0
    assert not summary.spent
    callers = [...]  # every `.spend(` call in the package, by AST
    assert not callers, f"a v0.10.0 code path calls seal.spend: {callers}"
```

The second half is the one that matters: it is not an assertion about *this run*, it is an assertion
that **no v0.10.0 code path can spend the seal at all**.

And `test_the_query_count_moves_only_on_a_granted_read` is its control — a counter that could never
move would make "query count 0" a statement about the code rather than about this release's conduct:

```
assert (await seal.summary(store)).query_count == 0     # after a REFUSED read
await seal.spend(store, ..., plan_sha256=PLAN, ...)
assert summary.query_count == 1                          # a granted read IS counted
```

## 5. The report

A new section, printed whether or not a seal exists:

```
-- THE SEALED HOLDOUT ----------------------------------------
  no seal has been constructed yet — one is cut on the first
  training tick after a labelled corpus exists
  QUERIES (times spent)                        0
  state                                   INTACT
  access-log rows (incl. refusals)             0
  The holdout is NOT YET CUT. Reserving later is
  impossible; spending later is always possible. Adaptive selection
  over 12 queries on 37 incidents inflates a reported rate by a median
  +11.1 points when every candidate is equally good, so four releases
  tuning against one holdout would report an improvement produced
  entirely by looking.
```

That is the entire diff against the frozen expectation. **The first draft printed *"The holdout is
CONSTRUCTED AND NOT SPENT"* two lines below *"no seal has been constructed yet"*** — caught by
reading the regenerated report before re-freezing it, which is why the project's convention is to
read the diff rather than accept it.
