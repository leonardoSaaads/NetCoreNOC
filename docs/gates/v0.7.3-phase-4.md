### 1.1 `engine_base.py` is a ninth module the plan did not name

`MODULE-ARCHITECTURE.md` §5.1's table did not list it, and §5.2 put `EngineBase` in `engine.py`
implicitly. The import graph forbids that: `engine.py` imports the three mixins in order to
assemble `Engine`, so a mixin importing `EngineBase` from `engine.py` is a cycle. `store/base.py`
sits apart from `store/__init__.py` for exactly the same reason, so this is the established shape
rather than a new idea. Recorded here and added to `MODULE-ARCHITECTURE.md` §1's layer map.

## 2. `COHESION_EXEMPT` — the measurement, and the decision it settles

Gate 0 §4.1 predicted 425 must-stay method lines and concluded the mechanism would be required.
**Measured: `engine.py` is 542 lines**, so it is.

```python
COHESION_EXEMPT = {
    "engine.py": (
        "ingestion is sacred (MODULE-ARCHITECTURE.md §1): the batch lock and every decision that "
        "reasons about it stay in one file, because the invariant is only auditable if the ingest "
        "path can be read without following imports"
    ),
}
COHESION_EXEMPT_CEILING = {"engine.py": 542}
```

Note what is **not** there: no owner, no release, no date. That absence is the entire semantic
difference from `DEBT_ALLOWLIST`, and `test_cohesion_exemptions_carry_no_owner_and_no_fix_date`
asserts it. The ceiling is real — `engine.py` may not grow past 542 without someone arguing the new
number on its merits.

`engine.py` is the **only** entry, against a cap of two.

### 2.1 What stayed, and the one departure from both module tables

`maintenance()` (22 lines) and `maintenance_loop()` (6) stayed in `engine.py`, against
`MODULE-ARCHITECTURE.md` §7 and the build prompt's §5.1 table, under §5.2's escape hatch
(DECISIONS #90). `maintenance` is the only extraction candidate that acquires `self.store.lock` —
the same `asyncio.Lock` object `_commit_batch` takes — and the only one that calls a directive-4
must-stay method (`_close_situation`).

The structural payoff is concrete: keeping it removed the only mixin→`Engine` call, which is why
`EngineBase` needs **no method declarations at all** and stays a pure declaration site.

## 3. The layer violation, resolved

```
Engine MRO: Engine → MaintenanceMixin → GapMixin → ScorerLifecycleMixin → EngineBase → object
```

`engine.py` does not import `netcorenoc.api`. `runner.py` does, legitimately — it builds the HTTP
server. `tests/test_layers.py::test_the_engine_does_not_import_the_http_layer` asserts the first
separately from the general rule, so the specific edge this release resolves cannot regress
quietly. `EXEMPTIONS` is `{}` and `test_the_exemption_list_is_empty` says so.

### 3.1 The guard found two things I had not

Worth recording, because it is the justification for Phase 2's "install the guards first".

1. **`engine_base` was unplaced.** `test_every_runtime_module_is_assigned_a_layer` failed on a
   module that had escaped the layer table by not appearing in it — exactly the hole that test
   exists to close.
2. **`main.py` was still classified `engine`, and started importing `runner` (http).** The guard
   flagged an upward import. It was right, and the fix is the release stated in one line: `main.py`
   is *no longer the domain*. It was classified `engine` because it used to be the `Engine` **and**
   the entry point — which is precisely the confusion §1 recorded as the violation. Now that
   `engine.py` holds the domain, `main.py` is an entry point and nothing else, and its layer says
   so. Reclassifying it is not weakening the rule; it is the rule finally describing the code.

## 5. Compatibility

`main.py`'s `__all__` is the explicit re-export surface — `mypy --strict` forbids implicit

`src/netcorenoc/__main__.py`'s runtime import is unchanged. Verified from an installed wheel in

### 5.1 The third patch target, and a correction

Gate 0 §5.3 predicted `test_promotion.py`'s `MAX_ENTITIES_PER_NE` patch would move to
`netcorenoc.engine`. It did — **and it needed a second line.** The constant is read in two places:
`_resolve_entity` (`engine.py`) *enforces* the cap, and `_promotion_sweep` (`maintenance.py`)
*reports* it in the `entity.promote` audit detail. Patching one leaves the audit row claiming the
real cap while the effective cap is the fixture's. Nothing asserts that field today, so a single
patch would have passed — which is exactly the sort of quietly-wrong fixture this release is
supposed not to leave behind. Both bindings are patched, with a comment saying why.

A full `make qa` also caught that the first attempt still named `netcorenoc.main`, which had
resolved while `main.py` transiently still imported the constant. The targeted subset had passed;
only the full run failed. Recorded because it is the argument for running the whole suite at a gate
rather than trusting a subset.
