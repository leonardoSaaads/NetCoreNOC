## 1. The eight corrections, each traced

### §9.1 — the sentence that produces the wrong model

**Where:** §3.1, struck through in place; the correction is the new **§3.1a**.

**The withdrawn sentence:** *"That is the majority class. Supervised training without it is
impossible: a model trained only on pairs that linked learns 'everything links'."*

**Why it is wrong — twice, and the second was only findable by measurement:**

1. **Conceptually.** The evaluated-and-rejected pairs are not the majority class of the **human
   label**. They are the **machine's own decision**. The human majority class does not exist in
   quantity and never will. Read in good faith by whoever writes v0.9.0 — and it *will* be read in
   good faith, because it is a specification — the sentence authorises training a challenger against
   `incumbent_linked`, which is the imitation trap: a model fitted to reproduce the champion cannot
   exceed it, and looks excellent while converging on it.
2. **Arithmetically, on this project's own corpus** (Phase 0 §3a):

   | Population | Count | Share |
   |---|---|---|
   | pairs evaluated | 194 341 | 100 % |
   | pairs accepted | 194 002 | 99.83 % |
   | links persisted after `MAX_LINKS_PER_ALARM` | 10 973 | 5.6 % |
   | links lost to truncation | 183 029 | 94.2 % |
   | **pairs evaluated and rejected** | **339** | **0.17 %** |

   The 17.7× amplification is **truncation of accepted links**, not rejection.

**The invariant now stated:**

> **No metric that decides promotion may be computed against `incumbent_linked`.**

with the scope of the prohibition made explicit — the column stays legitimate as provenance,
context, a feature, and the basis of champion/challenger comparison. The distinction is between a
*feature* and a *target*, and §3.1a says so.

**Traces to:** build-prompt directive 3 and §9.1; Phase 0 §3a for the measurement.
**Recorded as:** DECISIONS #103.

### §9.2 — the merge finding

**Where:** new **§2.2a**, immediately after the staleness argument it strengthens.

§2.2 justified the membership record by *staleness*. The stronger reason, reproduced by execution:
**a merged situation's label loses its referent entirely** — not "refers to a subset", refers to
**nothing**. The natural join `feedback ⋈ situation_alarm` returns empty; the surviving situation
holds the union of both bags plus the bridging alarm, with nothing distinguishing them.

**A second loss, found in the same reproduction and not previously recorded anywhere:**
`merge_situations` writes `status='merged'` but **not the destination**, so the merge chain is
unrecoverable too. This promotes §5c's situation lineage from a nicety to a **schema prerequisite**:
without a recorded merge edge, v0.10.0's split-by-incident cannot be built at all.

**This is what answers the draft's own open question §6a(3)** — with an argument, not a preference:
a digest proves that something changed and cannot say what it was, and after a merge there is
nothing left to compare it against. Hence server-side, ordered ids, a child table, digest stored
alongside.

**Traces to:** Phase 0 §1 and §2. **Recorded as:** DECISIONS #104.

### §9.3 — the formalism named

**Where:** new **§3.3a**.

> This is **multiple-instance learning**. `confirm` is an **all-positive bag**; `split` is a bag
> with **at least one negative**, and it does not say which.

The asymmetry is why `learn.penalize()`'s thirty-six-pair expansion is right as a *learning
heuristic* (bounded by F36, reversible, claims nothing about any pair) and wrong as *training data*
(fabricated negatives indistinguishable from observed ones). Naming the problem class tells v0.9.0
which problem it is solving rather than leaving *"we left it open"* to read as indecision — and the
section enumerates the four candidate derivation policies it must choose **between and evaluate**.

**Traces to:** build-prompt §9.3; draft §3.3, which had the fact but not the name.

### §9.4 — the leakage vectors

**Where:** new **§3.5**, four subsections, each naming the column that measures it.

| Vector | Measured by |
|---|---|
| (a) matrix epoch — a label at *T* is inside the features at *T+1* | `a_epoch`/`e_epoch` on the pair row, joined against `feedback.created_at` |
| (b) re-fire near-duplicates | the immutable observation row |
| (c) situation lineage — two labels that are one incident | situation id at label time **plus the recorded merge edge** |
| (d) four consecutive releases tuning against one small dataset | **nothing in v0.8.0** — a process hazard, named so v0.10.0 does not rediscover it |

**(d) is recorded as unmeasurable on purpose.** The honest statement is that the schema *enables* a
fix rather than providing one. A leakage vector listed without saying it is unmeasured would be
worse than not listing it.

**And §3.5a carries a correction to the build prompt itself** — see §2 below.

### §9.5 — the security posture

**Where:** new **§5a**.

The dataset is a **scope bypass by construction**: capture runs engine-side, where visibility
scoping does not exist and must not, because correlation learns across the whole estate. The corpus
therefore contains every NE, entity and raw varbind, ungoverned. Four rules, written so a later
release cannot soften them by increments: admin-only on every read path; aggregates only from the
report; any export is `config`-class and audited like the audit export; and the client fingerprint
is untrusted input that **must never become an existence oracle**.

**Traces to:** build-prompt directives 7 and 8; the F34/F37 precedent that "no such thing" and "not
yours" are one code path.

### §9.6 — "keys are not features", and store-what-cannot-be-recomputed

**Where:** new **§4a**, two named rules, with the store/derive/never-freeze table.

Rule 1 makes "be generous" operational: a column exists because it **cannot be recomputed** or
because it is a **key**, and for no other reason. Rule 2 states why `alarm_a`, `ne_id` and
`class_id` are joins and not inputs: `ne_id = 47` means "the forty-seventh NE this appliance ever
saw", so a model fed it learns one customer's topology and **generalises to nobody** — while scoring
extremely well on that customer's held-out data, which is what makes the mistake survive review.

### §9.7 — the acquisition channel

**Where:** new **§5b**.

v0.8.0 writes `organic` on every row and that is the whole behaviour. The column exists because
solicited labels have a **deliberately different distribution**, and mixing them into one
undifferentiated column would **destroy the bias characterisation retroactively** — including for
rows written before solicitation began. Adding it later costs a migration *plus* an ambiguity no
migration can resolve.

### §9.8 — confidence, uncertainty, and calibration

**Where:** new **§6b**.

Both halves, as required:

* **The direction (v0.9.0+)**, and the obligation that comes with it: **calibration is a metric
  v0.9.0 owes** — reliability, Brier or ECE — because a threshold on an uncalibrated score is
  meaningless, and calibration is not implied by accuracy.
* **The trap, as a rule**: *confidence may route what the operator is asked; it may never authorise
  autonomy.* The long-term roadmap's autonomy trigger is **measured agreement with humans**, never
  self-reported confidence. A confidently wrong model is more dangerous than an uncertainly wrong
  one precisely because confidence is what a self-authorising system would gate on.

## 2. Corrections this release makes to its **own build prompt**

Recorded because a gate that only confirms the brief has not checked it.

**The matrix epoch does not advance on `penalize()`.** The build prompt's §1.6 asks to "show that it
advances on `penalize()`", and §5.2 builds the case for the column on that mechanism. Executed
(Phase 0 §6):

```
epoch before penalize : (0, 0)
epoch after  penalize : (0, 0)     -> advanced: False
A/E pair mass before  : (1.0, 1.0)
A/E pair mass after   : (0.5, 0.5)   -> mutated: True
```

Since v0.7.1's F36 fix (DECISIONS #69) **neither** feedback path ticks the epoch. Only a closed
situation does. The contamination the column exists to expose is **real** — the mass moved 1.0 → 0.5
— but it travels through the **mass values**, not the epoch counter.

**The column survives; the stated reason does not.** §3.5a now gives the correct one: a captured
`A` value is a *decayed reading* against `Matrix.epoch` at that instant, so without the epoch a
reading of 0.4 at epoch 12 and one at epoch 900 are not comparable — and no later join recovers it,
because the matrix is mutated in place. The bias report's leakage item is consequently a **join of
pair epochs against label timestamps**, not a reading of the epoch alone.

Had this been taken on trust, v0.9.0 would have been briefed to look for contamination in a counter
that never moves, found none, and concluded there was none.

## 3. The draft's four open questions, answered by measurement

§6a Group C is answered in the new **§6a-answered**, each with the number that decided it.

| # | Question | Answer | Deciding measurement |
|---|---|---|---|
| 1 | Sink write synchronous or queued? | **Synchronous** | the batch is already one transaction per 500 items, so buffering leaves the transaction count unchanged and buys nothing — while putting dataset rows outside the atomicity the batch already provides |
| 2 | Observation row per trap or per activation? | **Per activation** | 3 159 traps → 2 256 activations (**0.7142**); the 903 extra rows are re-fires that never reached `score_link`, so nothing could join to them |
| 3 | Membership as columns or child table? | **Child table + digest** | the merge (§2.2a): after it there is nothing left to compare a digest against |
| 4 | Retention per sink? | **Three tiers, ordered, admin-set** | the sink grows with traffic and the dataset with labels, so one number cannot serve both |

Answer 1 is provisional on Phase 6's measurement, and §6a-answered says so; the others are settled.
