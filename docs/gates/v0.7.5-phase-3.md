## 3. Was dropping the strip safe? — the question answered by running it, not by arguing it

The build prompt asserted `docs/README.md` was safe because both its examples are fenced. Phase 0
§3.3 found that incomplete, and Run 3 settles it:

* Both **examples** are fenced and stay excluded. Confirmed.
* `docs/README.md` also carries **three real, un-fenced element tags** (lines 48/51/54, the draft
  index) which go from invisible to visible. The prompt did not mention them.
* They are harmless, but **not for the reason the prompt gave**. `docs/README.md` remains skipped by
  `test_a_documents_element_tags_match_its_own_release_claim` because that test examines only
  documents making **exactly one** governed claim, and `docs/README.md` makes **none** — its only
  `<!-- release-claim: -->` is inside a fence. The three tags are then seen only by
  `test_no_element_is_tagged_for_a_release_the_roadmap_does_not_name`, which skips `v0.7.5` (below
  `GOVERNED_FROM`) and accepts `v0.8.0` and `v0.13.0` because both are in the release table.

The conclusion the prompt reached is right; its reasoning was not the reason. Recorded because
"verify, do not assume" is the instruction, and the verification found something the assumption
would have missed.

## 4. The tests that were missing

Three added to `tests/test_documentation.py`. All drive the **real** guard function over a synthetic
document rather than re-implementing its logic — a re-implementation would be free to agree with
itself.

| Test | What it demonstrates |
|---|---|
| `test_the_element_tag_check_goes_red_on_a_backticked_stray_tag` | the failure mode, with the tag **backticked**. Its docstring says the backticks are the whole point and that removing them to make a future change pass would restore exactly the blindness this release fixed |
| `test_a_consistently_tagged_document_stays_green` | **the control** — same document, same backticks, tag matching the claim. Without it the test above could be detecting the injection rather than the inconsistency |
| `test_element_tags_inside_fenced_blocks_are_still_excluded` | dropping the inline strip must not drop the **fenced** strip with it. One tag in the repository depends on this |

`_drive_guard_over` redirects `live_docs` and `REPO_ROOT` (the guard reports
`path.relative_to(REPO_ROOT)`) but deliberately **not** `ROADMAP_TABLE_DOC` — the release table
stays the real one, so these tests check real claim keys.

## 5. The docstring, and the convention

`source_of`'s docstring gave the wrong reason for the strip: it claimed the strip was what made "the
convention" work, by keeping historical mentions from registering as claims. The convention is the
**opposite** — `docs/README.md` specifies the backticked form as *the* way to tag an element — so
the strip filtered the live tags, not the historical ones. Rewritten, with the measured figure in it.

`_normalised` has always kept inline code, for reasons its own docstring states. The two functions
now agree; that disagreement was the second thing wrong here.

`docs/README.md` gains a paragraph stating that backticks are the convention **and** that the guard
reads them, so the two rules cannot drift apart again — with the v0.7.4→v0.7.5 period named as the
window in which they had.

## 6. Not a security finding

No `F` number. It is a defect in a test: no attacker-reachable surface, no route, no data. It gets
DECISIONS #100 and this gate. Recorded here because the temptation to number it is real — it is a
guard failing open, which *sounds* like F40/F41/F42 — and the difference is that this guard protects
the repository's claims about itself, not the appliance.
