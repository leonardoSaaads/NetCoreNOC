# v0.10.0 — Gate 3: migration `0012`

**Exactly one migration**, additive, forward-only, and it seeds **nothing**.

---

## 1. What it adds, and why each piece is shaped as it is

| Table | Rows after upgrade | What it holds |
|---|---:|---|
| `holdout_seal` | **0** | one row, ever: the release, the ratified plan hash, the SHA-256 over the membership, the counts |
| `holdout_seal_member` | **0** | the explicit, ordered, immutable list of sealed incident ids |
| `holdout_access` | **0** | append-only: who asked, under which plan, what for, and what came back |

**The refusal is structural, not a rule somebody remembers.** `holdout_seal.singleton` is a constant
column carrying `UNIQUE` and `CHECK (singleton = 1)`, so a second `INSERT` fails at SQLite rather
than at whichever layer above thought to look first. *A seal that can be rebuilt is a seal that can
be rebuilt **after** seeing a result*, and the person rebuilding it would be doing so for a reason
that felt good at the time.

The rejected alternative — many seals, take the newest — reads as more flexible and is precisely the
affordance the plan forbids.

**An explicit list, not a predicate.** *"The last third by earliest label"* would be re-evaluated
against whatever the corpus looked like at read time, so the sealed set would **drift** as labels
arrived and a release could change what was sealed by changing what was labelled. Storing the ids
makes the seal a fact about a moment rather than a query about a table.

**Refusals are logged too**, and `granted` is what distinguishes them. A log recording only
successful reads answers *"how many times has the holdout been spent"* and not *"how many times has
somebody tried"* — and the second is the question a reviewer of a four-release tuning loop actually
needs. It is also the only way a missing-plan refusal leaves a trace.

**Not the audit log**, deliberately. `audit_log` is a hash-chained record of **operator** actions
reachable from HTTP; nothing here is reachable from a route and no principal performs it. Adding a
system-generated action to a frozen catalog is the decision `SECURITY-REVIEW-0.9.2.md` §4.6 declined
to make alone, and this release does not make it either.

## 3. No rows seeded — and why that is the opposite of `0011`'s decision

`0011` **backfilled** a column, and was right to, on DECISIONS #133's line: *recomputing a quantity
from evidence already stored is derivation, and may be backfilled.*

**A seal is not a derivation.** It is a **choice** about which evidence will be allowed to decide
something later, and manufacturing one during an upgrade would make that choice on behalf of an
operator who was never asked — at whatever size the corpus happened to be at the moment they ran
`pip install -U`. A fresh install and an upgraded one both start with no seal.

`tests/test_upgrade.py::test_v0100_upgrade_applies_0012_and_seeds_nothing` asserts it, and its
assertion is the inverse of `0011`'s: three tables, nothing in them.

## 4. The schema's refusals, exercised against the database

```
THE SCHEMA'S OWN REFUSALS, exercised directly:
        second seal refused         yes  (IntegrityError: UNIQUE constraint failed: holdout_seal.singleton)
        seal UPDATE refused         yes  (IntegrityError: holdout_seal is immutable: a seal that can be edited is not a seal)
        seal DELETE refused         yes  (IntegrityError: holdout_seal is immutable: deleting a seal is how it gets re-cut)
        access UPDATE refused       yes  (IntegrityError: holdout_access is append-only)
        access DELETE refused       yes  (IntegrityError: holdout_access is append-only)
        CONTROL: inserts still work  2 access rows
```

**The control found a real defect in the first version of the test**, and it is worth recording
because it is the exact failure Appendix B warns about. A `BEFORE UPDATE` trigger on an **empty
table fires on nothing**, so the first draft — which checked refusals before inserting anything —
reported *"the schema permitted an update to the membership"* while the trigger was in fact
present and correct. A refusal test that runs before any row exists proves nothing whatever.

The shipped test therefore **populates every table and asserts the inserts worked** before checking
a single refusal:

```python
assert row is not None and tuple(row) == (1, 1, 1), (
    "a table refused a legal insert, so every refusal asserted below would be meaningless"
)
```
