## Upgrade from a live v0.5.0 database — verified

`test_upgrade.py::test_v060_upgrade_preserves_grouping_and_seeds_provenance` builds a database at
schema v4 (a genuine v0.5.0 install), drives a fixture through the **real engine**, persists
learned state, and writes a chained audit row — then reopens the same file with migration `0005`
present:

| Property | Result |
|---|---|
| Schema | 4 → **5** |
| `integrity_check` / `foreign_key_check` | clean |
| **Grouping** | situation partition **identical member-for-member**, before and after |
| Learned state | `edge` rows identical |
| Active alarms | identical |
| Audit chain | still verifies |
| Provenance | seed active, `config_id` 1, fingerprint equals `AdditiveScorer().params_fingerprint()`, **zero** situations left with a NULL `scorer_config_id` |
| A fresh v0.6.0 database | reproduces the same partition from the same fixture |

`test_migration.py::test_migrate_populated_v050_database_seeds_the_scorer_config` covers the same
upgrade over a raw populated v0.5.0 schema and additionally asserts both append-only trigger sets,
the single-row `CHECK` on the pointer, and that a reopen neither re-runs the migration nor
duplicates the seed.

**A legacy `OPTICORR_*` variable now errors with the migration path**, in both entry points:
`test_f26_legacy_env_prefix_is_a_startup_error` (names every variable and replacement, plus
`MIGRATION.md`), `test_f26_legacy_env_error_names_no_value` (a CIDR and a key path never appear in
the message), `test_f26_cli_refuses_a_removed_legacy_env_alias` (exit 2 rather than silently
reading the default database).
