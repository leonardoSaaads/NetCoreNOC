# v0.9.0 — Gate 3: migration `0009`

**Exactly one migration**, `0009_shadow_mode.sql`, forward-only and additive, applying cleanly onto a
populated v0.8.1 database (schema v8 → v9).

---

## 1. What it adds

Two tables and two indexes. Nothing else — no column on an existing table, no trigger, no view, and
**no pointer from `scorer_config` to a challenger**.

| Table | Rows are | Counterpart |
|---|---|---|
| `challenger_run` | one per training attempt: identity, policy, training window, effective sample size, **the resolved thresholds**, the verdict, and the fit | `capture_run`, for the same reason — these are constants over a period, not per-opinion facts |
| `shadow_opinion` | one per **sampled** pair the challenger scored **online, inside the engine** — with its features **as served** | none; this is the half of the skew test that offline reconstruction cannot produce |

### The two design points that carry weight

**A `challenger_run` row is written even when nothing is fitted.** `sufficient = 0` with
`coefficients` NULL is this release's most likely outcome and it is a **result**, not an absence:
*which floors were missed, by how much, and how long until they would be met at the measured
labelling rate.* A schema that could only record a successful fit would make insufficiency
invisible — precisely what the pre-registration exists to prevent.

**`shadow_opinion` stores the features AS SERVED, and that is the whole point.** Offline
reconstruction recomputes the challenger's opinion from `dataset_pair`, which is tautologically
consistent with itself and therefore **cannot measure training/serving skew**. These columns are
the other side of the comparison. Their disagreement *is* the skew test (DECISIONS #119), the
pre-registered expectation is **0.0000 %**, and a non-zero rate is a defect rather than a tolerance
to widen.

`thresholds` is stored as JSON on the run row because `resolved = the more demanding of (project
floor, deployment policy)` (DECISIONS #114) — a "passed" that does not carry its bar is a claim, not
a result.

`coefficients` is JSON rather than columns for the reason `dataset_observation.varbinds` is opaque:
the feature set is a modelling decision this release is explicitly **not** freezing for v0.10.0.

### What it deliberately does not add

* **No target column**, in either table. The only label in this schema lives in `feedback` and
  reaching it requires the join — 0008's friction, preserved.
* **No pointer making the challenger activatable.** There is no promotion mechanism in this release,
  and the schema declines to make one convenient: adding a `scorer_config → challenger_run` edge
  would be a visible, arguable diff rather than an autocomplete away.
* **No route.** v0.9.0 adds none at all, which is the strongest possible form of the
  admin-only posture 0008 established.

## 2. Applied to a populated v0.8.1 database

`tests/test_upgrade.py::test_v090_upgrade_applies_0009_and_changes_no_grouping`, in the pattern the
repository has used since v0.6.0: a genuine v0.8.1 database is built by freezing the migration
directory at 0008 **by migration number**, so a later release adding 0010 cannot silently un-freeze
the fixture.

The fixture is not an empty database. `fiber_cut.json` is driven through a real engine, a real
maintenance pass persists learned state, a real label promotes a corpus, and an audit row is written.

Asserted **before the engine starts** — because `Engine.start` legitimately opens a new
`capture_run` in any new process, and the question here is what the *migration* did:

| Claim | Assertion |
|---|---|
| schema advances by exactly one | `schema_version() == latest_schema_version() == 9` |
| the corpus is untouched | `dataset_stats()` byte-equal to the pre-upgrade reading |
| **no rows seeded** | `COUNT(*)` is 0 in `challenger_run` **and** `shadow_opinion` |
| the audit chain verifies **to the same final hash** | `verify_chain().ok` and `final_hash` unchanged — the migration wrote no event |
| the database is healthy | `integrity_warnings == []` (the `PRAGMA integrity_check`/`foreign_key_check` pass) |

Then, after `Engine.start()`:

| Claim | Assertion |
|---|---|
| grouping is identical | the situation partition is member-for-member equal |
| learned state survives | `graph_snapshot(min_edge_n=0)["edges"]` equal; `(A.epoch, E.epoch)` equal |
| read models are identical | `stats()` and `list_situations(None, 500)` equal |
| **first boot writes no shadow row** | `COUNT(*) FROM shadow_opinion == 0` — capture opened a run; the challenger did not |
| the champion is still the champion | `active_scorer_config()['scorer_id'] == 'additive'`, and `correlator.scorer.active.scorer_id == 'additive'` |

The last two are the release's most important negative claim: **shadow mode changes no grouping, and
it changes none on the first boot after the upgrade either.** A shadow-mode release is structurally
tempted to arrive with an opinion already in the database. This one does not.

## 3. Packaging

Freshly built from the working tree:

```
$ python -m build
netcorenoc-0.8.1-py3-none-any.whl
netcorenoc-0.8.1.tar.gz

wheel  netcorenoc/migrations/0001_init.sql … 0008_feedback_dataset.sql, 0009_shadow_mode.sql
sdist  netcorenoc-0.8.1/src/netcorenoc/migrations/0001_init.sql … 0009_shadow_mode.sql
```

**Nine migrations in both artefacts.** `pyproject.toml`'s `package-data` already globs
`migrations/*.sql`, so no packaging change was needed — which is the F12/F13 fix continuing to pay
for itself, and it is asserted rather than assumed by `tests/test_deploy.py` and
`tests/test_supply_chain.py`.

(The version still reads 0.8.1 here: the bump to 0.9.0 is Phase 7's, gated by `make release-check`.)
