One migration, additive and forward-only, applied to a database written by **real v0.9.1 code**.

---

## 1. What `0011` adds

| Column | Tier | Meaning | Backfilled? |
|---|---|---|---|
| `excluded_reconciled` | **2** | `\|reported ∩ the server's own bag\|`, DISTINCT by alarm id | **yes** — derivation |
| `excluded_reconciled_source` | — | `'live'` \| `'backfill'` \| `NULL` | yes, as `'backfill'` |
| `excluded_reconciled_out_of_scope` | **3** | how many reconciled marks were about members the labeller could not observe | **no**, and there is no exception |

`excluded_count` is **re-documented, not changed**. Its bytes and its meaning are exactly what
v0.9.1 wrote: what the client reported, a measurement of the client, never of the evidence.

Three constraints ship with them, each enforced by SQLite itself (Gate 0 §7 established the
capability by experiment):

```sql
CHECK (excluded_reconciled IS NULL OR (excluded_reconciled >= 0
       AND member_count IS NOT NULL AND excluded_reconciled <= member_count))

CHECK (excluded_reconciled_out_of_scope IS NULL OR (excluded_reconciled_out_of_scope >= 0
       AND excluded_reconciled IS NOT NULL
       AND excluded_reconciled_out_of_scope <= excluded_reconciled))
```

`member_count IS NOT NULL` is stated **explicitly** and is not brevity: SQLite treats a `CHECK` that
evaluates to `NULL` as *satisfied*, so `x <= member_count` against a `NULL` `member_count` would
pass silently and a reconciled count could be written against a bag whose size was never recorded.

`excluded_reconciled_source`'s value set is deliberately **not** constrained in the schema, which is
`0010`'s own reasoning about `acquisition_channel` applied unchanged: a `CHECK` on the value would
have to be rewritten by every release that adds a source, and SQLite cannot alter one in place. It
is enforced in `store/feedback.py`, where it can be revised.

## 4. Two things that had to be decided in the SQL, and were

**`COUNT(DISTINCT x.alarm_id)`, not `COUNT(*)`.** `feedback_exclusion`'s primary key is
`(feedback_id, position)`, so a client may legitimately send `[5, 5, 5]`. Three rows are recorded as
evidence, and they reconcile to **one** mark, because they are one member of the bag. `COUNT(*)`
would have produced 3 and could — on a bag with one member — have produced a reconciled count
larger than `member_count`, which the `CHECK` would then have refused **during the migration**,
turning a hostile label into a failed upgrade. The hostile-input suite in Phase 3 covers this case
directly.

**The `WHERE` clause is the reports' own predicate.** `excluded_count IS NOT NULL AND member_count
IS NOT NULL` is exactly what `bias.py` uses to decide a row carries an assertion, so the backfilled
population and the reported population are the same set by construction. It also guarantees the
`member_count IS NOT NULL` the `CHECK` requires, so the migration cannot fail on a pre-v0.8.0 row.

## 5. What an operator will see

**Nothing numeric, on any corpus written by the shipped UI.** Gate 0 §6 counted the disagreement on
the fullest corpus this repository can construct: **0** rows where the reported count differs from
the reconciled one, **0** rows with `excluded_count > member_count`. The backfill corrects nothing;
it records that nothing needed correcting — which is what lets a later reader tell *reconciled and
equal* from *never reconciled*.

`MIGRATION.md` states this in the operator's own terms in Phase 7.
