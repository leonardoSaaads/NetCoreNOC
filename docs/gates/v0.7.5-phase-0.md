### 2.2 Correction to the build prompt's §4.1 table — *why* two shapes evade

The prompt's table says the `Mount` shape evades because it has "no `.path` on newer Starlette".
**On starlette 1.3.1 that is false, and the reproduction shows it:** the `Mount` carries
`path='/api/sub'`. It evades through the *other* fail-open branch — `methods=None`, so
`sorted(getattr(route, "methods", set()) or set())` is the empty sequence and the inner loop never
executes. The same is true of `APIWebSocketRoute`.

So `assert_every_route_is_declared` has **two** fail-open branches, not one:

| Branch | Shapes that take it (on 0.141.1) |
|---|---|
| `if path is None: continue` | `_IncludedRouter` |
| the inner loop over an empty `methods` | `Mount` (sub-app), `Mount` (StaticFiles), `APIWebSocketRoute` |
| the `HEAD`/`OPTIONS` exemption | an explicitly-registered `HEAD`-only `APIRoute` |

This makes the finding **larger** than the brief described, not smaller, and it changes the fix:
patching only the `path is None` branch would close one shape out of five. §4.3's shape allowlist
closes all of them at once, because it refuses on the *class* before either branch is reached.

### 2.3 `OPTIONS` and `HEAD`, measured

`OPTIONS` is **never** synthesised into `route.methods` — a `GET`-declared `APIRoute` carries
`{'GET'}` exactly. So the `OPTIONS` half of the v0.7.4 exemption never fires on anything, and
removing it costs nothing.

`HEAD` is subtler than the v0.7.4 docstring claims. A FastAPI `APIRoute` declared `GET` carries
`{'GET'}` — **no synthesised `HEAD`**. The only route on the probe app carrying `{'GET', 'HEAD'}`
is `/openapi.json`, which is a **starlette** `Route`; Starlette's `Route` synthesises `HEAD`
alongside `GET`, FastAPI's `APIRoute` does not. That is exactly the case §4.3's narrowed exemption
describes: skip `HEAD` only when `GET` is present on the same route. A `HEAD` that is a route's
sole method (shape 5) was asked for explicitly and currently passes unchecked.

### 5.2 The absence of a JS runtime — evidenced, with an honest caveat

Searched `pyproject.toml`, `Makefile`, `flake.nix` and `.github/workflows/` for `node`, `npm`,
`npx`, `jsdom`, `playwright`, `puppeteer`, `selenium`, `headless`, `quickjs`, `pyminiracer`,
`dukpy`, `js2py`: **every one absent.** There is no `package.json`, no `node_modules` and no `.mjs`
file anywhere in the repository.

* `flake.nix` `devShells.default` declares exactly `[ python pkgs.gnumake ]`.
* `.github/workflows/ci.yml` uses `actions/setup-python` and nothing else; every step is
  `make <target> PYTHON=python`.
* `pyproject.toml`'s `dev` extra is 11 Python packages, none of which embeds a JS engine.

**The caveat, stated because it would otherwise look like an oversight:** the *container this build
runs in* does have `node`, `npm` and `bun` on its `PATH` (`/opt/node22/bin/node`,
`/root/.bun/bin/bun`). They are part of the build environment, not of the project. Reaching for
them would produce a test that passes here and fails in CI, in the Nix dev shell, and on a
maintainer's machine — a test whose green tick is an artifact of the machine it ran on. That is
worse than no test, and it is a second, independent reason for §5.4's answer beyond the
"no new dependency" rule of §3.4. Recorded so that a later reader does not conclude the runtime
was simply overlooked.

**Consequence, accepted rather than engineered around:** the behavioural claims of §5.1–§5.3 —
"the same DOM node survives an SSE update", "the container is never displayed empty" — **cannot be
proved automatically in this repository.** The draft's §5 asks to "drive `applyUpdate` twice and
assert the same DOM node is still in the document". There is no DOM. §5.4(a)+(b)+(c) is what is
done instead, and Gate 4 states which claims rest on the manual protocol.
