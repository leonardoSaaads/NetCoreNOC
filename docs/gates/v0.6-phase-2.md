## The migration, in one screen

```
scorer_config   append-only, immutable; BEFORE UPDATE/DELETE -> RAISE(ABORT)
                (id, scorer_id, contract_version, w_t, w_a, w_e, tau_s, threshold,
                 params_hash, created_by, created_at, note)
                NO sanctioned deleter — the retention prune does not touch it
scorer_active   one row, CHECK (id = 1) -> apply and rollback are the SAME UPDATE
situation       + scorer_config_id INTEGER NULL REFERENCES scorer_config(id)
seed            id=1: additive / 1.0 / 0.3 / 0.35 / 0.35 / 30.0 / 0.5, active
backfill        UPDATE situation SET scorer_config_id = 1 WHERE scorer_config_id IS NULL
```

`params_hash` on the seed is the literal
`c490028245242445e9f58e46e11ac534e5a3f8be03bd9643135557a2e3183418`, the sha256 of the canonical
JSON `{"contract_version":"1.0","scorer_id":"additive","tau_s":30.0,"threshold":0.5,"w_a":0.35,"w_e":0.35,"w_t":0.3}`.
A Phase-3 test asserts it equals `AdditiveScorer().params_fingerprint()`, so a future change to
either the defaults or the canonicalisation cannot silently desynchronise the seed.

## Design decisions this phase locks in

- **Provenance by reference** (DECISIONS #47) — one nullable FK per situation into an immutable
  table, rather than five denormalised floats per situation or archaeology over the audit log.
- **Apply and rollback are the same operation** — an UPDATE of the single `scorer_active` row.
  There is no "delete the bad config" path, by construction.
- **No sanctioned deleter for `scorer_config`**, deliberately unlike `audit_log`'s audited
  retention prune: a situation's provenance must outlive the alarms that formed it.
- **The seed is what makes parity hold.** A migrated database and a fresh one both start at the
  coded defaults, and the backfill is *truthful* — every pre-v0.6.0 situation genuinely was formed
  by those parameters.
- **The reload point is explicit**: `Engine.start()` and the start of the next
  `Engine.maintenance()` pass (≤ 5 s). Never mid-batch, so a batch is always scored by exactly one
  configuration and a situation's recorded `config_id` is always the one that scored it.
