# v0.14.0 — Gate 1: scope, decisions, and the coverage band

**The scope is [`../scope/SCOPE-0.14.0.md`](../scope/SCOPE-0.14.0.md).** This gate records the
decisions taken before any model code existed, the one roadmap sentence this release had to correct,
and the coverage band — registered, as ADR #181 requires, **before the measuring run.**

ADRs continue from **#183**. Nothing before it is renumbered, and nothing before it is edited.

---

## 1. The correction, and why it is a new ADR rather than an edit

`docs/architecture/ROADMAP-0.8-TO-0.13.md` said, in a bullet written when the only non-additive kind
was a logistic model:

> tree ensembles … can only enter through the ONNX door, and that door opens in v0.13.0

**That is false, and this release is the proof.** A gradient-boosted model over three features is a
list of small trees and a shrinkage constant; it is a few hundred lines of pure Python, it needs no
runtime, and it enters through the same `model_version.scorer_for` branch a decision tree enters
through. The sentence conflated *"a model this project did not write"* with *"a model of this
family"*, and the second was never the constraint.

**ADR #183 supersedes it. The sentence itself is not rewritten.** What was added is an amendment
block *beneath* it, naming the ADR and stating what is wrong and why — the project's own convention,
and the reason is in `docs/adr/README.md`: a log whose entries change is a log of what a project
currently believes, not of what it decided and when. A reader who finds the bullet and reads on
learns something a corrected sentence would have hidden — *that this project believed the wrong thing
for two releases, and what changed its mind.*

The amendment names the confusion precisely, because the confusion is the interesting part:
**principle 5 forbids *dependencies*, not *implementations*.** v0.9.0 had already written logistic
regression in pure Python on the argument that *"logistic regression over a handful of features is
arithmetic"*. A CART over three continuous features is arithmetic too. **The ONNX door was never the
only door — it was the only one anyone had considered.**

The claim marker for the release table collided with the roadmap's own, and was resolved by
resequencing with ADRs #183 and #184 landing **before** the pre-registration. That ordering matters:
the plan is hash-pinned from the instant it is ratified, so anything that had to move around it had to
move first.

## 3. The coverage band

ADR #194 carries the arithmetic. The short form:

* **Measured first, on the Gate-0 commit** (`4aed642`, working tree clean, stashed for the purpose),
  before one line of model code existed: **96.03 %, 96.03 %, 96.05 %** over 1428 tests — a spread of
  **0.02 points**. An earlier triple was **discarded** for having been measured against a tree that
  was still changing, and `../gates/v0.14.0-phase-0.md` §7 records that it was.
* **The band, registered before the measuring run: 95.30 % – 96.40 %.**
* **Both bands are reported in Phase 8** — #181's 95.60–96.60 % and this one — and **neither is
  re-cut afterwards.** Part VII.10 forbids re-cutting #181's, and a band a release may widen after
  seeing its number is not a band.

The width is chosen so that **a whole module going untested fails it**, which is the test of whether
a band is a band, while 0.02–0.11 points of measurement noise are negligible against it.

## 4. What Gate 1 refuses, and why each is a refusal rather than an oversight

### 4.1 No cartridge, no subprocess, no IPC, no `onnxruntime`

Part 0 of the build prompt, and it is a security decision before it is an architectural one: **a
process boundary is a security boundary**, and one is not opened as a side effect of adding a decision
tree. This release's opinion about what v0.15.0 should do goes into `CARTRIDGE-0.15-DRAFT.md`, which
is a draft precisely so that it is not a commitment.

### 4.2 No shared base class over the three kinds

`tree.py`, `forest.py` and `boosting.py` each own their `KEYS`, `validate_payload`,
`scorer_from_payload`, `fit_document` and degeneracy rules (T1–T6, F1–F4, G1–G4). A base class would
have made three models with three different sets of rules read as variations on a theme, and **the
rules are the point** — they are what the plan registered before any of the three existed.

The single shared thing is `attribution.AttributedScorer`, and it is shared for the opposite reason:
from the correlator's side a tree, a forest and a boosted model *are* one thing — something that turns
three features into a score and three contributions — and three classes doing that identically would
be three places to get the contract wrong.

### 4.3 No plugin surface

`model_version.scorer_for`'s own docstring: *"deliberately closer to a `match` than to a plugin
surface."* Three new kinds are three new branches and **nothing at the call site.** A registry, an
entry-point group or a dynamic import would each turn "which models can this appliance run" from a
question the source answers into a question the environment answers.

### 4.4 No approximation in the attribution

`MAX_CELLS_PER_TREE = 4096` **refuses**; it does not sample. Plan §3 registers exact marginal Shapley
and §2 of the contract makes `sum(contributions) + base_value == score` a shipping condition, so a
model too large to explain exactly does not ship. A sampled Shapley value wearing the exact one's name
would be worse than a refusal, because the report would not be able to tell them apart.
