# v0.10.1 — guard demonstrations

**A guard nobody has watched fail is not a guard.** Every guard this release ships or repairs is
demonstrated red under an injected defect before its green counts as evidence. The shape is inherited
exactly from [`v0.10.0-guard-demonstrations.md`](v0.10.0-guard-demonstrations.md): the guard named
with its test id, the exact defect as a diff against the **corrected** tree, the command, the
verbatim RED, the verbatim GREEN, and **the control that had to pass in both runs**.

**A guard with no recorded red does not close this gate. A guard whose control was absent does not
close it either.**

Every injection below was applied to the corrected tree, run, and reverted, and **the tree was
verified green after every revert** — automatically, by the harness, so a run reporting RED is
reporting its own injection and not a leftover from the previous one. The command is the same
throughout:

```
$ .venv/bin/python -m pytest -q <the tests named in the row>
```

### M11a — one occurrence of two. **SURVIVED. A bad injection, and mine.**

The first attempt at re-running F48's drift injection replaced `AND m.source = 'server'` in
`Store.reconciliation_drift` **once**. It survived, and for a moment looked like a regression in a
v0.9.2 guard.

It is not. **The expression appears twice in that one method** — once in the `SELECT` list producing
the `recomputed` column, once in the `WHERE` clause deciding which rows are *returned* — and the
edit hit only the first. With the `WHERE` copy intact, no drift row is selected and nothing surfaces.

Re-aimed at both occurrences (**M11′**), it kills:

```
>       assert await store.reconciliation_drift() == [], (
E       AssertionError: the drift check disagreed with the live path on a stale-view label, which
        would send an operator hunting a write-path defect that does not exist
E       assert [{'feedback_i... 'live', ...}] == []

FAILED tests/test_evidence_boundary_f48.py::test_the_drift_check_reconciles_against_the_server_bag_only

```

**Recorded rather than quietly re-aimed**, exactly as v0.10.0 recorded its `A8′` bookkeeping slip.
An injection that misses its target and is reported as a survivor is how a healthy guard gets
"fixed".

**And it left an observation worth keeping.** `reconciliation_drift` carries the same correlated

### A1 — **the third release running in which the ledger found a real defect.**

The mutant passed the walk's *start* to `_cycle_members` instead of the re-visited node — a
one-token edit. The run **did not fail. It hung.** A ten-minute harness timeout was the only thing
that noticed, and the tree was left mutated.

The cause is in the shipped repair, not in the mutant: `_cycle_members`'s loop was
`while node != entry`, which terminates **only** because the caller passes a node that is on the
cycle. Give it a tail and the walk enters the cycle and never returns to a node that is not in it.

**`incidents.py` is the module whose entire subject is merge chains the schema does not forbid and
no code prevents.** A walk whose only stopping condition is an invariant is the wrong shape there,
and Appendix B says why in one line: *before trusting an invariant, ask what value of its inputs
would make it false.* Here there is one, and it is a single token away.

**Disposition: bounded by `MAX_CHAIN_DEPTH`, returning what it collected** — the same trade
`resolve` makes at its own bound, and for the same stated reason: a corrupt merge chain is a fact
about the corpus to be reported, not an error that should stop an offline report. It does not make a
violated precondition correct. It makes the failure **a wrong number instead of a hung process**,
and a wrong number is visible where a hang is a support ticket. DECISIONS #158.

Re-run after the repair, A1 is killed rather than hung, and A2 and A14 were seeded against the new
code and are killed too.

**The harness was changed as well**: each injection now runs under a 420-second timeout and reports
`HUNG` as a distinct outcome from `KILLED` and `SURVIVED`. A mutation ledger that cannot tell a hang
from a stall would have recorded this as neither.

### A8, A9, A10 — **three weak fixtures, and it is the same weakness three times**

All three survived, and none because the code was right. Measured rather than assumed:

```
bias fixture:      situations=4    labelled=4   unlabelled=0   merge edges=0
agreement fixture: situations=12   labelled=12  unlabelled=0   merge edges=0
```

* **A8** — `bias._incident_map` resolving *every* situation gives the same answer when **every
  situation is labelled**. `distinct_incidents` is the effective sample size of the *labelled*
  corpus, so an unlabelled situation must not enter it, and the frozen report cannot tell.
* **A9** — resolving against `{}` gives the same answer when there are **no merge edges at all**.
* **A10** — `min` versus `max` over the first-label ordering. **And this one is not merely a corpus
  accident.** `store.labelled_bags()` already returns **one row per situation** by its own
  sub-select, so `min` and `max` over a single-situation incident are identical *by construction of
  the query*. The `min` does work only when **two or more situations resolve to one incident**,
  which needs a merge — and neither corpus has one.

**This is `tests/test_incidents.py`'s own opening sentence arriving in three new places**: *the
corpus cannot demonstrate any of this.* It is also A1's lesson from Gate 0 in a different register —
**a test's fixture is part of the guard**, and a guard is only as wide as the inputs it was watched
to fail on.

**Disposition: all three closed with purpose-built fixtures**, in `tests/test_incidents.py`, next to
the guard they complete — and **not** by editing a byte-frozen corpus, which would have moved a
frozen report to buy a mutation kill. Re-injected:

```
A8'   bias._incident_map resolves EVERY situation                    KILLED
      FAILED tests/test_incidents.py::test_the_bias_incident_count_is_over_labelled_situations_only
A9'   agreement_bags resolves against an EMPTY edge map              KILLED
      FAILED tests/test_incidents.py::test_agreement_bags_follow_a_real_merge_chain
A9''  agreement_bags resolves ONE HOP rather than to a fixed point   KILLED
A10'  first_label_per_incident orders by the LATEST label            KILLED
```

A9″ was added because A9′'s fixture should separate **three** readings, not two — edge-less, one-hop,
and transitive — and a two-hop chain does.

### A6 — the unpooled z-test. **SURVIVED, and it is equivalent. Measured.**

```
  n=  37  pooled=0.24  unpooled=0.24
  n= 120  pooled=0.15  unpooled=0.15
  n= 300  pooled=0.1   unpooled=0.1
```

The pooled and unpooled two-sample z-tests are asymptotically equivalent, and at these sizes they
select **the same grid point** at all three registered sizes. There is no assertion that could
distinguish them without also making the pin depend on a choice the pin is not about.

**Disposition: recorded as equivalent, not fixed.** Reported with the measurement rather than as an
opinion, because "equivalent mutant" is the standard excuse for a mutant nobody wanted to chase.

### A13 — the bound one step early. **SURVIVED, and it is equivalent. Measured.**

```
  cycle of   2: correct=  2 min=0   one-early=  2 min=0   same_min=True
  cycle of  63: correct= 63 min=0   one-early= 63 min=0   same_min=True
  cycle of  64: correct= 64 min=0   one-early= 64 min=0   same_min=True
  cycle of  65: correct= 65 min=0   one-early= 64 min=0   same_min=True
  cycle of  70: correct= 65 min=0   one-early= 64 min=0   same_min=True
```

The member set differs only at cycles of **65 or more**, and **`resolve` cannot present one**: it
walks at most `MAX_CHAIN_DEPTH` steps and returns `unterminated` before a cycle that long is ever
detected, so `_cycle_members` is never called for it. One fewer iteration therefore changes no
output any caller can observe.

**Disposition: recorded as equivalent, with the limitation stated** — `test_the_bound_is_never_reached_on_a_real_cycle`
uses a cycle of exactly `MAX_CHAIN_DEPTH` and so catches a bound that fires *much* early (A14's
sibling would be caught at 32) but **not one that fires by one**. That is a real gap in the control
and it is named rather than papered over.

## Part 4 — limitations

**Stated, because a demonstrations document that claimed completeness would be the first thing in it
to be untrue.**

1. **F50 is unreachable through the write path, so no injection here can exercise it end to end.**
   `engine.py:466` does `sid = min(sids)`, so `merged_into` always points downward and a cycle cannot
   be written by any code path or API client. Every F50 test uses a purpose-built mapping. That is
   the honest situation for a guard whose whole value is in the case nobody expects to reach — and
   it is the reason the *docstring* mattered enough to make the mismatch a finding.

2. **The Monte-Carlo pin's tolerance is derived, not measured.** Its three terms (grid step,
   simulation standard error, discreteness) are argued from first principles in the test's own
   comments and total 0.010; the *observed* worst-case agreement is 0.0016. If the corpus ever
   shrinks below `n = 37` the discreteness term is the one that would have to grow, and nothing
   automatically re-derives it. M5 demonstrates that loosening it to 0.100 is caught — but by a
   *different* test (the naive-form control), not by the pin itself.

3. **`test_all_four_consumers_resolve_identity_through_the_one_implementation` reads call names, not
   call semantics.** A consumer that called `resolve_all` and then ignored the result would satisfy
   it. This is the same class of limitation v0.10.0 recorded for `test_no_incident_spans_two_folds`,
   and it is why the guard is presented as **one half of a pair** with
   `test_no_module_computes_incident_identity_in_sql` rather than as a guarantee on its own. M6
   happens to kill both, which is luck rather than design.

4. **The B2 guard scans `src/netcorenoc` only.** `eval/`, `tools/` and `tests/` are out of its
   scope, deliberately — the tests must be able to write the expression in order to test it — but
   that does mean a report added under `tools/` could compute one-hop identity unobserved.

5. **Coverage is not a guard and is not demonstrated here.** A3 pinned a command and reported a
   number; nothing makes a coverage regression fail a build beyond the 85 % floor, and this release
   did not add one.

6. **No injection here targets the ingest path, `engine.py`, `correlate.py`, `learn.py`, `scoring.py`
   or `capture.py`'s write path**, because this release does not touch them. Their guards are
   unchanged and were last demonstrated in v0.9.2 and v0.10.0; this document does not re-run those,
   and their green in `make qa` is a regression signal rather than a demonstration.
