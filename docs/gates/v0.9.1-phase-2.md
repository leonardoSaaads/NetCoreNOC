# v0.9.1 — Gate 2: migration `0010`

One migration, additive, seeding nothing.
[`../../src/netcorenoc/migrations/0010_partial_split.sql`](../../src/netcorenoc/migrations/0010_partial_split.sql).

---

## 1. What it adds

| Object | Kind | Why |
|---|---|---|
| `feedback_exclusion(feedback_id, position, alarm_id)` | new table, `WITHOUT ROWID`, `ON DELETE CASCADE` | the marked members — a **list**, so a child table, for DECISIONS #104's reason |
| `feedback.excluded_count` | nullable column | `\|marked\|`; **NULL means no exclusion was asserted**, and 0 cannot occur |
| `feedback.excluded_truncated` | nullable column | the bound was applied — a **fact**, never a silence |
| `feedback.remainder_together` | nullable column | three states: asserted true, asserted false, **NULL = the operator did not say** |

`feedback.member_count` — the bag size at label time — was already present from `0008` and is the
other half of every ratio: marking eight of nine is a different assertion from marking one of nine,
and neither number means anything alone.

**Why a separate table rather than a third `source` value on `feedback_member`.** A semantic reason
before a mechanical one: `feedback_member` records **what the bag was**; this records **what the
operator asserted about it**. Different questions, different trust — `feedback_member.source='server'`
is authoritative while every row here is the client's report — and only one of them survives a merge
as a statement of fact. (SQLite could not have altered that `CHECK` constraint in place either.)

---

## 2. It seeds nothing, and it backfills nothing

`0008` permitted itself exactly one data write, the `capture_provenance` marker, and justified it on
a fact **knowable at migration time**: a row that existed when `0008` ran predated v0.8.0's capture
path by definition.

**No equivalent fact exists here.** Nothing about *which* members an operator would have marked is
knowable from anything, so `0010` writes no data at all. Every label already in the corpus keeps
reading as exactly what it is — a **plain** split, which asserts the bag is at least two situations
and says nothing about any pair.

Asserted by `tests/test_upgrade.py::test_v091_upgrade_applies_0010_and_leaves_existing_labels_plain`:

```
SELECT COUNT(*) FROM feedback WHERE excluded_count IS NOT NULL
   OR excluded_truncated IS NOT NULL OR remainder_together IS NOT NULL   ->  0
SELECT COUNT(*) FROM feedback_exclusion                                  ->  0
```

### The one existing test this phase edited, and why

`tests/test_upgrade.py::test_v090_upgrade_applies_0009_and_changes_no_grouping` pinned
`Store.latest_schema_version() == 9`. It is the **only** place in 923 tests coupled to the schema
number — the full suite was run with `0010` present and nothing else moved, which is itself a useful
measurement and is carried into the test audit. Three changes, all minimal:

* `== 9` → `== 10`;
* the comment now says the fixture (frozen at 8) reaches the **current** schema through 0009 *and*
  0010, rather than naming 0009 alone;
* `feedback_exclusion` joins `challenger_run` and `shadow_opinion` in that test's own
  "no rows seeded" loop, so the claim it makes covers both migrations.
