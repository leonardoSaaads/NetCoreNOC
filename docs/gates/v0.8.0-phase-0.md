## 1. Situation merges destroy the label's referent

`engine._assign_situation` merges with `sid = min(sids)` (`engine.py:437`); `store.merge_situations`
(`store/situations.py:43`) moves `situation_alarm`, re-points `link`, marks `src` as `merged` — and
**does not touch `feedback`**. Reproduced on a fixture: two situations, a `confirm` on the one that
will be absorbed, then a bridging alarm.

```
situation A id=1  members=[1, 2]
situation B id=2  members=[3, 4]

posted confirm on situation 2 -> FeedbackResult(exists=True, inserted=True)
feedback rows: [{'id': 1, 'situation_id': 2, 'verdict': 'confirm', 'created_at': 1000001.0, 'principal_ref': None, 'role': None}]
situation_alarm for 2: [{'alarm_id': 3}, {'alarm_id': 4}]

after the bridging alarm: sid_of(bridge)=1
situation statuses: [{'id': 1, 'status': 'open', 'closed_at': None}, {'id': 2, 'status': 'merged', 'closed_at': 1000002.0}]

(a) feedback row after the merge: [{'id': 1, 'situation_id': 2, 'verdict': 'confirm'}]
    -> situation_id=2, the ABSORBED id (2)
(b) situation_alarm WHERE situation_id=2: []  (len=0)

(c) every table that could carry the answer, queried:
    feedback JOIN situation_alarm  -> []   (the natural join: EMPTY)
    link rows (re-pointed by merge)-> [{'situation_id': 1, 'alarm_a': 1, 'alarm_b': 5}, {'situation_id': 1, 'alarm_a': 3, 'alarm_b': 5}]
    link WHERE situation_id=2 -> []
    situation_alarm for the SURVIVOR 1 -> [{'alarm_id': 1}, {'alarm_id': 2}, {'alarm_id': 3}, {'alarm_id': 4}, {'alarm_id': 5}]
    -> the survivor holds the union of BOTH bags plus the bridge; nothing distinguishes
       the two members the verdict was about from the three it was not.
```

**(a), (b) and (c) all confirmed.** The verdict "these belong together" survives as a row pointing
at an id whose membership is empty, and the surviving situation holds the union of both bags plus
the bridge. There is no query — none — that recovers which alarms the operator was judging.

**A second loss, not in the build prompt and found here:** `merge_situations` records
`status='merged'` but **not the destination**. So the merge chain is not recoverable either. A
reader holding the labelled id cannot even follow it forward to the situation that absorbed it.
That makes §5.5's "situation lineage" requirement structural, not cosmetic — `0008` must record the
merge edge, or lineage is unimplementable.

**Frequency across the `eval/` corpus: 4 merges** over 2 256 activations and 10 corpus scenarios.
Rare — and that is the wrong reason to discount it: merges concentrate in exactly the multi-incident
scenarios (`dual_incident`, `fiber_cut`) whose labels are the most informative ones in the dataset.

## 2. What happens when feedback is posted to a **merged** situation

A live question, answered by execution:

```
=== §2: POST feedback to the merged (absorbed) situation ===
apply_feedback(absorbed=2, 'split') -> FeedbackResult(exists=True, inserted=True)
  exists=True (situation row still present, status='merged')
  inserted=True
  feedback rows before=1 after=2: [{'id': 1, 'situation_id': 2, 'verdict': 'confirm'}, {'id': 2, 'situation_id': 2, 'verdict': 'split'}]
  learner epoch before=(0, 0) after=(0, 0)
  engine.members[2] = None
  store.situation_members(2) = []
  -> learn.penalize() received: [] (an EMPTY bag)
  A.pairs changed: False
```

**Recorded:**

| Question | Answer |
|---|---|
| Status code | **200.** `add_feedback` gates on `SELECT 1 FROM situation WHERE id=?`, which still matches — `merged` is a status, not a deletion. |
| Is a row written? | **Yes.** A full `feedback` row, indistinguishable from one about a live situation. |
| What does `learn.penalize()` receive? | **An empty list.** `engine.members.get(sid)` is `None` (popped by the merge) and `store.situation_members(sid)` returns `[]` (the rows were deleted). |
| Net effect on learned state | **None.** `A.pairs` is byte-identical before and after. |

**This is a silent no-op that answers 200 and leaves a row claiming a judgement that had no
referent and no effect.** It is not a security defect and it is not a correctness bug in v0.7.5's
own terms — but it is a **row the dataset would otherwise treat as a label**, and it is
indistinguishable from a good one by any column that exists today.

**How it changes §5.4.** The server-side membership record must be written from the server's own
state *at the moment of the verdict*, and must record an **empty bag as empty** rather than
declining to write. Two rows that are identical in `feedback` today become distinguishable:
one carries two member ids, the other carries zero. The bias report can then count the second
population instead of averaging it into the first. It also means the membership record cannot be
`NOT NULL`-with-at-least-one-row — a zero-member bag is a legitimate, informative outcome.

### 3a. The finding the aggregate hides — and it is the important one

Counting at `score_link` rather than at `process()` separates three populations that the single
number conflates. `process()` truncates `links` *before* returning it, so `len(result.links)`
measures what the engine persists, never what the scorer accepted:

```
=== the three populations, counted at score_link ===
pairs EVALUATED (score_link calls)      : 194341
pairs ACCEPTED (result.linked is True)  : 194002
links PERSISTED (post-truncation)       : 10973
links LOST to MAX_LINKS_PER_ALARM=5     : 183029

pairs REJECTED (the population v0.7.5 discards): 339
  rejected / evaluated = 0.17%

activations whose accepted-link count exceeded 5: 2173 of 2256 (96.3%)
```

> **The 17.71× is not rejection. It is truncation.** 183 029 of the 183 368 discarded rows are
> links the scorer **accepted** and `MAX_LINKS_PER_ALARM` threw away. Only **339 rows — 0.17 %** are
> the "evaluated and rejected" population the draft's §3.1 calls *"the majority class, without which
> supervised training is impossible"*.

Per scenario, which is the only honest presentation:

```

**The accept rate is a property of the traffic, not of the scorer.** On quiet traffic
(`background_noise`) it is **0 %** — every pair is rejected. On storm traffic it is **100 %** —
nothing is rejected, because a storm saturates both affinity terms and `0.3·decay + 0.35·A + 0.35·E`
clears 0.5 on essentially every pair. The four storm scenarios contribute 188 999 of the 194 341
evaluated pairs (**97 %**), so they set the aggregate single-handedly.

**Three consequences, each load-bearing later:**

1. **Workstream 1 §9.1 is right, and for a second reason the prompt does not give.** "The majority
   class" is wrong conceptually (it is the machine's decision, not the human's label) *and* wrong
   arithmetically on this corpus (0.17 %). More than that: the class balance of `incumbent_linked`
   **swings from 0 % to 100 % with the traffic profile**. A quantity that unstable is not a training
   target and is certainly not an evaluation basis. The corrected §3.1 says so with these numbers.
2. **The sink's row budget is set by truncation, not by rejection.** A design that sized the sink
   for "the rejected pairs" would be wrong by two orders of magnitude. The sink must hold
   **every evaluated pair** — 194 341 rows where `link` holds 10 973.
3. **The corpus is storm-heavy by construction and overstates amplification for a quiet
   deployment**, and understates the *rejected* population for one. Recorded here so the Phase 6
   ingest-cost numbers and the security review's third critical note are read with it. This is not
   a corpus defect — it was built to stress correlation — but it makes the corpus a poor estimator
   of a regional ISP's steady state.

### 3b. §5.3 — is the observation row written per trap or per activation?

```
=== §5.3: observation row per trap or per activation? ===

**0.7142**, agreeing with the `dedup_ratio` of **0.7156** that `make eval` reports independently

## 6. `A` and `E` carry an epoch — located, and one correction

```
Matrix fields:
  kind: str
  lam: float
  epoch: int
  total: float
  total_e: int
  pairs: dict[tuple[int, int], tuple[float, int]]
  marginals: dict[int, tuple[float, int]]
  dirty: set[tuple[int, int]]

What advances it — every caller of tick():
  learn.py:353   self.A.tick()
  learn.py:354   self.E.tick()
  learn.py:352   if advance_epoch:
  engine.py:503  self.learner.learn_epoch(items, advance_epoch=False)
```

The epoch is `Matrix.epoch` (`learn.py:60`), one per matrix. Every mass is stored as
`(mass, at_epoch)` and read back through
`_decayed(mass, at_epoch) = mass · (1-λ)^(self.epoch - at_epoch)` (`learn.py:65`), λ = 0.05.

### The correction: `penalize()` does **not** advance the epoch

The build prompt's §1.6 says to "show that it advances on `penalize()`". Executed:

```
Executed, not asserted — does penalize() advance the epoch?
  epoch before penalize : (0, 0)
  epoch after  penalize : (0, 0)     -> advanced: False
  A/E pair mass before  : (1.0, 1.0)
  A/E pair mass after   : (0.5, 0.5)   -> mutated: True

  learn_epoch(advance_epoch=False) : (0, 0) -> (0, 0)   (feedback 'confirm' path)
  learn_epoch(advance_epoch=True)  : (0, 0) -> (1, 1)   (a CLOSED SITUATION)
```

**Neither feedback path ticks the epoch**, and that is deliberate: it is v0.7.1's F36 fix
(DECISIONS #69), which stopped a `POST /feedback` loop from ageing the whole appliance's learned
state. `penalize()` calls `scale_pair`, which mutates the mass and leaves `at_epoch` alone;
`confirm` calls `learn_epoch(advance_epoch=False)`. **Only a closed situation advances the epoch.**

**The leakage is real; the mechanism the prompt names is not.** A human label at time *T* changes
`A` and `E` — measurably: mass 1.0 → 0.5 above — so a pair evaluated at *T+1* does carry information
from an earlier human label. But it does so through the **mass values**, not through the epoch
counter, and the epoch would not move even if a thousand labels arrived.

**What this means for the schema, and it is not "drop the column".** Two columns are still right,
for a reason that survives the correction:

* `a_epoch` / `e_epoch` are what make a captured `A`/`E` **value** interpretable at all. The value
  is a decayed reading against `Matrix.epoch` at that instant; without it, a reading of 0.4 at
  epoch 12 and one at epoch 900 are not comparable, and no later join recovers the epoch because the
  matrix is mutated in place.
* Measuring *label contamination* specifically needs the epoch **and** the label times — and the
  label times are already on `feedback.created_at`. The bias report's "leakage exposure" item is
  therefore a join of pair epochs against label timestamps, not a reading of the epoch alone.

Recorded as a finding against the build prompt's §5.2 rationale, which states the mechanism
incorrectly. The **column** survives; the **sentence** does not, and Workstream 1 writes the correct
one into the specification so v0.9.0 is not briefed from the wrong mechanism.
