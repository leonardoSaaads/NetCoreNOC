## The design, in one page

### Capability resolution — `ceiling ∩ policy`, one site

```
ceiling(role) = { c ∈ PERMISSIONS : ROLE_RANK[role] >= ROLE_RANK[PERMISSIONS[c]] }

resolve_capabilities(role, principal_ref, policy):
    caps = ceiling(role)                         # the compiled map is the FIRST operand
    if policy is None or policy.malformed:       # unset / unreadable  -> the shipped baseline
        pass
    else:
        if role in policy.roles:           caps &= policy.roles[role]
        if principal_ref in policy.principals: caps &= policy.principals[principal_ref]
    if role == "admin":
        caps |= RECOVERY_CAPABILITIES            # ⊆ ceiling("admin"): the bound is preserved
    return caps
```

The invariant `resolve_capabilities(...) ⊆ ceiling(role)` holds for **every** input, because an
intersection cannot exceed its first operand and the one union is with a compiled subset of that
same ceiling. This is a *property*, so it can be tested property-based over generated and
adversarial policies — which is the difference between "escalation is forbidden" and "escalation is
impossible" (DECISIONS #53, #64).

Called from exactly three places: the `api.py` `security` dependency (replacing `role_allows` at
the same line), `GET /api/me` (the UI affordance gate), and the generated authorization matrix.

### Scope resolution and the read filter

Selectors (`ne:<id>`, exact IP, CIDR, host-glob) resolve to an NE-id set **and** its IP set on each
request — the graph is a `device` projection joined to `ne` by address, and id equality between the
two tables is a migration artefact rather than a declared invariant, so the filter joins on IP.

Layer composition (DECISIONS #63): an **unset** layer expresses no opinion; a **set** layer — even
empty — says "exactly these"; visible = union of the layers that express an opinion; none set ⇒ all
NEs. Admin is exempt before any policy is read (#58). A malformed policy ⇒ empty scope for
viewer/editor, plus warning and audit (#55).

Applied uniformly as **authorize → read → scope-project → field-shape** at every NE-bearing read:
lists filtered, edges only when both endpoints are in scope, situations listed iff ≥ 1 member in
scope with out-of-scope members redacted to a **count and type** (#59), out-of-scope detail ⇒ the
projection returns nothing ⇒ the handler's **existing** `if detail is None: raise 404` branch fires
(#60), enumerating aggregates computed over the in-scope set, SSE re-resolved per event.

### Where policy is read, with change invalidation

Per request: read the two-row `governance_active` pointer table; re-parse a document **only** when
its id differs from the parsed one held in memory. Correctness is per-request (a change lands on
the very next request, no restart); the parse cost is paid once per policy version. When no policy
is active the resolver short-circuits before touching the database, so parity costs nothing.

## Migration `0006_governance.sql` — schema v5 → v6

| Object | Shape | Discipline |
|---|---|---|
| `governance_policy` | `(id, kind ∈ {rbac,scope}, document, doc_hash, created_by, created_at, note)` | append-only via `BEFORE UPDATE`/`BEFORE DELETE` → `RAISE(ABORT)`; no sanctioned deleter (the retention prune does not touch it) |
| `idx_governance_policy_kind` | `(kind, id)` | history lookup per kind |
| `governance_active` | `(kind PK, policy_id → governance_policy.id, activated_by, activated_at)` | a **pointer**, not history: UPSERT to apply or roll back, DELETE to clear back to the shipped baseline |

**It seeds nothing, and that is the gate.** `0005` *had* to seed a row because the engine needs
parameters; governance has a compiled default (`PERMISSIONS` + full visibility), so a seed would be
the only way to make an upgrade change behaviour. Zero rows ⇒ no policy ⇒ the ceiling and full
visibility ⇒ byte-identically v0.6.0 (DECISIONS #54).

**`document` is the whole policy for its kind as canonical JSON, not one row per grant.** A policy
is read and applied as a unit on every request, so storing it as a unit makes "which policy was
active" a single id and makes rollback a pointer move rather than a replay.

**Validation lives in code, not in a `CHECK`.** A corrupt document must stay *readable* so the
resolver can recognise it as malformed and apply the fail-safe for its kind. A constraint that made
the row unreadable would make it unrepairable — the opposite of fail-safe.

## Two pre-existing tests corrected (not weakened)

Both were correct in v0.6.0 and became stale the moment a sixth migration existed. Neither
assertion was removed; both were made to track the tree.

1. `test_migration.py::test_migrate_populated_v050_database_seeds_the_scorer_config` asserted

   v0.1.0 and v0.2.0 migration tests in the same file already used.
2. `test_upgrade.py::test_v060_upgrade_preserves_grouping_and_seeds_provenance` froze the migration
   directory with `not p.name.startswith("0005")`, so `0006` leaked into what the test calls "a

   (`int(name.split("_")[0]) <= 4`), so a future release adding `0007` cannot silently un-freeze the
   fixture either — the same latent bug, fixed once. Its post-upgrade assertion likewise tracks
   `Store.latest_schema_version()`.

## Decisions added in this phase

- **#63** — an unset scope layer expresses no opinion; visible = the union of the layers that do.
  The literal reading of `role_scope ∪ principal_scope` would have made a per-principal scope
  incapable of restricting anything unless the role were also scoped, i.e. workstream 2's S5 would
  be a no-op in the common case. The chosen reading satisfies every clause of the specification and
  is the stricter of the two.
- **#64** — the admin's recovery capabilities (`self.read`, `rbac.read`, `rbac.write`, `scope.read`,
  `scope.write`) are unremovable, unioned back **inside the resolver**. A *well-formed* policy could
  otherwise remove `rbac.write` from `admin` and leave no authenticated path to repair the
  perimeter — a hard lockout the malformed-policy fallback would never catch. The set is a subset of
  `ceiling("admin")`, so the escalation invariant is untouched, and governance can still restrict an
  admin's `users.manage` / `audit.read` / `config.write` / `scorer.write`.
