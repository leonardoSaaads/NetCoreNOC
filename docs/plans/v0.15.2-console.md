# v0.15.2 — what is broken in the console, and what has no identity

<!-- release-claim: v0.15.2 = console-repair -->

**Measurements and open questions. Not a design.** Every number was reproduced on the v0.15.0 tree.
Two of them contradict the brief this document was written from; where they do, the measurement is
here and the correction is stated.

## 1. The detail panel is populated by one view of seventeen

> **Corrected by v0.15.2: it is zero of seventeen.** `situations.js` *imports* `setContext` and
> never calls it — `grep -rl` matches the import line, which is the whole of what it matched here.
> `grep -rn 'setContext(' src/netcorenoc/ui/` finds no call site outside `context.js` itself, and in
> a browser the panel reads *"Select something to see its detail here."* on all seventeen views,
> including Situations with a card expanded. Decision #219 removes the region; F66-F67 record the
> drive.

`setContext` is imported by exactly two files: `app/context.js`, which defines it, and
`app/views/situations.js`, which calls it.

```sh
grep -rl setContext src/netcorenoc/ui/app/
# src/netcorenoc/ui/app/context.js
# src/netcorenoc/ui/app/views/situations.js
```

Clicking anything in the other sixteen views produces nothing, and the panel shows
*"Select something to see its detail here."* permanently. A third of the screen, on every screen but
one, is a placeholder.

## 2. On a narrow viewport the panel does not exist

> **Corrected by v0.15.2 twice.** There are **three** `@media` blocks, not four — one
> `prefers-color-scheme`, one layout breakpoint, one `prefers-reduced-motion`; the fourth occurrence
> is inside a comment. And the conclusion below is wrong: the per-term contributions render in
> `#work`, not in the panel, so they are **reachable** at 390 px. What is lost there is the pair
> each row is about, clipped by a non-wrapping flex row — F67, decision #220.

`style.css` has **one** layout breakpoint — there are four `@media` blocks, but two are
`prefers-color-scheme` and one is `prefers-reduced-motion`:

```css
@media (max-width: 760px) {
  …
  /* The context panel collapses on a narrow viewport (draft §1). */
  .context { display: none; }
}
```

So the **per-term contributions — the product's central claim — are unreachable on a phone.** Not
degraded: absent. The comment shows this was a deliberate call in the v0.13.0 draft, which makes it
a decision to revisit rather than an oversight to fix.

## 3. There is no icon set

**Two `<svg>` elements in the entire console**, and both are data surfaces rather than iconography:

```
src/netcorenoc/ui/app/views/timeline.js:99   <svg id="timeline" role="img" …
src/netcorenoc/ui/app/views/graph.js:152     <svg id="graph" role="img" …
```

Everything else that reads as an icon is a Unicode glyph in `registry.js` — `◎ ◉ ⬡ ▤ ▢ ≡ ✓ ▦ ⚖ ◍ ⚿ ⚙
∿ ⛨ ⚑ ⛓ ◐`. They render at whatever weight the user's font stack decides, and they are not
consistent with each other because nothing chose them together.

## 4. System health — the brief's claim is wrong, and the real finding is sharper

The brief for this release says `/api/stats` returns five keys and that there is *"no queue depth,
no trap rate, no ingest lag."* **Measured against a running appliance, it returns eleven:**

```
active_alarms  classes  devices  ingest_gaps  latency_p95_s  open_ingest_gaps
open_situations  quarantined  queue_depth  receiver  warnings
```

and `receiver` carries `received / accepted / denied / quarantined / dropped`.

So the finding is not that the appliance does not measure itself. It is that **the console throws
most of it away**:

| Served | Rendered |
|---|---|
| `active_alarms`, `open_situations`, `devices`, `classes` | yes — Overview |
| `latency_p95_s` | yes — Overview |
| `ingest_gaps` | yes, when non-empty |
| `open_ingest_gaps` | yes — a shell banner |
| **`queue_depth`** | **no** |
| **`receiver.{received,accepted,denied,quarantined,dropped}`** | **no** |

`queue_depth` is *the* number that says whether the appliance is keeping up, and it is polled on
every refresh and dropped on the floor. `receiver.denied` is how an operator discovers their
allowlist is wrong. Neither has ever been on a screen.

**Genuinely absent from the API too**: CPU, memory, uptime, trap rate. Of those, trap rate is the
one an operator asks for first and it is derivable from `receiver.received` between two polls.

## 5. The console reads as generated rather than designed

**5 343 lines of JavaScript across 37 modules** (excluding vendored assets), with no visual identity:
no type scale, no spacing rhythm anyone chose, no icon system, and prose where a label would do —
`settings.js` alone carries about **146 words** of explanatory English inside its markup. That is a
symptom, not a defect list: the screens were built one at a time against a specification of *what
each must show*, and nothing ever decided what the product looks like.

## 6. Startup has options that fail

The maintainer has observed this. **v0.15.2 reproduces it before designing anything** — with a
control, per Appendix B: a probe that only records failures cannot tell a broken option from an
invented one. Enumerate the documented startup routes in [`../install.md`](../install.md), run each
one literally, and record what each did, including the ones that worked.

## 7. What v0.15.2's first decision must answer

1. **What is the detail panel?** Either every view populates it, or it belongs to Situations and the
   other sixteen should not reserve the space. "Sixteen views will each get a context payload
   eventually" is the answer that produced the current state.
2. **What happens to it below 760 px?** A drawer, a route of its own, or an inline expansion. The
   constraint is that the per-term contributions must be reachable, because they are the product.
3. **An icon strategy that adds no dependency and no build step.** Inline SVG in a shared module,
   a subset font, or a deliberate glyph set with a chosen fallback stack. Each has a cost; the
   no-npm rule (`tests/test_build_step.py`) is not negotiable and rules out the usual answer.
4. **Where does system health live, and what does it show?** `queue_depth` and the receiver counters
   exist today. Does v0.15.2 add CPU/memory/uptime to `/api/stats` — a new route surface, with a
   declaration and a capability — or does it render what is already served and stop there? The
   second is much smaller and might be most of the value.
5. **Does this release get a visual identity, or does v0.15.3?** Repairing four defects and choosing
   a type scale are different jobs, and doing both means neither is reviewable.
