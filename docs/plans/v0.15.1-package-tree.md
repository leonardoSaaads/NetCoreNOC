# v0.15.1 — the package tree

<!-- release-claim: v0.15.1 = package-tree -->

**Measurements and open questions. Not a design.** Every number here was reproduced on the v0.15.0
tree; the questions at the end are what v0.15.1's first decision has to answer, and this document
deliberately does not answer them.

## 1. The measurement

**58 modules at the package root**, of 104 `.py` files under `src/`.

`tests/test_layers.py` maps every runtime module to one of five layers, has enforced the dependency
rule since v0.7.3, and its exemption list is **empty**. The distribution it maps:

| Layer | Modules |
|---|---:|
| engine | **46** |
| cross-cutting | 8 |
| http | 4 |
| ingest | 3 |
| data | 1 |
| | **62** |

Module families visible in the filenames at the root:

| Prefix | Count |

## 2. The diagnosis

**The project has a layer model that is declared, tested and enforced — and a filesystem that
ignores it.** The layers live in a dictionary in a test file; the disk is flat, so a module's layer
is a declaration rather than an observation. And **`engine`, holding 46 of 62 mapped modules, is not
a layer — it is a bucket**: "the domain" is a true description of all 46 and a useful description of
none of them, and `correlate.py` and `bias_report.py` have nothing to do with each other.

## 3. The open question, and v0.15.1 must not inherit an answer to it

The project's taxonomy is by **layer**. The natural description of the problem is by **domain** —
correlation, models, inference, evidence. **These are different axes**, and a tree can express one,
the other, or one nested inside the other.

```
by layer                    by domain                   layer, domains inside
  http/                       correlation/                http/
  engine/                     models/                     engine/correlation/
  data/                       evidence/                   engine/models/
  ingest/                     inference/                  engine/evidence/
  crosscutting/               …                           data/  ingest/
```

Each has a real cost: layer-only leaves the bucket intact; domain-only abandons the one structural
rule this project has enforced for eight releases and has a test for; nested keeps both and makes
every path two levels deep, which the placement rule currently forbids.

**Decide this first.** Every other question here is downstream of it, and a tree built before it is
decided will be moved twice.

## 4. The proxy/agent deployment model — name it, do not answer it

The maintainer wants the structure to prepare ground for a **proxy/agent deployment model in the
shape of `zabbix-agent`**: a component that runs inside a customer subnet, collects locally, and
reports to a central appliance.

That is not built in v0.15.1 and this document does not specify it. What v0.15.1 owes it is one
thing: **the package tree should not make it awkward.** The questions that would make it awkward, if
answered wrongly and silently:

* Is `ingest` a layer of the appliance, or a *component* that could run somewhere else? Today it is
  three modules under the same import root as the HTTP layer.
* Would an agent share `events.py`'s vocabulary, or copy it? A shared vocabulary is a package
  boundary; a copy is a protocol.
* What does an agent NOT have? No store, no correlation, no console. A tree that puts the wire
  parser next to the batch loop makes "just the wire parser" a hard thing to ship.

Name the questions. Do not answer them in v0.15.1 unless the answer falls out of §3 for free.

## 5. Constraints v0.15.1 inherits

* **`TRAP_PATH_HASHES` pins five modules by content, read from `PKG / name`.** A move breaks the
  guard on **path**, not on content. The pins are updated in the same commit that moves the file, or
  the guard is briefly checking nothing — which is worse than it failing.
* **`tests/test_layers.py` would become a directory check**, and that is strictly better: a new
  module then lands in the right layer *by where it was saved*, and the declaration stops being a
  thing to remember.
* **The 400-line module guard** stays. So does `COHESION_EXEMPT` at `engine.py` alone — it is 569
  lines because the whole ingest path must be readable in one place, and that entry carries no owner
  and no date because there is no fix.
* **`DEBT_ALLOWLIST` is empty.** It must still be empty afterwards. A move release that adds debt has
  not moved anything, it has hidden something.

## 6. The gate v0.15.1 needs and does not have

**A behaviour-identity harness.** Boot the appliance on a deterministically seeded database, record
every read route's response, repeat on the refactored tree, diff byte for byte.

In a release that is *entirely moves*, *"the tests pass"* is a weaker claim than *"the HTTP surface
is unchanged"* — and the difference is not academic. v0.7.3 proved 141 store method bodies unchanged
by hash and that is what made its move reviewable. There is no equivalent for the HTTP surface, and
a package reorganisation is exactly the change that could alter a response shape without failing a
single assertion, because the assertions were written against the same code that produces the shape.

**Specify it. Build nothing.** It is v0.15.1's first workstream, before the first `git mv`, per
principle 8.

## 7. What v0.15.1's first decision must answer

1. **Layer, domain, or layer-with-domains-inside?** §3. Nothing else can start until this is chosen,
   in writing, with the cost of the other two stated.
2. **Does `engine` survive as one name?** If it does, what makes 46 modules one layer other than the
   absence of a better word?
3. **What does the behaviour-identity harness record**, exactly — which routes, which fixtures,
   which seed — and what does it do about responses that legitimately carry a timestamp?
4. **Does `test_layers.py` become a directory check in the same release as the move**, or after it?
   Doing both at once means the guard and the thing it guards change together, which is the shape
   that hides a mistake.
5. **What is the smallest thing an agent would be?** Not the design — the *list of modules*. If that
   list is not a subtree in the chosen taxonomy, say so now rather than discovering it in v0.17.0.
