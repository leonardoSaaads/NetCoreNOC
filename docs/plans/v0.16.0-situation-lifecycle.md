# v0.16.0 — the situation lifecycle

<!-- release-claim: v0.16.0 = situation-lifecycle -->

**Measurements and open questions. Not a design.** Written by the v0.15.3 build, which spent a
release inside `situations.js` and `why.js` under a standing instruction not to touch any of this
(VII.1). Everything noticed and left alone is here.

## 1. The schema as it stands

| | Today |
|---|---|
| `situation.status` | **`open` \| `closed` \| `merged`** — `0001_init.sql:58`, three values, one index |
| who writes `merged` | `store/situations.py` only, and only the correlator's own merge |
| who writes `closed` | `POST /api/situations/{sid}/close`, and the idle sweep at `IDLE_CLOSE_S` |
| operator verdicts | `confirm` \| `split`, on `POST …/feedback`, plus an optional verdict carried by `close` (`acquisition_channel='close'`) |
| a name | there is none. A situation is `#{id}` everywhere in the console and in the API |
| state-based clears | `state_clear` learns `(class, varbind, clear_value, raise_value)` and is **forward-only** — a learned field is never overwritten |

## 2. What the maintainer described, against that schema

Each of these is a **schema and domain change wearing a UI costume**, which is why v0.15.3 was told
to leave them and did:

* **self-clearing when the alarms clear.** `state_clear` already learns which varbind value means
  *cleared*; nothing closes a situation because its members cleared. The open question is not how to
  detect it — that is learned — but what a situation that self-cleared **is**: `closed`, or a fourth
  state that says "the network fixed this", which is a different fact for the operator and a
  different label for the model.
* **manual clearing of zombie traps.** An alarm that never clears holds its situation open forever.
  Clearing it by hand is an operator asserting something about the *network*, not about the
  grouping, and the feedback dataset currently has no channel for that assertion.
* **New / Open / Resolved.** Three tabs is a presentation of a state machine the schema does not
  have. `open` is not `New`, and `closed` is not `Resolved` — a situation an operator closed and one
  that timed out at `IDLE_CLOSE_S` are the same value today.
* **operator merge and split.** `split` exists as a *verdict* and moves no rows: it records that a
  grouping was wrong. Merge exists only as something the correlator does. An operator merge is a
  write to `situation_alarm` with no code path at all.
* **moving an alarm between situations.** The narrowest operation and the one with the widest blast
  radius: every link, every score and every `asserting_bag` that mentions that alarm was computed
  against the membership it is leaving.
* **semantic naming.** *"OLT 3 uplink cut"* rather than a bare id. Whether the name is written by an
  operator, derived from the root alarm, or proposed by a model changes what it is evidence of.

## 3. The measurement that makes it matter

**`asserting_bags = 0` since v0.9.1, and every release since has ended `INSUFFICIENT_EVIDENCE`.**
The promotion gate has never had enough operator judgements to decide anything, and the reason is
arithmetic: `confirm` and `split` are the only two channels, both require an operator to open a
situation and form an opinion about a grouping, and a NOC operator's day is not spent doing that.

**Every operation in §2 is a feedback signal the appliance is not currently collecting.** A merge
is an asserted positive across two bags. A split that moves rows is a stronger negative than the
verdict that only records one. Moving an alarm is a pair-level assertion. Closing a zombie by hand
says the *alarm* was wrong, which is a class-level signal nothing captures. That is the argument for
doing the lifecycle at all, and it is an evidence argument rather than a UI one.

## 4. Open questions, in the order they block each other

1. **Is a state machine being added, or is `status` being reinterpreted?** Everything else waits on
   this, and it decides whether there is a migration.
2. **Does an operator action write history, or mutate?** The audit chain is append-only and the
   feedback dataset is capture-once; a merge that rewrote `situation_alarm` would make earlier
   labels refer to a membership that no longer exists (`0008_feedback_dataset.sql:24` already warns
   about this for the correlator's own merges).
3. **What is a name evidence of?** An operator's name is a label; a derived name is a projection; a
   proposed one is a model output that needs the same seal discipline as any other.
4. **Which of these produce a training row, and with what `acquisition_channel`?** `'close'` was
   added for one case and the pattern would need extending, not repeating.
5. **What does the console show for a situation that self-cleared while an operator had it held?**
   The held card (ADR #173) freezes the payload; a state change underneath it is the v0.7.5 problem
   in a new place.

## 5. What v0.15.3 noticed and deliberately did not do

* `situations.js` filters on `open | closed | merged` with a fourth option, `any status`. Three tabs
  would go here and the file is ready for them. **Not added** — a tab for a state that does not
  exist is the placeholder rule (#219) with worse consequences.
* `why.js` computes the weakest link's margin over the threshold (#245). That number is a candidate
  input to *"should this situation self-clear or be proposed for a split"* and the temptation to
  make it one was real. It stays a display of the operator's own reading.
* The permalink makes a situation shareable during an incident, and the bare id is what gets
  pasted into a chat. A name would change what that link means. Left alone.
* `POST …/close` already accepts an optional verdict. That is the seam a lifecycle would widen, and
  widening it is a dataset change.
