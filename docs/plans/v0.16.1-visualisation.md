# v0.16.1 — what v0.16.0 measured and did not touch

**Measurements and open questions. Not a design.** Everything below is either a number this release
produced or a question it declined to answer during implementation, per
`PREREGISTRATION-0.16.0.md` §10: *ambiguity about anything analytical is reported as an open
question for the next release and never decided while writing code.*

## 1. The defect that must be fixed before any promotion decision is read

**F90.** `promotion_metrics._asserting_bags` rebuilds an operator's marked set as `members[:n]` of
**live** membership, while the ids the operator marked sit unread in `feedback_exclusion`.

    PROBE   bag [1..8]  marked [7, 8]  ->  judge reconstructed [1, 2]   disagree
    CONTROL bag [1..8]  marked [1, 2]  ->  judge reconstructed [1, 2]   agree

It has been invisible since v0.9.1 because `asserting_bags` was 0. **v0.16.0 makes it reachable**,
and it feeds `asserted_negative_respected_rate`, one of the four named quantities the promotion gate
reads. The repair is not one line: it has to decide **which bag a label is judged against once
membership mutates**, which is the analytical question v0.16.0 was forbidden to answer. Until it is
fixed, no promotion decision should be read from that quantity on a corpus containing
gesture-acquired bags.

## 2. The bag-identity question, from the other end

**F89.** `feedback` is `UNIQUE (situation_id, verdict)`, so a second move out of one situation
records its event and no second label. Loosening the index is not the fix; the fix is deciding what
a bag's identity is when membership changes underneath it. §1 and §2 are the same question and
should be answered together, once, in a pre-registered plan rather than in a patch.

## 3. Bag provenance is recorded and nothing reads it

Four columns on every asserting gesture — `bag_weakest_margin`, `bag_has_bridge`,
`bag_bridge_min_side`, `bag_link_count` — and two tests assert that no module which fits, scores or
judges can reach them. The open question is the one v0.16.0 registered and did not answer: **is a
bag held together by a single bridging link worth less as evidence than one that is densely
connected?** The data to answer it now exists. Answering it means amending a plan, not adding an
import.

## 4. What the census measured, and what it could not

    asserting_bags          0  ->  10      (floor 50)
    asserting_incidents     0  ->  10      (floor 30)
    asserted_negative_pairs 0  ->  2 222

`python tools/corpus_census.py --gestures`. Three facts about that 10 that a later release needs:

* **69 of the live windows offered a situation with a single member.** `eval/corpus/` was built to
  test correlation, not to be restructured. A corpus with more multi-member situations is a
  prerequisite for reaching the floor, and building one is a corpus change — which touches a gated
  artefact and belongs in a release that owns it.
* **One bag contributed 1 050 of the 2 222 asserted negative pairs** (`pon_dying_gasp`, 1 051
  alarms). `asserted_negative_pairs` is a corpus-size figure, not a quality figure, and any release
  that quotes it without the per-bag maximum beside it is quoting a storm.
* **39 of 41 situations are resolved by the end of the replay**, and a gesture on a resolved
  situation is refused by design. A census that gestures at the end measures that refusal.

## 5. Observed in the live pass, not touched

Chromium, 1440 / 1000 / 560 px, as editor and as viewer, driving the whole loop.

* **The gesture history says `by user:2`.** The card's third section names the actor by principal
  reference. It is correct, unforgeable and unhelpful to a human reading their own history. Whether
  the console should resolve it to a username — and what a deleted account then shows — is a
  question about identity display, not about this release.
* **A card leaves the New tab the moment you gesture on it.** Correct per DECISIONS #254, and mildly
  surprising the first time: the card an operator is working on disappears from the default tab.
  Whether the tab should follow the card, or the card should linger, is a design decision.
* **`/favicon.ico` is a 404** on every page load, at v0.15.5 as well. Harmless, pre-existing,
  recorded here so the next release does not rediscover it as new.
* **The search bar still filters on `` `#${s.id} ${s.status}` ``** — id and status only. It does not
  see the derived name or the operator name, so an operator who has just named a situation *"fibre
  cut, Ridgeway ring"* cannot find it by that name. v0.16.0 was explicitly forbidden to repair the
  search bar; it is now a worse gap than it was, because there is more on the card to search for.

## 6. The graph, the timeline, entities and alarm classes

Untouched, and each carries the same question v0.16.0 answered for situations: **what does an
operator do on this screen, and does the appliance record it?** The graph shows a grouping and
offers no way to correct it; the timeline shows what happened and offers no way to say it was wrong.
Neither is a defect. Both are the next place the same argument applies.

## 7. Two guards that need their own release

* **F91** — the behaviour record silently drops a route whose path parameter the seed cannot fill.
  `DELETE /api/tokens/{tid}` is absent from three of four principals with no line at all. The fix is
  one line plus a regenerated record, and the release that regenerates the record must be one whose
  own diffs are not competing with it.
* **F92** — `test_no_promotion_path_module_mentions_a_ground_truth_field` scans four hand-listed
  modules and the promotion path has five. The honest repair derives the set from the path rather
  than listing it.
